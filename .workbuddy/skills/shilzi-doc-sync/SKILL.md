# 文档同步（收尾必跑）

## 触发范围与执行方式

- 任务涉及文档、代码与说明一致性时使用：页面、接口、集合、索引、业务规则、权限、部署配置、操作步骤发生变化，或维护 README、交接材料、`AGENTS.md`、`.workbuddy/skills/**` 后需要核对关联入口。
- 接手时核实现状、“说明还对吗”“按文档做失败了”“链接打不开”“改完还有哪里要同步”等均适用，不要求出现“文档同步”或仅限规模数字变化。
- **只读核对**：按影响面检查，报告实际差异；用户只要求检查时不自动改文件。**实际同步**：只更新受本次变更影响的现行文档和关联入口，保留历史冻结边界。
- **仅改 Skill / 项目指令 / 局部说明**：核对技能描述、正文、`AGENTS.md` 路由与引用文件的一致性；未改变业务、规模数字或 docx 源文档时，无需为此重跑全量业务测试、更新规模数字或重建 docx。
- 代码批次正式收尾仍按下方五步流程校对 A1 文档；仅做范围明确的文档维护时执行命中项。只有需要引用新的测试基线、规模数字或重建产物时，才运行相应取值或构建命令。新建正式验收记录时叠加 `shilzi-acceptance-doc`。

## 为什么需要它

实测结论：同一批事实在文档里存在多个互相矛盾的值。

| 事实 | README | 交接说明 | 代码真值 |
|---|---|---|---|
| 页面数 | 42（5+37） | 39 | 43（5+38） |
| action 数 | 187（13/101/15/53） | 187 | 200（13/119/15/53） |
| 镜像文件 | 86（§1）、85（§5 图） | 77 | 87 |
| 测试基线 | 2858 用例 / 157 文件 / 123s | — | 2989 / 176 / 27.6s |

单份文档内部还自相矛盾（86 与 85）。**所以「记得更新文档」不是方案，机器校对才是。**

## 三类文档，只有一类能随手改

| 类 | 范围 | 规则 |
|---|---|---|
| **A1 数字校对** | `README.md`、`docs/交接说明.md`、`docs/云开发控制台操作指南.md`、`docs/数据库索引清单.md` | 每次收尾必须 audit 归零 |
| **A2 定点更新** | `docs/AI接手与后续施工指南.md`（只改顶部「现状补丁」表）、`docs/施工切片账本.md`（只追加行）、`docs/前端样式规范-2026-10-23.md`（只在规则变化时改） | 按需改指定位置，正文历史段落不回写 |
| **B 产物** | 三个 docx | 只由 md 构建，禁止手改 |
| **C 冻结** | `docs/*验收记录*`、`*只读审计*`、`*需求整理*`、`*隐患*`、`*调查*`、`.workbuddy/memory/**` | 一行不碰 |

粒度说明：A2 里的文件同时含历史与现行内容（AI 接手指南 683 行，正文多处已被现实推翻），**只改补丁表**，不要在正文里追着改。完整清单见 `references/document-map.md`。

## 五步流程

### 0 取真值（不抄文档）

```bash
npm test                                              # 文件数/用例数/耗时
npm run check:cloud-sync                              # 镜像数
node .workbuddy/skills/shilzi-doc-sync/scripts/doc-truth.js   # 页面/action/集合/镜像/测试文件
```

### 1 定影响面（先出清单，不动手）

对照 `references/update-matrix.md`，列出本批改动命中哪几份文档。摘要：

| 你改了 | 必改 |
|---|---|
| 页面增删 | README §1 §6、交接说明「规模」行 |
| action 增删 | README §5 计数+分组、交接说明「规模」行 |
| 集合增删 | 云控制台指南 §3、交接说明 §3、README §8 |
| 索引增删 | 数据库索引清单对应小节 |
| 业务口径 | 赛事管理员手册、交接说明 §4、README §4 |
| 部署/环境 | 云控制台指南、README §8 |
| 测试基线 | README §1、交接说明「规模」行（无该行则跳过） |
| 新批次 | 账本追加 + 新建验收记录（交给 `shilzi-acceptance-doc`） |

### 2 校对（只读，先看差多少）

```bash
node .workbuddy/skills/shilzi-doc-sync/scripts/doc-audit.js --cases=<真值>
```

输出形如：

```
README.md:142   页面总数      声明 42   →  真值 43   [漂移]
README.md:96    镜像文件      声明 85   →  真值 87   [漂移]
交接说明.md:9   页面总数      声明 39   →  真值 43   [漂移]
```

有漂移时退出码非 0。`--cases` 不传则跳过用例数校验（该值只能实跑得到），并提示「未校验」。

### 3 定向更新

- 只改 A1 的命中行；A2 只改指定位置；C 类不碰。
- 改数字不要改口径：`42 页（主包 5 + 分包 37）` 这类复合表述要**同时**改分解值，否则会产出新的自相矛盾。
- 校对器的 **25 条断言覆盖 17 类表述**（页面总数 / 页面分解 `主包 X + 分包 Y` / 分包页数 /
  action 总数与四组分解 / 集合三种写法 / 镜像三种写法 / 用例数 / 测试文件数）。改完复跑，直到 `0` 差异。

**为什么 apply 不做成一键**：「42 页」与「主包 5 + 分包 37」是同一事实的两种写法，全自动替换会误伤「5 个分包」这类句子。校对全自动、修改逐条人工放行。

### 4 重建产物

```bash
node .workbuddy/skills/shilzi-doc-sync/scripts/doc-build.cjs
```

缺 `python-docx` 时脚本会明确失败并给修复命令（本项目已装在隔离 venv，脚本优先用它）。**不允许**手改 docx 假装同步过。

### 5 三重自检

```bash
node .workbuddy/skills/shilzi-doc-sync/scripts/doc-audit.js --cases=<真值>   # 必须 0 差异
node .workbuddy/skills/shilzi-doc-sync/scripts/doc-audit.js --frozen-check   # 冻结文件零改动
```

第三重是链接可达性（人工或用 `--links`）：

- 文档里引用的 `docs/*.md` 是否存在；
- 新建的验收记录是否已挂到账本；
- 账本里的链接是否都有对应文件。

三重全过才算收工。

## 输出收尾报告

用 `templates/sync-report.md`，写清：本批命中的文档、每处改动的旧值→新值、未校验项及原因（例如缺 python-docx 导致 docx 未重建）、遗留风险。

报告给用户看的部分不超过 10 行，细节留在报告里。

## 三条纪律

1. **不改 C 类**，即使里面的数字明显过期 —— 那是历史。
2. **不为了 audit 归零而改口径**：数字对不上时，先确认代码真值是否正确，再看文档。
3. **不许删掉文档里的分解信息**（如把「主包 5 + 分包 37」简化成「43 页」）来躲避校对。分解信息是排查依据。
