# 石榴籽施工守则（总纲）

> 本文件只做索引：**规则 + 违反后的症状 + 该读 docs 的哪一节**。
> 不复制 docs 正文。docs 与本文冲突时，以代码为准，并顺手把 docs 改对。

## 触发范围与执行方式

- 本仓库的工程任务默认先读本技能：理解或评估需求、分析实现与依赖、review / 代码审查、性能或安全检查、故障定位、测试与构建诊断、规则调整、重构，以及维护 `AGENTS.md` / `.workbuddy/skills/**`。
- 按任务意图、涉及文件和当前对话触发，不要求用户说出技能名或某个触发词。泛化请求如“看看有没有问题”“这样改行吗”“这块为什么慢”也适用；与本项目无关的通用问答不触发。
- **只读分析 / 咨询 / 审查**：使用分层、权限、容量、镜像和运行时约束评估代码；按需做只读核查或复现，不自动修代码、改文档或生成验收记录。测试范围按需要验证的问题选择。
- **仅改文档 / Skill / 项目指令**：检查目标文件、引用路径、触发一致性与技能结构；没有运行逻辑变更时，不因加载本技能而要求全量业务测试、镜像生成或 docx 重建。
- **修改代码 / 配置 / 构建逻辑**：执行下方开工基线及对应验证矩阵；页面、云端和收尾任务再叠加对应专项技能。加载技能不代表扩大用户授权的修改范围。

## 一、开工三查（修改代码、配置或构建逻辑前）

```bash
git status --short          # 有没有别人/上一轮留下的未提交改动
git log --oneline -6        # 上一批做到哪
npm test                    # 记录基线：文件数 / 用例数 / 失败数 / 耗时
npm run check:cloud-sync    # 镜像是否已漂移
```

三条纪律：

1. **先记基线再动手**。测试一开始就是红的，要能说清「接手前就红」还是「我改红」。
2. **看到未提交改动先问**，不要当作自己的上下文继续改。
3. **基线数字只写进报告，不写进代码**（文档里的数字会过期，见 `shilzi-doc-sync`）。

## 二、分层与分包（改之前先定位自己在第几层）

```
pages / 分包页面     界面，只调 services
services             视图模型 + 数据源门面（MOCK / CLOUD 同一套接口）
utils                纯函数：计分、抽签、分组、榜单、积分、权限
cloudfunctions/data  唯一云函数：协议 2 信封 + 仓储 + 事务
```

**单向依赖**：分包可引主包（`services` / `utils` / `components` / `templates`），**主包不可引分包**。

- 违反症状：编译报「文件找不到」，看着像路径错，方向错才真因；WXSS 跨包 `@import` 同样失败。
- 结论：共用 WXSS 放 `templates/`，算法与组件一律留主包。
- 守它的测试：`tests/subpackage-boundaries.test.js`（查 `@import` / `import` `/` `include` / `usingComponents` / `require` 四种形式）。

详见 `README.md §5.1`、`docs/交接说明.md §二`。

## 三、云端镜像（本仓库最容易静默失败的一处）

改 `miniprogram/` 下的纯模块后：

```bash
npm run sync:cloud        # 写入 cloudfunctions/data/lib/
npm run check:cloud-sync  # 只校验
```

- **症状**：走 `handleSchoolRequest` 的测试读到旧副本，改动**静默不生效**，表现为「明明改了却断言失败」。
- **禁止**手改 `cloudfunctions/data/lib/**`；它由 `tools/sync-cloud-lib.js` 的 `MANIFEST` 生成，`tests/cloud-lib-sync.test.js` 逐字节校验。
- **新增 services 文件必须进 `MANIFEST`**，否则云端 `Cannot find module './xxx.js'`，而本地测试走 `miniprogram` 路径发现不了。

## 四、路由与 ID

- 跳转参数**只编码一次**（`encodeURIComponent` 嵌两次就会 double-encode）。
- 装载器探测到的真实编号（如 `eventId`）必须回传到页面实例；页面后续写操作使用回传值，不要自己从 `options` 重拼。
- 症状：`options` 里有 `%E8%B5%9B` 这类串 → 报「赛事不存在」。
- 学校键一律走统一工具（`school key` 工具函数），不要手拼字符串。

详见 `docs/AI接手与后续施工指南.md §9`。

## 五、权限与事务边界

- **浏览范围 ≠ 授权凭证**。`listXxx` 的过滤条件只决定看得见什么，写操作必须在**事务内**重读身份与主记录。
- 新增仓储原语**必须自带范围条件**：即使按 `_id in (...)` 查，也要把 `schoolId`（及 `association`）拼进查询，不能把归属校验留给调用方。
- 失败要「拒绝」而不是「返回空」：空列表会让调用方以为成功。

## 六、容量预算（只在云端成立，本地 mock 看不出来）

| 约束 | 上限 | 守在哪 |
|---|---|---|
| 单事务操作数 | ≤ 100 | `TX_OPERATION_BUDGET` 守卫 + 各批预算用例 |
| 建小组人数 | ≤ 30 | ≤ 约 90 次操作 |
| 批量加人 | ≤ 30（`TEAM_ADD_BATCH_MAX`） | 30 人 = 67 次操作 |
| 跨校名额 | ≤ 128 | `exchange-service.test.js` |

- 新增批量入口：**先算每人几次操作，再定上限常量**，并在事务前拒绝超限。
- 列表必须返回 `hasMore`；分页查询依赖索引，新查询要同步 `docs/数据库索引清单.md`。
- 禁止「整表读 + 内存过滤」写新代码；要下推就写成带条件的仓储方法（云端 `where` + 内存同口径 + 契约测试）。

## 七、样式体系（三条例，其余都是推论）

1. **不硬编码颜色与字号** —— 用 `app.wxss` 的变量（颜色组 + 10 档字号）。
2. **不重定义全局类** —— `.btn` / `.card` / `.tag` / `.empty-state` 已在全局，页面里再写同名块 = 偷偷换掉这一个页面的按钮。要差异就加变体（`.btn-primary` / `.btn-outline` / `.btn-ghost` …）。
3. **随协会切换的页面必须挂 `themeClass`**；`packageMeet`（运动会）例外，固定挂 `meet-theme` 且 json 里单独配金色导航栏。

危险语义（报错、删除、作废）不吃主色，一律 `--color-danger-text`，否则换肤后错误提示变金色。

详见 `docs/前端样式规范-2026-10-23.md §三`、`§八`。

## 八、小程序端运行时禁区

`miniprogram/**` 里禁止裸写：

```
process / Buffer / __dirname / __filename / require('fs')
```

- 需要环境差异时用 `typeof process !== 'undefined'` 保护，小程序端取安全默认值。
- **为什么**：全部测试跑在 Node 里，这类写法 2900+ 条用例全绿，真机白屏。
- 守它的测试：`tests/miniprogram-runtime-safety.test.js`（静态扫描 + `node:vm` 无 `process` 沙箱加载）。
- 白名单只允许有理由的条目，且每条必须配一条沙箱用例。

**共享模块只能站在小程序这一侧**：`miniprogram/services/**` 会被两端加载，云端专用逻辑必须显式判环境。

## 九、验证命令矩阵

| 改了什么 | 必跑 |
|---|---|
| 任何代码 | `npm test` |
| `miniprogram/` 纯模块 | `npm test` + `npm run check:cloud-sync` |
| 导入工具（`tools/*.py`） | `npm run test:py` |
| 验收收尾 | `node tools/acceptance-audit.cjs` |
| 单文件排查 | `node tools/run-tests.js --filter <名>` |
| 文档/数字 | `node .workbuddy/skills/shilzi-doc-sync/scripts/doc-audit.js` |

不要用裸 `node --test` 当结论：慢文件会拖住整套，`tools/run-tests.js` 有单文件硬超时与心跳。

## 十、留痕纪律

- 每批收尾必出验收记录 + 更新 `docs/施工切片账本.md` → 走 `shilzi-acceptance-doc`。
- 验收记录、只读审计、需求整理是**历史留痕**，冻结不改；事实变了更新现行文档，不要回写历史。
- 明确「不做什么」也要写理由（本项目的惯例：决定不做 = 一条带触发条件的记录，不是沉默）。

## 十一、三条硬禁止

1. **不许把缺陷包装成「成功的空列表」**让测试转绿。
2. **不许手改评分、手改镜像、手改生成物（docx）**来让检查通过。
3. **同一个问题连修三次未解决就停下**，说明已尝试方案并请人介入，不做「试试这个试试那个」。
