# 验收记录与收尾留痕

本项目的留痕惯例：**做过什么、验成什么样、没做什么、为什么**，四件事都要能在文档里查到。半年后接手的人只信这个。

## 触发范围与交付粒度

- 一项功能、修复、重构或阶段工作完成，需要验收、交付说明、发布前检查、交接材料、记录验证证据、遗留问题或“不做”的决策时使用；“整理这次结果”“给下个 AI 接手”“这批可以上线了吗”也适用。
- 代码批次正式收尾按下方十段模板和账本流程执行；用户明确要审计报告或交接材料时，只记录已核查的事实，区分已复现、待验证与建议，不把建议写成已完成修复。
- 只询问进度、简短总结或仅调整 Skill 触发描述时，按用户要求给出相应说明，不自动新建整套验收记录、追加账本或重建无关 docx。单独核对现有文档使用 `shilzi-doc-sync`。

前置：代码批次正式验收须跑通 `npm test` 与 `npm run check:cloud-sync`，记录现场结果；只读审计或文档任务按实际验证范围留痕，未跑的检查明确标注，不声称全量验收通过。

## 一、十段模板

新建 `docs/<批次名>-验收记录.md`，段落如下（顺序固定，缺哪段就写「无」，不要省略）：

| # | 段 | 内容要求 |
|---|---|---|
| 1 | 元信息 | 日期、提交号（`git log -1 --format=%h`）、范围一句话、开工前基线 |
| 2 | 本批完成 | 逐项：改了什么 + 涉及文件 + 对应测试名 |
| 3 | 关键口径 | 做了 A 不做 B 的理由；口径变更要写「旧 → 新」 |
| 4 | 踩坑与纠正 | 含「查证后不成立」的结论（如「以为是 bug，实际是两个单位」） |
| 5 | 验证结果 | 命令 + 真值（文件数/用例数/镜像数/失败数/耗时） |
| 6 | 部署前必做 | 索引、MANIFEST、数据回填、云函数重部署 |
| 7 | 未完成及原因 | 每条带「触发条件 + 将来怎么改」 |
| 8 | 回归与反向验证 | 为防「测试转绿但行为没变」做的反向验证 |
| 9 | 文档同步 | 本次命中哪些文档（见 `shilzi-doc-sync` 的矩阵） |
| 10 | 队列收尾 | 账本要追加的那一行 |

第 4 段是这个项目最有价值的部分。已有多处「审查报告结论不成立」的记录，避免后人重复讨论同一个伪问题。

## 二、基线数字必须现场取

| 数字 | 取法 |
|---|---|
| 文件数 / 用例数 / 耗时 | `npm test` 输出最后一行 |
| 镜像文件数 | `npm run check:cloud-sync` 输出 |
| 页面 / action / 集合 | `node .workbuddy/skills/shilzi-doc-sync/scripts/doc-truth.js` |
| 提交号 | `git log -1 --format=%h` |

**禁止**从 README 或上一份验收记录里抄数字。实测过：同一批事实在 README 与交接说明里有四个值互不相同（页面 42/39/43、action 187/187/200、镜像 86/85/77/87）。

## 三、账本追加

`docs/施工切片账本.md` 的队列表追加一行，格式照抄既有行：

```markdown
| <批次> | <一句话内容> | **已完成** | `<hash>` / [验收](<批次名>-验收记录.md) |
```

纪律：

- **只追加，不改历史行**。历史行的提交号与结论是当时的，即使现在看是错的。
- 状态词固定：`已完成` / **不做** / `进行中`。做不到就写「不做」并给理由，不要留空。
- 账本里有「合并批」的先例（用户觉得分批提交太碎），新批次先问要不要合并提交。

## 四、冻结边界

**不许修改**：`docs/*验收记录*`、`*只读审计*`、`*需求整理*`、`*隐患*`、`*调查*`、`.workbuddy/memory/*.md`。

理由：它们记录的是「当时的事实与判断」。事实变了，改的是现行文档；回写历史等于篡改证据链。

`shilzi-doc-sync` 的 `doc-audit.js` 会检查 `git diff` 是否碰到冻结文件。

## 五、docx 产物

Markdown 是唯一内容源，docx 是构建产物。当前三份：

| 源 | 产物 |
|---|---|
| `docs/赛事管理员操作手册.md` | `赛事管理员操作手册.docx` |
| `docs/云开发控制台操作指南.md` | `云开发控制台操作指南.docx` |
| `docs/交接说明.md` | `交接说明.docx` |

```bash
node .workbuddy/skills/shilzi-doc-sync/scripts/doc-build.cjs        # 全部
node .workbuddy/skills/shilzi-doc-sync/scripts/doc-build.cjs 交接说明  # 单份
```

脚本会先检查 `python-docx`。本项目已把它装在隔离 venv
（`binaries/python/envs/default`），脚本会优先用这个解释器；换机器后若报缺依赖：

1. 明确告诉用户「md 已更新，docx 未重建」，不要假装成功；
2. 修复：`<python> -m pip install python-docx`（装进隔离 venv，不要污染系统环境）；
3. 不要手改 docx 绕过构建。

## 六、收尾检查清单

```
- [ ] npm test 全绿，基线数字现场取
- [ ] npm run check:cloud-sync 一致
- [ ] node tools/acceptance-audit.cjs 无异常（涉及验收项时）
- [ ] 验收记录十段齐全
- [ ] 账本追加一行，历史行未改
- [ ] docx 已重建，或已明确告知未重建及原因
- [ ] 冻结文档零改动（git diff 核对）
- [ ] 交接给 shilzi-doc-sync 做全量文档校对
```
