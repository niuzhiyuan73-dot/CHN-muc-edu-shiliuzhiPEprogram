### 1.1 「点报名说赛事不存在」

我先做**反证**（证明修复点在页面，而不是把服务端放宽了），再做页面级实跑。

```

     :: encoded 直写 -> 赛事不存在；台账仍 0 人
PASS 03 B2 正控：真编号直调服务端写成功（说明拒绝只针对未解码值）
     :: 真编号报名 ok=true，quotaText=1/8 人
PASS 04 B3 页面（开发者工具环境）：encodeURIComponent 当 query，报名成功
     :: page.eventId=sev:muc:pkb:e%3Ademo_muc_admin%3Areq_uks8ixjp；报名后 1/8 人 / 已报名
PASS 05 B4 跳转名次页只编码一次（不能二次编码）
     :: /pages/event-placement/event-placement?eventId=sev%3Amuc%3Apkb%3Ae%253A...%253Areq_s8dlkc9z
PASS 06 B5 名次页（开发者工具环境）：提交名次真的结束了同一场赛事
     :: status=2（FINISHED=2），名次 2 条
```

原始现场（B1 / B3 的 EVIDENCE 行）：

```
B1 encoded=sev%3Amuc%3Apkb%3Ae%253Ademo_muc_admin%253Areq_u9cgxfhi -> ok=false message=赛事不存在
B3 page.eventId=sev:muc:pkb:e%3Ademo_muc_admin%3Areq_uks8ixjp 报名后 quotaText=1/8 人 mySignupLabel=已报名
B4 url=/pages/event-placement/event-placement?eventId=sev%3Amuc%3Apkb%3Ae%253A...%253Areq_s8dlkc9z -> 解码一次=真实编号
```

要点：

- 页面用 `encodeURIComponent(eventId)` 当 query 打开详情后，`page.eventId` 被换成**真实编号**，
  报名成功（`mySignupLabel=已报名`、`quotaText=1/8 人`），服务端台账里确有本人的报名记录（`getSchoolEvent` 的 `mySignup` 非空）。
- **未解码编号直调服务端写仍然被拒**（`ok=false / 赛事不存在`），说明服务端没有被放宽 —— 修复确实落在
  「页面采纳装载器回传的编号」这一层。
- 跳转名次页只编码一次：把跳转 URL 的 query 按 Node 环境（`URLSearchParams`）解码一次后正好是真实编号，
  没有二次编码。
- 名次页同样在未解码 query 下采纳真实编号，提交后赛事落到 `FINISHED`（=2），名次 2 条。

同一条 DTO 上取三个数字：列表行 `signupCount` / 详情 `event.signupCount` / 详情顶层 `signupCount`，
外加 `quotaText`。合成数据与原始输出（F1 的 EVIDENCE，原文照贴）：

```
F1 一致性表=[
 {"key":"stale",       "list":4,"detailEvent":4,"detailTop":4,"quotaText":"4/16 人","results":2},
 {"key":"inflated",    "list":2,"detailEvent":2,"detailTop":2,"quotaText":"2/16 人","results":2},

```

- 三处数字**处处一致**，`quotaText` 也一致（版本 A/B/C 都一样）。
- 读操作**不写库**：合成赛事主记录 `signupCount` 始终是 0，展示为 4（H2：`主记录 0 / 展示 4`）。

### 5.1 名额口径分叉（F3/F4）——版本 A 发现，版本 B/C 已修复，我按不变式复测通过

**过程记录（版本 A，当时的实测输出）**：

```
F3 读端 canSignUp=false(名额已满)；直接调写接口 ok=true；写后展示=3/2 人      ← 读端说满、写端放行 → 超员
F4 读端 canSignUp=true(2/3 人)；写端 ok=false message=名额已满                ← 页面能点、服务端拒绝
```

**版本 C 的实测（同一场景、同一脚本，改成不变式断言）**：

```
PASS 24 F3 名额不变式：台账已满（2/2）而计数为 0 → 读端说满时写端必须拒绝、不得超员
     :: 读端说满 / 写端拒绝，写后 2/2 人
PASS 25 F4 名额不变式：计数偏大（3）台账 2 → 读端与写端结论必须一致
     :: 读端=false 写端=false（一致）
PASS 26 F5 计数回填：计数偏小（0）而台账 2，成功报名后计数收敛到 3
     :: 2/5 人 → 3/5 人
```

原始现场（版本 C）：

```
F3 读端 canSignUp=false 提示=名额已满
F3 直接调写接口 ok=false message=名额已满；写后展示=2/2 人        ← 不再超员
F4 读端 canSignUp=false 提示=名额已满；写端 ok=false message=名额已满
F5 报名前 2/5 人 → 报名后 3/5 人（主记录计数应已回填为 3）
```

我用的判据是**不变式**而不是照抄实现：把「读端说满/说可报」与「写端实际收不收」对起来，
再断言写后不超员。版本 A 上它判失败（正是我报的分叉），版本 C 上通过——所以这不是我改松了断言，
而是行为真的变了。修复后的实现（`occupiedSignupCount` = 主记录计数与台账取大，读写同一把尺子，
报名成功把占用数回填主记录）与 Lead 的说法一致，我核对过源码。

### 5.2 边界：台账全取消时的表现（F2，仍然存在，属口径边界）

```
F2 all-canceled 展示=0，而 results=2（名次仍在）——台账优先的边界表现
```

三处数字仍然自洽（都显示 `0/16 人`），但页面上会同时出现「名次表 2 行」与「0 人」。
属于口径边界，不是自相矛盾；提一句以免用户再报一次「人数不对」。

### 5.3 仍存疑（版本 C，两处设计取舍，我如实记录，不判失败）

**（1）展示人数与「是否已满」用的是两个不同的数（L4）**

```
PASS 38 L4 计数虚高（9）而名额 5、台账 2：展示与闸门各自的口径（记录用）
     :: 展示 2/5 人 + 提示「名额已满」，读写一致（都拒）
L4 展示=2/5 人，闸门提示=名额已满，读端 canSignUp=false，写端=名额已满
```

展示走台账（真值 2 人），闸门走「占用数」（计数 9 ≥ 名额 5）。**读端与写端是一致的（都拒）**，
所以不会再出现版本 A 那种「点了才被拒 / 说满了却放行」；但页面上会同时出现「2/5 人」和「名额已满」，
用户看可能觉得矛盾。触发条件是主记录计数虚高（历史导入 / 人工修数），不是本轮引入的数据形态。

**（2）取消仍按「计数 − 1」（Lead 已声明是保守取舍）**

计数被回填成占用数后，取消只会把计数减一。在「计数虚高」的数据上，占用数可能比真实活跃报名多，
表现为「取消了一个人，页面人数少了，但席位不一定能立刻再放一个人进来」。**方向是安全的（只会少放人，不会超员）**，
我实测的所有场景都没有出现超员；Lead 说已在 `cancelSchoolEventSignup` 注释与验收记录「已知边界」里写明。
我**没有**为此单独构造对抗用例（事务内读不到台账，属已知限制），如实标注。

### 5.4 首席要求的三个对抗点（我自己构造，版本 C 实测）

```
PASS 35 L1 计数偏小 + 台账接近满：连续 / 并发报名都不超员
     :: 连续 1 成功 2 拒（台账 3）；并发成功 1/3（台账 3）
PASS 36 L2 报名成功后返回给页面的人数是否等于台账真值（故意让计数与台账分叉）
     :: 写响应 3 = 台账 3
PASS 37 L3 报名被拒时主记录与台账都不得被改动（名额满/性别/小组/已抽签/已截止）
     :: 名额满:名额已满 / 性别:本赛事为男单，仅限男会员报名 / 小组限制:本次赛事仅限指定小组成员报名 /
        已抽签:已抽签，报名名单已定 / 已截止:报名已经截止了
```

**① 连续与并发报名会不会超员（L1）**：名额 3、主记录计数 0、台账已有 2 人（最坏组合）。
连续三次用三个不同会员报名 → **1 成功 2 拒**，最终有效台账 3 人、主记录计数 3；
再开一局用 `Promise.all` **真并发**发三次 → **恰好 1 次成功**，最终台账 3 人、计数 3。
两种打法都没有超员。

```
L1 连续：demo_muc_member:true / demo_muc_admin:false / demo_muc_college_leader:false → 台账 3 人，计数 3；
   并发：成功 1/3 → 台账 3 人，计数 3
```

**② 报名成功后回给页面的人数是不是台账真值（L2）**：故意造「计数 9、台账 2、名额 20」的分叉数据，
报名成功后看写接口的返回体：

```
L2 写响应 event.signupCount=3 quotaText=3/20 人；台账真值=3；随后的详情读数=3；主记录计数=10
```

返回给页面的 **3 = 台账真值 3**（不是被回填成 10 的计数器），随后的详情读数也是 3。
Lead 的说法成立；顺带可见主记录计数确实被回填成 10（占用数口径），而展示/返回一律走台账。

**③ 报名被拒时主记录有没有被改动（L3）**：用自己的仓储直读赛事文档、台账与审计表，
对五种拒绝路径各做一次「前后逐字节比对」：

```
L3 五种拒绝：名额满:名额已满 / 性别:本赛事为男单，仅限男会员报名 / 小组限制:本次赛事仅限指定小组成员报名 /
   已抽签:已抽签，报名名单已定 / 已截止:报名已经截止了；每种的主记录、台账、审计均逐字节未变
```

五种拒绝下 `repo.events.getById()` 的文档 `assert.deepStrictEqual` 前后一致，台账条数不变，审计条数不变。
（构造提示：演示赛事模板的 `discipline` 是 `null`，所以「性别」这一路必须由我自己显式落 `discipline:'MS'`
才构造得出来——第一版用例因此误判过一次，是我的夹具问题，不是缺陷。）
