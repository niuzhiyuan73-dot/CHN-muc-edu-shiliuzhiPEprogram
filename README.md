# 中央民族大学石榴籽体育管理小程序

一个原生微信小程序（WXML / WXSS / JS，零框架），把校内**多个体育协会**的等级分、赛事、训练与校级活动装进同一套系统。

- 当前进度：篮球五人制与实时计分已落地；足球 F0—F3 已完成，支持赛后报告与成绩；足球/篮球已有协会内“我的球队”累计统计页签
- 自检：`npm test` → **3188 项用例通过 / 0 失败 / 0 超时**（194 个测试文件 / 19.1 秒）
- 云端共享库：`npm run check:cloud-sync` → 94 个文件一致
- 界面预览：F01–F17 首轮优化留在工作区待用户看效果，**未提交、未部署，F18 排除**；范围与检查方法见[预览说明](docs/前端体验优化-F01-F17-预览说明.md)
- 数据源：默认**本地模拟**（`miniprogram/config.js` 的 `CLOUD_ENV_ID` 为空），填入环境 ID 即切云端，页面代码一行不改

---

## 一、这是什么

核心不是「报名工具」，而是**一套可核验的等级分账本**：每一场比赛是一笔流水，会员的等级分由服务端在「确认比分」的同一个事务里逐场结算，分数落在 `member_ratings`，不靠事后重算。赛事、训练、运动会都是往这本账上记账的不同入口。

在此基础上长出了三层业务：

| 层级 | 栏目 | 能做什么 |
|---|---|---|
| **校级活动** | 石榴籽杯 | 学院团体赛：一个球类项目一届杯赛，报名 → 收名单 → 抽签 → 排阵 → 大场 → 名次 |
| | 运动会 | 校运会全流程：发起 → 配项目 → 学院报名 → 编排与派裁判 → 录分发布 → 学院总榜与个人荣誉 |
| | 跨校邀请赛 | 与外校的交流赛，**不计个人等级分**，成绩单独留档 |
| **协会** | 协会空间 | 长期小组、内部通知、训练发布与报名签到 |
| | 排行榜 | 单打榜、进步榜、赛事积分榜（按协会、按性别分开展示） |
| | 比赛 | 全部比赛流水：录分、确认、驳回、弃权、改判入口 |
| | 赛事 | 协会级个人赛：发布 → 报名 → 抽签 → 开赛 → 录分 → 名次 |
| **个人** | 我的 | 注册入会、学校身份、我的成绩与荣誉、会员审核、公告管理 |

六个协会在代码注册表 `miniprogram/utils/associations.js` 里：`pkb` 匹克球、`tt` 乒乓、`bd` 羽球、`tn` 网球、`bk` 篮球、`fb` 足球。前四个是球拍运动；篮球和足球走团队工作台（协会空间 / 组队 / 我的球队 / 赛事），不进个人等级分。足球、篮球的球队与累计成绩入口位于各自协会的“我的球队”页签。足球已完成 F0—F3：自由组队、建赛与报名、赛程、赛后报告、审核更正及个人/球队成绩；不提供实时计分，见 [F2/F3 验收记录](docs/足球协会-F2F3赛后录分与成绩-验收记录.md)。

## 二、导航长什么样

底部三个页签：**首页 / 协会 / 我的**。

```
首页 ── 公告、近期赛事、协会快捷入口
协会 ── 六个协会宫格（点进「协会工作台」）
      └─ 石榴籽杯（校级活动）
      └─ 运动会（校级活动）
我的 ── 我的成绩 / 会员审核 / 公告管理 / 学校身份 / 跨校邀请赛
```

协会工作台顶部四个页签：**协会空间 · 排行榜 · 比赛 · 赛事**。所有协会内内容都从这里进，切换协会回「协会」页签。

## 三、账号与会籍

一个人只有一个平台账号，但可以在多个学校、多个协会拥有不同身份。控制台里对应五张表：

| 概念 | 集合 | 说明 |
|---|---|---|
| 平台账号 | `users` | 一个微信号一条，`openId` 唯一；全局角色 `role`（0 会员 / 2 管理员） |
| 学校会籍 | `school_members` | 「某人在某校」的会籍与状态（待审核 / 正常 / 禁用 / 离校） |
| 校级角色 | `school_roles` | 校级管理员 |
| 协会角色 | `memberships` | `staff` 学院负责人、`leader` 协会负责人；无行即普通会员 |
| 学校 × 协会 | `school_associations` | 该校是否启用该协会；没启用就进不去 |

有效角色是合成的：`schoolAdmin` > `associationLeader` > `collegeLeader` > 会员。详见 [云开发控制台操作指南](docs/云开发控制台操作指南.md) 第五节。

**部署时别漏了索引**：本地 mock 用内存 Map，没有索引概念；云端缺索引会增加扫描与排序成本。要建哪些索引见 [数据库索引清单](docs/数据库索引清单.md)；比赛分页依赖 §2.3，公告分页与团队首页摘要新增的 5 条组合索引见 §2.6。

## 四、计分与积分规则

### 4.1 等级分（Elo）

| 项 | 规则 | 出处 |
|---|---|---|
| 起评分 | 男 1450 / 女 1300（性别未知按 1450） | `utils/elo.js` |
| 定级 | 新会员前 5 场按对手水平定出起点分，向下取 50 的整数倍 | `utils/elo.js` |
| 日常约球 K | 全员一律 16，不再按人分段 | `utils/elo.js` |
| 赛事 K | 一级 32 / 二级 24 / 三级 16 | `utils/elo.js` |
| 结算 | 零和；确认比分时在事务里逐场结算，写入 `member_ratings`，序号来自 `rating_counters` | `services/school-rating-service.js` |
| 不计分的场次 | 双打、弃权、跨校交流赛 | 同上 |
| 防刷 | 一对会员**每赛季最多 15 场**日常约球计入等级分（赛事与学院赛小场不占名额） | `constants.RATED_PAIR_LIMIT` |

> **已确认生效的比赛没有「撤销」**。录错了只能在「待确认」阶段由对手驳回；一旦确认即最终结算。

### 4.2 赛事积分

参与分 2 分 + 名次档位（1→20 / 2→14 / 3→10 / 4→7 / 5–8→4，未进八强 0）× 等级倍数（一级 ×4 / 二级 ×2 / 三级 ×1）。同一赛事只按最终名次计一次；双打不计。

### 4.3 网球（唯一的三级计分）

一局 4 分（15/30/40，40:40 需净胜 2 分，可选无占先一分定胜负）；一盘先到 6 局且净胜 2 局，6:6 打 7 分抢七，抢七胜者以 7:6 拿下该盘；一场可选一盘决胜或三盘两胜。

比分数组的元素因此从「每局得分」变成「每盘局数」，抢七小分单独存 `tiebreaks`，展示成 `7:6(5)`。见 [网球计分方案](docs/网球计分-需求与实施方案.md)。

## 五、技术架构

```
pages + 5 个分包 / components   界面（43 个页面 + 面板组件）
        │
services                 视图模型 + 数据源门面（MOCK / CLOUD 同一套接口）
        │
utils                    纯函数：计分、抽签、分组、榜单、积分、权限
        │
        ├── tools/sync-cloud-lib.js ──逐字节镜像──▶ cloudfunctions/data/lib/（94 文件）
        │
cloudfunctions/data      唯一云函数：协议 2 请求信封 + 仓储 + 事务
        └── src/core      身份上下文、路由、四个领域的 action handler（共 201 个）
```

**为什么只有一个云函数**：权限、身份解析、错误信封只写一份；云函数按个数部署与计费。当前 201 个 action 按领域分成四组：会员与身份 13、协会空间与个人赛/团队 119、跨校邀请赛 16、运动会 53。

**为什么有 `lib/` 镜像**：微信云函数按目录打包，`require` 不出目录。算法必须两端同一份实现，所以把纯模块复制进 `cloudfunctions/data/lib/`，并由 `tests/cloud-lib-sync.test.js` 逐字节守着。改了 `miniprogram/` 下的纯逻辑而忘了同步，测试立刻变红。

### 5.1 分包

主包只留 **tabBar 三页 + 登录 + 协会工作台外壳**，其余按域拆成 5 个分包，按需下载：

| 分包 | 页面 | 体积（gzip） |
|---|---|---|
| `packageEvent` | 赛事列表 / 详情 / 编辑 / 名次、比赛录分 | 49 KB |
| `packageMeet` | 运动会：列表、详情、编排、学院报名、赛程、录分、榜单 | 58 KB |
| `packageTeam` | 球队、团队赛事、我的球队、实时计分、足球比赛 | 65 KB |
| `packageCollege` | 石榴籽杯、学院赛报名 / 名单 / 对抗 / 名次 | 61 KB |
| `packageMember` | 会员主页、审核、公告、资料、学校身份、跨校邀请赛 | 46 KB |

> 体积是最近一次打包实测值，本地 `npm test` 覆盖不到；**增删页面后需重新打包核对**，不要按页数推算。

上次打包记录：主包 **939 KB（gzip）**，全量 1217 KB；本轮共享组件和交互改动后的体积待微信开发者工具重新打包核对。约定：

- **分包可以用主包的 `services` / `utils` / `components` / `templates`，反过来不行。** 所以算法、门面、面板组件、共用样式一律留在主包，分包里只放页面。共用的 WXSS 放 `templates/`（如 `templates/team-profile-view.wxss`），两边都从主包 `@import`——**主包组件引用分包里的 wxss 会编译失败**，报错长得像「文件找不到」，实际是方向错了。
- 页面目录深度保持两级（`<包>/<页面>/`），页面里的 `require('../../services/...')` 因此不用改。
- 只有「我的」页对 `packageMember` 做 wifi 预下载；其余按需拉取——四个包全预载等于把分包的意义抵消掉。
- 测试别写死 `pages/<名>/<名>`：用 `tests/helpers/page-registry.js` 的 `pageFileOf(name)` / `pagePathOf(name)` 从 `app.json` 查。分包页面**不在** `app.pages` 里，判断注册要用 `isRegistered(name)`。
- 引用方向由 `tests/subpackage-boundaries.test.js` 守着，把 WXSS `@import`、WXML `import/include/wxs`、`usingComponents`、`require` 四种形式全查一遍。这类错误单元测试天然看不见，只有编译器会报。

### 5.2 容量边界（云端约束）

本地 mock 用内存仓储，**没有事务操作数上限、没有索引、没有读配额**——这三件事只在云端成立，所以都做成了显式约束，而不是等它上线后自发暴露。

| 约束 | 现状 | 守在哪 |
|---|---|---|
| 单事务操作数 ≤ 100 | 锁名单 **8 次**（与人数无关）；建小组 ≤ 30 人（约 90 次）；跨校名额 ≤ 128 | `TX_OPERATION_BUDGET` 守卫 + `exchange-service.test.js` 的操作数用例 |
| 个人赛事报名容量 | 单打 ≤ 88 人、双打 ≤ 176 人；名额填 0 仍受此限制；抽签前按实际生成场数及重读预算复核 | `school-draw-budget.test.js`，覆盖六赛制满容量与重抽 |
| 整表读放大 | 已把 7 处「整表读 + 内存过滤」改成按 `eventId` 的条件查询 | `docs/数据库索引清单.md` 第四节 |
| 索引缺失 | 需在控制台按清单建（本地无从验证） | `docs/数据库索引清单.md` |
| 展示时区 | 固定东八区，与运行环境无关（云函数是 UTC） | `format.test.js` 的 `TZ=UTC` 子进程用例 |

**跨校邀请赛锁名单的操作数不随人数线性增加**：锁名单产出一份写在赛事文档上的名册快照；后续抽签、录分、名次、签到都读这份名册，不逐条改报名记录。实际发布名额仍限制在 128 人以内。

权限与并发写入在事务内复核：重抽逐场检查比赛版本及结算状态；学院管理范围取 `memberships.collegeId`；开台、判球、撤销、定稿及重置赛季重读当前身份。跨校详情只补已指派裁判姓名，候选由管理者按已接受邀请的学校搜索分页。足球排期按资源及时间窗查询，比赛面板离开页签即停止订阅。部署前新增索引见[索引清单 §2.5](docs/数据库索引清单.md#25-第九轮查询索引2026-10-28)。本批验证与限制见[第九轮验收](docs/第九轮权限并发与规模边界修复-验收记录.md)。

前后端界面契约已同步：转校待办使用转校审批；学院名单从授权范围选择学院，授权页区分学籍与管理学院；跨校邀请支持选择 2–8 校及各校名额；公告公开列表和台账提供游标续页；运动会筛选丢弃过期响应；首页汇总个人赛及足球、篮球团队赛事并跳转对应详情。个人赛事表单实时显示单打 88 / 双打 176 人上限，详情保留报名限制原因。见[第十轮验收](docs/第十轮前后端界面契约修复-验收记录.md)。

## 七、常用命令

```bash

npm run sync:cloud        # 把纯逻辑镜像到 cloudfunctions/data/lib/

node .workbuddy/skills/shilzi-doc-sync/scripts/doc-audit.js --cases=<npm test 的用例数>  # 文档数字校对
```

**施工约定 skill**：`.workbuddy/skills/` 下四份守则（施工总则、页面、云函数 action、验收留痕）
加一份文档同步器，随代码入库。改动前先读 `shilzi-construction-guard`；每批收尾跑
`doc-audit` 并按影响面重建 docx；只读审查、页面组件维护、已有接口和技能指令维护也按意图加载，入口见 `AGENTS.md`。

`npm test` 走 `tools/run-tests.js`，而不是裸的 `node --test`：单个测试文件超过默认 8 分钟
会被杀掉并点名，运行期间每 15 秒打一行「正在跑谁」，慢文件在总结里单独列出。
`tests/page.test.js` 的耗时随机器变化，运行器会持续报告进度和实际耗时，避免整套测试长时间没有输出。

```bash
node tools/run-tests.js --timeout 120000   # 临时收紧单文件超时
```

## 八、首次部署三步

1. **填环境 ID**：`miniprogram/config.js` 的 `CLOUD_ENV_ID`。
2. **建集合**：按 [云开发控制台操作指南](docs/云开发控制台操作指南.md) 第三节建 52 个集合，权限全部设为「所有用户不可读写」。
3. **部署云函数**：`npm run sync:cloud` → 开发者工具右键 `cloudfunctions/data` →「上传并部署：云端安装依赖」→ 创建第一个校级管理员。

> **本批有存量账号迁移要求**：先按[安全与性能实施方案](docs/安全与性能优化-实施方案.md)备份迁移并补齐目录字段，按[索引清单](docs/数据库索引清单.md)第 2.4 节建新索引，再部署。

> **改完代码一定要重新部署 `data`**。云函数不随小程序编译更新，漏部署的典型症状是新增接口报「该操作尚未支持学校范围」。
