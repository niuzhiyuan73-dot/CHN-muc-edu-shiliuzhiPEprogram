# 性别审查（需求整理）

> 2026-09-13 需求整理。承接 `学院赛设计方案.docx` 与 `college-demo.js` 演示场景。
>
> **本文档只做整理与方案，尚未改动任何代码。**
> 请先确认 §五 的四条待定口径（其余按默认执行），再按 §七 的顺序动工。

---

## 一、需求原文

> 现在的学院赛测试种子太简陋了，还有男单和女单是同一个人的情况，现在的男女比赛
> 根本不在报名的时候审查性别，这是我们之前没有注意到的 bug，现在开始增加性别
> 审查功能，包括个人赛和学院赛。

---

## 二、需求拆解

| 编号 | 需求 | 涉及体系 | 类型 |
|---|---|---|---|
| 1 | 男单/女单/男双/女双/混双等小项，排阵时按小项审查上场队员性别 | 学院赛 | 新增校验 |
| 2 | 个人赛（如「男子单打赛」）**报名时**按赛事性别审查报名人 | 个人赛 | 新增校验 + 数据字段 |
| 3 | 学院赛演示种子重做：同一人不能既打男单又打女单；单性别学院要能真凑出名单 | 模拟数据 | 重做种子 |
| 4 | 两套体系共用同一份「小项 → 性别」定义，不许各处各写一套 | 架构约束 | 重构 |

## 三、现状与根因

### 3.1 性别字段一直有，但只用在校级「定级」与「榜单」，从不参与参赛校验

`utils/constants.js:125` 定义 `GENDER = { MALE: 'M', FEMALE: 'F' }`，注册时采集，
且是列为不可自改的实名字段（`services/auth.js` 的 PROFILE_RULES；
`services/profile.js` 的 IMMUTABLE_FIELDS）。它目前只喂两处：

- **定级**：`utils/elo.js:135` `initialRatingFor` —— 女会员初始分低
  `genderInitialGap`（150）分，即男 1450 / 女 1300；
- **榜单**：`utils/constants.js:232` `RANK_PROJECT_CONFIG` —— 男单榜 / 女单榜按性别过滤展示。

**没有任何一处把性别用于「谁能报名 / 谁能上场」。** 全仓 grep：`services/event.js`、
`services/match-record.js`、`services/college-entry.js`、`services/college-lineup.js`、
`services/college-view.js` 里 `gender` 命中数为 **0**。

### 3.2 学院赛：小项名字里写着性别，排阵却完全不看

`LEG_DISCIPLINE`（`constants.js:649`）= MS 男单 / WS 女单 / MD 男双 / WD 女双 / XD 混双。
可全项目没有一处把「小项 → 需要什么性别」编码出来：

- `college-lineup.js:38` `playersPerLeg` 只会**数人数**（双打 2、单打 1）；
- `validateLineup`（`college-lineup.js:96-172`）逐小项只校验「人数够不够、在不在名单里、兼项」；
- `college-tie.js:182` `disciplineToMatchType` 只把 MS/WS 映成单打、MD/WD/XD 映成双打。

所以**男单可以派女队员、女双可以派男队员、混双可以两个男**，一路畅通无阻。

### 3.3 演示种子的三处失真，把上面这个洞放大成了肉眼可见的错

`college-demo.js` 造的「16 进 8」场景：

1. **同一人既打男单又打女单。** `lineupEntries`（`college-demo.js:85-91`）：

   ```js
   for (let i = 0; i < need; i += 1) players.push(ids[i % ids.length]);
   ```

   `i` 在**每个小项内部**从 0 重新数；单打 `need === 1`，于是每个小项都取 `ids[0]`。
   男单、女单因此派了**同一个（名单里第一个）人**。16 所学院无一例外：
   10 名男队员被塞进女单、6 名女队员被塞进男单。

2. **名单只有 1–2 人，且多数学院单性别。** `rosterIdsOf`（`:71-79`）取「本院在册、
   非干事」的全部人；24 名种子会员摊到 15 所学院后，理学院 / 生命与环境科学学院 /
   中国少数民族语言文学学院 / 美术学院 / 音乐学院 / 哲学与宗教学院等只有单一性别，
   法学院更是被 `u06`（干事）排除后只剩孙悦一人（`tests/college-demo.test.js:243`
   正断言 `rosterCount === 1`）。`rosterMin: 1`（`:152`）让这种畸形名单也能过审。

3. **个人赛的性别只写在标题里。** 种子 `eventPlan`（`seed.js:630-637`）给男 / 女单
   赛事硬编码 `gender: 'M' / 'F'` 并按性别挑人（`seed.js:660-668`），但**这只存在于
   种子生成脚本里**：`buildEventRecord`（`services/event.js:575`）产出的赛事记录
   **没有 `gender` 字段**，`canSignUp`（`services/event.js:245`）也不看性别。
   也就是说，「男子单打赛」这个身份在数据里根本不存在，只有标题字符串在暗示。

### 3.4 必须先厘清：单打「男女合池」≠「男女分组赛事」

这是本次最容易改错的地方，两条既有设计写得很明确：

- `constants.js:140` MATCH_TYPE 注释：「单打（不分男女，男女可以互相对打）」；
  `RATING_POOL` 注释（`:161-177`）详述男女单打**合并成一个池**、榜单只是分开展示；
- `seed.js:215` 起专门解释「为什么一定要留出男女对打」，`tests/seed.test.js:190-206`
  断言单打里必须存在男女对打的比赛。

因此**不能**把「单打一律禁止男女同场」当成这次的需求——那会推翻定级口径，并让
现有测试与种子大面积失效。正确的口径是：

> **比赛可以男女对打（合池）；但赛事 / 小项本身可以声明自己是分性别的，
> 此时只有相符性别的人能报名 / 上场。**

「男子单打赛」限男报名，是**赛事级限制**；两名不同性别的会员私下打一场单打，
仍然合法且照常计分。这两件事互不冲突。

## 五、待确认口径

### 5.1 必须拍板（选错要返工）

**Q1：个人赛的性别审查，落在哪个字段上？**

| 方案 | 做法 | 结果 |
|---|---|---|
| **A（推荐）** | 赛事加一个**可选字段** `gender`（`null` / `'M'` / `'F'`，缺省 `null` 表示不限）；仅当它不是 null 时，报名 / 录分才按性别拦人 | 改动最小、向后兼容；种子里的男 / 女单赛事补上该字段即可。缺点：表达不了「男双 / 女双 / 混双」这类更细的分组 |
| B | 引入完整的「赛事项目」枚举（男单 / 女单 / 男双 / 女双 / 混双），与学院赛 `LEG_DISCIPLINE` 对齐 | 表达力最强，但与「双打不分男女、只设一个双打池」的既有口径冲突，改动面大 |
| C | 不动赛事，只在录分时按赛事标题里有没有「男 / 女」来推断 | 不推荐：靠字符串猜规则，标题一改就失效 |

**Q2：学院赛的性别校验，卡在哪一层？**

| 方案 | 做法 |
|---|---|
| **A（推荐）** | **只卡排阵**：`validateLineup` 按小项校验；名单阶段不拦，只在名单页给出各性别人数提示 |
| B | 名单也卡：提交名单时要求「每种小项都能凑齐」——但 `legPlan` 可能只用到 MS/WS，且名单允许替补，硬卡容易误伤 |
| C | 两层都卡：名单按 `legPlan` 的性别需求给**软提示**，排阵按**硬校验** |

**Q3：双打小项的性别口径？**（推荐全按字面）

- **MD 男双**：2 名男队员；**WD 女双**：2 名女队员；**XD 混双**：恰好 1 男 + 1 女。

**Q4：演示种子怎么修？**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐，呼应「种子太简陋」）** | 扩种子：给单性别学院各补 1–2 名异性会员，使 16 所演示学院都能真派出 MS + WS；`rosterMin` 提到 4 | 会员数 24 → 约 34，写死会员数的测试要改，榜单 / elo 全量重算 |
| B | 缩场景：`legPlan` 改成两端都能凑出的项目（如只打 WS + WD），或把演示学院减到 6 所 | 改动小，但场景不再「16 进 8」，演示效果打折 |
| C | 折中：扩种子到「每院至少 1 男 1 女」，赛事仍保持 16 所 | 改动适中 |

### 5.2 按默认执行（如无异议就这么做）

1. **一个真相源**：在 `utils/constants.js` 新增
   `LEG_DISCIPLINE_GENDERS = { MS:['M'], WS:['F'], MD:['M','M'], WD:['F','F'], XD:['M','F'] }`
   及助手 `requiredGendersOf(discipline)`。全项目的性别校验只准调它。
2. **失败关闭**：性别不符一律**拒绝并给明确文案**（如「男单只能派男队员」
   「混双需要一男一女」），不做灰按钮、不做静默降级。
3. **已发生的比赛不回溯**：新校验只作用于新写入；历史流水与已打完的大场不回填、
   不报错（种子改好后自然干净）。
4. **兼项与性别相互独立**：性别校验管「这个人能不能上这个小项」，兼项校验
   （`allowMultiEntry`）管「一个人能上几个小项」，各按各的规则，互不加码。
5. **UI 同步**：排阵页每个小项的候选按性别**过滤**（不符合的直接不出现），
   小项标题写明「限男 / 限女」；名单页给每位候选人显示性别。

## 六、建议方案（分层，供拍板后照此实施）

### 6.1 真相源（两套体系共用）

`utils/constants.js`：

```js
const LEG_DISCIPLINE_GENDERS = {
  [LEG_DISCIPLINE.MS]: [GENDER.MALE],
  [LEG_DISCIPLINE.WS]: [GENDER.FEMALE],
  [LEG_DISCIPLINE.MD]: [GENDER.MALE, GENDER.MALE],
  [LEG_DISCIPLINE.WD]: [GENDER.FEMALE, GENDER.FEMALE],
  [LEG_DISCIPLINE.XD]: [GENDER.MALE, GENDER.FEMALE],
};
```

配 `requiredGendersOf(discipline)`；`playersPerLeg` 可改为从真相源取长度
（`DOUBLES_DISCIPLINES` 保留给 `college-tie.js` 等其它消费者，避免重复定义）。

### 6.2 个人赛

- `services/event.js:575` `buildEventRecord` 增写 `gender`（校验只能取 `null` / `'M'` / `'F'`）；
- `services/event.js:245` `canSignUp` / `:334` `buildSignupRecord`：
  `event.gender && actor.gender !== event.gender` → 拒绝；
- （推荐）`services/match-record.js:375` `buildMatchRecord` 二次把关：赛事声明了性别时，
  参赛者性别须相符；
- 赛事编辑页：新建 / 编辑时选择「不限 / 男子 / 女子」；
- 种子 `eventPlan` 的男 / 女单赛事把 `gender` 写进事件记录。

### 6.3 学院赛

- `services/college-lineup.js:96` `validateLineup`：逐小项取
  `requiredGendersOf(leg.discipline)`，把上场队员的 `gender` 排序后比对；不符时给出
  **具体小项 + 原因**的文案。为此 `ctx` 需传入 member 对象（mock 已传 `load().members`，
  云端 `submitLineup` 需一并 `getDataset`）；
- `services/college-view.js:500` 排阵候选：带上 `gender`，按当前小项过滤 / 置灰；
- `services/college-view.js:117` 名单候选：带上 `gender` 显示；
- `pages/college-lineup/*`：小项标题显示「男单 · 限男」等提示。

### 6.4 种子

- `college-demo.js:85` `lineupEntries` 改为**按小项所需性别从名单里挑人**
  （而非 `ids[i % len]`），并保证同一人不被塞进性别冲突的两个小项；
- `college-demo.js:152` `rosterMin` 由 1 提到默认 4；
- 按 Q4 扩 `MEMBER_SEED`，使演示学院都能凑齐各性别。


## 八、工程约束

1. **镜像同步**：`utils/constants.js`、`services/event.js`、`services/college-lineup.js`、
   `services/match-record.js` 都在 `tools/sync-cloud-lib.js` 的 MANIFEST 内，改完必须
   `npm run sync:cloud`，并用 `npm run check:cloud-sync` 复核；`college-demo.js` 是
   mock 专用，不在清单内。
2. **动作注册表不动**：本期不新增云端接口（复用既有 `signUpEvent` / `submitLineup` 等），
   `actions.js` 的读 / 写名单保持不变。
3. **不落库派生值**：性别校验是即时判定，不新增持久化字段（赛事 `gender` 是用户输入，除外）。
4. **权限判定仍只在一处**：性别校验属于「业务校验」而非「权限」，放在各 `validate*` 里，
   `services/permission.js` 不动。
5. **向后兼容**：`event.gender` 缺省 `null` 即「不限」，既有赛事与流水一行不改。

## 九、明确「不做」的事

- ❌ 不禁止「不同性别私下打单打」——合池口径不变，男女对打照常计分。
- ❌ 不改 elo 的 `genderInitialGap`、不改排行榜的性别拆分口径。
- ❌ 不回溯校验 / 回填历史比赛。
- ❌ 不引入完整的「赛事项目（男单 / 女单 / 男双 / 女双 / 混双）」枚举（除非 Q1 选 B）。
- ❌ 不做「性别变更」流程（`gender` 仍由管理员核改）。
