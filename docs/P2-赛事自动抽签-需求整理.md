## 二、适用范围与前置条件

1. **仅单打赛事**（决策 1）：赛事 `matchType` 为单打时才提供抽签；双打赛事的创建表单与详情页**完全不变**。
2. **抽签窗口**：赛事处于「**报名中**」（`EVENT_STATUS.SIGNUP`）。一旦点过「开始赛事」（进行中）或已结束，**不可抽签、不可重抽**。
3. **参赛者口径**：**未取消的报名者**，即 `SIGNUP_STATUS` 为「已报名」或「已签到」的人，**不看签到**（决策 7）。
4. **人数下限**：参赛者 ≥ 2 人方可抽签；不足 2 人时抽签入口置灰并说明原因。
5. **抽签后冻结报名**：抽签完成后，该赛事**不再接受新的报名 / 取消报名**；如需变更，只能由管理员在开赛前**重抽**。

## 四、抽签算法

### 4.1 签位规模与轮空

- 设参赛人数 `N`，签位规模取**不小于 N 的最小 2 的幂** `P = 2^R`（如 6 人 → 8 签，11 人 → 16 签）。
- 轮空数 = `P − N`，**全部优先分配给高种子**（决策 6）。
- 复用现有标准种子排位表 `standardSeedOrder`（`miniprogram/services/seed.js:391`，8 人为 `[1,8,4,5,2,7,3,6]`），本期把它**提取到镜像内的公共工具层**，`seed.js` 反向引用，避免两份实现。

### 4.2 落位规则（一个函数覆盖「纯随机」与「有种子」）

把 `standardSeedOrder(P)` 的输出理解为「**位置 → 实力名次**」，再按名次填人：

| 名次区间 | 填入内容 |
|---|---|
| `1 .. S` | **种子**，按选定的种子来源排序后依次落位（S = 实际种子数） |
| `S+1 .. N` | **非种子**，**洗牌后**填入 |
| `N+1 .. P` | **轮空** |

该规则天然满足：① 头号与二号种子分处上下半区，决赛前不相遇；② 轮空自动落到对阵高种子的位置，即**高种子首轮轮空**；③ **种子数 S = 0 时退化为纯随机抽签**。

### 4.3 种子来源与顺序

- `elo`：按 `getPoolRating(member, 'singles').elo` 降序取前 S 名。
- `points`：按当前赛季积分 `member.points` 降序取前 S 名。
- `manual`：管理员**逐个指定序号**（1 号种子、2 号种子…），不靠系统自动排序。
- 数据来源与 `events-view.js:412` 一致——报名记录 + 会员名单（`getMembers` 的回放产物）拼装。

### 4.4 随机源与可复核

抽签时生成一个**随机种子值 `seedValue`**，与结果一同落库；任何人可据此复核抽签未被事后改动（`createSeededRandom` 已具备，`utils/random.js:28`）。

## 五、抽签产物与比赛生成

### 5.1 落库内容

赛事记录新增 `draw` 字段，形如：

```
draw: {
  seedMode, seedCount, seedValue,      // 抽签参数与随机种子
  drawnAt, drawnBy, drawCount,          // 抽签时间 / 操作人 / 第几次
  size: P,                              // 签位规模
  slots: [entryKey|null, ...],          // 长度 P，null 表示轮空
  seeds: [userId, ...],                 // 实际种子（有序）
  byes:  [userId, ...],                 // 轮空者
}
```

### 5.2 比赛生成（决策 5）

- 抽签**立即生成首轮比赛**，比赛记录**带上 `eventId`**；首轮轮空者不生成比赛。
- **后续轮次逐轮生成**：淘汰赛只有在上一轮打完、胜者确定后才能排出下一轮对阵。规则为**某一轮比赛全部确认生效后，再生成下一轮**；半决赛结束后：
  - `bronzeMode = PLAYOFF`：生成**三四名决赛**；
  - `bronzeMode = TIED`：两名半决赛负者**并列季军**，不额外生成比赛。
- 比赛沿用现有流程：**提交 → 对手确认 → 生效**，赛事生成的比赛初始为「待确认」。

### 5.3 名次推导

与 P1 §2.4 既有口径保持一致：淘汰于第 `r` 轮者名次为 `2^(R−r−1) + 1`（轮空本身不产生名次事件）。
最终名次齐全后，**仍走现有 `validatePlacements` 校验并写入 `results`**，赛事积分与 P1 完全同源，不新增积分规则。

## 六、重抽（决策 7）

- **仅管理员**、且**仅在开赛前**（报名中）可重抽。
- 重抽会**作废**该赛事此前生成的、**尚未确认**的比赛，然后按新随机值重新生成首轮。
- 每次抽签累加 `drawCount`，保留历史参数与操作人，便于追溯。

## 九、推导细节（已确认）

以下为把七项决策落到可执行规则时推导出的细节，**需求方已全部确认**：

1. **抽签窗口**：赛事处于「报名中」状态；点过「开始赛事」后不可抽签 / 重抽。✅
2. **参赛者**：未取消的报名者，**不论是否签到，一视同仁**。✅
3. **实际种子数**：取 `min(选定种子数, 参赛人数)`；若参赛人数 ≤ 种子数，则人人按来源顺序排位、不再随机。✅
4. **手工指定**：管理员**逐个指定序号**（1 号、2 号…），系统不代为排序。✅（按需求方修正）
5. **重抽前置**：只要该赛事**已有比赛被确认（已计 elo）**，就**禁止重抽**；仅「已生成但全部未确认」时允许重抽。✅
6. **名次收官**：全部比赛确认、名次齐全后，由管理员在名次录入页复核并点「结束赛事」写入名次（沿用 `finishEvent`），**不自动结束**。✅
7. **抽签是可选动作**：创建时选了种子来源，管理员也可以**不抽签**，直接走现有「手动录名次」流程。✅

- **写接口**：`drawEvent(id, actor, { seedValue, manualOrder })`，mock 与云端锁步，

- **界面**：创建赛事表单（`pages/event-edit`）增加种子来源 / 数量；

  「比赛」页（`pages/match`）与录入页（`pages/match-entry`）支持赛事比赛录分。

### 12.2 实现中新增的判定：先录分再确认

抽签排出的比赛没有比分，若此时被确认，回放会读到空胜方并崩溃。
因此新增 `needsScore(match)`（`services/match-record.js`），并在云端与 mock 的
`confirmMatch` 各加一道**胜方守卫**：没比分时拒绝确认，界面只给「录分」入口。

### 12.3 已知缺口

1. **`manual` 模式的界面缺失**：数据层已支持 `manualOrder`（`resolveSeeds` 会校验并按序取种），
   但界面**没有逐个指定种子的入口**；`pages/event-detail` 的 `onDraw` 只传 `seedValue`。
   因此若创建赛事时选了「手工指定」，直接点「抽签」会以「请指定 N 位种子」失败。
   补一个按序指定种子的对话框即可闭合（数据层与测试已就绪）。
2. 第二节的「人数下限」与「抽签后冻结报名」均已实现并测试；
   未做的是抽签结果的**导出 / 打印**（本期未提出需求）。
