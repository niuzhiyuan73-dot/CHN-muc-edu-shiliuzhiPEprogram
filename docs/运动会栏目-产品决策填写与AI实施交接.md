版本：待产品确认版 v1。日期：2026-10-17。

项目目录：`C:\Users\17789\Desktop\石榴籽程序`。

**用途：用户先填写第 3、4 节，再将完整文件交给下一位 AI 实施。本文不是已实现功能说明。本文档新增不改变现有业务代码。**

## 1. 下一位 AI 必须先读

### 1.1 工作目标

新增与各协会入口并列的「运动会」学校级栏目，完成运动会创建、项目选择、学院报名、限额、排程、多裁判录分、正式名次、学院积分总榜及个人荣誉的完整闭环。

不得只做页面原型、只做 mock 或只把运动会加入协会常量后宣告完成。必须接通真实仓储、服务端权限、页面、模拟数据与测试。

### 1.2 决策读取规则

1. 第 2 节为用户已明确要求，除非用户填写时明确修改，否则必须满足。
2. 第 3、4 节的「用户填写」是产品决定。推荐项仅帮助用户选择，**空白不等于接受推荐**。
3. 实施前列出尚未填写的阻塞项，集中询问；可以先做独立的数据隔离、页面骨架、纯函数和测试基础设施，不得擅自上线未定规则。
4. 同一事项填写冲突时，列出冲突请用户解决，不能自行选择对开发更方便的一项。
5. 不需要让用户决定文件名、主键编码、事务封装等一般技术细节；实施者负责合理设计。
6. 本文不授权清空数据库、自动部署、发消息给其他人或修改不相关的 Elo 产品规则。
7. 必须重新读当前代码与适用的 AGENTS.md；之前的 Elo 改造可能已在其他任务中完成，不得按旧聊天假设代码仍是旧状态。

## 3. 产品决策填写区

### 3.0 填写方式

- 在最后一列填写选项和补充要求；可以写「采用推荐」。
- 不需要的功能明确写「本期不做」，不要留白让实施者猜测。
- 标为 ★ 的条目会影响主流程、权限、计分或数据结构，是开工前必须明确的关键项。
- 所有数值题均为产品参数，下面的例子不是已经批准的默认值。
- 第 4 节是每个项目的实际规则表，必须一起填写；第 3 节可以先规定统一默认，再在第 4 节覆盖个别项目。
- 如果某项由每届管理员配置，请写「每届配置」，同时填写允许范围和默认值；这是一项明确决定，而不是把规则留空。

```text
          ├─ 基本信息、状态与报名时间
          ├─ 项目清单及剩余名额
          ├─ 赛程：日期、场地、轮次、裁判
          ├─ 学院总分榜 → 学院各项目得分明细
          ├─ 项目详情 → 分组、名单、成绩、名次
          └─ 按角色显示动作
              ├─ 学生：我的参赛意向／入选情况（D10 开启时）
              ├─ 学院负责人：本院申请池／各项目正式名单／提交
              ├─ 裁判：我的任务／检录（若启用）／录分
              └─ 校管理员：配置／赛程／审核／发布／更正
```

详情的分区可以是区块、二级页面或锚点；不要新增多个栏目一级标签违背 R02。对“历史运动会里面加学院总得分”的实现至少包含详情总榜，列表可以显示前三学院摘要而非塞入完整表格。

### 5.2 发起与发布

草稿基本资料 → 必选项目 → 设置组别、限额、计分规则 → 设置报名窗口 → 发布报名 → 负责人提交 → 关闭报名 → 排程与裁判配置 → 发布赛程 → 比赛录分 → 发布结果 → 归档。

报名发布前必须确定会影响报名资格/学院选拔的规则：限额、组别、兼项、学院计分规则等。赛程是否可后补由 D53 决定。已开始报名后修改规则必须有版本和影响检查，不得静默缩减已接受名额或改学院积分规则。

### 5.3 双层报名（D10 采用推荐时）

学生选择本届项目/组别 → 系统验证学校学院身份 → 提交参赛意向 → 本院负责人在候选池中选择 → 组成个人名单或队伍 → 服务端核对资格/兼项/名额 → 负责人正式提交 → 按 D21 直接生效或进入校级审核。

学生意向并非正式 entry，不占正式限额。页面清楚显示「待学院选拔」「已被学院选中」「已正式报名」「未入选」「已退出」，不能申请成功后告诉学生已经正式报名。

学院项目列表应展示「已报名 2/3 人」「未报名」「1/2 队」，零与不足上限均合法。**少报队数合法不代表四人接力队可以只报两名正式队员**，队伍最低人数另行校验。

### 5.4 成绩到积分和荣誉

裁判独立录分 → 收齐规定评分 → 服务端汇总原始成绩 → 按项目规则产生临时名次 → 审核正式发布 → 形成版本化正式结果 → 计算学院名次积分 → 更新本届学院总榜与个人荣誉。

未提交评分不是 0；弃权、犯规、无成绩是单独状态。按 D63 执行平均，不默认去最高最低。计时、距离、次数不能统一按“分数越高越好”。

团体第 1 名为学院计一次该名次应得分；向多名队员发个人荣誉不能让学院积分乘队员数。

## 6. 学院积分与历史一致性

### 6.1 计算模型

每个正式结果包含明确的 collegeId、entryId、rank、成绩与积分规则版本。积分纯函数输入为正式结果和冻结的规则，输出每条参赛记录的学院分数及原因。

```text
某学院本届总分
= 所有已生效正式项目结果中属于本学院的计分贡献之和
+ 用户明确批准的奖励分
- 用户明确批准的扣分
```

只在用户批准时引入奖励分/扣分。每笔必须说明来源，不能出现无来源的总分手工覆盖。

示例仅用于测试设计：若名次分为 9、7、6，且并列第二采用所占名次均分，则两人各得 (7+6)/2=6.5。这不是已批准分表，也不表示并列第二规则已确定。

### 6.2 发布与更正

- 每个项目组别正式结果有不可混淆的发布版本和生效状态。
- 重复点击发布不能重复加学院分或重复生成个人荣誉。
- 更正从版本 v1 切换为 v2，积分贡献和荣誉采用替换生效版本，不叠加两个版本。
- 可以在规模较小时从已发布结果聚合总分；规模需要时做可重建快照，但正式结果仍是事实来源。
- 若分批生成结果/积分/荣誉，使用版本构建＋完成标记＋原子切换可见版本，不能半批就显示正式总榜。
- 个人页、项目结果和学院总榜必须读取同一已生效发布状态；异步构建未完成时显示处理中，不冒充最终结果。
- 更正导致下游晋级变化时必须先检查后续轮次状态；不能只重排预赛名次却让已举行决赛参赛者静默改变。
- 归档保存当届学院/项目名称与参赛归属快照；学院后来改名、合并或学生转院不改变当时事实。

## 7. 权限与身份：实现中最容易出错的地方

### 7.1 角色边界

| 能力 | 学生 | 学院负责人 | 被指派裁判 | 校管理员 | 平台管理员 |
| --- | --- | --- | --- | --- | --- |
| 看公开资料 | 按 D02/D03 | 同左 | 同左 | 本校管理可见 | 跨校管理可见 |
| 提交本人意向 | 按 D10 | 作为学生时可以 | 作为学生时可以 | 不隐含参赛资格 | 不隐含参赛资格 |
| 提交学院正式名单 | 否 | 仅授权学院 | 否 | 默认否，D13 可明示例外 | 默认否，D13 可明示例外 |
| 发起和配置运动会 | 否 | 否 | 否 | 仅本校 | 可跨校 |
| 提交裁判成绩 | 否 | 仅另获指派时 | 仅指派场次 | 需指派或 D70 代录授权 | 同左 |
| 发布/更正结果 | 否 | 否 | 按 D84 | 按决策 | 按决策 |

同一账号可以同时有多个职责，但一次操作必须匹配该操作的资格。不因是高级管理员就默认覆盖 R11 的“只有学院负责人提交”要求。

### 7.2 当前代码的适配风险

现有 `miniprogram/services/school-permission.js` 包含 schoolRole、association membership、collegeId 等角色。其通用 `manageCollege` 判断可能允许协会负责人和校管理员，不适合直接作为本模块正式报名权限。

现有 `schoolReadable`/`canSchoolAction` 还依赖 schoolAssociation，运动会应设计独立学校级 context，不能强行挂到匹克球协会让停用协会影响运动会。

学校级学院负责人权限模型需要按 D11 决定；若新增授权关系，必须包括授予/撤销入口、学校/学院范围、有效状态和审计。

服务端不能信任客户端传入的 schoolId、collegeId、裁判 ID 或“我是负责人”标志。写入事务内重查当前有效身份、权限及记录范围。

## 9. 接口与事务方案

### 9.1 接口分组（示意，不要求逐字采用名称）

- 读取：listSportsMeets、getSportsMeet、searchSportsEventTemplates、listMeetEvents、getMeetSchedule、getCollegeStandings、getPublishedResults。
- 管理：createSportsMeet、updateMeetDraft、configureMeetEvent、publishMeetRegistration、closeRegistration、publishSchedule、archiveMeet。
- 学生：submitMeetInterest、withdrawMeetInterest、getMyMeetParticipation（D10 采用双层时）。
- 学院：getCollegeApplicantPool、saveCollegeEntryDraft、submitCollegeEntries、withdrawCollegeEntry、replaceCollegeParticipant；按决策开放。
- 裁判：getMyMeetJudgeTasks、saveJudgeScoreDraft、submitJudgeScore。
- 结果：previewMeetResults、publishMeetResults、requestResultCorrection、publishResultCorrection。
- 荣誉：统一用户荣誉读取，将协会和运动会正式结果映射成统一 DTO。

每个写接口具备鉴权、范围校验、幂等语义、revision 冲突处理、可理解的失败原因，云端与 mock 的 action 白名单一致。

### 9.2 正式报名事务

1. 重读本人及学院负责人授权；从服务端确认学院归属。
2. 检查运动会及项目状态、报名截止时间、规则版本。
3. 验证名单真实存在、属于本校本院且符合组别资格；不能只检查操作人。
4. 检查重复、兼项、团队人数/替补/跨队冲突。
5. 点读学院及全校额度计数、个人占用声明、旧报名版本。
6. 计算净增减占用，原子写新名单、计数、声明和审计。
7. 返回成功的确切项目及状态；若整院批量操作，明确按项目成功与失败，不能部分失败后仍显示全部提交成功。

同一学院两位负责人并发提交最后一个名额不能超限；先查数量后普通写入是不安全的。撤回、驳回、更换名单应原子释放/替换占用，重复请求不能释放两次。

当前云端事务仓储不允许事务内任意集合查询，需通过确定性主键点读，或建立可验证版本的预读方案。不要把整个运动会几千人写在一个事务里。

### 9.3 裁判提交与正式发布

- 服务端重读裁判指派和评分开放状态，确保裁判只能提交自己的评分。
- 唯一评分键防重复，revision 防止旧草稿覆盖新提交。
- 汇总读取固定指派版本下的有效评分；替换裁判必须明确哪些分数保留。
- 用十进制定点或明确的精度策略计算，不直接依赖浮点偶然误差判断同分。
- 并发评分与发布通过状态/版本保护，保证冻结后的快照完整一致。
- 发布任务幂等；大规模结果采用分批构建和生效切换，失败可恢复。
- 事务回调内不调用通知、外部服务等不可回滚副作用。

## 10. 前端关键体验与错误处理

- 学生清楚区分申请、入选、正式报名；能看到代表学院和项目组别。
- 负责人一屏看每个项目的「已报/可报」和候选学生；未选项目允许为空。
- 提交前检查面板逐项说明超额、资格不符、重复报名、缺队员等原因。
- 已满额或截止时保留草稿但明确不能提交，不展示虚假成功。
- 管理员看各院提交进度，但不能用进度条强迫各院报满所有项目。
- 评分页明确单位、有效范围、剩余裁判数；断网重试不能重复计分。
- 临时成绩与正式结果显著区分；总榜显示已发布项目数量。
- 学院总分可点开到每个项目名次及计分理由。
- 「我的」每条荣誉注明赛事、项目组别、成绩、名次、代表学校学院；团体荣誉标记团体。
- 正式结果更正后显示最新版本及必要更正说明，避免个人页旧奖牌与总榜新成绩并存。
- 普通用户不得从接口响应拿到不需要的学号、电话或未公开原始评分。

各阶段有完整可验证的功能，不以静态页面占位冒充完成。若用户要求所有已选能力一期上线，不可自行把胜负赛或预决赛等关键能力延后。

## 12. 验收清单

### 12.1 权限与身份

- 普通学生、协会负责人无法发起运动会；本校校管理员可发起，外校校管理员不可写。
- 普通学生即使伪造 action/collegeId 也不能提交正式报名。
- 学院负责人只能替自己有效授权的学院报名，撤权立即生效。
- 管理员代报仅在 D13 明确允许时可用，且可审计。
- 裁判不能读取/修改其他裁判私有草稿，也不能录未指派场次。

### 12.2 报名与配额

- 至少选一个项目；未报名项目合法，未报满合法。
- 个人名额和队伍名额分别计算；队伍人数不足按 D39 正确处理。
- 学生申请不自动变正式报名，不错误占用正式配额。
- 同学院、全校、个人兼项限额并发不超卖；重复提交不重复占用。
- 学院不能提交不属于该院的成员，不能通过客户端改学院绕过。
- 截止边界使用服务端时间；撤回、驳回、换人释放占用正确。
- 多负责人旧草稿不能覆盖他人新名单；返回清晰冲突。
- 团体正式队员、替补、跨队重复与混合组资格准确校验。

### 12.3 评分与名次

- 三裁判 88/90/92 的纯平均为 90；只有两人提交时按 D62 处理，不能默认第三人为 0。
- 替换裁判不混用旧新名单分母；重复评分、重试只保留有效版本。
- 时间越少排名越前，距离/次数/评分按规则排序；单位精度一致。
- 多次试投先按每次尝试汇总，再取最好；无效尝试不当作有效 0 分。
- 并列、参赛人数不足、犯规、弃权、全部无成绩均有确定输出。
- 预赛不发最终荣誉；晋级边界同分和后续轮次依赖正确处理。

### 12.4 学院积分与荣誉

- 每个项目名次严格按用户填表计分，团体贡献只计一次。
- 同院多人、多队、并列积分、倍数与参与分按确认规则处理。
- 只有正式发布结果计入总榜，未结算项目不被当成 0 分最终结果。
- 所有学院贡献之和与全届总分一致，明细可追溯。
- 同分学院总榜排序确定；零分学院按决策展示。
