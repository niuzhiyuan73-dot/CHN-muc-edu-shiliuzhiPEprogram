# 篮球、足球、排球协会：调研与实施规划

日期：2026-10-19。状态：方案草案，尚未实施。文中的“建议”均不是已经确认的产品决策。

> **2026-10-20 足球进度更新**：用户已确定先做十一人制、允许自由组队；时长、报名人数、换人规则及淘汰赛决胜方式在发布赛事时选择，首版采用赛后录分。足球当前范围、调研默认值及 F0—F3 分期以 [足球协会-需求与实施规划](足球协会-需求与实施规划.md) 为准；F0—F3 已完成，全量 2799 项用例通过，见 [F2/F3 验收记录](足球协会-F2F3赛后录分与成绩-验收记录.md)。

## 1. 目标和范围

新增篮球、足球、排球三个协会，沿用学校、协会成员、通知、训练及权限体系。新协会工作台建议为“协会空间 / 组队 / 赛事”。移除的是新协会的独立 Elo 排行榜和普通比赛入口；赛事内部仍有赛程、对阵、单场比赛及必要的赛事积分表。原有球拍运动协会保持现状。

组队不是一次填写多人姓名：需要长期球队、队员加入与退出、队长管理、赛事报名名单、单场出场名单，以及历史成绩归属。赛事按球队报名、编排、录分、排名。个人保存各运动的累计技术统计，并能追溯到单场记录。

暂不默认增加个人得分排行榜、自由约战、跨校球队或职业级战术分析。用户说的“比赛去掉”先解释为取消独立普通比赛栏目，而不是取消赛事中的比赛。

## 2. 调研结论：共用球队流程，分别设计三项统计

### 2.1 篮球

FIBA 的统计体系区分投篮、罚球、篮板、助攻、抢断、失误、盖帽、犯规等。助攻需要判断传球与得分的直接关系，不能由比分自动推导。[FIBA 统计员手册 2024](https://assets.fiba.basketball/image/upload/documents-corporate-fiba-statisticians-manual-2024.pdf)

建议基础版记录：得分、助攻、个人犯规。实用扩展记录：进攻/防守篮板、抢断、盖帽、失误、两分/三分/罚球命中及出手。只有记录了出手数，才能展示命中率；没有记录不能显示为 0%。

五人制建议得分由命中记录计算：2 × 两分命中 + 3 × 三分命中 + 罚球命中。三人制具有不同计分规则，必须使用独立规则模板，不能只把人数从 5 改成 3。

个人犯规、球队犯规、技术犯规、违例需要分开建模；不能把走步等违例都算成个人犯规。校园赛的节数、节长、犯规限制、加时等应保存为赛事规则快照。

### 2.2 足球

比赛规则负责判定比分、比赛结果与纪律；助攻还需要独立统计口径。Opta 将常规助攻与幻想足球助攻分开，乌龙球、直接任意球进球等情形不能机械附加常规助攻。[IFAB 比赛结果规则](https://www.theifab.com/laws/latest/determining-the-outcome-of-a-match/)、[Opta 事件定义](https://optaplayerstats.statsperform.com/en_GB/opta-event-definitions)

建议基础版记录：进球、助攻、犯规、黄牌、第二张黄牌罚下、直接红牌。可选记录：射门、射正、扑救、上场时间。一次犯规不必有牌，一张牌也不一定对应一次犯规，不要自动绑定计数。

乌龙球增加受益球队比分，但不能给该队某名球员增加个人进球。点球大战单独保存、单独显示，建议不计入常规个人进球累计。例：1:1，点球 4:3；不能展示为 5:4。

建议先支持用户确定的一种人数制。五人制室内足球、七人制校园足球、十一人制不能共用全部人数、犯规及换人规则。联赛允许平局与淘汰赛决胜规则也要分别配置。

### 2.3 排球

排球采用每球得分，比分包括局比分与每局小分。官方记录还涉及阵容、轮转、换人及自由人管理，不能用一个总比分输入框概括。[FIVB 基本规则](https://www.fivb.com/volleyball/the-game/basic-rules/)、[FIVB 2025—2028 官方规则](https://www.fivb.com/volleyball/the-game/official-volleyball-rules/)、[FIVB 官方记录表入口](https://www.fivb.com/inside-fivb/refereeing/reports-documents/)

建议基础统计包括发球直接得分、进攻得分、拦网得分、失误；助攻作为明确口径后的可选统计，不能把每次二传都视作助攻。球队还会因对方失误或处罚得分，因此球队小分不等于本队个人得分之和。

多人拦网必须明确统计口径。建议第一版每个得分回合只记一次球队得分，个人得分归属可指定一人或记为待归属；参与拦网的人可另记参与次数。此为待确认的校园简化规则，不宣称等同所有专业技术统计规则。若要正式拦网助攻及分摊统计，应另设统计政策，不能把每名参与者都加一分再汇总为球队得分。

排球“犯规”建议拆成失误类型与纪律处罚，不照搬篮球个人犯规累计或足球红黄牌处理。

### 2.4 共通设计

正式比分、技术统计、纪律处罚各有独立字段和校验。每场保存规则版本与统计口径版本。技术统计需要区分“确认是零”“尚未记录”“本赛事不统计”，不能统一默认 0。

建议提供基础与详细两种统计模板，由赛事创建时选择，开赛后不得随意改变导致历史数据不可比。个人页面显示统计覆盖范围，例如“已统计助攻 6 场 / 已出场 8 场”，场均分母使用相应已完整统计的出场场次。

后端必须验证该协会支持团队赛事，且新比赛绝不进入旧 submitMatch/Elo 更新路径。隐藏按钮不足以隔离功能。球队数据不得借用运动会报名或运动会计分集合。

## 4. 页面与操作流程

### 4.1 组队

球队列表支持名称搜索、我的球队、招募中筛选。球队详情包含队徽、名称、简介、队长、队员、招募状态、赛程及历史成绩。

建议学生申请建队，协会管理员审核；队长管理入队申请。邀请加入须本人接受，不能任意把别人加入球队。队长权限只作用于自己的球队，不因此获得协会管理权限。球队解散采用归档，历史赛事仍可查询。

分清三份名单：长期球队成员、某赛事报名名单、某场比赛名单。赛事报名锁定后形成快照，之后退队、改名、改号码不会重写历史。报名人数上下限、同队号码冲突、同一赛事重复代表不同队等由后端校验。

### 4.2 团队赛事

建议流程：管理员建赛事 → 设置运动规则、人数与报名要求 → 队长报名并提交队员 → 审核 → 锁定名单 → 编排 → 分配时间/场地/裁判/记录员 → 比赛录分 → 审核发布 → 更新赛事及个人数据。

首版支持循环赛、单淘汰、小组循环加淘汰。编排输入改为队伍，不是假装每队是一名个人选手。复用已有抽签算法前，检查人数、轮空、平局与晋级规则假设。

每场保存裁判列表与主记录员；裁判和统计员是不同职责。可以有多名裁判，但客观比赛事件不能采用运动会裁判成绩取平均。首版只允许一个主记录员操作正式比分；其他授权人员补充统计或审核。

赛程必须检查球队、场地及裁判的时间冲突。赛事创建时就检查报名上限、分组人数和晋级名额的可实现性。球队不足、退赛、轮空、比赛中断、弃权要有明确处理入口；弃权判定分不虚构为球员个人得分。

### 4.3 录分界面

共同布局：顶部固定队名/比分/阶段/保存状态；中间按号码展示队员；底部固定主要操作；附近显示最近记录与纠错入口。横屏可增强，但竖屏必须可用。

| 运动 | 主要操作 | 补充与校验 |
|---|---|---|
| 篮球 | 选择球员 → 罚球/两分/三分命中；犯规；助攻等 | 得分后可选助攻人或稍后补记；不能本人助攻本人；详细模式记录投失和篮板；按节展示 |
| 足球 | 进球 → 得分者 → 可选助攻；乌龙；犯规/牌 | 正常点球进球与点球大战区分；第二黄与直接红区分；显示半场和比赛分钟 |
| 排球 | A/B 得一分 → 原因 → 可选球员 | 先保证得分不被长表单阻塞；显示局数与本局比分；局结束校验目标分及领先差 |

提供赛后技术统计表格补录入口；采用实时事件的指标从事件汇总，不能又在汇总表重复加一次。补录必须有明确模式和版本。

现场计时首版可作为辅助，不宣称替代正式计时设备。若启用自动计时，使用服务端锚点和暂停记录，不依赖小程序在后台持续运行。

纠错保存审计记录，并同步修正关联助攻、球员和球队分数。发布后的修改必须填写原因并重新发布；这与旧 Elo 全局回放无关，只更正本场及受影响的赛事统计。

### 4.4 结果与我的页面

赛事详情提供赛程、单场比分/局分、队员技术统计、赛事积分或晋级图。建议设“审核并发布本场”和“批量发布已审核场次”，批量操作列出成功、失败及未就绪项，不一键误发全部草稿。

个人页按运动显示累计与赛季数据，点击可查看单场来源；提供我的球队、参赛经历、团队名次。区分报名与实际出场，未上场替补不能自动计为出场。荣誉覆盖整份名单还是实际出场人员，需确认。

公开页面只读取已发布版本。实时比分如果开放，要标注“进行中/非最终结果”。管理员能看到草稿不等于普通成员也能看见；必须以普通成员账号验收。

## 5. 数据结构建议

以下是逻辑实体，不要求机械地每项对应一个集合；实施时根据查询与事务边界确定。

| 实体 | 关键内容 |
|---|---|
| team | schoolId、association、sport、名称、队长、状态 |
| teamMember | teamId、userId、角色、加入/退出时间、状态 |
| teamEvent | 赛季、规则快照、统计政策、报名范围、赛制、状态 |
| eventEntry / eventRoster | eventId、teamId、审核状态、锁定名单、姓名与号码快照 |
| teamMatch / matchRoster | 双方队伍、阶段、场地、时间、裁判、记录员、实际出场、比分、revision |
| matchAction | requestId、操作序号、操作者、事件类型、球员、阶段、负载、纠正关系 |
| publishedMatchStats | matchId、发布版本、个人及球队统计、完整性状态 |
| playerSeasonStats | userId、运动、赛季、汇总与来源版本；作为可重建派生数据 |

关键唯一约束：一次请求只生效一次；同一赛事同一球员的参赛资格满足单队政策；同一球队号码在相应名单内唯一；一场比赛每个发布版本只贡献一次累计。

个人总分不应只在用户文档上不断加一。保留每场已发布统计作为依据，累计值可缓存。重新发布本场时替换该场贡献，不能再次累加。不需要为此重放其他运动的 Elo 或所有历史比赛。

规则、比分操作、已发布数据分别留版本。赛事名次或晋级受更正影响时，先列出受影响后续对阵；已进行的下一轮不得静默换队。

## 6. 上云及 UI 风险防范

1. **作用域与权限**：每次写入重新验证学校、协会、赛事、球队、人员和职责关系，不能信任前端传来的队长或裁判身份。客户端切换协会后，旧异步响应不得覆盖新协会界面。
2. **多人写入**：主记录员锁或租约配合服务端 revision；管理接管需明确提示。只禁用按钮无法防止两台手机同时加分。
3. **重试与弱网**：requestId 在重试时保持不变；页面区分待发送、已确认、失败。可保存本地待提交草稿，但首版不承诺离线多人录分合并；有未确认操作时禁止终场发布。
4. **发布一致性**：比分、个人统计、赛事排名不能各写一半后宣布成功。小规模使用事务；超出事务边界时用可重试发布任务、准备状态和版本指针，全部准备就绪后公开。失败要可恢复。
5. **查询规模**：查询必须分页和限定作用域；提前建立索引。不能读取默认第一页就当作全部队员或全部历史比赛。不要把全部事件与全部赛季统计塞进一个无限增长文档。
6. **记录可见**：选择裁判后立即显示已选姓名和角色；保存后重新读取仍应一致。成员换名或暂不可查时保留快照/占位，不让已选项消失。
7. **错误可见**：字段旁错误 + 固定操作区摘要；必要时滚动至错误位置。长页底部提交不能只在页首提示失败。按钮区分保存中、成功和失败。
8. **状态恢复**：切页、重新进入、断网重连后恢复服务端权威比分；重复打开不能重复启动时钟或提交操作。服务器返回冲突时刷新并明确说明。
9. **部署完整性**：同步云端共享代码、动作注册、集合权限和索引；用真实云环境验证，不以 mock 测试通过替代部署验收。

## 7. 实施顺序和验收门槛

| 阶段 | 交付 | 完成条件 |
|---|---|---|
| A 产品规则 | 决策表、规则模板、统计字典、权限表 | 至少确定各运动首版人数制、统计范围、球队及发布权限 |
| B 协会与球队 | 动态工作台、建队、入队、队长管理 | 三协会隔离正确，旧协会回归通过，非法旧比赛入口被后端阻止 |
| C 团队赛事 | 报名名单、审核、赛程、裁判与场地 | 人员/队伍/赛程约束完整，名单锁定和快照有效 |
| D 录分闭环 | 先篮球贯通，再足球和排球规则模块 | 三者均能录分、纠错、重进恢复、审查发布，不共享错误的计分假设 |
| E 展示与汇总 | 已发布赛果、个人数据、荣誉 | 普通成员可见；重复发布不翻倍；更正后总计与明细一致 |
| F 真实云验收 | 多账号、多手机、弱网、冲突、索引与部署验证 | 核心流程和下列异常场景通过后再对用户开放 |

必须覆盖的业务用例：

- 篮球三分附助攻，更正为两分后比分和个人统计同步；重复点击、请求超时重试不重复加分。
- 足球乌龙、普通点球、点球大战分别计数；第二黄不重复算成直接红；平局进入正确阶段。
- 排球对方失误得分不强行归本队球员；多人拦网不重复加球队分；超过目标分但领先不足时不提前结束。
- 同一球员同时通过两个队报名的并发请求只能符合政策的一份成功；名单锁定后无法绕过页面直接改人。
- 队伍退出、轮空、奇数队、组内未完赛、同分排名、下一轮已开赛后的结果更正均有明确结果。
- 两个记录员同时操作、后台切换、跨协会快速切换、裁判撤权、断网再连均不污染比分。
- 发布时中断后可恢复；个人累计与公开单场一致；无技术统计的比赛不以全零拉低场均。
- 已报名未出场、转队、球队归档、成员改名不会错误重写历史数据或荣誉。

测试侧重点为规则单元测试、服务端权限/并发/发布集成测试，以及真实手机的主要 UI 流程，不必为每个纯展示字段单独编写形式化测试。

## 9. 给实施者的约束

先把已确认决策转成字段、状态转换和验收例子，再开发。未确定的关键规则不能擅自隐藏为代码常量。先完成一种运动的完整闭环以验证共享模型，再扩展另外两种；最终交付范围仍包含三项运动。

不要复制现有球拍比赛后只改文案；不要将训练小组、学院大场、运动会项目或 Elo 累计当作球队赛事模型；不要把专业比赛规则与可选校园统计口径混为一谈。

上线门槛包括：真实云部署、普通成员可见性、权限隔离、并发幂等、发布一致性和手机录分可用性。仅管理员页面看起来正常，不能视为完成。
