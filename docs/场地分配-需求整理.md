# 场地分配（需求整理）

> 2026-09-18 需求整理。承接个人赛「赛事 → 签表 → 比赛」与学院赛「赛事 → 大场 → 小项」两条线。
>
> **状态：已拍板，已实施完成。** Q1–Q12 的结论见 §七开头的「拍板结论」表，施工与验证见 `docs/场地分配-实施记录.md`。
> 涉及体系的现状全部来自代码实测，引用格式为 `文件:行号`。

## 一、需求原文

> 现在开始准备增加分配场地功能，要求每个比赛中同一轮次的场地不能重复，在创建比赛的时候管理员必选本次比赛可以使用的场地总数，不需要给每场比赛排具体时间，不考虑跨赛事排场地，场地只有编号区别，管理员只需要输入一个数字，比如 3 就代表本次比赛可以使用 123 这三个场地。

## 二、需求拆解

| 编号 | 需求 | 类型 | 备注 |
|---|---|---|---|
| 1 | 赛事级新增「可用场地总数」，创建时**必填**，输入一个整数 | 新增字段 + 表单 + 校验 | 3 ⇒ 1/2/3 号场 |
| 2 | 每场比赛分到一个场号 | 新增字段 + 分配算法 | 落地载体见 §4.3 |
| 3 | **同一轮次内场地不重复** | 核心不变量 | 「同一轮次」如何定义见 §4.2 |
| 4 | 不给每场比赛排具体时间 | 边界（不做） | 但场地不足时会引出「分批」，见 Q1 |
| 5 | 不考虑跨赛事排场地 | 边界（不做） | 场地池是赛事私有的 |
| 6 | 场地只有编号区别 | 边界（不做） | 不做名称、不做规格、不做启用状态 |

需求 1 是一件事（赛事级参数），2–3 是另一件事（分配算法）。4–6 是三条「不做」，它们把问题规模压得很小——**这是一个纯函数能解决的问题，不需要新的集合，也不需要排程器**。

## 三、现状（为什么现在还没有场地）

### 3.1 赛事级只有一个自由文本 `location`

赛事记录由 `buildEventRecord` 组装（`services/event.js:618-670`），其中与场地沾边的只有：

```js
location: draft.location,          // services/event.js:654，≤40 字的自由文本
```

表单占位符写的是「例如：体育馆 1 号场」（`pages/event-edit/event-edit.wxml:187`）。它表达的是**整场比赛在哪座馆**，不是「第几号场」，也无法拆成可比较的编号。

`quota` 字段是本次要照抄的样板——一个「表单必填或选填的数字 → 收敛 → 校验 → 落库 → 展示」的完整链路：

| 环节 | 位置 | 行为 |
|---|---|---|
| 表单初值 | `pages/event-edit/event-edit.js:186` | `''` |
| 输入 | `pages/event-edit/event-edit.wxml:193-203` | `type="number"`，`onInputQuota` 原样存字符串 |
| 类型收敛 | `services/event.js:445-449,484` | `''`→`0`；小数截断；非数字→`NaN` |
| 校验 | `services/event.js:592` | `NaN` 或 `<0` →「名额必须是不小于 0 的整数」 |
| 落库 | `services/event.js:656` | `quota: draft.quota` |
| 展示 | `services/event.js:921` | `quotaText`（如「12/16 人」） |

### 3.2 比赛记录上的 `location` 是从赛事抄下来的副本

抽签生成首轮比赛时（`services/draw.js:844-879`）：

```js
location: event.location || '',     // services/draw.js:866  ← 整场赛事共用一个串
matchTime: event.startTime,         // services/draw.js:867  ← 整轮共用一个时刻
```

学院赛小场同理（`services/college-tie.js:293`）。也就是说：**今天每一场比赛的 `location` 都一模一样**，且全仓库没有任何写接口能改单场比赛的 location（写动作名单见 `src/actions.js:46-85`）。

结论：字段载体已经有了，缺的是「一个可比较的场号」与「一个分配规则」。

### 3.3 「轮次」不是一个字段

比赛记录的唯一编号是 `eventMatchKey(eventId, round, stage, slot, group)`（`services/draw.js:621-627`）：

```
无小组：x_{eventId}_r{round}_{stage}_{slot}
有小组：x_{eventId}_g{group}_r{round}_{stage}_{slot}
```

`stage` 取值 `main / bronze / group / wb / lb / gf / placement`（`utils/constants.js:295-303`）。各赛制下「同一轮」的构成：

| 赛制 | 轮次构成 | 依据 |
|---|---|---|
| 单败淘汰 | `stage='main'` + `round` | `services/draw.js:680-750` |
| 季军赛 / 排位赛 | `stage='bronze'` / `'placement'`，`round` 与决赛同轮 | `services/format-plan.js` 的 `planNextRound` |
| 循环赛 | `stage='group'` + `round`（单组） | `services/format-plan.js:506-534` |
| 小组赛阶段 | `stage='group'` + `group` + `round` | `services/format-plan.js:516` |
| 双败 | `stage`（`wb`/`lb`/`gf`）**各自从 round=1 重新计数** | `services/format-plan.js:378,401,415,431` |

**这是本功能第一个必须定义清楚的地方**：双败的胜者组第 1 轮与败者组第 1 轮，`round` 都是 1，但它们不是同一批同时进行的比赛；而小组赛里 A 组第 1 轮与 B 组第 1 轮，`group` 不同、`round` 相同，却通常同时开打。**不能简单按 `round` 分组，也不能简单按 `stage+round` 分组。** 建议口径见 §4.2。

### 3.4 现有排序（可复用）

赛事详情页的签表行已经有一套稳定的排序（`services/events-view.js:692-710`）：

```js
// 多阶段赛制（分组 / 双败）：阶段优先
stageOrder(a.stage) - stageOrder(b.stage)
  || Number(a.group || 0) - Number(b.group || 0)
  || a.round - b.round
  || a.slot - b.slot
// 纯单败：轮次优先
a.round - b.round || stageOrder(a.stage) - stageOrder(b.stage) || a.slot - b.slot
```

`stageOrder` 定义在 `services/events-view.js:510-518`：`group=0, wb=1, lb=2, bronze=2, placement=3, gf=3`，`main` 默认 1。

分配算法要复用这套次序，保证「界面上看到的顺序」与「场号分配的序号」一致。

### 3.5 学院赛是「大场套小场」

```js
tie  : _id = t_{eventId}_{round}_{stage}_{slot}      // services/college-draw.js:229-231
leg  : _id = l_{eventId}_{tieId}_{legNo}             // services/college-tie.js:214-216
```

- 一个大场含 `event.legPlan.length` 个小项（1–20 项，`services/college-event.js:51-52`），`startTie` 时一次性把全部小场落成 `matches` 记录（`src/core/college-handlers.js:453-486`）。
- 大场**没有** location 字段；小场有，且值取自 `event.location`（`services/college-tie.js:293`）。
- 有一个成熟的先例可照抄：**裁判写在大场、再下推到每个小场**（`src/core/college-handlers.js:663-679`，生成小场时由 `buildLegMatchDrafts` 从 `tie.referee` 带入，`services/college-tie.js:302-305`）。

所以学院赛的场地分配最自然的做法是「大场层分配 → 下推小场」，与裁判完全同构。**但「一个大场的多个小项是同时在不同场地打，还是依次在同一块场地打」直接决定这个选择对错**——见 Q4 / Q5。

### 3.6 当前完全没有场地概念

全仓 grep：`venue` 零命中；`court` 只出现在实时计分台的 CSS 类名与界面注释里（`pages/live-score/live-score.wxss:136`）；「场地」二字只出现在 `location` 的中文标签与 `docs/交接说明.md` 的一处描述。**属于全新概念，没有历史包袱，也没有需要兼容的旧数据。**

## 四、方案

### 4.1 数据模型

**赛事新增一个字段：**

```js
courtCount: Number   // 可用场地总数，≥1 的整数。3 表示 1/2/3 号场
```

**比赛新增一个字段：**

```js
courtNo: Number      // 场号，1..courtCount；0 表示未分配（默认）
```

理由：

- **不复用 `location`**。`location` 是「在哪座馆」的自由文本，`courtNo` 是「第几号场」的可比较编号。混在一起会同时毁掉两者：展示上无法拼（「体育馆 1 号场 · 3 号场」），逻辑上无法判重（字符串比较）。
- **不新增集合**。分配结果必须和比赛一起读（列表、签表、录分页都要显示），存在 `matches` 上是零额外查询成本的；单独开一张 `courts` 表会带来 N+1 拼装与两处不一致的风险。
- **编号从 1 起**，与「第 N 号场」的人话一致，也避开了 `0` 与「未分配」的歧义。

### 4.2 「同一轮次」的口径（Q1 之外最关键的一处）

定义一个**场地池键** `poolKey`，同一个池内的比赛共用同一批场地：

| stage | poolKey | 理由 |
|---|---|---|
| `main` / `bronze` / `placement` / `gf` | `ko\|{round}` | 同属一棵淘汰树，同轮次的决赛、季军赛、排位赛通常同时开打，必须共享场地池才不会撞号 |
| `wb` / `lb` | `{stage}\|{round}` | 双败的两个区各自从 round=1 计数，混在一起会把胜者组第 1 轮与败者组第 1 轮当成同一批 |
| `group` | `group\|{round}` | 各组同轮次通常同时开打，跨组合并成一个池 |

池内排序沿用 §3.4 的既有次序：`stageOrder → group → slot → _id`（最后用 `_id` 兜底保证全序，与 `replay.js` 的 `compareForReplay` 同一手法）。

### 4.3 分配算法

```
输入：同一池内的有序比赛列表 matches[]、可用场地数 N
输出：每场比赛的 courtNo

for i, match of matches:
    courtNo = (i % N) + 1        // 1..N 循环
    wave    = floor(i / N) + 1   // 第几批
```

性质：

- **同一批内绝不重复**。这是需求 3 的准确满足。
- **场地够用时（N ≥ 池内场次数）恒有 wave = 1**，即「同一轮次场地完全不重复」的字面要求成立。
- **确定性**：只依赖「有序列表 + N」，与读库顺序无关，重算结果一致——这一点是硬约束，因为下一轮的生成走「只补不覆盖」（`src/core/match-handlers.js:189-191`），分配必须可重入。
- **不依赖时间**：`wave` 只是序号，不是时刻。需求 4 的「不排具体时间」没有被破坏。

> **`wave` 是否落库？** 建议**不落库**，由展示层按「同池 + 同 courtNo 的先后」推出来。这样比赛记录上只多一个 `courtNo`，少一个需要同步维护的状态。若确认要给管理员看「第几批」，再议（Q9）。

### 4.4 计算与落库的时机

分配是**纯函数**，不碰数据源；调用它的地方只有三个，且都在「整轮比赛刚生成完」的那一刻：

| 时机 | 位置 | 说明 |
|---|---|---|
| 抽签生成首轮 | `src/core/event-handlers.js:447-484`（`drawEvent`） | 首轮整批生成，一次算完 |
| 确认 / 弃权后推进下一轮 | `src/core/match-handlers.js:166-198`（`advanceAfterConfirm`） | `planStageMatches` 返回的是「还缺的整轮」，每轮各自算 |
| 学院赛开始大场 / 小项出结果后推进 | `src/core/college-handlers.js:453-486`、`src/core/college-advance.js:38-94` | 按大场分配，下推到小场草稿 |

**不需要额外的 `bumpSeason`**：分配结果是在比赛草稿 insert 之前就写进去的，而这三条通路本来就会失效回放缓存（`match-handlers.js:195`、`match-handlers.js:341-344`）。只要不给场地单独做「事后改派」的写接口，就不会有第二处需要失效的写入。

### 4.5 需要新增的写接口：一个也不要

需求 1 的场地数在**创建时**写入，而项目当前**没有赛事编辑接口**（个人赛写接口只有 8 个，清单见 `src/core/event-handlers.js:487-497`，无 `updateEvent`）。分配是全自动的。所以本功能**不需要新增任何 action**，也就不必改 `actions.js`、`write.js`、`cloud.js`、`mock.js` 的写接口登记处——这是它相对「裁判」「实时比分」两个功能最大的不同。

（代价见 Q6：场地数填错了，今天没有回头路。）

## 六、边界与明确不做的事

- **不做跨赛事**：场地池是赛事私有的，不同赛事各自从 1 号场开始。
- **不做具体时间**：不引入「时段」「开赛时刻」，`wave` 只是序号。
- **不做场地名称**：只有编号，与需求原文一致。
- **不做手动改派**：一期全自动。若将来要做，必须同时处理 `bumpSeason`（改的是 `matches`，读路径走 dataset 缓存）。
- **不做场地占用冲突检测**：跨赛事的全局占用不在范围内。
- **不动 `location`**：原有的「赛事地点」自由文本保持原样，与场号并存展示。

## 七、待确认（Q1–Q12）

### 拍板结论（2026-09-18）

| 编号 | 结论 | 影响 |
|---|---|---|
| Q1 | **A 自动分批** | 算法骨架：`courtNo = (i % N) + 1`，`wave = floor(i/N) + 1` |
| Q2 | 只落 `courtNo`，批次由展示层推出 | 比赛记录只多一个字段 |
| Q3 | `main`/`bronze`/`placement`/`gf` **共池** | `poolKey = ko\|{round}` |
| Q4 | `wb` / `lb` **分开** | `poolKey = {stage}\|{round}` |
| Q5 | `group` **跨组共池** | `poolKey = group\|{round}` |
| Q6 | **A 大场级分配 + 下推小场** | 与 `assignTieReferee` 同构 |
| Q7 | **一个大场只占一块场地**，小项依次同场 | 小场的 `courtNo` 全部 = 大场的 `courtNo` |
| Q8 | 保留「第 N 场」签位号，场号用独立样式渲染（见 §5.3） | 纯展示，不改数据语义 |
| Q9 | **个人赛与学院赛都要** | 两套表单都加 |
| Q10 | **(a) 暂不支持改**，填错重发赛事 | 不新增写接口，无 `bumpSeason` 问题 |
| Q11 | 上限 **20**，下限 **1**，**必填** | 与 `LEG_PLAN_MAX` 同量级 |
| Q12 | 学生端也显示 | 展示层全量加 `courtText` |

> Q7 的直接后果：学院赛的「同轮次场次数」= **大场数**（不是大场数 × 小项数），场地压力与个人赛同量级；`legNo` 的顺序天然就是同一块场地上的台次顺序。

### 7.1 会显著改变实现量的两个

**Q1：场地数少于同轮场次数时怎么办？**

需求 3 的「同一轮次场地不能重复」，在「同轮 8 场、只有 3 块场地」时是**数学上做不到**的。而场地数在创建时就要填，那时参赛人数还没定，冲突是会发生的。

- **A（推荐）自动分批**：同池内按序每 N 场一批，**同一批内绝不重复**。场地够用时自然退化成「同轮完全不重复」。始终可行，不新增任何管理员操作，也不违反「不排具体时间」。
- B 创建时校验「场地数 ≥ 预期场次」：创建时不知道报名人数，无法校验；而抽签时才发现不足的话，今天没有改场地数的接口，会直接卡死。
- C 允许重复（简单取模）：与需求原文直接冲突。

**Q2：分批之后，管理员要不要看到「第几批」？** 还是只要每场比赛挂一个场号即可（推荐：只要场号，批次是推出来的）。

### 7.2 「同一轮次」的定义

**Q3：`main` / `bronze` / `placement` / `gf` 是否共用同一个场地池（§4.2 的建议）？** 例如同轮次的决赛与季军赛是否同时开打——若是，必须共池，否则俩比赛会同时拿到 1 号场。

**Q4：双败的胜者组与败者组是否共用场地池？** 建议分开（两区 `round` 各自从 1 计数）。

**Q5：小组赛里 A 组第 1 轮与 B 组第 1 轮，是否共用场地池？** 建议共用（通常同时开打）。

### 7.3 学院赛

**Q6：学院赛按大场分配还是按小场分配？**

- **A（推荐）大场级分配 + 下推小场**：与裁判完全同构（`college-handlers.js:663-679`），管理员在赛事详情页就能看到每个大场用哪块场地；也符合团体赛「一轮对抗在一张台上依次打完」的惯例。
- B 小场级分配：适用于「一个大场的多个小项同时在不同场地开打」。此时「同轮次」的场次数会变成 `大场数 × legPlan.length`，场地会更紧张。

**Q7：同一大场的多个小项，是同一块场地依次打，还是各自占一块场地？** 这直接决定 Q6。若依次打，则小场之间的 `legNo` 顺序就是台次顺序；若并行，则必须选 B。

**Q8：学院赛详情页现在把「第 N 场」用作签位号**（`pages/college-event-detail/college-event-detail.wxml:132` 的 `第 {{item.slot + 1}} 场`），再显示一个场号会不会让人混淆？要不要把签位号改成「第 N 组对抗」之类？

### 7.4 范围与口径

**Q9：个人赛与学院赛都要这个字段吗？** 建议都要（推荐）。若只要一个，实现量减半。

**Q10：场地数填错了怎么办？** 当前个人赛没有赛事编辑接口，发布后改不了。三个选项：(a) 一期不支持改，错了就重发赛事（推荐，最省事）；(b) 补一个「改场地数 + 全量重算场号」的写接口（需要 `bumpSeason`）；(c) 只允许在抽签之前改。

**Q11：场地数上限取多少？** 建议 20（与 `LEG_PLAN_MAX` 同量级）。下限 1。是否允许「不填」？（需求说必填，建议不允许。）

**Q12：场号要不要显示在学生端？** 还是只在管理视图里出现。建议全都显示（推荐）——参赛者最关心的就是「我去几号场」。
