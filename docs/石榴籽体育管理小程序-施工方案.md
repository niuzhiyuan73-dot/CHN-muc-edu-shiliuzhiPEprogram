## 一、总体设计

「协会」= 租户维度；「账号」= 全局一份；「内容数据」= 按协会分区。

```
微信 OpenID ──1:1──> users 账号（全局：实名信息、globalRole）
                       │
                       ├─ memberships（按协会的角色，稀疏）
                       │     mb_<md5(userId|assocId)>  仅存 leader / staff
                       │
                       └─ 参与「当前协会」的内容数据
                             matches / events / event_signups / announcements /
                             college_events / college_entries / ties / lineups /
                             live_scores        ← 每条带 association 字段

utils/associations.js（代码注册表，可放 N 个）
   ├─ 品牌：name / shortName / logoGlyph / theme
   ├─ 规则默认：format / elo / ratedPairLimit
   └─ status：active | disabled
```

**三条不变量：**

1. 账号按 OpenID 唯一，永远只有一份。
2. 内容读写一律以 `ctx.association` 为准（读过滤、写盖章）。
3. 协会清单在代码里、按 N 个设计，**业务代码永不判断「是不是乒乓/羽毛/匹克球」**。

## 二、协会模型（代码注册表）

### 2.1 协会注册表 `utils/associations.js`

新增纯模块（**需镜像到云函数**）。它是协会的唯一真相源，三端共用同一份清单：

```js
// utils/associations.js（示意）
const ASSOCIATIONS = [
  {
    id: 'pkb',                                   // 写进内容文档的 association 字段
    name: '中央民族大学匹克球俱乐部', shortName: '民大匹克球', logoGlyph: '匹',
    theme: { primary:'#1E7A55', primaryDark:'#166041', primaryLight:'#E8F4EF', accent:'#FF7A45' },
    format: { gamePointsOptions:[11,15,21], bestOfOptions:[1,3,5], defaultFormat:{ gamePoints:11, bestOf:3 } },
    elo: { initialRating:1450, genderInitialGap:150, kStandard:16, eventK:{1:32,2:24,3:16} },
    ratedPairLimit: 15,
    status: 'active',
  },
  { id: 'tt', name: '中央民族大学乒乓球协会', /* … 蓝主题 … */ },
  { id: 'bd', name: '中央民族大学羽毛球协会', /* … 橙主题 … */ },
  // 以后可继续加：网球 'tn'、排球 'vb' …
];

function allAssociations() {}          // 全量清单（供选择页、校验）
function activeAssociations() {}       // 仅 status==='active'
function getAssociation(id) {}         // 取一个；未知 id 抛错
function isKnownAssociation(id) {}     // 校验
function defaultAssociationId() {}     // 兜底默认（首个 active）
```

要点：
- **协会定义在代码里，不进数据库、不做后台增删改。**
- 业务代码**只按当前 `association` id 泛化处理**，任何地方都不写「是不是乒乓/羽毛/匹克球」
  的分支、也不写死数量。加第 N 个协会时，业务逻辑与云端接口都不需要改。
- 与 `constants.js` 同属**需镜像到云函数**的纯模块（`tools/sync-cloud-lib.js` 的 MANIFEST
  加一行；`tests/cloud-lib-sync.test.js` 守卫一致性）。

### 2.2 「加一个协会」要改什么

| 步骤 | 改哪里 | 是否必须 |
|---|---|---|
| 1. 加一条协会定义（id/名称/简称/图标字/主题色/规则默认值） | `utils/associations.js` | **必须** |
| 2. 若该协会要用独立品牌图（首页大图、分享图等） | 新增图片资源 | 视需要（当前首页只用文字徽标，通常可免） |
| 3. 镜像同步 | `node tools/sync-cloud-lib.js` | 必须（同步测试守卫） |
| 4. 数据迁移 | **无需** | 内容按 `association` 字段分区、角色按 `memberships` 记，新协会天然容纳 |
| 5. 云函数 / 业务逻辑 / 云端接口 | **无需** | 全部按 id 泛化 |

> 这正是你的判断：**新增协会是一次必然的前端改动**（要有人定名称与配色）。
> 但它被压到**只动注册表这一处、不碰数据、不碰业务逻辑、不改云端接口**，
> 且**按 N 个设计**——不会因为「当初只写了三个」而返工。

## 三、账号与身份

### 3.1 全局账号（主键不变）

- `memberKey(openId) = u_<md5(openId)>`（`idempotency.js:69`）**保持不变** ——
  账号全局唯一，注册一次即可（需求 U1）。**这是本版相对第一版最大的简化：账号集合无需任何迁移。**
- 实名信息（姓名/性别/学号/学院/手机号）全局一份（需求 U4），字段与企业无关。
- `role` 字段语义收窄为**全局角色**，合法值只有 `MEMBER(0)` 与 `ADMIN(2)`；
  `STAFF(1)` 不再作为全局值存储（改为协会角色，见 3.2）。

### 3.2 `memberships` 集合（按协会角色）

**建模的关键选择：会员资格是隐式的，`memberships` 只记「高配角色」。**
需求 U2/U3/A4 都是「注册即属于全部协会（含未来新增）」——若把会员资格物化成
一行行记录，新增协会就要给全体会员补录，反而制造负担。因此：

- **「是不是某协会的会员」= 该账号是已激活会员 且 协会处于 `active`**，无需记录。
- `memberships` **只在某人于某协会获得 `staff` / `leader` 角色时才有行**；无行 = 普通会员。

| 字段 | 说明 |
|---|---|
| `_id` | `mb_<md5(userId\|assocId)>`（新增 `membershipKey`） |
| `userId` / `association` | 谁、在哪个协会 |
| `role` | `'staff'`（学院负责人）/ `'leader'`（协会负责人） |
| `updatedAt` | 审计 |

好处：U2「注册即入全部协会」、U3「新协会自动纳入已有会员」、A4「新增协会全体自动成为成员」
**全部自动成立**，零补录、零代码分支。

### 3.3 有效角色解析（`cloudfunctions/data/src/core/context.js`）

`buildContext`（`context.js:28`）新增 `association` 入参，并按成员表算出**有效角色**：

```
ctx.globalRole = Number(actor.role || 0)            // 账号原始全局角色
ctx.association = 本次调用的协会（来自 event.association，校验为已知且 active）
ctx.membership  = actor ? repo.memberships.get(mb_<userId|assoc>) : null

有效角色 role：
  globalRole >= ADMIN               → ROLE.ADMIN      （全局管理员）
  membership.role === 'leader'      → ROLE.ADMIN      （协会负责人：在本协会内等同管理员）
  membership.role === 'staff'       → ROLE.STAFF      （学院负责人：本协会内、按学院）
  其余                              → ROLE.MEMBER

ctx.actor = { ...actor, role: 有效角色 }   // 覆盖为有效值，既有 canManage 调用零改动
ctx.isGlobalAdmin = globalRole >= ROLE.ADMIN
```

要点：
- **不重编号 `ROLE`**（`constants.js:16-26` 注释要求数值不动）。协会负责人以「有效角色=ADMIN」
  表达，从而对既有 `canManage(ctx.actor, { minRole: ADMIN })` 直接放行，无需改业务判定。
- **有效角色覆盖回 `ctx.actor`**，使全部既有 `canManage(ctx.actor, …)` / `managesCollege(ctx.actor, …)`
  调用**不用改一行**就按新语义运行。
- 协会负责人「管理本协会全部内容」= 有效角色 ADMIN；`managesCollege` 中 ADMIN 全校通行，
  因此协会负责人可管理本协会内任何学院的学院赛——符合需求。

### 3.4 权限判定的边界（**安全红线**）

有效角色会把「协会负责人」和「全局管理员」都算成 `ADMIN`，于是 `canManage` **无法区分二者**。
因此「角色任免」要分两类判定：

**（a）仅全局管理员可做**（读 `ctx.globalRole`，**禁止用 `canManage`**）：

- **任命 / 免除协会负责人**（写 `memberships.role='leader'`）。

> **凡「任免协会负责人」类操作，一律只认 `ctx.globalRole === ROLE.ADMIN`。**

**（b）有效角色 ≥ ADMIN 即可做**（用 `canManage(ctx.actor, { minRole: ADMIN })`）：

- **任命 / 免除本协会学院负责人**（写 `memberships.role='staff'`）——即**本协会的协会负责人或全局管理员**都能做。

两者都只写 `ctx.association` 名下的 `memberships`，因此协会负责人**天然只能任免本协会的人**，
越界无从发生（请求携带的 `association` 就是他所在的协会）。

这会作为**独立安全用例**写进测试：协会负责人**可以**任免本协会学院负责人，**不可以**任免协会负责人。

`services/permission.js` 现有函数（`isActive` / `canManage` / `managesCollege`）逻辑不变，
仅新增一处 `isGlobalAdmin(actor)` 供不依赖 ctx 的纯函数场景使用（按 `actor.role` 原始值判断）。

## 四、数据隔离

### 4.1 隔离真相源 = 文档上的 `association` 字段

所有内容集合的每个文档带 `association`。**读路径按它过滤，写路径给它盖章**，
与主键无关。`association` 的取值即 `utils/associations.js` 注册表里的协会 `id`。

### 4.2 自然键并入协会（**不改前缀**）

第一版主张给主键加 `{assoc}_` 前缀。本版改为更省事、更均匀的做法：
**把协会并进自然键的摘要输入**，前缀一律不变。这样：

- 代码里没有「某些协会带前缀、某些不带」的分支；
- 跨协会同名内容永不碰撞（摘要不同）；
- 旧数据的 `_id` 原样保留（只回填字段），不做级联重排。

`cloudfunctions/data/src/core/idempotency.js` 改动：

| 键 | 现状 | 改造 |
|---|---|---|
| `memberKey` | `u_<md5(openId)>` | **不变**（账号全局） |
| `matchNaturalKey` | `m_<md5(pool\|…)` | 摘要加入 `record.association` |
| `eventNaturalKey` | `e_<md5(pub\|title\|start)>` | 摘要加入 `record.association` |
| `announcementNaturalKey` | `a_<md5(pub\|title\|content)>` | 摘要加入 `record.association` |
| `collegeEventNaturalKey` | `ce_<md5(…)>` | 摘要加入 `record.association` |
| `signupNaturalKey(eventId,userId)` | `s_<md5(eventId\|userId)>` | **不变**（`eventId` 已含协会） |
| `collegeEntryNaturalKey(eventId,college)` | `cn_<md5(…)>` | **不变**（父 id 已含协会） |
| `collegeLineupNaturalKey(tieId,college)` | `ln_<md5(…)>` | **不变**（父 id 已含协会） |
| 签表生成比赛 `x_<eventId>_…` | 含 `eventId` | **不变**（`eventId` 已含协会） |
| `liveScores` `ls_<matchId>` | 含 `matchId` | **不变**（`matchId` 已含协会） |

> 只需给「顶层内容」（比赛 / 赛事 / 公告 / 学院赛）的自然键并入协会；
> 其余键要么是账号（全局），要么由父 id 派生（父已带协会），天然隔离。
>
> **可接受的边界**：`pkb` 旧文档的 `_id` 按旧算法生成（不含协会），迁移后若有人
> 「重新提交一场与旧记录完全相同」的内容，会生成新文档而非命中旧文档。这是弱网重试
> 才可能触发的极小概率边界，远优于「重排 `_id` 并级联改写 `events/matches/ties/live_scores`
> 交叉引用」的高风险操作。

### 4.3 两个全局单例必须拆开

现状唯一的**结构性阻塞点**：

- `SEASON_ID = 'current'`（`cloudfunctions/data/src/core/season.js:28`）
- `RANKING_SNAPSHOT_ID = 'current'`（`cloudfunctions/data/src/core/derive.js:50`）

改造：改为按协会取值 `current_<assoc>`。

- `season.js`：`loadSeason(repo, association)`、`bumpSeason(tx, { association, … })`、
  `writeSeasonReset(tx, { association, … })`、`defaultSeason(association)`。
- `derive.js`：`getDataset(ctx)` 用 `ctx.association` 组织缓存键与 `rankings` 主键；
  `readSnapshot` / `writeSnapshot` / `resetMemo` 均带协会。
- `memoByRepo` 缓存键**显式加入协会**（除了 `season._id` 已含协会外，再加一道保险）。

匹克球旧单例文档（各仅一条）在迁移时重命名为 `current_pkb`（无交叉引用，风险极低）。

### 4.4 读过滤 / 写盖章的落点

云端 `list()` 整表读回后在内存过滤（第一版 §4.2 实测），因此**每个读处理器都要显式按
`ctx.association` 过滤**；写处理器把 `ctx.association` 盖到记录上。涉及：

- `read-handlers.js` / `match-handlers.js` / `member-handlers.js` / `announcement-handlers.js` /
  `season-handlers.js` / `event-handlers.js` / `college-handlers.js` / `live-handlers.js`
  （共 29 读 + 35 写，见 `cloudfunctions/data/src/actions.js:14-86`），
  外加**新增的协会管理处理器**。
- `audit_logs`：唯一无自然键的集合（`repository.js:83`）。写入时盖 `association`，
  读取（若有）按协会筛选。
- `users`：**全局集合，不按协会过滤**（账号一份）。

## 八、数据迁移（线上匹克球数据）

> 原则：**加字段、不重排主键**。把旧数据原样纳入 `pkb` 命名空间。

1. **建集合**：仅创建 `memberships`（协会注册表在代码里，不建 `associations` 集合）。
2. **回填字段**：为 `matches / events / event_signups / announcements / college_events /
   college_entries / ties / lineups / live_scores / audit_logs` 中缺 `association` 的文档，
   批量写 `association:'pkb'`。
3. **主键保持原样**：`pkb` 全部 `_id` 不变；新协会自然键因并入协会而必不相同（§4.2）。
4. **迁移单例**：`seasons`、`rankings` 各一条 `_id='current'` → 重命名 `_id='current_pkb'`。
5. **拆分角色**：
   - `users.role === 2` → 保留（全局管理员）。
   - `users.role === 1` → 写一条 `memberships`：`(userId, 'pkb', 'staff')`；随后把 `users.role` 置 0。
   - `users.role === 0` → 不动。
6. **迁移脚本**：新增一次性脚本 `tools/migrate-associations.js`（云函数侧运行），
   **先 dry-run 输出将改动的文档数**，人工核对后再执行；执行前对目标集合做快照/导出。

## 十一、风险与验收

### 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 有效角色掩盖全局管理员 | 协会负责人与管理员同为「有效 ADMIN」，误用 `canManage` 判协会负责人任免 | **任免协会负责人一律只认 `ctx.globalRole`**，独立安全用例兜底 |
| 微信对外名称只能一个 | 多协会共用一个中性名 | 内部选择页 + 页内品牌区分；向用户方明确此限制 |
| 遗漏隔离点 | 某读处理器忘按协会过滤 → 跨协会串数据 | 每个集合写隔离测试作回归闸门 |
| 单例假设残留 | `seasons/rankings='current'` 是唯一硬阻塞 | P1 优先处理并专测 |
| 旧数据迁移误伤 | 回填字段 / 单例重命名 | dry-run + 快照 + 只加字段不重排主键 |
| 镜像不同步 | 改 `utils/*` 未同步云函数 | `tests/cloud-lib-sync.test.js` 守卫 |
| 测试规模膨胀 | 1987 用例、改动面大 | 分期推进、每期跑全量、先加测试再改码 |

### 验收标准（不变量）

1. **隔离**：在协会 A 登录，任何页面都读不到协会 B 的会员/比赛/赛事/公告/学院赛/榜单。
2. **一致**：各协会下同一功能页与流程完全一致，差异只在品牌与规则默认值。
3. **可扩展**：新增协会 = 在注册表加一条并配品牌（**一次开发改动**），**不碰数据、不改业务逻辑、不改云端接口**；新增后全体会员自动纳入。
4. **权限**：协会负责人管本协会全部内容、可任免本协会学院负责人；学院负责人限本协会本学院；协会负责人的任免仅全局管理员。
5. **幂等**：同一协会内重复提交同一操作仍按自然键去重。
6. **迁移无损**：匹克球历史数据（会员、比赛、赛事、等级分、赛季、公告）逐条可见、数值不变。
7. **回归**：`node --test "tests/**/*.test.js"` 全绿，且不少于 1987。
