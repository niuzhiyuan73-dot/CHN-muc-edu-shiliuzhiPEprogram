### H1｜27 个内部辅助函数被注册成协议 2 的 action

**现状**（本轮实测）：`school-space-handlers.js:18-22` 与 `school-mock.js:25-29` 都用  
`Object.entries({...11 个 service}).filter(([, v]) => typeof v === 'function')` **全量注册**。  
实测云端空间侧注册 **108** 个 action，其中 **27 个是内部辅助函数**，客户端从不声明：

```
activeSignupCount  advanceSchoolEvent  badgeOf        buildDirectory   buildRows
compareNotices     countRegistered     defaultSeason  displaySignupCount
eventSummary       isAnnouncementDoc   isCollegeEventDoc  isCollegeTieDoc
isEventDoc         isMatchDoc          legacyRoleOf   loadSeason       matchSummary
medalOf            normalizeCapacity   occupiedSignupCount  parseTime
recordOptions      returnPendingOnSeasonReset  seasonKeyOf  tallySignups  trainingState
```

**危害**（读了 `school-request.js` 之后的准确判断，比审计记录说得更具体）：  
`handleSchoolRequest` 只做了 `hasOwnProperty(handlers, action)` 检查，而 `handlers` 就是全量注册的那个对象  
——所以这 27 个名字**能通过检查**，并会被 `(event.payload || {}, ctx)` 直接调用，且**返回值不做信封包装**。

- 大概率后果是「滑稽的报错」：`buildDirectory(ctx)` 会把客户端可控的 `payload` 当 `ctx` 用 → `ctx.repo` 为  
  `undefined` → TypeError → 被入口的 try/catch 兜成「服务异常，请稍后再试」。
- **但不能保证全部安全**：任何「只凭 payload 就能取到数据」的辅助函数都会变成绕过业务校验的读口。  
  当前 27 个里没找到这样的函数，但这属于「靠运气」而非「靠设计」。
- 攻击面扩大是确定的：客户端根本不声明这些名字，服务端却接受调用。

**建议**：把「注册」从「全量推导」改成**显式清单**，并用测试与客户端门面对齐。具体三步：

1. 在 `school-space-handlers.js` 与 `school-mock.js` 各维护一份 `ACTIONS` 白名单（27 个名字剔除后，  
   空间侧应恰好是客户端 `forAssociationSpace` 声明的那些）；
2. 新增一条测试：**云端注册集 == 客户端三面（identity + space + exchange）声明集**，双向断言。  
   这与本批已落地的 `tests/school-write-guard.test.js` 是同一手法——那边守「写动作名单」，  
   这边守「注册面」；
3. 若嫌手写清单啰嗦，退一步的做法：约定内部辅助函数**统一加后缀**（如 `xxxOf` / `isXxxDoc`）并在  
   `filter` 里排除。但我不推荐靠命名约定——清单 + 测试才是可验证的。

**为什么阻塞上线**：协议 2 的 action 是字符串匹配，任何拿到 OpenID 的客户端都能构造调用。

### H2｜`member_ratings` 集合全链路无用

**现状**（本轮实测）：

- 云端 `repository.js:102` 有 `memberRatings: 'member_ratings'`，本轮补齐三件套后已可读写；
- mock 侧 `school-memory-repo.js` 的 `KEYS` **没有** `memberRatings` → `repo.memberRatings` 不存在；
- 但 `school-mock.js:105` 与 `school-seed.js:111` **都在往 `seed.memberRatings` 里写数据**，  
  而 `createSchoolMemoryRepo(seed)` 只按 `KEYS` 建 Map → **这两处写的数据被静默丢弃**；
- 全仓没有任何服务读写 `repo.memberRatings`（唯一的提及是 `exchange.js:12` 的注释）。

**危害**：不是崩溃，是**误导**。读代码的人会以为「学校维度等级分存在 `member_ratings` 集合」，实际上  
等级分一贯是「按 scope 重放 `matches` 流水推导、从不落库」。留着它，将来很可能有人真的往这里写分数  
——那就破坏了「比赛流水是唯一事实来源」这条核心设计。

**结论：删掉**（工程判定，已采纳），理由是它与设计原则冲突。落地清单：

1. 云端 `repository.js` 去掉 `memberRatings`，`COLLECTIONS` 从 31 → 30；
2. `school-repository.js` 的 `SCHOOL_COLLECTIONS` 去掉 `memberRatings`；
3. `constants.js` 去掉 `COLLECTION.MEMBER_RATINGS` 与 `utils/school.js` 的 `ratingKey`；
4. mock 侧删掉 `school-mock.js:105` / `school-seed.js:111` 两处 seed 写入；
5. `exchange.js:12` 的注释改为「不写校内 `events` / `matches`」；
6. 三处测试改为不依赖它（`exchange-cloud.test.js`、`exchange-service.test.js`、`school-foundation.test.js`）；
7. README 的集合清单相应改为 30 个（学校身份组 7 → 6）。

若将来产品确有「等级分落库缓存」的打算，再走另一条路：保留并补 mock 的 `KEYS`——但要清楚  
**那是给「分数不落库」开一个例外**，得先说服设计原则让步，而不是悄悄加回来。

### H3｜性能：整表读 + N+1

**现状**（本轮核实）：

- `school-actor.js:64`（`buildDirectory`）与 `:111`（`buildCollegeDirectory`）都读 `ctx.repo.users.list()`  
  ——云端按 100 条一页翻到底，而这两个函数**几乎每次判权都会被调用**；
- `school-member-service.js:68` 在 `for (const row of rows)` 循环里 `await ctx.repo.users.getById(row.userId)`  
  ——一本校 200 人就是 200 次 RPC；同类写法还有 `association-member-service.js:43`、  
  `association-training-service.js:350,394`。

**危害**：小规模（几十个用户）完全看不出来；一旦 `users` / `school_members` 到千级，  
判权与名录页会到秒级——而这是**每次操作都要走的路**。属「上线后一定会痛，但不是上线当天就炸」。

**建议**：分两半，**只做前半**。

- **前半（建议现在做，成本半天）**：`school-member-service` 的循环 `getById` 改成  
  「先一次 `users.list()` 建 Map，再从 Map 取」——`buildDirectory` 已经是这个写法，照抄即可。  
  这去掉 N+1 里最刺眼的一处，且不新增仓储接口。
- **后半（建议缓做）**：给云端仓储加 `getByIds(ids)`（分批 `where({_id: _.in([...])})`，每批 100），  
  把 `buildDirectory` 的 `users.list()` 换成「只取本校 members 对应的那批 user」。这一步要改  
  `cloud-repo.js` 的查询能力，且云开发的 `_.in` 有 100 上限要分批，属新机制。
- **不建议**做的：「把 `platformStatus` 冗余进 `school_members`」——那要给所有状态变更写路径同步，  
  改动面大、易漏，收益不足以抵。
- **顺带加一条可观测**：云端 `readAll` 翻页超过 N 次就 `console.warn`，上线后能早发现慢在哪。

### H4｜`forScope()` 两端接口面不对称

**现状**（本轮实测）：云端 `forScope` 返回 `list / getById / set / insert / update`；mock 的  
`forScope` **只返回 `list`**（探针确认：`mock forScope.events 方法: list`）。当前业务只用到 `list`。

**危害**：低。因为「mock 先崩」的形态会被测试抓到；真正的风险是**两端契约无声分叉**——  
将来有人单边加一个方法，另一端没人察觉。

**建议**：不急着补齐实现，先**加一条契约测试断言两端 `forScope` 暴露的方法名集合相等**（约 10 行）。  
一旦相等这条断言立起来，谁想单边加方法就得同时改另一端——这比现在「靠自觉」可靠。  
测试落地后，再决定是给 mock 补齐还是把云端收窄。

### H6｜路由判据把顶层 `schoolId` 当协议 2 信号

**现状**：`cloudfunctions/data/index.js:76`  
`if (event.protocolVersion !== undefined || event.schoolId !== undefined)` → 走协议 2。

**危害**（读完 `school-request.js` 后降级为**低**）：`handleSchoolRequest` 内部严格要求  
`event.protocolVersion === 2`，所以旧协议请求即便带顶层 `schoolId`，也只会得到一句  
「学校接口需要协议版本 2，请升级客户端」——**报错，但不会误执行业务**。误导性在于这句错误文案会让  
排查方向跑偏。

**建议**：判据收窄为 `if (event.protocolVersion !== undefined)`。协议 2 客户端**总是**带  
`protocolVersion: 2`（`school-cloud.js` 的 `requestFor` 里写死），所以 `schoolId` 这个条件纯属多余。  
顺带补一条测试：旧协议请求带顶层 `schoolId` 仍走旧分支。**改动 1 行 + 1 条测试。**

### H7｜cloud 数据源也加载整套 mock 演示数据

**现状**（本轮实测）：`school-identity.js:4`、`association-space.js:14`、`exchange.js:16` 顶部  
`require('./school-mock.js')`，而该模块**在加载时就执行 `reset()`**（建 seed + 演示内容）。  
实测 `require` 耗时 **420ms**（Node 环境；小程序端同量级）。

**危害**：低——只是冷启动白花几百毫秒，**不串数据**（数据源是 cloud 时这些 mock repo 没人读）。  
审计记录里写成「云端会先加载」不准确：**加载发生在客户端**，与数据源是 mock 还是 cloud 无关。

**建议**：把三处 `require` 改成惰性加载（`const loadMock = () => require('./school-mock.js')`），  
只在走 mock 分支时调用。注意 `school-identity.js` 的 `getDemoActors` / `setDemoActor` 直接引用了 mock  
的方法，改成在函数体内 `loadMock()` 即可。**成本半小时**，收益是每次冷启动省几百毫秒。

### H8｜死代码

- `pages/index/index.js:283` 的 `onOpenMember`——`index.wxml` 里**没有任何 `bindtap="onOpenMember"`**  
  （同名的 `onOpenMember` 在 4 个 component 里都有且都绑定了，那是另一批方法）；
- `services/school-demo.js:300` 的 `hasSchoolDemo`——全仓**零调用**（只有 `:645` 的导出）。  
  `docs/协会空间-需求与施工规划.md:790` 已记录这条，并判定「非缺陷（可选清理）」。

**建议**：一并删除。`hasSchoolDemo` 的语义已被「`schoolList.length > 1`」取代（同一文档已说明）；  
`onOpenMember` 的会员主页入口在别的面板里已有，首页这条是残留。**成本分钟级**，收益是少两个「看起来  
能用其实没人调」的方法——它们正是将来被误当作接口复用的源头。

### H9｜`login()` 在云端不可达

**现状**：`services/auth.js:251` 在**函数体内** `require('./index.js')`（`auth.js:240-247` 的注释详细  
解释了这是为规避 `mock → auth → index → mock` 的循环依赖，属有意设计）。镜像到  
`cloudfunctions/data/lib/services/` 后，`index.js` **不在 MANIFEST 里** → 云端该文件不存在。

**危害**：低，且**已知**——`tools/sync-cloud-lib.js` 的清单注释已写明「云函数不要调用 `login()`，  
云端自行按 OpenID 取用户」，云端也确实不调。

**建议**：把这条隐含约定**变成红灯**：加一条测试，静态扫 `cloudfunctions/data/lib/services/**` 的  
`require` 语句，断言没有任何文件 require `'./index.js'`。**成本 15 分钟**，不改业务代码。  
（另一种做法是在 `login()` 里 try/catch 优雅失败，但那是在给一个不该发生的调用兜底，不如直接禁止。）

### H10｜页面把服务端异常统一说成「网络异常」

**现状**：`login.js:469` catch → `errorText: '网络异常，请稍后重试'`；  
`profile-edit.js:163` catch → `firstError: '保存失败，请检查网络后重试'`。  
两者都 `console.error` 了真实原因，所以**排查不受影响**，只是用户话术不分场景。  
（另外注意：`profile-edit.js` **已经有 try/catch**，审计 §5.2 的「无 try/catch」名单不包含它。）

**建议**：优先级最低，**可选**。真要改，就把兜底文案从「网络异常」改成更诚实的  
「服务暂时不可用，请稍后重试」——而不是把 `err.message` 直接吐给用户（内部错误不该暴露）。  
业务性失败现在已被门面收敛成 `{ok:false, message}`，根本走不到 catch，所以这两处 catch  
兜的本就是「基础设施坏了」这一种情况，文案统一其实**不算错**。

### P1｜`users._id` 双方案 —— 现在统一最便宜

**现状**：

- 旧协议 `src/core/idempotency.js:96`：`memberKey(openId) = 'u_' + digest(openId)`
- 协议 2 `lib/utils/school.js:170`：`schoolAccountKey(openId) = schoolKey('acc', openId)`（即 `acc:<openId>`）
- 读取端 `cloud-repo.js:140-144` 用 `.where({openId}).limit(1).get()`，**没有 `orderBy`**

同一微信身份若既走过旧注册、又走协议 2 注册，会留下两条 `users` 文档，此后「解析到哪条」**不确定**，  
表现为「注册过却进不去」「榜单里没有我」。

**关键事实（决定了这件事的难度）**：`miniprogram/config.js` 的 `CLOUD_ENV_ID` **仍为空**，  
线上**没有任何真实数据**。所以所谓「数据迁移口径」目前**是个不存在的问题**——没有数据要迁。

**结论（产品已定）**：**统一到协议 2 的 `acc:` 键**，且**趁现在没有数据就做**。分两步：

- **第一步（已定，立即做）**：给 `getByOpenId` 加 `orderBy('_id', 'asc')`。  
  这一步**不改语义**，只把「不确定」变成「确定、可复现、可测试」。  
  （`readAll` / `readWhere` 里已经因为同样的理由加了 `orderBy`，这里是漏掉的一处。）
- **第二步（已定，紧接第一步）**：把旧协议的 `memberKey` 一起改成 `acc:` 键——  
  让两套协议落到同一条 `users` 文档。**成本极低**（改一处键生成 + 跑全量测试）；  
  一旦上线跑出真实数据，「统一」就必须附带迁移脚本，**越晚越贵**。
- 这条能立刻做，正是因为 **P10 已定「完全下线协议 1」**：既然旧协议不留，`u_` 键就没有存在理由。
