## 三 关键口径

1. **名册用 `_id` 游标，不用 skip。** 名册主键是 `sm:<schoolId>:<userId>`，同一校内按 `_id` 升序等于按 userId 升序，展示顺序与改造前一致；skip 会随页码线性变慢，且写入时窗口漂移（与 `cursorCond` 同一条理由）。
2. **总数的来源变了。** 原来 `members.length` 就是总数；现在 `total` 由 `countByStatus`（聚合计数、不读文档）给出，页面标题改用它，不再用「这一页的条数」冒充总数。
3. **待审是软上限不是分页。** 审核页是逐条处理的，处理完一条就整页重载，翻页没有使用场景；200 条只为挡住「一次读几千条」，超出时回 `hasMore`。
4. **学号判重保留两层，但都不是整表。** 事务外按 `studentId` 窄查（索引见索引清单），事务内仍写 `studentIdClaims`（同一学号写同一 `_id`，冲突即重试）。事务外那一层只为兼容尚未生成 claim 的存量身份。
5. **`readMatchPage` 只删一次计数，不动 DTO。** `total` / `pendingCount` 照旧下发（页面要显示「共 N 场」「待确认 N 场」），只把「还有没有下一页」从一次全范围 count 换成「多取一条」。
6. **`MAX_READ_ROWS` 是兜底，不是性能目标。** 10000 条远超本项目任何一个「本就该整表读」的集合；它拦的是失控调用，让失败从「3 秒超时 + 服务异常」变成一句能指导修改的中文错误。

## 四 踩坑与纠正

1. **`match-list-pagination.test.js` 的两条断言是按旧实现写的。** 改完先红了「103 !== 102」和 `limit=0` 时 `hasMore` 为真。前者是「多取一条」的直接后果，改断言并补一条「`limit` 传的是 101」；后者核查后确认**旧行为是对的**——`limit=0` 是「只要计数」的调用（首页数量），此时没有「多取的那条」可判，所以改的是实现（加分支），不是测试。
2. **曾担心搜索防抖会打断既有用例。** 核查发现「排行榜」「公告」两个面板的 `onInputKeyword` 是**纯本地过滤**（同步返回，用例不 await），只有协会空间面板走云端。所以只给这一个面板加防抖，其余不动。
3. **`getSchoolMembers` 改协议形状时，`context-cache.test.js` 仍在调它。** 该用例只关心「5 秒内两次调用的上下文是否复用」，不关心返回条数，所以不改；但这也说明「方法名是读动作前缀就进缓存」这条规则对返回值形状变化是透明的。
4. **文档里的「3040 条」不是一处。** README、交接说明（3 处）、接手指南补丁表各有一份，doc-audit 只覆盖 A1 的 README 与交接说明，接手指南要人工改（本轮已改）。

| P-5 上下文缓存跨实例失效（撤权后 ≤5s 仍按旧权限放行读） | **暂不做** | 写路径有事务内 `freshContext` 复核，不构成越权写；5 秒窗口在行政流程里不构成实质风险。触发条件：出现「撤权后仍能看到名单/公告」的投诉，或云函数稳定跑在多实例高频写。改法：给缓存键加账号级版本号（撤权动作 +1），或把 TTL 降到 2s |

## 八 回归与反向验证

- **契约钉住两端**：`for-scope-contract.test.js` 的「方法面就是约定的那一套」扩到 `listByStatus` / `countByStatus` / `listByStudentId`，云端与本地 mock 单边缺失即红——这三个方法一旦只在一端存在，就是「本地能翻页、云端翻不动」那类只在真机出现的毛病。

- **分页语义未变**：`match-list-pagination.test.js` 仍断言「一页查询 + 两个 count，次数不随台账增长」，只把返回条数改成 `limit + 1`。
