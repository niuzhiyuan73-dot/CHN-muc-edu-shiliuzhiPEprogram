# P-3 修复回退原因调查

日期：2026-10-22。基线：`da3c6a8`。

关联：[第二轮审查报告](代码审查报告-第二轮-2026-10-22.md)的 P-3 与「为什么 P-3 没有上线」。

## 结论

P-3 的比分批读没有因功能错误而失败。它减少了异步等待次数，暴露出 mock 演示数据缓存的并发初始化缺陷：**缓存只保存完成后的结果，没有保存正在执行的 Promise**。页面测试不断 reset，在首份快照生成前重复启动整套运动会演示生成，导致数百份相同工作并行推进。

这次独立对照复现了「批读本身更快、整文件反而慢约 73%」；仅合并演示数据初始化任务后，差异消失。因此，原报告把原因归为「测试夹具时序敏感」方向正确，但没有追到具体缺陷，也没有做排除该缺陷的控制实验。回退是当时未能解释回归的工程决策，不是批读方向不可行的证据。

本次只调查：未修改产品代码、原有测试文件或云端镜像。实验通过 Node 预加载脚本在单个测试进程中替换实现。

## 因果链与代码位置

1. `tests/page.test.js:315–321`：每条测试的 `beforeEach` 同步调用 `schoolMock.reset()`；部分测试夹具还会额外 reset。
2. `miniprogram/services/school-mock.js:218–226`：reset 创建新仓储，直接启动 `loadMeetDemo(repo)`，把 Promise 赋给 `meetDemoReady`，但不等待。重新赋值也不会取消旧任务。
3. `miniprogram/services/school-mock.js:158–162`：`loadMeetDemo` 先取演示记录，再逐条装入对应仓储。只有运动会入口会等待 `meetDemoReady`；普通页面测试可以继续推进。
4. `miniprogram/services/meet-seed.js:631–650`：`createMeetDemoRecords()` 只检查 `meetRecordsSnapshotJson`。它在三届真实服务流程全部结束后才写入快照，期间所有调用都看见缓存为空，各自执行一次三届生成流程。
5. `miniprogram/services/school-match-service.js:311–314`：旧列表实现逐行 `await withLive(...)`，每行内部又 await 点读。大量让出执行权的机会，使后台演示生成获得推进机会。
6. 改成一次批读后，页面请求更快完成，后续测试更快进入下一次 reset；首份快照生成前，更多重复初始化任务已被启动。它们各自继续运行，争用同一进程的 CPU 和内存，抵消并超过批读收益。

这是 Promise 异步任务累积，不需要 `setInterval`。因此原报告的「定时器创建数为零」不能排除这个原因。不同用例耗时变化也能得到解释：用例耗时包含它让出执行权期间其他初始化任务执行的时间，不能直接当作该用例自身的计算成本。

缓存已经存在时，每次 reset 仍需装载一份独立数据；本次发现的主要放大来自**冷缓存期间重复生成**，不是这些必要的数据隔离。

## 四组控制实验

环境：Windows、Node `v24.14.0`，当前基线 `tests/page.test.js`，四组顺序运行，不相互并发。所有组都加载同一份计数探针。

实验变量只有两个：

- 列表实时比分仍逐条点读，或重建等价的 `listByIds` 批读版本；批读保留学校/协会归属校验和原有 DTO 生成。
- 演示生成使用现有缓存，或在导出入口共享一个初始化 Promise；共享的是生成工作，每个调用仍 JSON 反序列化得到独立数据，失败时清掉 Promise 以允许重试。

| 实验 | 整文件耗时 | 冷缓存生成次数 | 峰值未完成生成数 | 通过/总数 |
|---|---:|---:|---:|---:|
| 原逐条点读 + 现有缓存 | 79.88 秒 | 249 | 249 | 292/292 |
| 批读 + 现有缓存 | 137.91 秒 | 415 | 415 | 292/292 |
| 原逐条点读 + 共享初始化任务 | 8.79 秒 | 1 | 1 | 292/292 |
| 批读 + 共享初始化任务 | 8.73 秒 | 1 | 1 | 292/292 |

辅助观测：

- 原实现首次快照约 54.90 秒生成，批读版约 70.90 秒才生成；共享任务后分别为 2.84 秒、4.36 秒。
- 四组均调用比赛列表接口 258 次，测试用例数量不变。
- 列表接口累计等待耗时分别约 52.05、5.30、2.49、0.87 秒。该指标包含其他异步任务运行时间，**不是纯 CPU 耗时，也不是云数据库延迟**。
- 原实现与批读版的测试子进程 CPU 用户时间分别约 95.09、165.98 秒；共享任务后约 10.86、10.61 秒。CPU 用户时间可能包含运行时其他线程工作，不等同于墙钟耗时。

原报告的历史批读补丁没有出现在所查 Git 提交中，本次按当前接口重建最小批读改动，因此不声称恢复了当时补丁的每一行。历史数字 98.98/174.25 秒也不是本次实测值。这里复现的是同类回归，并用控制变量实验定位其原因；不能据本地结果推算线上毫秒收益。

## 为什么上次停在回退

1. 检查集中在列表读次数、单个接口耗时、比赛页子集和轮询定时器，没有统计冷缓存生成次数及尚未完成的初始化任务。
2. 页面测试并不只执行当前页面：全局 reset 会在后台运行与当前页面无关的三届运动会全流程。因此改变一个接口的 await 数量，能改变其他工作被启动的数量。
3. 只缓存结果在串行调用下看起来有效，但不能阻止首次完成之前的重复执行。已有克隆优化减少了每份生成的成本，没有限制生成份数。
4. 将整文件运行时间作为回退依据本身可以理解；缺失的是找出额外耗时来源，再在隔离干扰后的条件下验证优化。

## 建议的后续修复顺序

1. 在 `createMeetDemoRecords` 内部合并首次初始化：共享正在生成的 Promise；成功缓存快照，每次返回独立副本；失败清理状态，允许后续重试。针对并发只生成一次、返回值隔离、失败后可重试补测试。
2. 单独恢复比赛列表的实时比分批读。补充查询次数断言、无实时状态、混合归属、空列表、返回顺序和 DTO 等价性校验，再跑页面回归。保留详情页的单条读取即可。
3. 另做数据库过滤与分页下推。当前 `listSchoolMatches` 仍先读完整范围台账，再筛选、排序和 slice；仅比分批读只解决 P-3 的一半。下推时须保留 `pendingCount` 在 status 筛选之前计算的口径，并验证稳定排序与翻页边界。

不需要为了这次测试回归改成页面侧请求合并。页面侧合并既不能修复上述初始化重复，也不能让一个列表请求内部的全量台账读取或逐条比分读取自动消失。

## 后续实施（同日，用户授权修复后）

上述「本次只调查」描述的是首次调查阶段。后续已实施以下改动：

- `meet-seed.js` 保存并共享进行中的生成 Promise，成功缓存 JSON，失败释放任务供重试；各调用仍拿到独立副本。
- `school-match-service.js` 列表改调受范围的 `matches.listPage`，只对本页执行一次 `liveScores.listByIds`；仍逐条校验实时态的学校/协会归属。
- 新增共用的 `match-list-query.js`，保留原有有效记录、pool、eventId、双方参赛者、status 筛选口径；`pendingCount` 不受 status 筛选影响。
- 云端适配器使用聚合 `match / sort / skip / limit / count`，只返回本页比赛及计数；普通首屏最多 3 次台账查询（当前页、total、pendingCount），传游标时最多 4 次，状态为待确认时复用计数查询。limit=0 不查询比赛文档，不读取比分。
- 稳定排序为 `matchTime desc + _id desc`，新增 `cursor: { matchTime, id }` 入参与 `nextCursor` 出参；保留旧 offset。游标与非零 offset 混用会返回业务错误。超出结果集的 offset 不发送巨大 skip。
- 本地 mock 与云端业务测试夹具新增同名分页原语，契约测试同步；云端共享库已同步。

API 示例（筛选条件翻页期间应保持一致）：

```js
const first = await api.listSchoolMatches({ userId, limit: 100 });
if (first.hasMore && first.nextCursor) {
  const second = await api.listSchoolMatches({ userId, limit: 100, cursor: first.nextCursor });
}
```

新增专项回归位于 `tests/meet-seed-cache.test.js` 和 `tests/match-list-pagination.test.js`，共 11 条；覆盖冷缓存并发合并、失败重试、副本隔离、三种仓储口径、稳定翻页、并发插入、畸形数据、跨校隔离、读取次数、limit 上限和空页等。

一万场的 SDK 管道模拟测试断言首屏只返回 100 条比赛文档及 2 条计数结果，台账查询固定为 3 次；这验证查询构造和回包量，不等同于真实云环境的索引命中或计费读量。完整本地测试 165 文件 / 2927 用例通过。
