# 安全与性能优化实施方案

日期：2026-10-23。优化前基线提交：`00cb2b9`。本地基线：176 个测试文件、2989 项用例通过，87 个云端镜像一致。

## 范围与顺序

| 问题 | 实施要求 | 验证重点 |
|---|---|---|
| 他人学号泄露 | 仅本人及本校会员审核者可读取学号 | 普通会员、协会负责人、校管、外校身份分别验证 |
| 编号暴露 OpenID | 使用不可逆账号编号，提供存量导出数据迁移工具 | 编号稳定、重复注册、嵌套引用、迁移冲突与幂等 |
| 转校清理覆盖并发退队 | 事务内重读队籍和学校身份，按球队处理 | 已退队者不复活、并发交接不覆盖、事务预算 |
| 超长昵称与头像 | 注册和资料修改复用长度与地址规则 | 超长输入拒绝、现有 cloud 文件 ID 与 HTTPS 头像兼容 |
| 名录分页读取全校账号 | 数据库内关联、筛选、稳定排序和游标分页 | 不再拉回全量名册；保留 NFKC 搜索和前缀优先 |
| 团队个人成绩读取无关历史 | 按本人、历史名单、关联球队与赛事取数 | 篮球足球均覆盖，退队后成绩保留，统计口径不变 |
| 限流桶不回收 | 正常流量也定期清理过期桶，并保护容量 | 回收有效、当前窗口限流不被重置 |

## 发布与数据兼容

代码完成后先同步云端镜像、完成回归、更新索引说明及验收记录，再重新部署 `data`。实际云端数据修改、凭据配置和部署不在本次本地实施中自动执行。

账号编号与目录搜索字段涉及已有数据时，必须先导出备份，在维护窗口迁移全部集合并检查引用；迁移工具默认生成新文件，不直接修改云数据库。具体命令及发布步骤见下节。

## 验收边界

本地仓储、协议入口、数据库适配器查询形状和事务预算分别验证；真实云端事务重试、索引执行计划、延迟及真机表现仍需部署环境验收。发现旧报告严重程度过高时保留历史，现行结论采用六项中风险、一项低风险。

## 已实现的数据约定

- 新账号编号为 `acc:` 加 SHA-256(OpenID) 的前 40 个十六进制字符；同一身份重试保持稳定，公开编号不再包含可逆 OpenID。OpenID 仅留在服务端账号文档中用于身份解析。
- 名录使用 `users.directoryVersion=1`、归一化姓名和排序键；只有本人或本校会员审核者可收到学号。头像地址上限 2048 字符，昵称上限 12 字符；空昵称由真实姓名的前 12 字符兜底。
- 团队历史读取认历史队籍、报名快照、已发布个人统计及足球报告，退出球队后不丢历史；按球队、赛事和编号批读。离校清理按球队事务执行，每次最多检查 20 个候选，事务内重读队籍与本校有效身份。
- 限流每秒清理过期桶，最多保留 20000 个当前窗口身份；满容量时拒绝新身份，不淘汰当前有效桶来重置额度。

## 存量导出迁移与回滚

1. 在维护窗口暂停写入，完整导出代码 `COLLECTIONS` 对应的 52 个集合。输入格式为一个 JSON 对象，键是控制台物理集合名，值是文档数组；空集合也必须提供 `[]`。备份放在已被 git 忽略的 `backup/` 下。
2. 先只检查：`node tools/migrate-account-ids.js --input=backup/export.json`。缺集合、重复微信账号或迁移后主键冲突会明确失败；不连接云端，不打印 OpenID，不覆盖原文件。
3. 生成迁移副本：`node tools/migrate-account-ids.js --input=backup/export.json --output=backup/migrated.json`。已有输出文件会拒绝覆盖。工具重写旧 `acc:<OpenID>` 的账号 ID、引用、嵌套编码主键、数组及按用户编号组织的对象键，并补齐所有账号的目录字段；姓名、正文与 OpenID 原值保留。
4. 比较前后每个集合的文档数量、主键唯一性及跨表引用，抽查会籍、球队、报名、评级和比赛结算快照。重复执行迁移应得到相同内容。历史不透明业务 ID 保留；维护后客户端必须重新加载并生成新的创建请求编号，不重放迁移前缓存的创建操作或旧深链接。
5. 经管理员核对后，在维护窗口完整恢复迁移后的集合，并移除旧主键文档；不能仅追加导入，否则旧账号和旧引用仍会保留。此步骤是实际数据变更，需在目标环境单独执行并验收，本次未执行。
6. 建好[新增索引](数据库索引清单.md)，运行 `npm run sync:cloud` 和 `npm run check:cloud-sync`，上传部署 `data`，发布对应客户端；核对登录、重复注册、名录翻页、隐私权限与历史成绩后恢复写入。目录字段缺失时会明确拒绝查询，不静默漏掉旧账号。
7. 如验收失败，保持停写并完整恢复原始导出以及优化前代码版本，再检查文档数量与关联。恢复写入后产生的新数据需另行保全，不能直接用旧备份覆盖。

没有存量用户的新环境无需迁移旧编号；已有 `users` 文档即使编号本来不含 OpenID，也必须回填目录字段。手工直接修改昵称或姓名后须同步这些字段，优先使用应用资料修改接口。
