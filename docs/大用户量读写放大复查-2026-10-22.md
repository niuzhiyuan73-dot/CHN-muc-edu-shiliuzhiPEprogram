# 大用户量读写放大复查（2026-10-22）

**范围**：`miniprogram/services/**`（与云端同源，经 `lib/` 镜像上云）、`miniprogram/components/**`、云函数适配层
  
**方法**：按已确认的五种放大模式做全仓模式扫描，再逐个核对调用链与集合量级；只报**尚未修复**的，已修的 9 项不重复。

**量级假设**（用于估算，不是实测）：某校在册 2000 人、启用 6 个协会、单协会 3 年积累 events 120 / matches 8000 / associationNotices 60 / trainingRegistrations 3000 / teamMembers 400；云开发单次查询上限 100 条/页，每日读配额按 5 万次计。

## 结论

**已修的 5 处（`users.list()`、榜单全量、团队整表、判球目录、录分台账）不是孤例，而是同一模式的样本——模式本身还在 20+ 处。**

这次查出两件事，性质和上一轮不同：

1. **有一个确定性故障（不是性能问题）**：运动会「发布成绩」在事务内按条写结果行与荣誉，操作数 ≈ 64 + 4N，**一个项目报名超过约 9 条就写不进去**（26 个学院满员时）。这与 B-1「名单提交」是同一个病、另一条路径——当时只算了名单，没算成绩。**已修**：12 条报名实测 110 → 26 个操作。
2. **最贵的读不在列表接口，而在「按协会扇出」**：一个普通成员打开一次首页，就会对 6 个协会各发 4 个请求，其中两个是「整表读 + 内存分页」，估算约 **1180 次读/首页**，5 万配额约 **42 次打开**见底。

> W-0 与用户量无关，小规模也会踩；H-1 ~ H-3 才是「大用户量下先崩」的那一类。
>   
> **已完成 W-0、H-1、H-2、H-6、H-8；H-3 / H-4 / H-5 各修掉能被安全修掉的那部分**，见各自小节末尾的「已修」。
>
> 三处残余（榜单 120、个人主页排名 123、名录分页）的根因是同一个——**排序键与过滤键跨集合**。
> 方案 A（把 `gender` / 在册状态物化进评级表）的**四步已于 2026-10-23 全部落地**：
> 写入侧 → 回填工具 → 榜单切读 → 个人主页排名切读。
> **上线顺序是死的：先跑回填、再切读。** 没回填就切，榜单与排名会**自动回落**到全量路径
> （有保护，不会白屏，但读量退回原样并打告警日志）。细节见[方案评估 §六](成员档案物化方案评估-2026-10-23.md)。

## W-0 发布成绩：项目报名超过约 9 条就写不进去（P0，确定性故障）

**位置**：`miniprogram/services/meet-score-service.js:611-905`（`publishMeetResults`）

事务内逐条写（不是只在内存里构造，`rowDigest` 构造完还要落库）：

```js
for (const row of rows) {                                   // 每个报名一条
  await tx.sportsMeetResultRows.set(meetResultRowKey(...), { ... });   // 2 个操作
}
for (const [collegeId, change] of delta) { ... }            // 每个有分的学院
for (const row of rowDigest) {
  await tx.sportsMeetHonors.set(key, { ... });              // 2 个操作
}
```

**操作数推算**（`TX_OPERATION_BUDGET = 100`，且事务内每次 `set` 都要先读归属）：

| 项                                              | 操作数                      |
| ---------------------------------------------- | ------------------------ |
| `freshMeetContext` + meet/event/publication 读写 | ≈ 12                     |
| 学院总榜：每个受影响学院 `getById` + `set`                 | 2 × 学院数（26 个学院都有人时 = 52） |
| 结果行：每条报名 `set`                                 | 2 × N                    |
| 个人荣誉：每条 `set`                                  | 2 × N                    |
| **合计**                                         | **≈ 64 + 4N**            |

> **N ≈ 9 就撞上限**（26 院满员时）。一个 100 米项目一个学院报 3 人、26 个学院就是 78 条 → 必然抛「事务读写总操作预算不足」，而管理员看到的是「服务异常」。

**与 B-1 的关系**：这是同一个病（事务预算 vs 业务规模不自洽）。B-1 修的是「提交名单」，这条是「发布成绩」——**同一批人写的另一条路径，当时只算了名单没算成绩**。

**修复方向**

1. **按学院分批提交**：一次只发布一个学院的结果行（26 批），每批 2N' + 2 个操作，学院内几十人也不超预算；总榜按批增量累加（现在的 `delta` 机制已经支持增减，改成跨事务累加即可）。
2. 或者把「结果行 + 荣誉」改成一次批量写入（云开发没有多文档批写，只能在事务外做幂等补偿）。
3. 止损：`publishMeetResults` 入口加一条明确上限（如单次发布 ≤ 40 条），超出提示「请按学院分别发布」，并同步到操作手册。

### ✅ 已修（2026-10-22，`meet-score-service.js`）

按方向 2 落地，但做得更彻底——**把「必须原子」与「可重建」拆开**：

| 放在事务内（原子）          | 放在事务之后（分批，`writeMeetResultDetail`） |
| ------------------ | ---------------------------------- |
| 发布快照（含全部行的 digest） | 结果行 `sportsMeetResultRows`         |
| 学院总榜（净额非零才写）       | 个人荣誉 `sportsMeetHonors`            |

配套改了三处：

1. **版本戳校验替代逐条比对**：原来 `unchanged` 对报名、成绩、裁判指派逐条点读（52 条报名 + 150 份成绩 = 200 多个操作，光校验就超预算）。改为比一次 `event.revision`——所有会动到这些集合的写路径（报名提交／审核／撤回、抽签、场次、指派、录分／提交）都调了 `touchEvent`，语义等价而且更严。
2. **发布快照带 `value`**：明细没写完的窗口里，展示靠快照兜底（`publishedRowsOf`），少了它成绩值会显示成「—」。
3. **总榜跳过净额为 0 的学院**：重发同样结果时一分都不写。

**实测**（`tests/meet-publish-budget.test.js`，12 条报名 / 36 份成绩）：

|    | 最贵的一个事务                            |
| -- | ---------------------------------- |
| 改前 | **110 个操作**（> 100，必抛「事务读写总操作预算不足」） |
| 改后 | **26 个操作**                         |

> 临界点比原来推算的更低：12 条报名就已经炸了。26 个学院满员时改后约 63 个操作，仍在预算内。

**明细写入失败怎么办**：发布已经成立，读取侧回落到发布快照（`getPublishedResults` / `listMeetPublishedResults` / 晋级读的都是 `publishedRowsOf`），下次重新发布会整体覆盖自愈。返回值带 `detailPending: true` 供页面提示。

## H-1 首页按协会扇出：一次打开 ≈ 1180 次读（P0）

**位置**：`miniprogram/services/school-home-view.js:135-174`

```js
const perAssociation = await Promise.all(allAssociations().map(async (assoc) => {
  const api = client.forScope({ schoolId, association: assoc.id });
  const [eventDocs, matches, season, members] = await Promise.all([
    collectEvents(api),                    // 循环分页取完全部赛事
    api.listSchoolMatches({ limit: 1 }),   // 只为拿 total
```

**为什么贵**（6 个协会各跑一遍）：

| 子请求                            | 实际动作                                                                 | 读次数（2000 人 / 120 赛事）  |
| ------------------------------ | -------------------------------------------------------------------- | --------------------- |
| `collectEvents`                | 每页 50，循环到取完；每页要 `events.list()`（整表）再内存切片；每行再点读「我报名了没」                | 6（3 页 × 2）+ 120 = 126 |
| `listSchoolMembers`            | 全校 `school_members` 分页 20 页 + `users.listByIds` 20 页；**只用到 `total`** | 41                    |
| `listSchoolMatches({limit:1})` | 两次聚合计数（total / pending），不回文档                                         | 2                     |
| `getSchoolSeason`              | 点读 1 条                                                               | 1                     |
| **单协会小计**                      |                                                                      | **≈ 170**             |
| **×6 协会 + 25 次身份解析（25×6）**     |                                                                      | **≈ 1180**            |

**影响**

- 5 万/天配额按 **≈42 次首页打开** 见底；开学季一个班打开一遍就把全校配额打空，现象是「所有页面加载失败 / 提示服务异常」。
- 首页是唯一「每个用户每次进小程序都会过」的页面，它比任何列表接口都更该按预算设计。
- 25 次 `callFunction` 还意味着 25 次冷/热启动调度与 25 次限流计数。

**修复方向**

1. **砍扇出**：首页概况只需要「会员总数 / 比赛总数 / 赛事数 / 赛季号」，应新增一个 `getSchoolHomeSummary` 聚合接口，服务端一次算完（总数用聚合 `count`，赛事只取前 3 条），客户端 1 次调用替代 24 次。
2. **会员数不要读名单**：`schoolMembers` 上用聚合 `count({ schoolId })` 只回数字；比赛数用 `count`（`listPage` 已具备该能力）；赛季号一次点读。
3. **赛事只取需要的 3 条**：`collectEvents` 现在「取完再前端筛前 3 条」，应把「报名中/进行中、按开赛时间升序、前 3 条」下推成查询条件。
4. 短期止血：`collectEvents` 改为只取第一页（`limit: 50` 不循环），首页本来只展示 3 条。
5. 若产品确实要「6 个协会的横向对比」，也应一次请求带 6 个 scope 在服务端并发，而不是 24 次 callFunction。

按方向 3 + 4 + 2 组合落地（没有新增聚合接口，先把扇出里的重复读砍掉）：

## H-3 赛事：列表整表读 + 每行点读；详情读全协会小组（P0）

**修复方向**

1. `events` 复用本轮新增的 `listPage` 思路：把 status/置顶/时间排序与分页下推（`events` 量级小，可先做「只取前 N 条」）。
2. 「我的报名」改一次批读：`eventSignups.listByIds(本页 eventId 拼 key)`，替代 N 次点读。
3. 小组成员判断：`associationGroupMembers` 的 `_id` 是「范围 + groupId + userId」，可先 `associationGroups.list()`（几十条），再对「我所在的组」点读，或给 `userId` 建索引后按人查；**不要**读全协会成员表。

### ◐ 已修两项（2026-10-22，`school-event-service.js` + 仓储）

| 改动         | 原先                              | 现在                                                   |
| ---------- | ------------------------------- | ---------------------------------------------------- |
| 「我报名了没」    | 当前页每行点读一次（一页 20 条 = 20 次 RPC）   | 按页一次 `eventSignups.listByIds`（1 次）                   |
| 「我在不在指定小组」 | 读整个协会的小组成员行再筛（6 协会 × 若干组 × 数十人） | `associationGroupMembers.listByUser(我)`（1 次，随人数不再增长） |


新增仓储原语 `listByIds`（EVENT_SCOPED 八个集合通用）与 `associationGroupMembers.listByUser`，两端同口径、契约测试钉住。**部署前要建索引**：`association_group_members` 的 `schoolId + association + userId`。

**没做的**：`events.list()` 仍是整表读 + 内存排序分页（`school-event-service.js:313`）。不做的理由：events 量级是 120 条 / 3 年，整表读只有 2 页；而下推要新增一条六字段复合索引（schoolId + association + pinned + status + startTime + \_id）并把「置顶优先」的排序搬进查询，收益 2 页换一次索引与排序行为变更，不划算。等 events 真的涨到几百条以上再改，改法已在报告开头写明（`EVENT_STATUS` 的取值顺序恰好等于状态优先级，可以直接下推成 `orderBy('status')`）。

## H-6 排行榜每次装载 5 个集合（P1）

### ◐ 已修一步（2026-10-23）

榜单每行只有 elo / 胜负 / 出场数 / 昵称，**不用赛季积分**——积分是个人主页的事。而积分要从 `events` + `associationTrainings` + `trainingRegistrations` 三处聚合，只读不写也要 **33 页** RPC（训练报名 30 + 赛事 2 + 训练 1）。

> 踩到一个坑：`registrationsOf` 一开始写成先算 Promise 再由三元挑，查询在赋值那一刻就已经上路了，`needPoints: false` 也拦不住。改成惰性函数才对。用例 `榜单不读积分事实` 就是钉这个的。

### ✅ 已完成（2026-10-23，方案 A 第 2~3 步）

**120 页 → 约 5 个 RPC。**

冗余字段落地后，「本池 + 本项目性别 + 在册 + 按 elo 前 N」可以一条查询完成：

| 步骤 | 原读量 | 现读量 |
|---|---|---|
| 前 N 名（`listTop`，同时充当搜索范围） | 评级 80 页 | 1 页 |
| 上榜总人数（`countRanked`，聚合计数） | 名册 40 页 | 1 次（不读文档） |
| 我的名次（比我高的人数 + 1） | 名册 40 页 + 评级 80 页 | 1 次（不读文档） |
| 昵称头像（`users.listByIds`，前 50 + 我） | 账号 20 页 | 1 批 |
| 我这条评级（`listByUser`） | — | 1 页 |

名次仍由本地用同一比较器重算（`elo → 胜率 → 胜场 → 时间 → 编号`），与旧路径逐位一致。

**两个刻意的取舍**：

1. `allRows` 从「全榜」收窄到「前 50 + 我」。搜索范围因此变小——搜榜外的人会搜不到；但自己一定在（榜外也补一行），而全量下发 2000 行本身也是流量负担。
2. 回填未完成时**整体回落**旧路径。判据不是"新路径取到几条"，而是 `memberStatus` 字段存在性计数：部分回填时若只走新路径，没回填的人会被静默滤掉，**榜单看起来正常却少了人**，比空榜更难发现。

用例：`tests/rank-read-budget.test.js` 6 条（不整表读评级、前 10 顺序、女单按性别下推、榜外名次、转出的人不上榜、回填未完成时整体回落）。

## H-7 通知列表全表读（P1）

**位置**：`association-notice-service.js:97` —— `associationNotices.list()` 全量 + 内存排序分页。

**影响**：通知**只增不减**，第三年打开通知页要翻全部历史；虽然单协会通知量不大（几十~几百），但它是「复制这段代码到别处」的模板，和 P-3 修掉的 `matches` 同源。

**修复方向**：按 `publishTime desc` + 游标分页；`isNoticeDoc` 的有效性条件下推。

### ⏸ 暂不做（2026-10-23 评估）

查过一遍，**收益与风险不成比例**：

1. 通知列表**已经有游标分页**（`payload.cursor` 支持「置顶 → 发布时间 → 编号」三元组），客户端不会一次拉完；只是排序在内存里做。
2. 量级小：一个协会三年积累 60 条（0.6 页）。就算第五年翻倍，也还是 1~2 页。
3. 真正下推要处理「置顶优先」的**三元组游标**（`pinned` / `publishedAt` / `_id` 的字典序比较），云开发需要 `_.or` + `_.and` 组合，而这条路径的翻页语义（不重不漏）目前靠内存里的 `compareNotices` 保证——改错就是翻页丢通知。

结论：等真的出现"通知几百条、打开变慢"再加。改法已写明（`associationNotice` 加 `pinned + publishedAt + _id` 复合索引）。

## 判定口径（供后续复用）

不是所有 `list()` 都要改。按「集合是否只增不减 + 是否在普通成员路径上」两条判断：

| 可以保留整表读                                                                            | 必须改                                                                                                                                         |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `colleges`（一校 26 条）、`schools`（一校 1 条）、`schoolRoles`（一校几人）、`associationGroups`（几十条） | `matches`、`eventSignups`、`trainingRegistrations`、`associationGroupMembers`、`associationNotices`、`memberRatings`、`teamMembers`、`sportsMeet*` |

一条经验规则：**「先全量读、再 slice 出 20 条」的写法一律视为缺陷**——分页若不在数据库里，读量就与页数无关、只与总量有关。
