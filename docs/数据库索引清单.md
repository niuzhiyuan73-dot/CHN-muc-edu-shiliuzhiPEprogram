# 数据库索引清单（云端）

> 本地 mock 用内存 Map，**没有索引这个概念**；云端没有索引就是全表扫。
> 所以「本地一切正常、上线后列表页越来越慢、读配额见底」这件事，
> 只能在部署时按本清单补上。新增任何 `where` 条件字段，都要回到这里登记。

## 一、为什么必须有这份清单

云端适配层 `cloudfunctions/data/src/adapters/cloud-repo.js` 的读取有两条路径：

| 路径 | 代码 | 用到的条件字段 |
|---|---|---|
| 按范围列集合 | `readWhere`（`listByScope` / `listByEvent`） | `schoolId`、`association`、`eventId` |
| 按主键读 | `readDoc` | `_id`（自带索引，无需配置） |

云开发单次查询上限 100 条，`readAll` 会按 `_id` 升序翻页；**没有索引时每一页
都是全表扫描**，一个赛季上千场比赛就能把「打开一次比赛页」变成十几页 RPC。
官方每日读配额是「万次」量级（按套餐不同），列表页是主要消耗方。

> **分页契约（2026-10-26 审查 P2-9）**：列表接口用「多取 1 条」判 `hasMore`，
> 而单次读取上限是 100 条。`forScope(...).schoolMembers.listByStatus` 这类
> 需要 101/201 条的调用由仓储按 `_id` 游标自己续读（`school-repository` 的
> `readUpTo`）；适配器的 `top` 超过 100 条直接报错，不再静默截断。
> 新增分页接口时**不要**假设「一次查询想取多少就取多少」。

## 二、必须建的索引

### 2.1 范围索引（每个受范围集合都要有）

集合清单见 `cloudfunctions/data/src/school-repository.js` 的 `SCOPED_COLLECTIONS`。

| 集合 | 索引字段 | 说明 |
|---|---|---|
| `matches` `events` `eventSignups` `collegeEvents` `collegeEntries` `ties` `lineups` `liveScores` `seasons` `associationGroups` `associationGroupMembers` `associationNotices` `associationTrainings` `trainingRegistrations` `pairCounts` `memberRatings` `ratingCounters` `exchangeEvents` `exchangeInvitations` `exchangeSignups` `exchangeMatches` `teams` `teamMembers` `teamEvents` `teamEventEntries` `teamMatches` `teamMatchStats` `memberships` `schoolAssociations` | `schoolId` + `association`（组合） | 协会空间的每一次列表读取都走这两个字段 |
| `colleges` `schoolMembers` `schoolRoles` `sportsMeetCollegeLeads` `announcements` | `schoolId` | 学校级集合，只按学校过滤 |

> 组合索引的字段顺序按「等值字段在前」即可，两者都是等值条件，顺序不影响命中。
> 团队运动 6 个集合（2026-10-22 补录）此前只写在 `cloudfunctions/README.md`，
> 本清单漏登记——漏建的后果是球队/赛程列表逐页全表扫。

| `schoolMembers` | `schoolId` + `studentId` | 入会审批的学号判重（`listByStudentId`，P-7）。不建则每次审批都要把整校名册读回来比对学号 |
| `sportsMeet*`（运动会各集合） | `schoolId` + `meetId` | `forMeet` 的所有读取 |
| `memberRatings` | `schoolId` + `association` + `pool` + `gender` + `memberStatus` + `elo ↓`（复合） | **榜单与个人主页排名的唯一入口**（2026-10-23 方案 A 第 2 步）。`listTop` 要「本池 + 本项目性别 + 在册 + 按 elo 前 N」，`countRanked` 要两次聚合计数；没有这条索引，两者都退化成整表扫，方案的收益一条也拿不到 |
| `memberRatings` | `schoolId` + `association` + `userId` | 个人主页 / 榜单的「我这条评级」（`listByUser`） |
| `sportsMeetEntries` | `schoolId` + `meetId` + `eventKey` | 运动会录分页只列**本项目**的报名（`listByProject`，2026-10-23 H-9）。一届的报名是「项目 × 学院 × 名额」，上千条，而一个项目几十条 |
| `sportsMeetScores` | `schoolId` + `meetId` + `sessionKey` | 录分页只取**本场次**的成绩（`listBySession`）。成绩是「报名 × 裁判」，比报名还多 |
| `sportsMeetSessions` | `schoolId` + `meetId` + `eventKey` | 判「本项目有哪些场次」用（`listByProject`，2026-10-23 H-9 第二轮）。原来读一届全部场次 |
| `sportsMeetJudgeAssignments` | `schoolId` + `meetId` + `judgeId` | 「我在本届被指派到哪些场次」（`listByJudge`）。一届指派是「场次 × 裁判数」 |
| `sportsMeetJudgeAssignments` | `schoolId` + `meetId` + `sessionKey` | 本场次的裁判名单（`listBySession`），同一条集合上的第二个查询方向 |
| `sportsMeetInterests` | `schoolId` + `meetId` + `userId` | 「我的参赛页」只显示本人报的项目（`listByUser`，2026-10-23 第三轮 X-9）。原来把一届意向全读回来再按 userId 筛，报名旺季数千条 = 30~50 页 |
| `sportsMeetInterests` | `schoolId` + `meetId` + `eventKey` | 提交正式名单时判「这些学生对本项目有没意向」（`listByProject`，2026-10-26 第五轮审查 E）。原来读全届意向再按 userId 挑 |
| `sportsMeetScores` | `schoolId` + `meetId` + `eventKey` | 成绩预览 / 发布成绩 / 已发布结果都只取本项目（`listByProject`，第五轮审查 B）。成绩是「报名 × 裁判」，一届数千条，而一个项目几十条 |
| `sportsMeetPublications` | `schoolId` + `meetId` + `eventKey` | 同上（发布快照按项目取）；`eventKey` 在发布时落库 |
| `sportsMeetJudgeAssignments` | `schoolId` + `meetId` + `eventKey` | 本项目有哪些指派（`listByProject`，第五轮审查 B）；「我的任务」走 `listByJudge`，本场裁判走 `listBySession`，三者互补 |
| `sportsMeetResultRows` | `schoolId` + `meetId` + `eventKey` | 晋级与成绩公示按项目取结果明细（`listByProject`，第五轮审查 B）。明细是「一条报名一条」，发布后按 (快照, 报名) 覆盖写 |
| `sportsMeetEntries` | `schoolId` + `meetId` + `userIds` | 同上（`listByUser`，第三轮 X-9）。`userIds` 是数组，索引按多键处理；一行是「项目 × 学院」的名额占位，一行可有多名参赛者，所以是「包含」而不是等值单值 |

> `memberRatings` 那条复合索引的字段顺序**不能调**：`schoolId` / `association` /
> `pool` / `gender` / `memberStatus` 都是等值条件，`elo` 是排序字段，必须排在最后。
> `matchCount > 0` 作为附加过滤留在索引之外（范围条件放中间会截断后续字段的排序能力）。
> 若索引过多影响写入，可先只建这一条——它同时服务榜单、个人主页排名与回填监控。

### 2.3 比赛列表分页索引（2026-10-22，P-3）

`matches.listPage` 在数据库内过滤、排序、分页并统计总数，比赛文档最多返回 100 条。
以下索引均为**非唯一**；字段按列出的顺序添加。`↑` 表示升序，`↓` 表示降序。

| 索引名建议 | 字段顺序 | 对应入口 |
|---|---|---|
| `by_scope_match_time` | `schoolId ↑`、`association ↑`、`matchTime ↓`、`_id ↓` | 协会比赛列表、首页数量与时间游标 |
| `by_scope_event_match_time` | `schoolId ↑`、`association ↑`、`eventId ↑`、`matchTime ↓`、`_id ↓` | 某一赛事比赛列表 |
| `by_scope_status_match_time` | `schoolId ↑`、`association ↑`、`status ↑`、`matchTime ↓`、`_id ↓` | 按状态列表和待确认统计 |
| `by_scope_team_a_match_time` | `schoolId ↑`、`association ↑`、`teamA ↑`、`matchTime ↓`、`_id ↓` | 我的比赛，A 方参与者分支（`listMineSince`，2026-10-23 第三轮 X-7） |
| `by_scope_team_b_match_time` | `schoolId ↑`、`association ↑`、`teamB ↑`、`matchTime ↓`、`_id ↓` | 我的比赛，B 方参与者分支（同上） |

`teamA` / `teamB` 是数组，两条参与者索引分开建立，不要把两个数组字段合进同一条组合索引。
`pool` 与其余组合条件仍下推，由上述索引缩小候选范围后进一步过滤；若某个组合成为慢查询，
再根据真实分布增加索引，不预建所有筛选字段排列。

分页排序使用持久化的 ISO 时间串；与 `listSince` 一样，依赖仓储的时间规格化约定。
若环境含早期手工导入的 BSON Date 或非标准时间串，应先统一为 `toISOString()` 格式。
已有 offset 调用继续兼容数据库 skip；连续翻页可传上一页的 `nextCursor`，避免深 skip 和新记录插入引起的窗口漂移。

### 2.4 成员目录与个人团队历史（2026-10-23）

以下集合名采用控制台物理表名；新增索引全部不唯一，末尾 `_id` 升序配合游标翻页。

| 集合 | 索引字段（均升序） | 用途 |
|---|---|---|
| `school_members` | `schoolId` + `status` + `userId` | 成员目录先筛本校在册会员，再关联 `users._id` |
| `team_members` | `schoolId` + `association` + `userId` + `_id` | 本人的现役及历史队籍、离校清理 |
| `team_members` | `schoolId` + `association` + `teamId` + `_id` | 关联球队人数、队长继任候选 |
| `team_event_entries` | `schoolId` + `association` + `roster.userId` + `_id` | 历史报名快照中的本人，退队后仍可查 |
| `team_matches` | `schoolId` + `association` + `teamA` + `_id` | 关联球队历年战绩 |
| `team_matches` | `schoolId` + `association` + `teamB` + `_id` | 同上，另一侧球队 |
| `team_matches` | `schoolId` + `association` + `eventId` + `_id` | 本人参加的赛事比赛 |
| `team_matches` | `schoolId` + `association` + `footballPublished.sides.A.players.userId` + `_id` | 足球已发布报告中的本人 |
| `team_matches` | `schoolId` + `association` + `footballPublished.sides.B.players.userId` + `_id` | 同上，另一侧球员 |
| `team_match_stats` | `schoolId` + `association` + `published.players.userId` + `_id` | 篮球基础统计中的本人 |
| `team_match_stats` | `schoolId` + `association` + `published.rows.userId` + `_id` | 篮球按节统计中的本人 |

数组路径分别建多键索引，不把两个独立数组路径放进同一条组合索引。`teams`、`team_events` 和比赛按编号批读使用已有 `_id` 索引，并附带学校、协会条件。

成员目录通过聚合 `lookup` 关联当前账号，数据库内做搜索和排序，只返回当前页加一条用于判断 `hasMore`。`users.directoryNickName` / `directoryRealName` 保存 NFKC 归一搜索值，`directoryNickSort` / `directoryRealSort` 保存 UTF-16 排序键，注册和资料修改同步维护。已有账号发布前必须按[实施方案](安全与性能优化-实施方案.md)回填。

任意子串搜索、前缀优先及关联后的排序仍需数据库处理本校候选集；本次消除应用层全量拉取与逐页 RPC，不声称数据库扫描成本已经降为常数。查询使用的聚合能力见 [CloudBase 聚合文档](https://docs.cloudbase.net/database/aggregate)。真实执行计划及延迟需在目标环境验收。

### 2.5 第九轮查询索引（2026-10-28）

以下 5 条索引为本批新增，均不唯一、字段升序。足球候选查询含资源等值及时间范围，并按 `_id` 续读；上线后需核对查询计划与扫描量。

| 物理集合 | 索引字段 | 用途 |
|---|---|---|
| `school_members` | `schoolId` + `status` + `collegeId` + `_id` | `listSchoolMembers` 先筛有效会籍及学院，再批读账号；未筛学院时复用原状态索引 |
| `team_matches` | `schoolId` + `association` + `teamA` + `matchTime` + `_id` | 足球排期按 A 方球队及时间窗查冲突候选 |
| `team_matches` | `schoolId` + `association` + `teamB` + `matchTime` + `_id` | 同上，B 方球队分支 |
| `team_matches` | `schoolId` + `association` + `location` + `matchTime` + `_id` | 同场地及时间窗 |
| `team_matches` | `schoolId` + `association` + `refereeId` + `matchTime` + `_id` | 同裁判及时间窗 |

跨校裁判候选复用 §2.4 的 `school_members` 目录索引和 `users._id` 关联，不新增集合或账号字段。仅管理者可按已接受邀请的学校查询，一页默认 20、最多 50 人；普通详情不查询候选名册。

## 三、怎么建

云开发控制台 → 数据库 → 选中集合 → **索引管理** → 新建索引：

1. 索引名：`by_school_assoc` 之类，能看出字段即可；
2. 字段：按上表依次添加；§2.3 按箭头设置方向，其余索引用「升序」；
3. 是否唯一：**全部不唯一**（唯一性由业务主键 `_id` 保证）；
4. 建完等状态变为「可用」再压测。

## 四、读放大治理（2026-10-21 已做）

原来有 7 处「整表读完再在内存里过滤」，已改成按 `eventId` 的条件查询：

| 位置 | 改动 |
|---|---|
| 赛事详情 · 报名名单 | `eventSignups.list()` + filter → `listByEvent(eventId)` |
| 赛事详情 · 签表名单 | 同上 |
| 报名台账（名额判断） | 同上 |
| 代签校验 | 同上 |
| 赛事结算 · 报名 | 同上 |
| 赛事结算 · 比赛 | `matches.list()` + filter → `listByEvent(eventId)` |
| 编排比赛 | 同上 |

两端同时提供 `listByEvent`（内存仓储 `school-memory-repo.js`、云端
`school-repository.js`），方法面由 `tests/for-scope-contract.test.js` 逐字守住。

**仍有一处整表读**：赛事列表页要统计「全部赛事」的报名人数
（`school-event-service.js` 的 `eventSignups.list()`）。赛事数量上百后建议
改为「赛事文档上维护 `signupCount` 汇总字段」，读列表时不再碰报名表。

## 五、维护约定

- 新增 `where` 条件 → 在 §2 登记 → 控制台建索引 → 在 PR 说明里写一句；
- 不确定某条查询走不走索引时，先在控制台「慢查询」里观察再决定；
- 集合清单以 `cloudfunctions/data/src/repository.js` 的 `COLLECTIONS` 为准，
  少建集合会报 `-502005`（错误信息已写明是哪个集合）。
