## 二、F3 方案 B 的实现与接线

**数据模型**：`pair_counts` 集合，`_id = pairCountKey(a, b, 赛季分界点, scope)`
（`schoolKey('pc', schoolId, association, stamp, first, second)`，两人编号升序，不用 `|` 拼接）。
文档字段：`schoolId / association / seasonStamp / seasonNumber / pairKey / users / count / revision / updatedAt`。

- **赛季键取「分界点」而不是赛季号**：台账那边「本赛季」的定义是
  `matchTime >= season.resetTime`（见 `rating-cap.countedMatches`）。计数键与它同源，
  两处才不可能分叉；重置赛季时 `resetTime` 变、键跟着变，旧赛季计数天然失效、无需迁移。
- **懒初始化**：计数文档不存在（历史数据、规则生效前录的场次）时，用事务外按台账算出的
  用量做初值写进去。两个并发请求同时初始化时，内存仓储是串行事务、真库是写冲突重试，
  后到的那次必然读到先到的结果，所以不必先跑批。
- **释放**：作废（撤销 / 驳回）在同一事务里减一；**没有计数文档就不建**——那一场是新口径
  之前录的，凭空建一条 `count=0` 会把台账里的占用抹掉，下次提交按台账懒初始化自然会算上。
- **边界**：只对「自行录入」的日常约球计数（与 `isCasualMatch` 同源），赛事 / 学院赛比赛不设限；
  双打按 `crossPairList` 一次占四对，任一对满额则整笔拒绝；赛季重置后另起一份计数。
- **接线**（新增集合要动的地方）：`utils/constants.js`（`COLLECTION.PAIR_COUNTS`）、
  `cloudfunctions/data/src/repository.js`（逻辑名 → 集合名）、
  `cloudfunctions/data/src/school-repository.js`（`SCHOOL_COLLECTIONS` + `SCOPED_COLLECTIONS`）、
  `miniprogram/services/school-memory-repo.js`（`KEYS` + `forScope`）。
  云适配器按 `COLLECTIONS[key]` 泛化读写，无需另改；`derive.js` 不读这个集合。
- **部署提醒**：真实云端上线前需要在云控制台**新建 `pair_counts` 集合**（本轮不部署、不推送）。
