### 关键取舍（与原建议不同的地方）

**P0-2 没有按原计划砍 `allRows`，改成砍「读比赛流水」。**
读到榜单源码才发现：每行的 elo / 胜 / 负 / 出场数全部来自 `member_ratings`
（Elo 逐场结算后已落库），积分来自 events + 训练事实——**`matches` 只有个人主页的
走势用得到**。所以让 `loadScopeView` 支持 `needMatches: false`，榜单与成绩直接不读
这个只增不减的最大集合，数字一个都不变、协议形状也不动。
`allRows` 保留是产品取舍：它是「搜索前十之外的人」的唯一数据源，砍掉等于让搜索
退化成只能搜前十，而传输量并不是当前瓶颈（真正的问题是那 7 次整表读）。

**P1-6 没有做「身份上下文缓存」。**
10 秒 TTL 的上下文缓存能让轮询每拍从 6 读降到 0 读，但它引入「撤权后 10 秒内仍
可读」的窗口。写路径仍在事务内 `fresh*Context` 重判，所以只是读侧延迟——不过
这类"用安全换性能"的决定应当由你拍板，代码里没有擅自加上。本轮先做零风险的两件：
批读（5 轮 RTT → 1 轮）与空闲降频（无 live 时 2 秒 → 8 秒）。

**P2-8 改完又撤回：这条原本判断过重。**
先按"仅管理者可见 realName"改了一版，结果 `page.test.js` 里「用真实姓名也能搜到同一个人」
直接失败——那是真实的学生使用场景（找队友、核对成绩）。回头看风险本身：
榜单行只包含**出场过比赛的参赛者**（`buildRows` 过滤 `matchCount > 0`），本来就在
赛事公示名单里，不属于超范围收集；`realName` 也从不渲染，只做搜索键。
所以恢复原样，改为在注释里写清这个边界。
**仍然值得收紧的是另外两处**：`listSchoolMembers` 与 `getSchoolMembers` 会把
**全体在册会员**（含从未参赛者）的 `realName` 下发给每个在册会员。那是产品决策
（报名选人、审核要用），不是代码问题——要不要改由你定。

**P2-9 有意不改。**
`assertEligibleMembers` 的 60 次点读确实逼近事务预算，但它是**事务内**的资格重判：
移到事务外就等于校验完到写入之间出现 TOCTOU 窗口（人被移出学校后仍被加进组）。
项目的一致性纪律是「权限必须在写入的同一事务里再判一次」，这条不能为性能让步。
真要扩容，方向是把「30 人上限」改成「分批提交」，而不是放松事务内校验。

### 限流的第二层：收窄匿名面（同日补）

限流只能按 OPENID 计数，而匿名流量没有身份可分——所有匿名请求共享同一个桶。
只把额度调低解决不了问题（攻击者换个来源继续打），所以补了一层入口拦截：
`school-request.js` 的 `ANON_ACTIONS` 只放行两个公开动作（`getSchoolDirectory`
选校/选院目录、`getSchoolIdentitySession` 未登录时的 guest 会话，登录页启动就要用），
其余未登录请求直接返回「请先登录后再使用」，不再白读「学校 + 协会」两条记录。

配合匿名桶 3 读/秒，匿名流量的读消耗被压到可忽略；攻击面从 100+ 动作缩到 2 个。
新增公开接口必须来这张白名单登记，默认要求登录——这条已用测试钉住
（`school-membership.test.js` 末尾的「未登录只放行两个公开动作」）。

## 结论摘要

整体工程质量高于同类项目：注册面是显式白名单（`school-actions.js` + `pickActions`），写操作在事务内重判权限（112 处 `fresh*Context`），客户端不直连数据库（全走云函数），仓库内无硬编码凭据。**安全问题集中在"数据最小化"而非"越权"，性能问题集中在"读放大"而非"算法复杂度"。**

真正会先出事的不是某段代码写错了，而是**读放大**：一个榜单页请求要打 20+ 次数据库 RPC，其中还把**全平台所有学校**的用户表拉进内存。用户量一上来，先撞的是 3 秒级响应墙和每日读配额，不是业务逻辑。

## P0-1　8 处 `users.list()` 跨校全表读，单请求 RPC 放大到 20+

**位置**

- `cloudfunctions/data/src/school-repository.js:126` —— `list: () => io.query(key, {})`
- `cloudfunctions/data/src/adapters/cloud-repo.js:117-136` —— `readAll` 无 where 条件，100 条/页全翻
- 调用点（8 处）：`lib/services/school-actor.js:64`、`school-actor.js:115`、`school-member-service.js:67`、`school-rank-service.js:133`、`association-group-service.js:136`、`association-member-service.js:42`、`association-training-service.js:349`、`association-training-service.js:395`、`exchange-service.js:667`

**原因**

`users` 是**平台级**集合（账号跟着微信 OpenID 走，不含 `schoolId`），所以 `attachSchoolRepository` 给它的 `list()` 是 `io.query(key, {})`——**空 where**。落到 `readAll` 就是"把这个集合整个翻一遍"。

于是每一次要"给一批 userId 补昵称/头像"的地方，实际做的是"把全平台所有学校的账号都读进内存再建 Map"。注释里写的"一次取齐本校账号建索引"（`school-member-service.js:64-65`）与代码实际行为不符：**取的是全平台，不是本校**。

一次典型请求的实际 RPC 数（以 `getTeamEvent` 为例，200 条报名、1000 名平台用户计）：

| 阶段 | RPC |
|---|---|
| `buildSchoolContext`（学校/协会/账号/学籍/角色/membership） | 6 |
| `teamEvents.getById` | 1 |
| `teamEventEntries.list()` 分页 | 2 |
| `teams.list()` 分页 | 2 |
| `buildDirectory` → schoolMembers + colleges + **users(全平台 10 页)** | 13 |
| **合计** | **≈ 24** |

**影响**

- 响应时间随**平台总用户数**线性增长（不是本校人数），跨校越多越慢。
- 云开发每日读配额 5 万次，一次榜单/详情页就吃掉 20+，三四百次访问即见底。
- `config.json` 的 `timeout: 20` 秒兜底，但 1000+ 用户 × 多集合分页后，接近超时只是时间问题。

**改进建议**

1. 给 `users` 补批量点读，替换所有"全表建 Map"：

```js
// src/school-repository.js
repo.users.listByIds = async (ids) => {
  const uniq = [...new Set(ids.filter(Boolean))];
  const out = [];
  for (let i = 0; i < uniq.length; i += 100) {
    const res = await io.query('users', { _id: _.in(uniq.slice(i, i + 100)) });
    out.push(...res);
  }
  return out;
};
```

2. `buildDirectory` 改为先读 `schoolMembers`（有 `schoolId` 索引，已是按校），再 `listByIds(成员 userIds)`——RPC 从"全平台页数"降到"本校成员数 / 100 ≤ 3"。
3. 若要按校查，给 `users` 建 `primarySchoolId` 索引，但**账号可转校**，点读 + 批量仍更稳。

## P0-2　榜单/成绩每次全量装载 7 个集合，全量会员行下发客户端

**位置**

- `lib/services/school-rank-service.js:180-189` —— `loadScopeView` 一次 `Promise.all` 读 6 个集合，加 `loadSeason` 共 7
- `lib/services/school-rank-service.js:130-146` —— `replayMembersOf` 再读 `schoolMembers` + `users`
- `lib/services/school-rank-service.js:318-338` —— `getSchoolRanking` 把 `allRows`（全部会员行）原样返回
- 消费方：`miniprogram/components/rank-panel/rank-panel.js:170`、`events-panel/events-panel.js:162`

**原因**

1. `ctx.repo.forScope(ctx).matches.list()` 取的是**本范围全部历史比赛**，赛季过滤 `match.status === 1 && settlement` 与 `resetTime` 全在应用层做（`:204-212`），没有下推到查询条件。
2. 榜单需要"前 10 + 我的名次"，但 `allRows` 无截断地下发——注释说"不参与渲染"（`events-panel.js:123`），但它确实进了网络包和内存，只为支撑客户端本地搜索。

**影响**

- 榜单页、个人主页、赛事成绩页三个高频入口全部吃这份开销；比赛流水是只增不减的集合，**越用越慢**。

**改进建议**

1. 赛季过滤下推到查询：仓储加 `matches.listRated(schoolId, association, resetTime)`，where 里带 `{ schoolId, association, status: 1, matchTime: _.gte(resetTime) }`，索引已在 README §三 建了 `schoolId+association+status`，把 `matchTime` 补进复合索引。
2. `allRows` 改为服务端搜索：新增 `searchSchoolRanking({ keyword, limit })`，只回匹配行（`limit ≤ 20`）；`getSchoolRanking` 只返回 `rows`(top 10) + `me`。
3. 榜单单次计算量固定后，用 `seasons.version` 做 60 秒容器内快照（`defaultSeason` 已预留 `version` 字段，正好是失效键），避免每次进榜页都重算。

## P0-3　读接口零频率限制，单账号可打爆当日读配额

**位置**

- `cloudfunctions/data/src/core/school-request.js:24-40` —— 分发前只做 `protocolVersion` / `action` / `schoolId` 校验，无任何频次控制
- 对照：`school-live-service.js:184-215` 只控制了"单次批量大小"，不控制"请求次数"

**原因**

读接口的门槛是 `canReadAssociationSpace(ctx)`——**任何在册会员即通过**。而 `getSchoolRanking` 这类接口一次就是 7 个集合全量读（数十 RPC）。攻击成本几乎为零。

**影响**

- 一个在册账号写个循环，几分钟内耗尽**全校**当日 5 万次读配额，全校业务停摆；云开发按量计费，直接产生费用。
- 这是本项目最现实的"低成本 DoS"，比任何注入类风险都更容易发生（学生好奇就能做到）。

**改进建议**

在 `handleSchoolRequest` 入口加持久化滑动窗口计数（云函数无状态，不能放内存）：

```js
// core/rate-limit.js（示意）
const LIMIT = { read: 10, write: 3 };           // 每秒每账号
async function guardRate(repo, actorId, kind, weight = 1) {
  const sec = Math.floor(Date.now() / 1000);
  const id = `rl:${actorId}:${kind}:${sec}`;
  await repo.rateLimits.set(id, { userId: actorId, kind, sec, n: weight }); // 事务 + inc
}
```

要点：`_id` 用「账号 + 秒」保证同窗口内冲突；`db.command.inc` 累加；超阈值返回 `{ ok:false, message:'操作过于频繁' }`。重接口（榜单/详情）单独设更低阈值。同时给 `rate_limits` 集合加 TTL 清理任务。

## P1-4　`skip` 深翻页：成本 O(offset)，并发写入会重读/漏读

**位置**

- `src/adapters/cloud-repo.js:117-136`（`readAll`）、`:185-203`（`readWhere`）

**原因**

`skip(offset)` 在 MongoDB/云开发语义里是"排序后扫描并丢弃前 offset 条"。两个后果：

1. **性能**：第 10 页要扫 900 条丢 900 条，成本随页数线性上升，不是常数。
2. **正确性**：翻页期间若有新文档插入到游标之前，第 2 页会与第 1 页**重叠**（同一条被读两次）；插入到之后则可能**漏读**。注释 `:107-111` 已意识到排序不确定的问题并用 `orderBy('_id')` 修了"顺序"，但 `skip` 本身的偏移漂移没修——`orderBy` 只能保证顺序稳定，不能保证"翻页窗口"稳定。

**影响**

- 集合超过 500 条后，每次整表读的墙钟时间明显上升（`DEEP_READ_WARN` 只是告警，没解决）。
- 并发确认比赛时可能重复计算或漏算等级分——这正是注释里"等级分少算一场，且查不出原因"的场景。

**改进建议**

改游标分页，偏移漂移问题与成本问题一起消失：

```js
async function readWhere(scope, name, where) {
  const out = [];
  let lastId = null;
  for (;;) {
    const cond = lastId ? { ...where, _id: _.gt(lastId) } : where;
    const res = await scope.collection(name).where(cond)
      .orderBy('_id', 'asc').limit(PAGE_SIZE).get();
    const batch = res.data || [];
    out.push(...batch);
    if (batch.length < PAGE_SIZE) break;
    lastId = batch[batch.length - 1]._id;
  }
  return out;
}
```

## P1-5　团队运动服务整表读后内存过滤（查询未下推）

**位置**

- `lib/services/team-event-service.js:269`（`teamEventEntries.list()`）、`:337`、`:363`（`teamMatches.list()`）、`:378`（`teamMatchStats.list()`）、`:1236`、`:974`
- 根因：`src/school-repository.js:26` —— `EVENT_SCOPED` 白名单只有 `['matches','eventSignups','collegeEntries','ties','lineups']`

**原因**

`teamEventEntries` / `teamMatches` / `teamMatchStats` 三个集合都有 `eventId` 字段，但没进 `EVENT_SCOPED`，所以 `forScope` 不生成 `listByEvent`。业务只能 `list()` 全量读后 `.filter(row => row.eventId === event._id)`。

**影响**

一个杯赛 60 场、一年 3 届 → 180 条 match + 数百条 stat，全部读入只为筛出 60 条；`getTeamEvent`（详情页高频）每次都这样。历史累积后与 P0-2 同性质。

**改进建议**

```js
// src/school-repository.js:26
const EVENT_SCOPED = ['matches', 'eventSignups', 'collegeEntries', 'ties', 'lineups',
  'teamEventEntries', 'teamMatches', 'teamMatchStats'];
```

同时在 `school-memory-repo.js` 补同名 `listByEvent`（`tests/for-scope-contract.test.js` 会守住两端一致），业务改调 `repo.teamMatches.listByEvent(event._id)`。

## P1-6　实时比分 2 秒轮询，每拍 6 次身份读

**位置**

- `miniprogram/services/live-watch.js:34` —— `POLL_INTERVAL = 2000`
- `lib/services/school-live-service.js:184-215` —— `getSchoolLiveScores` 每拍都完整走 `buildSchoolContext`
- `lib/services/school-context.js:9-23` —— 每次 2 轮并发、共 6 次点读

**原因**

轮询每 2 秒触发一次，每次请求都重新解析"学校 / 协会 / 账号 / 学籍 / 校级角色 / membership"这 6 条**在秒级内根本不会变**的数据。看 10 场比赛时，每拍 16 次读、每分钟 480 次。

**影响**

- 单个观众看 1 小时 ≈ 2.9 万次读，**5 万/天配额 1.7 小时见底**；10 人同时看，10 分钟见底。
- `LIVE_READ_BATCH = 10` 只压了并发度，没压总量。

**改进建议**

1. 轮询走轻量鉴权：只校验"账号有效 + 本校在册"两项（2 读），跳过协会/membership/role（这些只在计分写路径才需要）。
2. 容器内对 `(openId)` 做 10 秒 TTL 的上下文缓存，撤权延迟上限 10 秒可接受（写路径仍在事务内 `fresh*Context` 重判，不受影响）。
3. 间隔自适应：全部比赛 `status !== 'live'` 时降到 10 秒；有比赛在打用 3–5 秒。`live-watch.js` 已是唯一轮询出口，改这一处即可。
4. `getSchoolLiveScores` 用一次 `where({_id: _.in(ids)})` 取完（≤50 条，一次 RPC），替代 N 次点读。

## P2-8　`realName` 无差别下发全校客户端

**位置**

- `lib/services/school-rank-service.js:247、255` —— 榜单行携带 `realName`，注释写"只参与搜索，不渲染"
- `lib/services/school-member-service.js:39` —— `memberRow` 下发 `realName`
- `lib/services/association-group-service.js:154` —— 组名单下发 `realName`

**原因**

`realName` 是真实姓名。三个接口的门槛都只是"在册会员"，且 `getSchoolRanking` 还把全量会员行（含 realName）一次性下发（见 P0-2）。"不渲染"不等于"不下发"——抓包即得。

**影响**

任何在册会员可获取全校参赛者 `userId ↔ 真实姓名` 完整映射。按《个人信息保护法》最小必要原则，这属于超出收集目的的分发；一旦被导出传播，属于真实的数据泄露事件，不是理论风险。

**改进建议**

1. 普通会员：只下发 `nickName` + `avatarText`，`realName` 字段直接删掉。
2. 需要按真实姓名搜索时，走服务端接口 `searchSchoolRanking({ keyword })`，服务端匹配后只回命中行（同时解决 P0-2 的传输量问题）。
3. 管理角色（`canManageAssociationSpace` / `canSchoolAction('reviewMembers')`）才下发 `realName`。

## P2-9　事务内按人循环点读，逼近 100 操作预算

**位置**

- `lib/services/association-group-service.js:96-109` —— `assertEligibleMembers` 每人 2 次 `getById`
- `association-group-service.js:276` —— `for (const userId of members.ids) await tx...set(...)`
- `exchange-service.js:136-152` —— 按学校数循环读 2 次 + 写 1 次

**原因**

`MAX_MEMBERS_PER_WRITE = 30`（`:47`），30 人 = 60 读 + 31 写 = 91 次操作，`TX_OPERATION_BUDGET = 100`（`cloud-repo.js:33`）。**只差 9 次就撞墙**。`instrumentTransaction` 会抛"事务读写总操作预算不足"，用户看到的是失败。

**影响**

上限从 30 调到 50（产品很容易这么改）就必然超限；现在也几乎没有余量容纳一次额外读。

**改进建议**

资格校验移出事务：事务外批量读 `schoolMembers.listByScope` + `users.listByIds(memberIds)` 建 Map 校验，事务内只保留"重判权限 + 写"，操作数从 91 降到 ~33。

## P2-10　`memberIds` 等入参无长度上限，直通 `_id`

**位置**

- `lib/services/association-group-service.js:79-89` —— `normalizeMemberIds` 只判 `typeof id === 'string' && id`
- `lib/utils/school.js:28-33` —— `schoolKey` 用 `encodeURIComponent` 后拼 `_id`

**原因**

只限制了**条数**（30），没限制**单条长度**。id 一路进入 `associationGroupMemberKey` → `_id`。`encodeURIComponent` 对非 ASCII 还会膨胀 3 倍。

**影响**

单条 1 MB 的 id → `_id` 约 3 MB，写入报错或占用异常存储；30 条可构造 ~90 MB 请求体，配合 P0-3 的零限流，可直接当作资源耗尽手段。

**改进建议**

```js
const ID_PATTERN = /^[A-Za-z0-9_-]{1,64}$/;
if (!ID_PATTERN.test(id)) return { ok: false, message: '成员编号无效' };
```

与 `GROUP_ID_PATTERN` 保持同一口径，同时给 `payload.groupId`、`payload.eventId`、`payload.matchId` 等所有进入 `schoolKey` 的字段补同样校验。

## P2-11　`stripForStorage` 每次写入全量深拷贝

**位置**

- `src/adapters/cloud-repo.js:157-176`，被 `withoutId`（所有写）与事务读缓存（`:441`）调用

**原因**

对任意文档递归重建对象与数组。事务里"读一次、改一处、整条 `set` 回去"的模式很常见（如 `finishSchoolLiveScore` 写整条 match），每次都要把大文档完整复制一遍。

**影响**

单次几毫秒，批量结算（几十场）时是纯 CPU 开销，占用云函数执行时间；`team_event` 这类带 `rules/entries/roster` 的大文档尤其明显。

**建议**

只在值确实含 `Date` 或 `undefined` 时才拷贝：

```js
function needsNormalize(v) { /* 浅层探测：Date 实例 / undefined 值/数组元素 */ }
function withoutId(doc) {
  const copy = needsNormalize(doc) ? stripForStorage(doc) : { ...doc };
  delete copy._id;
  return copy;
}
```

## P2-12　轮询失败无退避，故障期形成重试风暴

**位置**

- `miniprogram/services/live-watch.js:106-112` —— `catch` 里 `return undefined`，下一拍仍按 2 秒重试

**原因**

失败后不区分原因、不降低频率。云函数故障或限流时，**所有在线客户端保持同一 2 秒节奏持续打**，故障恢复期被打得更久。

**影响**

故障从"几秒"延长到"几十秒"；限流阈值被持续顶满，恢复变慢。

**改进建议**

```js
target.failStreak = (target.failStreak || 0) + 1;
const backoff = Math.min(2000 * Math.pow(2, target.failStreak), 30000);
// 成功时 target.failStreak = 0，并按 POLL_INTERVAL 复位节奏
```

## 已核查、确认无问题的点

避免误伤，以下项逐条看过，**未发现问题**：

- **越权**：写操作在事务内用 `freshContext` / `freshMeetContext` 重判权限（112 处），撤权即时生效；跨校写入由 `forScope` 的 `expected` 字段在写入前校验（`school-repository.js:70-75`）。
- **动作暴露面**：四个注册表都走 `pickActions` 白名单，内部辅助函数不会变成 action（`school-request.js:26` 用 `hasOwnProperty` 判存在，`__proto__` 之类的键进不来）。
- **客户端直连数据库**：全仓 `miniprogram/` 下无 `wx.cloud.database()`，数据面只有一个入口，权限规则集中。
- **硬编码凭据**：扫描无命中；`config.js` 的 `CLOUD_ENV_ID` 是空占位，符合预期。
- **凭据/密钥泄露**：`tools/` 下 Python/Node 脚本无硬编码 appid/secret/token。
- **定时器泄漏**：`setInterval` 仅出现在 `live-watch.js` 一处，`clearTimer` / `pause` / `stopped` / `inFlight` 齐备，页面 `onHide`/`onUnload` 有对应出口。
- **并发判球**：`recordSchoolRally` 事务内重读 + `rallyId` 幂等，重复提交不会多计一球。
- **单集合记录数**：实时比分、评级、赛季计数都用确定性复合 `_id` 单条点读，O(1)，无隐患。

## 一句话结论

**先修 P0-1（`users.list()` 跨校全表读）和 P0-3（限流）**——这两条是"一个好奇的学生就能把全校系统打瘫"的组合，且改造成本最低（半天 + 一天）。P0-2 的榜单改造次之。安全侧没有越权漏洞，唯一需要产品拍板的是"真实姓名给谁看"。
