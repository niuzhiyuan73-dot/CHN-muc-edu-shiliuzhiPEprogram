## 三 关键口径

1. **团队轮询：3 次读是上限，不是「大约」。** 比赛/赛事/球队各一次 `_.in`，其中球队那一批在「管理员」或「本场记录员」的情况下根本不发——这两个身份在判队长之前就返回了。用例把「0 次 `getById`、总计 ≤3 次读」钉死，任何人想退回逐场点读都会红。
2. **跨校名册不设条数上限。** 裁判候选是「参赛校的在册会员」，逐校翻到底而不是取前 N 条：这是管理员挑人用的全量候选，截断会让某些人永远选不到。成本已按校收窄（每 200 人 1 页），极端情况由 `MAX_READ_ROWS` 兜底。
3. **E 只完成了一半，必须说清楚。** 账号与意向已批读，**学籍仍是每人一次点读**：运动会上下文没有 `association`，`forScope` 进不去（`schoolScope` 要求学校 + 协会），而顶层 `schoolMembers` 只有按校整表读的 `listBySchool`。缺的是「学校级、按编号批读」的入口，补它要动仓储分层，归到 B 批一起做。当前每次提交的读次数为 `N + 2`（N ≤ 20），原为 `3N`。
4. **`listByProject` 的第三个使用者。** 原本只挂在 `sportsMeetEntries` / `sportsMeetSessions` 上；意向文档同样带 `eventKey`（`meet-registration-service` 写 `submitMeetInterest` 时落的），所以直接复用同一个原语，不新增概念。

## 四 踩坑与纠正

1. **E 的第一版用了 `ctx.repo.forScope(ctx)`，27 个运动会用例一次全红。** 报错是「必须提供有效的 association」——运动会上下文按设计就不带协会（见 `meet-context.js` 文件头：带上协会等于把运动会挂到匹克球上）。改成 `forMeet(scope)` 取意向、学籍退回点读。**这条也是 §三.3 那个「只完成一半」的由来**。
2. **C 的第一版回归用例用「把 `schoolMembers.list` 换成抛错」来钉，用例自己炸了。** 内存 mock 的 `listByStatus` 内部就是 `repo[key].list()` 再过滤，而云端是真正的条件查询——同一个方法名在两端的**实现方式**不同，这种「抛错探针」只在云端同构时成立。改成「记录 `forScope` 打开过哪些学校」，这个断言对两种实现都成立，而且正好是「不许跨校读」这条底线本身。
3. **A 不需要改客户端。** `live-watch` 的指纹只比 `matchId` 与比分字段，本批没有改返回的字段集合，页面一行未动。
4. **`canRecordTeamMatch` 保留未删。** 它还有单场调用的地方（录分页的入口判定）；本批只在轮询里换成「预取球队 + 本地判队长」，两者口径一致（管理员 → 记录员 → 队长）。
