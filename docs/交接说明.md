## 一、这个项目是什么

给校内**六个体育协会**（匹克球 `pkb`、乒乓 `tt`、羽球 `bd`、网球 `tn`、篮球 `bk`、足球 `fb`）共用的等级分与赛事系统，覆盖三层业务：

1. **协会级**：个人赛、排行榜、协会空间（分组 / 通知 / 训练）。
2. **校级活动**：石榴籽杯（学院团体赛）、运动会、跨校邀请赛。
3. **个人**：注册入会、报名、录分确认、成绩与荣誉。

核心是一本**可核验的等级分账本**：比赛流水是唯一事实来源，但分数**不是**每次读时重算——确认比分时在同一个事务里逐场结算，结果写入 `member_ratings`，结算顺序由 `rating_counters` 的序号决定。这让「谁在第几场之后多少分」是确定的、可审计的。

## 二、分层与不可破坏的约定

```
pages / components  →  services（视图模型 + 数据源门面）  →  utils（纯函数）
                                    │
                    tools/sync-cloud-lib.js（逐字节镜像）
                                    ▼
                        cloudfunctions/data/lib/（97 文件）
```

**约定 1：纯函数不碰 wx、不碰 I/O。** `utils/interface-view.js` 以及个人体育中心两个服务模块进入云端镜像；客户端交互装饰器放在 `templates/`，不进入纯模块镜像。当前 3244 条用例仍在 Node 中验证。

**约定 2：镜像必须同步。** 云端不能 `require` 目录外的文件，所以 `tools/sync-cloud-lib.js` 把纯模块复制进 `cloudfunctions/data/lib/`，`tests/cloud-lib-sync.test.js` 逐字节守着。改了源文件忘了同步，测试立刻红。

**约定 3：只有一个云函数。** 权限、身份解析、错误信封只写一份。新增接口 = 在 `cloudfunctions/data/src/core/school-*-handlers.js` 加一个 handler，同时在 `services/school-cloud.js` 登记。

**约定 4：业务失败包在顶层 `ok:true` 里。** 只有基础设施故障才返回顶层 `ok:false`。前端据此区分「拿到失败对象」与「抛异常」，两条数据源才不会分叉。四组处理器统一由 `src/core/school-request.js` 的 `acceptResult` 收口（2026-10-28 第十轮审计 P1：运动会组此前直接回顶层 `ok:false`）。客户端例外一处：运动会门面 `forMeet` 仍把业务拒绝抛成异常（6 个运动会页面按 catch 写的，改成值返回会静默吞掉提示），见 `services/school-cloud.js` 的 `throwOnRefused`。

**约定 5：请求必须带协议版本。** `{ protocolVersion: 2, schoolId, association, action, payload }`；旧协议已完全下线。

**约定 6：演示身份不要乱改。** 演示账号由 `school-seed.js` / `school-mock.js` 维护，页面与协议测试依赖其身份关系；不要把它当真实账号配置。

## 三、数据模型速览

| 层 | 集合 | 一句话 |
|---|---|---|
| 平台账号 | `users` | 一个微信号一条，`openId` 唯一 |
| 学校会籍 | `school_members` | 「某人在某校」的状态与学院 |
| 校级角色 | `school_roles` | 校级管理员 |
| 协会角色 | `memberships` | `staff` 学院负责人 / `leader` 协会负责人 |
| 学校 × 协会 | `school_associations` | 该校是否启用该协会 |

比赛与分数：`matches`（流水，含个人赛、学院赛小场、日常约球）→ 确认时结算 → `member_ratings`（当前评级）+ `rating_counters`（序号）。赛事积分与训练积分是独立聚合，不进评级表。

其余按域分包：`events` / `event_signups`（个人赛）、`college_events` / `college_entries` / `ties` / `lineups`（石榴籽杯）、`live_scores`（实时台）、`association_*` / `training_registrations`（协会空间）、`exchange_*`（跨校）、15 个 `sports_meet_*`（运动会）。

完整 52 张表与字段见 [云开发控制台操作指南](云开发控制台操作指南.md) 第三节。

## 四、计分口径（改代码前必须知道）

| 项 | 值 | 出处 |
|---|---|---|
| 起评分 | 男 1450 / 女 1300 | `utils/elo.js` |
| 定级 | 前 5 场按对手水平定，向下取 50 倍数 | `utils/elo.js` |
| 日常 K | 16（全员统一，不再分段） | `utils/elo.js` |
| 赛事 K | 一级 32 / 二级 24 / 三级 16 | `utils/elo.js` |
| 不计分 | 双打、弃权、跨校邀请赛、运动会 | `school-rating-service` |
| 防刷 | 一对会员每赛季 15 场日常约球 | `constants.RATED_PAIR_LIMIT` |
| 赛事积分 | 参与 2 + 名次档（20/14/10/7/4）× 等级倍数（×4/×2/×1） | `utils/points.js` |
| 网球 | 分 → 局 → 盘；一局 4 分、一盘 6 局（或 4 局短盘）、6:6 抢七 | `utils/match-format.js` |

学院负责人的管理范围只取 `memberships.collegeId`，与 `school_members.collegeId` 的学籍归属分开。学院名单、排阵在事务内用当前身份和目标学院复核。实时计分四类写操作及赛季重置也在事务内重读身份；抽签逐场重读版本与结算状态，拒绝覆盖已确认比赛。

个人赛事当前上限为单打 88 人、双打 176 人，名额填 0 也受此限制；发布、报名和抽签三处共用容量限制，抽签另校验实际操作预算。历史超限赛事需调整报名名单后再抽签。会员全量选人接口保留，但先在数据库筛状态、学院，再补账号；跨校裁判改为独立的管理接口 `listExchangeRefereeCandidates`，按已接受邀请的学校搜索分页。

界面使用同一容量模块 `utils/event-capacity.js`；切换单打/双打即时更新名额提示，超额标记名额字段。学院报名默认从赛事下发的 `submittableCollegeIds` 选择，学籍学院只在获授权时作为默认项；授权面板单独选择管理学院，会话和名册分别返回 `managedCollegeId` 与学籍 `collegeId`。

转校待办由会员审核页识别并调用 `reviewSchoolTransfer`。两处审核入口若待办超过服务端当前批次，会明确提示还有更多申请，处理后刷新继续。跨校发起表单支持 2–8 校及各校独立配额。公告服务端以置顶、时间、编号倒序分页，返回 `total / hasMore / nextCursor`，公开页与台账保留相同游标顺序；台账状态计数只指已加载记录。运动会筛选、公告续页均使旧请求失效。首页团队赛事通过 `listTeamEvents({home:true})` 取限量摘要与计数，不读取全量报名和比赛。

**已确认生效的比赛不可撤销**——这是刻意的产品决定，不是缺口。撤销链（`revokeSchoolMatch`）在 Elo 逐场结算改造时整体删除，改判只能在「待确认」阶段驳回。

## 五、怎么验证

```bash
npm test                  # 全量（3080 条）
npm run test:py           # 导入工具的 Python 契约
npm run check:cloud-sync  # 镜像是否漂移
node tools/acceptance-audit.cjs   # 验收探针
```

测试分三层：纯函数（算法、校验、赛制）、服务层（内存仓储 S2）、页面装配（`tests/page.test.js` 直接把页面配置喂给假 wx 运行）。

**没有覆盖的**：真实云数据库事务、真机渲染、微信登录态、文件存储。

## 六、部署（三步）

1. `miniprogram/config.js` 填 `CLOUD_ENV_ID`。
2. 按云控制台指南建 52 个集合（权限「所有用户不可读写」）。
3. `npm run sync:cloud` → 上传部署 `cloudfunctions/data` → 建学校与协会 → 提第一个校级管理员。

第九轮部署增加 5 条查询索引，见[索引清单 §2.5](数据库索引清单.md#25-第九轮查询索引2026-10-28)。先等待索引可用，再重新部署 `data` 并上传小程序。裁判候选使用已存在的账号目录派生字段，旧环境仍须先完成目录回填；本批没有新增数据迁移。

第十轮的 §2.6 五条索引仍须在目标环境核对。F01–F17 已提交 `581104f`，学院选人复用既有目录索引。个人体育中心新增 `personal-sports-query.js`、`personal-sports-service.js`，共 96 个镜像文件；新增只读 action `getMySportsDashboard`，无新集合或回填。按 §2.7 新增 13 条关系/管理范围索引并核对六类关联外键索引，再同步镜像、重新部署 `data`、上传小程序。三份 docx 从 md 重建，当前环境缺少可用渲染器，版式待补验。

个人体育中心按用户授权完成验收后提交。首页提供下一场与三条待办，“我的”增加护照入口；个人/学院比赛、团队赛和运动会按本人关系及当前权限聚合。护照区分确认比分、已发布名次、名单入选和报告收录，名单不推定实际出场，不生成成长值。个人比赛复用现有面板单场模式，写接口继续事务内鉴权。新增 34 条回归；11 个源码代表界面已核对三种宽度及字体放大，原生字体、键盘、刘海、包体与真实云端性能仍待验证。细节见[个人体育中心说明](个人体育中心-使用与实现说明.md)。
