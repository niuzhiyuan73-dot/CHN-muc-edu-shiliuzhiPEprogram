## 一、这个项目是什么

一个微信小程序（原生 WXML/WXSS/JS，没有用任何框架），给校内各体育协会的会员算等级分、排名次、办赛事。核心是一套 ELO 等级分：**比赛流水是唯一的事实来源，会员的分数由「按时间回放全部比赛」推导出来**，分数本身从不落库。

分层：`miniprogram/utils/`（纯函数，不碰微信 API）→ `miniprogram/services/`（数据源门面 + 视图模型）→ `miniprogram/pages/`、`templates/`（界面）。

这样分层的意义：

1. 算法层能直接在 Node 里跑单元测试，不必开微信开发者工具；
2. 同一份算法能被云函数复用——`tools/sync-cloud-lib.js` 把 `utils|services` 下的**纯模块逐字节复制**到 `cloudfunctions/data/lib/`，不会出现「两处实现不一致」。

数据源可一行切换：`services/index.js` 的当前数据源（默认 `MOCK`）与 `cloud.js` 必须导出**完全相同的函数名与参数形态**。页面上会显示「模拟数据」标注。

目前共 **26 个页面**：5 个 tabBar 页（首页 / 排行榜 / 比赛 / 赛事 / 我的）+ 21 个功能页。

### 多协会（一个平台承载多个体育协会，2026-10）

小程序已从「单一匹克球俱乐部」升级为「一个平台承载校内多个体育协会」。要点：

- **协会采用代码注册表**（`utils/associations.js`），首批 `pkb` 匹克球 / `tt` 乒乓 / `bd` 羽球，**按 N 个设计**——新增协会只动注册表一处，不改业务逻辑、不改数据库、不改云端接口。协会不进数据库，不做后台自助增删。
- **账号全局一份**（以 OpenID 唯一）：注册一次即自动属于全部协会（含未来新增），实名信息全局共用。协会角色（协会负责人 / 学院负责人）另存 `memberships` 集合：`leader` 在本协会内等同管理员，`staff` 在本协会内按学院生效。
- **内容数据按协会隔离**：比赛 / 赛事与报名 / 公告 / 学院赛（大场·名单·排阵）/ 实时比分 / 赛季 / 排行榜，每条带 `association` 字段，读过滤、写盖章；**积分与等级分各协会独立**；学院名单三个协会共用一份。
- **角色分层**：会员 < 学院负责人 < 协会负责人 < 管理员。协会负责人由**全局管理员**任免、可一人负责多个协会；学院负责人由**本协会的协会负责人或管理员**任免。
- **界面**：首次进入选择协会；首页与「我的」提供切换入口，只切换中间三个界面（排行榜 / 比赛 / 赛事）的数据范围。默认取「**该用户比赛最多的协会**」、**不记忆**上次选择（见 `docs/石榴籽体育管理小程序-需求整理.md` §十一）。
- **分期**：P0 地基、P1 数据隔离开（内核）、P2 处理器隔离、P3 客户端门面与 mock、P4 界面与品牌**均已完成**；P5 规则参数化、P6 迁移与上线待做。计划见 `docs/石榴籽体育管理小程序-施工方案.md`。

## 四、P1：赛事闭环与赛季积分（已完成）

提交：`7edd6f8`（赛季管理 / 赛季积分榜 / 资料编辑）、`4ad3d12`（赛事闭环）、`039e7f8`（赛季编号修复）。

### 4.1 赛事状态机与闭环

- 状态：`EVENT_STATUS`＝报名中 `0` / 进行中 `1` / 已结束 `2`（**「已结束」必须仍取值 2**，否则种子数据全废）。
- 流程：管理员**发布赛事**（必选等级与三四名赛方式）→ 会员**报名 / 取消** → 管理端**代签** → 管理端**录入名次** → **结束赛事**（手动触发，不自动结束）。
- 签到只有管理端代签（决策 4），会员不能自助签到。
- 抽签后该赛事的报名随之冻结（见第五节）。

### 4.2 赛季积分（只来自赛事）

- 积分**只来自赛事**：日常约球不再产生任何积分，只影响等级分（决策 9）。
- 单次赛事积分 = **参与分 2 分 + 名次分**；同一赛事打多轮只按最终名次计一次，不逐轮累加（2.5）。
- 名次分基础分：冠军 20 / 亚军 14 / 季军 10 / 第四 7 / 八强 4 / 未进八强 0；再乘等级倍数 **一级 ×4、二级 ×2、三级 ×1**。
- 名次 → 档位：1 冠军 / 2 亚军 / 3 季军（「并列」模式下两名半决赛负者都取此档）/ 4 第四（仅「打三四名」模式）/ 5–8 八强 / ≥9 未进八强。
- **双打赛事不计分**（决策 3）。
- 赛季积分**每赛季清零**；赛事成绩（哪场、什么等级、第几名、多少分）**永久保存**，离校后仍可查看。

### 4.3 赛事比赛的等级分（elo）

- 赛事比赛 K 值**按等级固定**：一级 32 / 二级 24 / 三级 16，与选手的场次、分数无关。
- 日常约球不再分档：**全员统一 K = 16**，没有「前几场用大 K」的定级期，也没有高分段降 K。
  因此三级赛事的 K 与日常恰好相同。
- 赛事比赛**仍计入** `matchCount`，也**仍算进前 5 场定级样本**——但它与日常比赛在 K 上已无差别。

### 4.4 开始新赛季（只清积分，不动等级分）

- 赛季文档记一个 `resetTime` 分界点，并把 `seasonNumber` 加一。重放以 `resetTime` 为界切积分。
- **分界只切积分**：`finishedAt` 早于分界点的赛事属于上一个赛季，不计入本赛季（`replay.applyEventPoints`）。
  归属按**结束时刻**判：赛事可能计划开赛时间在分界之前、录入名次却在分界之后（见 `replay.test.js`）。
- **等级分跨赛季连续累计，不做任何压缩**。曾经有过一版 `R′ = R × 0.75 + 1450 × 0.25` 的软重置，
  已移除：它让一个打了三年、稳定在 1800 分的老会员在新赛季第一天被打回 1712 分，而他一场球都没打。
  `startElo`（进步榜的起点快照）同样不刷新，只在会员首次入池时写一次。
- 权限：`ROLE.ADMIN`（`services/season.js` 的 `canResetSeason`）。小程序内没有入口，由云控制台触发。

### 4.5 其他 P1 改动

- **赛事 tab**：tabBar 由 4 个变 5 个，新增第 4 个 tab「赛事」（位于「我的」前）。
- **离校状态**：`USER_STATUS.LEFT`；离校后不上榜、不可报名，但个人页与赛事成绩仍可见。
- **赛季编号修复（`039e7f8`）**：赛季编号不再拿缓存版本号顶替，未开始新赛季前恒为第一赛季。

## 五、P2：赛事自动抽签（已完成）

提交：`13d634b`。需求细则见 `docs/P2-赛事自动抽签-需求整理.md`（已冻结）。分五期实现（算法 → 数据层 → 比赛生成 → 界面 → 回归），全部完成。

### 5.1 适用范围

- 最初**仅单打赛事**；后续已把双打与之同步（见 5.8），现在单打、双打都支持抽签。
- 抽签窗口：赛事处于**报名中**。一旦「开始赛事」或已结束，不可抽签、不可重抽。
- 参赛者口径：**未取消的报名者**，不看签到。单打人数 ≥ 2 才可抽签；双打 ≥ 4 且为偶数（两两成队）。
- **抽签后冻结报名**：不再接受新报名 / 取消报名，只能由管理员在开赛前重抽。

### 5.2 创建赛事新增两项（单打 / 双打都要选）

创建时必选：**种子来源**与**种子数量**（2 / 4 / 8，默认 8）。
- 单打：来源为 `manual` 手工指定 / `elo` 按等级分 / `points` 按赛季积分；数量指「位」。
- 双打：来源只有 `manual` / `elo`（双打没有赛季积分，见 `DOUBLES_SEED_MODES`）；数量指种子「组数」，每组两人。
- 双打的种子队由两人组成：`elo` 取两人**双打等级分之和**排序后相邻配对，`manual` 则按管理员点选顺序每两人合成一组（见第十节）。

### 5.3 抽签算法

- 签位规模 `P` = 不小于 N 的最小 2 的幂；轮空数 = `P − N`，**全部给高种子**。
- 落位：`standardSeedOrder(P)` 的输出按「位置 → 实力名次」解释，名次 `1..S` 填种子（按来源排序），`S+1..N` 填洗牌后的非种子，`N+1..P` 为轮空。种子数 0 时退化为纯随机。
- `standardSeedOrder` 已从 `seed.js` **提取到 `utils/bracket.js`**，`seed.js` 反向引用，正式抽签与造数据共用一份。
- 抽签生成随机值 `seedValue` 并随结果落库，任何人可据此复核抽签未被事后改动。

### 5.4 抽签产物与比赛生成

- 赛事记录新增 `draw` 字段：`{ seedMode, seedCount, seedValue, drawnAt, drawnBy, drawCount, size, slots, seeds, byes }`。
- 抽签**立即生成首轮比赛**，比赛带 `eventId`；首轮轮空者不生成比赛。
- **后续轮次逐轮生成**：某一轮全部确认生效后，才排出下一轮。半决赛结束后：`PLAYOFF` 生成三四名决赛；`TIED` 两名半决赛负者并列季军、不额外生成比赛。
- 比赛沿用现有流程：**提交 → 对手确认 → 生效**，赛事生成的比赛初始为「待确认」。

### 5.5 重抽（决策 7 / 9.5）

- **仅管理员、仅开赛前**（报名中）可重抽。
- 重抽作废该赛事此前生成的、**尚未确认**的比赛，再按新随机值重排首轮；`drawCount` 累加，保留历史参数与操作人。
- **只要已有比赛被确认（已计 elo），就禁止重抽**。

### 5.6 展示与录入

- 「比赛」tab 与赛事详情页**两处都能看到并录入**赛事生成的比赛，复用同一套录入与确认逻辑。
- 赛事详情页新增「抽签」卡片（显示抽签摘要与轮空名单）与「签表」卡片（按轮次分组，含录分 / 确认按钮）。
- 报名名单每人后面附**本场池的当前等级分与赛季积分**（`buildSignupRows` 的 `statText`，小字），报名时即可看出对阵双方的实力差。
- 轮次名由 `roundLabelOf(round, totalRounds, stage)` 统一给出（决赛 / 半决赛 / 四分之一决赛 / 第 N 轮）。总轮次优先取 `draw.size` 推出，没有 `draw` 的老赛事退化为该赛事比赛的**最大轮次**（`maxRoundOf`）；轮次或总轮数缺失、非法时一律显示「轮次待定」，**绝不再吐出「第 undefined 轮」**。
- 录入页支持从签表带入：对阵、赛制、时间、场地一律照抄并锁死，只能填比分。

### 5.7 配套修复：先录分再确认

抽签排出的比赛天生没有比分，若此时被「确认」，回放读到空胜方会把整个赛季回放带崩。因此新增 `needsScore(match)` 判定，并在云端与 mock 的 `confirmMatch` 各加一道**胜方守卫**；界面上没比分的场次只给「录分」，录完才给「确认」。

### 5.8 双打与单打同步（后续补做）

P2 收官时双打还只是「不计分、不抽签」，后来把双打与单打拉齐：

- **抽签、种子、赛制全部同步**：双打不再是特殊路径，`planDraw` 按 `matchType` 分流到 `planDoublesEntries`；`canDrawEvent`、`startBlockedReason`（「请先抽签，再开始赛事」）单打双打一致；`buildEventRecord` 也照写 `seedMode` / `seedCount`。
- **双打去掉了「按赛季积分」**：双打没有赛季积分，`DOUBLES_SEED_MODES = [manual, elo]`；切到双打时若原先选了 `points` 会被清掉重选，校验报「双打没有赛季积分，请选择手工指定或按等级分」。
- **双打种子 = 两人一组**：队号是两名成员编号用 `TEAM_ID_SEPARATOR`（`|`）拼起来（`teamIdOf` / `splitTeamId`）。`elo` 取两人**双打等级分之和**排序后相邻配对；`manual` 按管理员点选顺序每两人合成一组，其余按 `seedValue` 洗牌。人数须为偶数且 ≥ 4，否则拒绝抽签。
- **显示改成两人一起看**：`teamTextOf` / `entryTextOf` 把一方两人用「、」连起来；签表、轮空名单、双打积分表（`buildStandings` 按队号统计，任一人是我即整行高亮）、名次页（`buildTeamRows` 一行一支队、带 `userIds`）都按此显示。
- **双打名次按队录、按人落**：名次页一行一支队，提交时把一行的名次摊到 `userIds` 两名成员（两人同名次）；`validatePlacements` 按 `teamSize`（双打 2）判「恰有一组冠军」。

### 5.9 学院赛小项序列：勾选改为逐项添加

原先发布学院赛时「小项」是一组复选框，勾选只是一个集合，**定不了先后**。现改为：默认先摆 1 项（男单），管理员点「＋ 添加小项」逐项增加、每项用下拉在男单 / 女单 / 男双 / 女双 / 混双里选，**行号即出场顺序**。至少 1 项、至多 20 项，同名项目可重复。校验与落库不变（`legPlan` 非空、取值合法）。

### 5.10 场地分配（同轮次不重复用场）

需求只有一句「同一轮次场地不能重复」。它落在 `services/court.js` 这一个纯模块里，**没有新增任何云端 action**。

- **赛事新增 `courtCount`**：发布个人赛 / 学院赛时填「场地数」，取值 `COURT_LIMITS.MIN`–`MAX`（1–20），必填。**填错了不能改**（项目没有赛事编辑接口），只能重发赛事。
- **比赛 / 大场新增 `courtNo`**：落库的只有场号。**批次（第几批开打）不落库**，由展示层按同一个纯函数重算得到。
- **算法**：同一池内按序 `courtNo = (i % N) + 1`、`wave = floor(i / N) + 1`。场地够用时 `wave` 恒为 1，退化成「同轮次完全不重复」；不够时同一批内绝不重复，多出来的排到下一批。
- **「同一轮次」的口径（`poolKeyOf`）**：`main`/`bronze`/`placement`/`gf` 共用一个池（同轮的决赛与季军赛会同时开打，必须共池）；`wb`/`lb` 分开（两区 `round` 各自从 1 计数）；`group` 跨组合并成一个池。阶段缺省按正赛，轮次非数字按 0。
- **必须可重入**：逐轮推进走「只补不覆盖」，同一批比赛会被重算，因此池内排序是**全序**（阶段 → 组 → 轮次 → 签位 → `_id`），且 `_id` 兜底用的是**非 locale 的字符串比较**，结果不随读库顺序或运行环境漂移。
- **学院赛按大场分配**：一个大场占一块场地，名下的多个小项在同一块场地上依次打完，小场的 `courtNo` 全部等于大场的 `courtNo`。开赛后仍可改派裁判，但**场号不随之变**。
- **展示**：签表行、比赛行、大场行、小场页都带 `courtText`（如「2 号场」）；赛事详情页另有「场地分配」卡片，按场号分组列出每块场地上依次要打的比赛。老数据没有 `courtNo` 时显示空串，赛事没有 `courtCount` 时显示「未设置」，都不会渲染出「0 号场」。
- **模拟数据**：种子里七场赛事都带了 `courtCount`，对局场号由同一个 `withCourts` 现算（一处手写都没有）；场地数故意取了不同的值，4 块的是「一人一块」、2 块的要排第二批，两种情形都有样本可看。点开「九月男子单打赛」即见「场地分配」卡片。

> 完整的 12 个设计取舍见 `docs/场地分配-需求整理.md`，施工过程与验证见 `docs/场地分配-实施记录.md`。

## 六、算法与规则口径（以代码为准）

### 6.1 两个分数池，三张榜

池是「计算口径」：单打池 `singles`（男女合并）、双打池 `doubles`（不分男女）。榜是「展示口径」：男单榜、女单榜取同一个单打池的分数按性别过滤，因此男女分数直接可比。排行榜会过滤掉「从未在该池出场」的会员并重新连续编号。

历史说明：编号 2 的「女子单打」比赛类型已废弃，不要复用。

### 6.2 初始分与 K 值

- 初始分：男 **1450**、女 **1300**（`genderInitialGap = 150`）。性别缺失回落到 1450（有意为之，兼容无 `gender` 的老数据与测试假数据）。
- K 值：**日常约球全员统一 16**（`kStandard`），不按场次或分数分档；**赛事比赛**按等级取 32 / 24 / 16（`eventK`，见 4.3）。
- 中途入会者按前五场对手定级；实现上跑两遍回放。
- **管理员指定初始分**：审核通过一位申请时可在面板里选填一个整数等级分（`INITIAL_ELO_MIN`–`INITIAL_ELO_MAX`，即 0–3000）。填了就写进账号的 `initialElo` 字段，回放时**直接以该分起步、跳过前五场定级**（单打 / 双打两池同时生效），并且这个人不再进入定级观测；留空则字段不出现，照旧走自动定级。校验在 `services/member-review.js` 的 `validateInitialElo`，前端与云函数各跑一遍，请求体里的数值不被信任。
- 等级分**没有赛季重置**：`elo` 与 `startElo` 跨赛季连续累计，见 4.4。

### 6.3 积分

`DEFAULT_POINT_CONFIG`：参与分 `eventParticipate = 2`；名次基础分 `{1:20, 2:14, 3:10, 4:7}`，5–8 名共用 4，>8 为 0；再乘 `EVENT_LEVEL_MULTIPLIER`（一级 4 / 二级 2 / 三级 1）。日常比赛不调用任何积分函数。

### 6.4 赛制与成绩校验

每局目标分 11 / 15 / 21；局制一局一胜 / 三局两胜 / 五局三胜；每局「先到目标分且净胜 2 分、不封顶」。胜方由比分**反推**，`winner` 不接受人工指定，因此「记为 A 胜、比分却是 B 赢」不可能出现。

### 6.5 抽签相关常量

`SEED_MODE`（`manual` / `elo` / `points`）、`SEED_COUNTS = [2,4,8]`、`DEFAULT_SEED_COUNT = 8`、`BRACKET_STAGE`（`main` / `bronze`）、`EVENT_BRONZE_MODE`（`tied` / `playoff`）、`EVENT_LEVEL`（1/2/3）、`MATCH_STATUS`（待确认 0 / 已生效 1 / 已撤销 2）。比赛键 `eventMatchKey(eventId, round, stage, slot)` 是确定性的，重抽不会让比赛翻倍。

### 6.6 角色与权限

角色有三档数值（`utils/constants.ROLE`）：普通会员 `0` / 学院负责人 `1` / 管理员 `2`。全局判定只有一处——`services/permission.js`，页面里不写角色判断。多协会版在其上再加一档**协会负责人**：它不是账号字段，而是「某人在某协会」的属性（存 `memberships.role = 'leader'`），解析后**有效角色 = 管理员**（`ROLE.ADMIN`），从而直接复用既有 `canManage` 判定；是否全局管理员另由 `globalRole`（账号原始 `role`）区分，「任免协会负责人」只认 `globalRole`。

**学院负责人不是「小号管理员」，权限以学院为界**（`permission.managesCollege`：管理员全校通行；学院负责人须 `actor.college` 与目标学院**严格相等**）。这一条决定了每条门槛怎么定：

| 事务 | 门槛 | 谁 |
|---|---|---|
| 发布 / 修改 / 抽签 / 开始 / 结束赛事 | `ROLE.ADMIN` | 仅管理员（`event.canManageEvent`） |
| 开始新赛季 | `ROLE.ADMIN` | 仅管理员（`season.canResetSeason`） |
| 学院赛发布 / 抽签 / 开始 / 名单审核 | `ROLE.ADMIN` | 仅管理员（`college-event.canManageCollegeEvent`） |
| 裁判指派 | `ROLE.ADMIN` | 管理员 / 协会负责人（有效角色即管理员） |
| **发布 / 下架公告** | `ROLE.ADMIN` | 仅管理员（`announcement.canPublish`） |
| **审核入会申请** | `ROLE.ADMIN` | 仅管理员（`member-review.canReview`） |
| 代签到 | `ROLE.STAFF` + 本学院 | 管理员或本院学院负责人（`event.canCheckIn`） |
| 学院赛交名单 / 排阵 | `ROLE.STAFF` + 本学院 | 管理员 / 协会负责人 / 本院学院负责人 |
| 录分 / 确认 / 驳回 | 参赛者 / 裁判 / 管理员 | 见 `match-record.js` |
| **撤销已生效的比赛** | `ROLE.ADMIN` | 仅管理员（`match-record.canRevoke`） |

表内 `ROLE.ADMIN` 门槛在**协会内**对协会负责人同样成立——协会负责人解析下来就是有效管理员，所以发布赛事 / 公告、审核、抽签这些「仅管理员」的动作，他在本协会里都能做；「任免协会负责人」是唯一的例外，只认全局管理员。

公告与入会审核为什么收归管理员而不是下放学院负责人：**它们没有学院边界可收**。公告是发给全协会的，不存在「某学院的公告」；入会审核批下来的是会员身份，拿到手就能报名、上榜、算积分，与申请人填的哪个学院无关，台账也是一份全校名单。收不出范围，就只能收归管理员。其余带学院边界的事务（签到、名单、排阵）才交给学院负责人。

撤销为什么单独一档、连录入者都不给：**驳回与撤销是两条路，分量不一样**。驳回（`canConfirm`，界面上与「确认比分」同源）发生在比分**生效之前**，把一条待确认的录入打回去，不涉及任何回滚——日常录错了走这条就够了。撤销（`canRevoke`）是**向后改写已经计入等级分与积分的账本**。早先撤销放给「管理员 + 录入者」，理由是「谁录的谁最清楚」；但录入者不是第三方，他是录分时自己选的（`recorder` 取 A 队第一位），于是场上的一方可以自己录分、再自己撤销，等级分照样回到从前。现在撤销只认管理员。

`permission.canManage(actor, { minRole })` 的默认门槛是 **`ROLE.ADMIN`**（最保守的那一档），且**已无任何调用方依赖默认值**——每个业务函数都显式声明自己那一级。默认值取管理员而不是学院负责人，是因为它只在「调用方忘了声明」时生效：早先默认学院负责人，公告与入会审核两个业务没传 `minRole`，直接吃下默认值，一个学院范围的角色就这样握住了全协会权限（见《界面精简与权限收敛-需求整理》§九）。同样忘一次，默认管理员挡住的是越权，而不是放行。

### 6.7 防刷分：同一对会员每赛季 15 场

实现：`services/rating-cap.js`（纯模块，已上云）；上限常量 `RATED_PAIR_LIMIT = 15`。

日常约球没有门槛，两个人可以一周内互录二十场，赢的那个的等级分就被同一份对阵反复推高——分数反映的不再是水平，而是约球次数。赛事刷不出来（有名次、有赛程、有裁判），所以这条上限只管日常。

| 口径 | 规则 |
|---|---|
| 计数对象 | 一对会员、一个赛季，最多 15 场计入等级分 |
| 什么算「日常」 | 没有 `eventId` / `collegeEventId` / `tieId`（`isCasualMatch`）。三者任一存在即赛事或学院赛，**不设上限，也不占日常名额** |
| 双打怎么算对 | **跨队无序对**：一队两人对对手两人，四组组合各记一场；(甲,乙) 与 (乙,甲) 是同一个人对，不重复计数。同队两人之间不算对——他们没交手 |
| 名额什么时候占 | **提交即占**，包括待确认（PENDING）。只数已生效的话，连录 15 场等对手逐一确认就能绕过；被驳回或撤销（REVOKED）才释放 |
| 赛季怎么切 | 以 `season.resetTime` 为界，之前的场次属于上一个赛季，不占本赛季名额。从未开始过新赛季则全部流水都算本赛季。等级分本身不跨赛季重置，两件事互不影响 |
| 超限之后 | **提交当场被拒**（`checkSubmitAllowed`），比赛根本不入台账，用户立刻知道该换对手。抽签排定的比赛走「按编号补录」那条路，不受这道闸门管 |
| 双打整场拦下 | 四组对里只要有一组满额，整场录不进去。一队的分数变动是四人共用一个 delta，没法只给其中几对记账，也就没有理由让它入账 |
| 界面上看得见 | 录分页选对手的面板里，每个人后面标出「交手 N 场」，满额的标红。数字由 `getSeasonPairCounts` 给出，与提交闸门是同一份算法，不会出现「显示 14 场却被拦下」 |

**两道闸门，各管一段。**

| 层 | 函数 | 管什么 |
|---|---|---|
| 提交时 | `checkSubmitAllowed` | 管**以后**：拦住新录的比赛。落在数据层（`mock.js` / `match-handlers.js`），前端算出来的数字只用于展示，不作数 |
| 回放前 | `findCappedMatchIds` | 管**已经在库里的**：历史成绩导入、控制台直接改库、本规则上线前录下的场次都绕过提交闸门，只能在这里筛掉——它们留在台账里，但不进流水，因而也不进等级分、成绩公示与逐场战绩（与弃权同一路数） |

判定放在数据层（`derive.js` / `mock.js` 的 `activeOnly`），与 `isEloEligibleMatch` 并列，在回放入口之前完成；回放引擎不必知道防刷分这件事。顺序用回放同款的 `compareForReplay`，否则「哪一场是被挤掉的那一场」会随排序抖动。

云端在闸门之前先查一次自然键：**重试必须先于闸门**。上一轮若已经把这场写进去了，名额此刻已经算上它，再拿「名额已满」把重试挡回去，用户会看到失败而库里其实有这条（幂等被破坏），他多半会换个对手再录一次。

**为什么超限干脆不让录，而不是「记录在案但不计分」**：让比赛入账却不计分，会让「这场为什么没加分」变成一个没人解释得清的状态。当场拒掉，用户立刻知道该换对手，而不是事后来问。既有的历史数据没法退回，才由 `findCappedMatchIds` 兜底——那时也只能「记录在案但不计分」，两害相权取轻。

## 九、下一步建议

按优先级排列，前两项是「从小到大真正上线」的关键路径：

1. **云端接入（P0，最大价值）**
   在云开发环境部署 `data` 云函数与集合，把 `index.js` 的数据源切到 `CLOUD`，逐接口联调。重点验证：写操作的事务与幂等（`idempotency.js`）、`bumpSeason` 触发重算、失败契约（业务失败包在 `ok:true` 里）。切完后所有页面应无需改动即可跑通——这是分层设计要兑现的地方。

2. **历史数据导入（P0）**
   用 `tools/import-matches.py` 把现有 Excel 按 `matches` 结构导入；同时确定**赛季首场时间**（写入 `season.anchorTime`，锚点一旦写入即钉死）。导入后要跑一遍 `npm test` 与人工抽查榜单，确认定级结果合理。

3. ~~补上「手工指定种子」的界面（P1，P2 收尾）~~ **已完成**：赛事详情页的抽签卡片已有「指定种子顺序」面板，按顺序点选后把 `manualOrder` 传给 `drawEvent`（双打点的是参赛者，每 2 人合成一组）。

4. ~~**防作弊（P1）**~~
   ~~重复对阵拦截（同一对选手在短时间内重复提交）~~ **已完成**：同一对会员每赛季 15 场，见 6.7。超限当场拦在提交那一步，录分页的选对手面板里每个人后面标出本赛季已交手的场次，满额标红。
   剩下的是**异常提交检测**（分数分布离群：同一天录十几场、比分分布明显不像真打）。

5. **段位 / 徽章（P2，体验）**
   按池内百分位切段位（前 5% 金牌、前 20% 银牌…），或直接显示「超过了 X% 的会员」。个人主页已展示百分位，接上即可。

6. **工程卫生**
   - 每次改完纯模块跑 `npm run sync:cloud`，提交前跑 `npm run check:cloud-sync`。
   - 改任何影响分数 / 积分 / 名次语义的代码，必须把 `cloudfunctions/data/src/core/season.js` 的 `ALGO_VERSION` 加一，否则容器缓存与 `rankings` 快照里的旧分数不会重算。**当前 `ALGO_VERSION = 7`（7 = 加入防刷分上限；调整 `RATED_PAIR_LIMIT` 也要再 +1）。**
   - 需要新云端接口时，记得同步改 5 处（`services/cloud.js`、`mock.js`、`actions.js`、dispatch/handler、测试），`tests/datasource.test.js` 与 `tests/cloud-core.test.js` 会对拍。

## 十、注意事项

1. **这已经是 git 仓库了**（与更早的交接文档相反）。分支 `master`，动手前先看 `git status`；大改动建议单独开分支。
2. **镜像同步**：`miniprogram/utils|services` 下的纯模块会被逐字节复制到 `cloudfunctions/data/lib/`。**`lib/` 下的文件是产物，永远不要手改**，改了会在下次同步时被覆盖且 `tests/cloud-lib-sync.test.js` 会失败。
3. **动作注册表锁步**：新增云端接口必须同步改 5 处，否则 `tests/cloud-core.test.js` 对拍断言失败。
4. **等级分与积分不落库（权威数据）**：一律由 `replaySeason()` 按 `season.version` 重算。`rankings/current` 里那份是**重放结果的落库缓存**（键 = 赛季版本 + 算法版本 + 锚点 + 赛季分界），随时可删、写失败不影响读、体积超限自动退回重放；它不改变「流水是唯一事实来源」。改语义必须动 `ALGO_VERSION`。
5. **`INTERNAL_FIELDS`（`trueSkill`、`joinWeek`）绝对不能进入对外数据**，否则「隐藏真实水平」就白藏了。
6. **权限口径本地与云端已完全一致**：`permission.js` 判定只看角色，`isMock` 传进来也只当普通选项（早期为单账号演示放宽过管理权，现已删除，改为在种子里给 `u01` 管理员 / `u02` 干事两个**真实角色**，见 6.6）。本地要演示管理功能（审核入会、发公告、发布赛事、**撤销已生效的比赛**），把 `mock.js` 的 `DEFAULT_CURRENT_USER_ID` 换成 `u01`（全局管理员）——这些门槛都是 `ROLE.ADMIN`，本地与云端一致。种子里的演示账号与切换办法见 `docs/mock演示账号.md`。确认权仍有 mock 演示口径（见 `demoNotice`），别把它当成真实规则。
7. **`eventId` 是赛事与比赛的唯一关联**：赛事比赛必须有 `eventId`；`getMatches`（公示）只给已生效的比赛，`getMatchRecords`（台账）给全部含待确认 / 已撤销。赛事详情页必须走台账，否则签表为空。
8. **mock 台账按编号去重**：种子里的比赛（`m*` / `x_*`）与本次会话写入的（`lm*` / 抽签覆盖的 `x_*`）在 `mock.buildCache` 里拼接。凡是种子已有、又被现场录分覆盖的场次（演示赛事 e07 的半决赛就属此类），必须让新录的那份**顶替**种子那份，不能两份并存——否则 `findRecord` 的 `.find()` 命中排在前面的空比分版，点确认永远报「还没有比分」，签表还会同场渲染两行。云端因是原地 `update` 同一文档，没有这个问题（`tests/datasource.test.js` 有回归用例）。
9. 改任何算法参数的默认值之后，务必重跑 `npm test`；`tests/page.test.js` 会顺带验证一遍页面链路。
10. 配套文档：本目录另有《开发进展汇总.docx》《项目策划书.docx》《单元测试记录.xlsx》《单打评分实验记录_男1450女1300.xlsx》；需求正本在 `docs/` 下的 P1 / P2 两份 Markdown。
