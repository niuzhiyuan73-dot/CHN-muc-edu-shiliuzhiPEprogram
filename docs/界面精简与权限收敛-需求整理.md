## 一、需求原文

> 我还发现一些问题，比如现在我的界面上面有三个功能，包括审核、发公告、赛季重置，
> 赛事界面也有发比赛的发布功能，但是对于普通会员这些功能完全没用，能不能把它们
> 对于普通会员隐藏起来，只有对应权限的用户才有这几个按钮；然后现在在首页有一个
> 我的分数功能，但是显示为暂时没有比赛记录，这个功能没有必要留着了，把它去掉；
> 然后优化一下首页，把公告放到上面来，近期比赛删掉改成近期赛事；同时把比赛栏
> 里面的全部比赛这个也删掉，让每个人只能看到自己打的比赛和自己待确认的比赛；
> 还有就是优化一下排行榜，把进步榜去掉只留下等级榜，同时等级榜也只保留前十名，
> 这样每个人都只能看到前几名的同学，以及在我的界面看自己的排位。

## 三、现状与根因

### 3.1 第 1 条：普通会员为什么看得见管理入口

判定链已经集中在一处，是好的；问题出在**模拟数据源把门槛放宽了**：

```
pages/profile/profile.js:174  syncEntries()
  → member-review.canReview / announcement.canPublish / season.canResetSeason / event.canManageEvent
    → services/permission.js:44  canManage(actor, { isMock })
       └─ if (isMock) return true      // ← 演示数据源下「是会员就能管」
```

再看两处事实：

- `services/seed.js:496`：种子里 24 位会员 `role` **全是 0**（普通会员），没有干事、没有管理员。
- `services/mock.js:102`：模拟登录恒为 `u06`（一位普通会员）。

两条叠在一起，本地每个登录会员都会看到「会员审核 / 公告管理 / 赛季管理」三张入口卡，
赛事页也会出现「＋发布」。**云端判定是严格的 `role >= ROLE.STAFF`，普通会员本就看不到**
——也就是说，本条要修的是**模拟数据源在说谎**，不是界面漏了判断。

> ⚠️ 放宽不能一删了事：它还承担着「让演示真的能发布赛事、发公告、审核入会」的职责
> （`permission.js` 顶部注释已说明）。删掉放宽的同时，必须给演示账号一个**真实角色**，
> 否则本地演示会从「谁都能管」变成「谁都管不了」。

### 5.1 必须拍板（选错要返工）

**Q1：模拟数据源下的管理权限怎么改？**

| 方案 | 做法 | 结果 |
|---|---|---|
| **A（推荐）** | 种子里给少数人**真实角色**（如 `u01` 管理员、`u02` 干事），其余仍是普通会员；`permission.js` 不再为 `isMock` 放宽 | 与云端完全一致；默认登录的普通会员看不到入口，换成管理员账号才看得到。代价：需要能切换演示账号 |

- **普通会员**（如 `u06`）：默认就能看到「界面精简后」的效果，符合本次需求；

- **管理员**：管理入口默认都在，但看不出「普通会员看不到」这件事。

> 我倾向 **Q1=A + Q2=普通会员**：让本地默认视角与现实一致，管理功能用一个
> 可切换的演示管理员账号来演示。切换入口可以极简（登录页加一个「以管理员身份演示」），

## 九、实施后修正：公告与入会审核的门槛收到管理员

> 本节记于实施完成后。上面 §三 / §五 里「严格口径 = `role >= ROLE.STAFF`」这句话，
> **对公告与入会审核已经不成立**，保留原文只为留下当时的判断过程。

**问题**：本期把 mock 的放宽删掉之后，判定确实只剩角色一条，但门槛定成了干事。
结果干事既能发公告、又能审入会申请。而同一份 `services/permission.js` 里，
干事又被定义成「学院负责人，权限以学院为界」（`managesCollege`）；`event.js` 也
写明干事只保留「代签到与录入比分」两项临场事务。一个学院范围的角色握着俱乐部
全局的权限，这是本期漏掉的一处越权。

**修正**：两个业务自己声明门槛 `minRole: ROLE.ADMIN`——

| 位置 | 原门槛 | 现门槛 |
|---|---|---|
| `services/announcement.js` `canPublish` | `ROLE.STAFF` | `ROLE.ADMIN` |
| `services/member-review.js` `canReview` | `ROLE.STAFF` | `ROLE.ADMIN` |

**为什么不能像代签到那样按学院收口**：公告是发给全俱乐部的，没有「某学院的公告」；
入会审核批下来的是「俱乐部会员」这个身份，拿到手就能报名、上榜、算积分，与申请人
填的哪个学院无关，台账也是一份全校名单。两者都没有可靠的学院边界可收，只能收归
管理员。判定仍是**一处**（两个业务各自转调 `permission.canManage`），页面里依旧
不写角色判断——§七 第 4 条并未破例。

**顺带把默认值也换了**：`canManage` 的 `minRole` 默认由 `ROLE.STAFF` 改为
`ROLE.ADMIN`。默认值只在「调用方忘了声明」时生效，那就该取最保守的一档——
正是这个默认值让漏传 `minRole` 的两个业务静默地放行了干事。改完之后漏传仍是错，
但错的方向从「放行越权」变成「挡住越权」。目前没有任何调用方依赖默认值
（`event.canCheckIn` 那处干事档是显式传 `ROLE.STAFF` 的）。

**连带影响**：

- 干事（`u02` 张宇轩，以及演示里被任命为法学院负责人的 `u06` 赵明宇）不再看到
  「会员审核 / 公告管理」入口，也调不动这两个写接口。本地要演示它们得切到 `u01`。
- 干事权限不受影响的部分：本院代签到、本院学院赛名单与排阵、录分 —— 照旧。
- `canManage` 的默认门槛已改为 `ROLE.ADMIN`，且**没有任何调用方依赖它**；每个业务
  都显式声明自己那一级（见 `permission.js` 的注释）。

## 十、同类修正：撤销比赛的门槛收到管理员

> 与 §九 是同一种病、同一个开法，故并记于此。判定不在 `permission.js`，而在
> `services/match-record.js` 的 `canRevoke`——它不走角色门槛那一套，所以 §九
> 那次扫门槛没有扫到它。

**原口径**：「管理员 + 录入者」。理由写的是「谁录的谁最清楚录错了」。但录入者
**不是第三方**——他是录分时自己选的（`buildMatchRecord` 里 `recorder` 默认取 A 队
第一位，录分页也可以挑人）。于是场上的一方可以自己录分、再自己撤销，不必伪造比分，
只要事后把记录抹掉，等级分照样回到从前。这与 §九 的干事越权同型：把一个不该持有
全局权限的角色（那里是学院范围的干事，这里是当事人自己）当成了可信收口人。

**修正**：`canRevoke` 只认 `role >= ROLE.ADMIN`。录入者、干事、裁判一律不放行。

**与「驳回」的分工**（两条路不要混）：驳回走 `canConfirm`，发生在比分**生效之前**，
不涉及任何回滚，仍是「对手方 / 裁判 / 管理员」——日常录错了走这条就够了。撤销是
**向后改写已经计入等级分与积分的账本**，才需要收到管理员。界面上两者也分得开：
`pages/match` 的「驳回」按钮归 `canConfirm`，「撤销」按钮归 `canRevoke`。

**连带影响**：比赛页与学院赛大场页的「撤销」入口只对管理员显示；已指定裁判的场次，
裁判也不再能撤销**已生效**的成绩（录分、确认、驳回不受影响）。改动落在
`services/match-record.js` + 两个写入端（mock 与 `src/core/match-handlers.js`）+
五个测试文件；详细影响面见《裁判与实时比分-需求整理》§10.3 第二处。
