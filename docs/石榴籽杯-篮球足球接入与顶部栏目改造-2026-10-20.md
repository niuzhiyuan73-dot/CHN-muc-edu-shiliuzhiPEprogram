## 0. 本轮已完成（可先在真机确认）

### 0.1 缺陷：「已记录出场」恒为 0

**现象**：我的球队页显示「累计得分 73 / 累计助攻 40」，上方「已记录出场」却是 0。

**根因**：出场只认 `match.lineups`（某一场定过的出场名单）。而计分台在名单为空时按**整份报名名单**录分，个人统计因此照常落库并发布——于是出现「有分、没名单、出场 0」。演示数据本身也没写名单，把这个问题放大成了普遍现象。

**修法**：出场按两处证据取并集，不做推定。

| 证据 | 含义 |
| --- | --- |
| 该场 `lineups[side]` 包含本人 | 赛前定了名单，本人在其中 |
| 该场已发布统计里有本人的行 | 统计只在某一项真填了数字时才落行（`saveTeamMatchStats` / `writeLiveStats`），有行即确实上场 |

两处都没有的场次仍不计出场（不凭报名或空格推定）。另外新增 `statOnlyAppearanceGames`（靠统计认出来的场次），页面提示改成「其中 N 场有本人出场记录（出场名单或个人统计）」，让口径看得见。

改动文件：
- `miniprogram/services/team-event-service.js`（云端镜像同步）
- `miniprogram/templates/team-profile-view.wxml`（提示文案）
- `miniprogram/services/team-demo.js`（演示数据补 `lineups`，名单页不再显示「未定」）
- `tests/team-profile-workbench.test.js`（口径断言 + 一条「名单为空、只有统计」的回归用例）

### 0.2 缺陷：顶部项目栏藏项目、缺搜索

**现象**：截图里副标题写着「学院赛 · 篮球」，但一排 chip 只看得到匹克球 / 乒乓 / 羽球 / 网球——篮球、足球被横向滚动藏到屏幕外，连「当前选中哪个」都看不见。

**修法**：

1. **项目栏改等宽网格换行**（三列，两行放六个项目），去掉横向滚动；选中项实色填充，永远在可视区内。
2. **加搜索栏**：圆形输入框置于列表控件上方，输入即筛（300ms 防抖），支持一键清空；搜索时列表聚成「搜索结果」一组，不再按状态拆散。
3. **服务端按关键词过滤**：`listCollegeEvents` 新增 `keyword`，匹配**赛事名称与场地**，且在**分页之前**过滤——前端只筛当前页等于「只在 50 条里碰运气」。
4. **并发保护**：搜索走 silent 重取（不把整页切回「正在加载」，否则输入框被卸载、键盘收起一个字都打不完），并用请求令牌丢弃过期响应。

改动文件：`pages/cup-home/*`、`miniprogram/services/school-college-service.js`（云端镜像同步）、`tests/cup-home-pages.test.js`、`tests/school-college.test.js`。

> 说明：这里的搜索是**赛事搜索**。若你要的是「搜项目」（项目多到一屏放不下时用打字切协会），改动很小，说一句即可调整。

## 1. 接入目标与边界

### 目标

- 篮球、足球在「石榴籽杯」里能被**看见、筛选、搜索、点进去、发起新的**，与球拍项目同一个入口体验。
- 一个入口覆盖全部运动：石榴籽杯 = 该校该项目的**赛事总览**，页面不因运动类型换位置、换导航。

### 不做

- **不合并两套赛事模型**（`collegeEvents` 与 `teamEvents` 的数据、集合、状态机都不动）。
- **不改**录分、统计、名次、ElO/积分口径。
- **不做**「石榴籽杯总榜」（跨项目/跨学院积分总榜），这一层留到学院维度规范化之后再说。

---

## 2. 现状盘点：两套模型为什么不能直接混

| 维度 | 球拍项目（现有学院赛） | 篮球 / 足球（团队赛事） |
| --- | --- | --- |
| 集合 | `collegeEvents` + `collegeEntries` + `lineups` + `matches` | `teamEvents` + `teamEventEntries` + `teamMatches` + `teamMatchStats` |
| 参赛主体 | **学院**（`collegeId`） | **球队**（`teamId`，带自由文本 `college`） |
| 内部结构 | 小项（男单/女单/混双）→ 大场（tie）→ 小场 → 排阵 | 报名球队 → 抽签 → 逐场（无小项、无大场） |
| 状态机 | `报名中 / 待开赛 / 进行中 / 已结束`（数字 0–3） | `draft / registration / locked / scheduled / running / finished / canceled` |
| 时间锚点 | `publishTime`（发起时间） | `createdAt`（发起时间） |
| 读接口 | `listCollegeEvents` | `listTeamEvents` |
| 详情页 | `college-event-detail` | `team-event-detail` |
| 发起入口 | `college-event-edit` | `team-event-list` 页内建赛（足球走表单组件） |

结论：两者**只共享「赛事」这一层语义**，往下没有任何可对齐的字段。任何「合成一张表」的做法都要写一层双向映射，将来加排球要再写一遍。

## 3. 方案选型

### 方案 A（推荐）：读端聚合，页面按运动类型分派

新增一个只读服务 `cup-feed`，按当前项目的 `sportType`（`utils/associations.js` 已有 `sportTypeOf` / `isTeamSport`）选择数据源，把两边**整形成同一行 DTO** 交给页面。写入路径完全不动。

- 优点：改动集中在一个新文件 + 一个页面；状态机、判权、集合结构零风险；加排球只加一个分支。
- 代价：多一层适配代码（约 120 行），两边的状态要有一张显式映射表（见 §4.2）。

### 方案 B：把团队赛事改造成「学院赛」

给篮球/足球也建 `collegeEvents`（学院报名 → 学院队），复用学院赛整条链路。

- 优点：模型真正统一，未来「学院总榜」直接可算。
- 代价：球队模型与学院报名模型要合并或双写；`teamMatches`/`teamMatchStats` 的录分、实时计分、统计审核全部要接进 `matches`；足球的报告模型（`footballPublished`）也要改。**属于重写级别，不建议在现有节奏里做。**

### 方案 C：杯赛页只做球拍，篮球/足球留在工作台「赛事」页签

- 优点：零改动。
- 代价：用户已经明确要「接进石榴籽杯」；同一个「石榴籽杯」入口在不同项目下行为不同，本身就是认知负担。

**建议走 A**；B 作为 §8 的长期项，等学院维度规范化后再评估。

## 4. 接口设计（方案 A）

### 4.1 新动作 `listCupEvents`

```
listCupEvents({ status?, year?, keyword?, offset?, limit? })
→ { ok, feed: 'college' | 'team', sportType, canManage, total, hasMore,
    events: [ 统一行 DTO ], message }
```

统一行 DTO（页面只认这些字段，不再分运动判断）：

| 字段 | 说明 |
| --- | --- |
| `eventId` | 学院赛编号 或 团队赛事编号 |
| `kind` | `college` / `team`（页面据此选详情页路由） |
| `title` | 赛事名 |
| `status` / `statusLabel` / `group` | 原始状态、展示文案、**归组**（见 4.2） |
| `startTimeText` | 开赛时间（服务端格式化，避免 UTC 误差） |
| `location` | 场地 |
| `metaText` | 一行副信息：学院赛 =「小项 · 名单 1–5 人」；团队赛 =「5v5 · 已报名 4 队」 |
| `pinned` | 置顶（团队赛事恒 false，保留字段以便将来统一） |
| `canSubmit` | 我这边有可提交的入口（学院赛=交名单；团队赛=报名/待审核） |
| `canManage` | 管理入口 |
| `createUrl` / `detailUrl` | 由服务端给出，页面不拼路由（编号需 `encodeURIComponent`） |

### 4.2 状态归组映射

杯赛页只有四组分组标题，团队赛七个状态要压进去：

| 团队状态 | 归组 | 分组标题 |
| --- | --- | --- |
| `registration` | signup | 报名中 |
| `locked` / `scheduled` | ready | 待开赛 |
| `running` | ongoing | 进行中 |
| `finished` | finished | 已结束 |
| `canceled` | finished | 已结束（行标签仍显示「已取消」） |
| `draft` | — | 仅管理员可见，归「报名中」组并标「草稿」 |

映射表放在 `cup-feed` 内**一处**，不散到页面：将来排球接入时只加一行。

### 4.3 年份、搜索与筛选口径

- 年份：统一按「**发起时间**」——学院赛取 `publishTime`，团队赛取 `createdAt`。两者语义相同（都是这场赛事开出来的时间），不按开赛时间算（一场可以提前半年发布、也可以跨年开赛）。
- 关键词：团队赛按 `event.name` + `location`，与学院赛同口径；仍在**分页之前**过滤。
- 状态筛选：页面传的是**归组后的组值**（`signup/ready/ongoing/finished`），由 `cup-feed` 翻回各模型的原始状态集合。页面不再出现「篮球的状态枚举和球拍的不一样」这种泄漏。

## 6. 前置数据问题（必须先定，否则接进来也是错的）

1. **球队的学院字段是自由文本**（`team.college`，建队时 `String(payload.college||'').trim()`，不校验、无长度上限）。这会让「按学院统计」「学院赛语义」全部不可信。
   建议：改为 `collegeId` + 从本校学院目录校验（与学院赛的 `collegeId` 同一套主键），旧的自由文本保留为展示兜底。**列入 C3，不阻塞 C0/C1。**
2. **足球建赛入口与篮球不同**（篮球页内表单、足球组件 `football-event-form`）。`team-event-list?create=1` 需要能同时覆盖两条路径，否则足球点「发起」会落到一个不认识的表单。
3. **草稿与已取消的可见性**：`draft` 只有管理员可见，`canceled` 是否算「已结束」需确认（本方案按「归入已结束、行标签显示已取消」处理）。
