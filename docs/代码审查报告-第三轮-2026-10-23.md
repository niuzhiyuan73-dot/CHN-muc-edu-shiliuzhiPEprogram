### 关键修复的落地方式

**X-1（P0）**：`planExchangeMatches({ full: true })` 交的是「此刻应当存在的全部对阵」，而调用方逐场 `getById` 只为判断要不要补写。现在先在事务外比对「台账（已合并本次比分）vs 投影」，只把**新出现的**与**换人的**挑出来落库。台账是事务外读到的、事务内还有 `event.revision / match.revision` 比对兜并发，所以差分提前算不改语义。一次录分通常只影响本场 + 下一轮一条，与签表规模无关。

**X-2**：根因是「读请求数随协会数线性增长」。本轮做的是客户端排队（6/秒，低于服务端 8、留并发余量），把「被拒后静默降级成空」换成「晚几百毫秒到」。真正的根解是**首页聚合接口**（15 → 1~2 个请求），那要新增 action 与双端仓储，留作下一步。

**X-3**：`listSchoolMatches` 原来每次翻页 `buildDirectory`（2000 人 = 41 次 RPC）。现在按「这一页参赛者」批读学籍：非学院负责人给空目录（管理员与参赛者本人在 `canRecordScore` 里更早返回，学院映射只对学院负责人挡行级权限），学院负责人多花 2 次批读。为此给 `schoolMembers` 补了受范围的 `listByIds`（双端 + 契约）。

**X-7（第二批）**：新增 `matches.listMineSince(userId, sinceIso)`。`teamA` / `teamB` 是数组字段，一条等值查询表达不出「我在任一侧」，所以分两支查再按 `_id` 合并去重（同一手法在 `teamMatches.listByTeams` 已有先例），两支各吃一条 §2.3 已登记的索引，**不新增索引**。口径不变的依据是 `seasonPairCounts` 内部先过 `countedMatches`、再只保留含本人的场次——缩输入不改算法。下推只加 `schoolId / association / matchTime` 与参与者，`status`、是否约球仍在 `countedMatches` 里判，`pairInfo` 与整赛季算法逐字相同（差分用例守着）。录分页因此从 30 页 RPC 降到 1~2 页。

**X-9（第二批）**：`forMeet` 范围补 `sportsMeetInterests.listByUser`（键 `userId`）与 `sportsMeetEntries.listByUser`（键 `userIds`，一行多人取「包含」）。运动会集合的归属是 `{schoolId, meetId}`，所以**不能**并进「学校 + 协会」那条按人循环——拼出带 `undefined` 的条件会两端一起静默变空。取回后不再按 `userId` 复筛：那一层留着会把原语写错的问题盖住。

**X-13（第三批）**：保留最近 20 球作为撤销窗口，更早的**只在局边界**折叠成 `folded`：`base`（局数 / 盘数 / 第几局）+ 已结算的 `games / sets / tiebreaks` 摘要。三个取舍必须一起成立：

1. **重算要能续算**：`replayRallies(rallies, format, base)` 从 `base` 起算，所以「局数过半即整场结束」的判定仍看得到折叠前赢下的局。不这么做，折叠后 `finished` 会算错，比分 3:0 的比赛停在 2:0 继续进行。
2. **不能只合并摘要**：摘要里的局数只用于拼正式比分；若把「前缀进度」和「窗口进度」相加来省掉续算，`finished` 会因为两边各自没到局数而漏判——这正是必须让 replay 知道 base 的原因。
3. **定稿必须拼两段**：`toOfficialScores` 把 `folded.games/sets/tiebreaks` 与窗口内的合并。只算窗口那一份会把前面的局整段漏掉，正式比分从 3:1 变 1:1 且不报错。

撤销口径随之变更：**旧**「可一直撤到开场」→ **新**「最近一局 + 最近 20 球，折不到开场」；窗口撤空时给「更早的判球已归档」而不是「没有可撤销的判球」。幂等窗口同样收窄到窗口内（判重靠 `rallyId` 扫 `rallies`）。

## 二、P0 / P1 详述

### X-1　跨校邀请赛录分：事务内逐场重读整张签表（确定性故障）

**位置**

- `miniprogram/services/exchange-service.js:566-584`
  ```js
  const built = planExchangeMatches({ event: snapshot, draw: snapshot.draw, entrantsById: map, matches: ledger });
  return ok(await ctx.repo.transaction(async tx => {
    ...
    for (const row of built.matches) {              // ← 整张签表，不是本轮受影响的场次
      const clash = await tx.exchangeMatches.getById(row._id);   // 1 读/场
      if (!clash) { await tx.exchangeMatches.set(...); continue; }  // +1 写
      ...
    }
  ```
- `cloudfunctions/data/src/adapters/cloud-repo.js:658` —— `stats.reads + stats.writes > TX_OPERATION_BUDGET`（100）即抛「事务读写总操作预算不足」
- `miniprogram/services/exchange-service.js:120` —— 报名名额上限 `quota > 128` 才拒

**原因**

`planExchangeMatches({ full: true })` 返回的是「此刻应当存在的**全部**对阵」，不是「本次提交改变的那几场」。服务端随后对每一条都做一次事务内点读，只为判断是否需要补写。签表越大，事务操作数线性增长，而云端上限是 100。

**实测（探针：按轮次重放 `planExchangeMatches`）**

| 签表规模 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 决赛 |
|---|---|---|---|---|
| 64 人单败 | 32 | 48 | 56 | 63 |
| **128 人单败** | 64 | **96** | **112** | **127** |

64 人还能过（63 读 + 数条写 ≈ 70）；**128 人在第 2 轮第一次录分就要 96 次读**，加上 `exchangeEvents` 读、`current` 读、2 次写与 1 条审计，已越过 100 的预算。

**影响**

- `submitExchangeScore` 对第 2 轮及之后的每一场都失败，回包是 `fail('服务异常，请稍后再试')`（`index.js:110` 的兜底），管理员看到的是故障而不是「签表太大」。
- **比一开始就失败更难查**：抽签正常、第 1 轮全部正常，到第 2 轮突然集体失败。此时已有比分落库，重试也不会好，只能改库。
- 触发区间与产品上限完全重叠：单败 ≥128 人、循环赛 ≥14 人即进入必失败区，而报名名额上限正是 128（`exchange-service.js:120`）。

**修复方向**

1. 只对「本次受影响的场次」做读改写：`planExchangeMatches` 已经能算出 draft，把「与 ledger 内容不同的那几条」挑出来（比较 `_id + playerA + playerB + status`），其余不动 —— 单场录分通常只影响 1~2 条（本场 + 下一轮对阵），操作数从 O(签表) 降到 O(1)。
2. 若要保持现有写法，把整表刷新挪到事务外（这些是可从「已确认比分 + draw」重建的派生数据，不需要与「本场比分」原子），事务内只写本场。
3. 无论选哪条，都补一条**预算用例**：签表跑满 128 人，断言单事务操作数 < 100（`tests/meet-entry-budget.test.js` 的探针可直接复用）。

### X-2　首页 15 个读请求 vs 8 次/秒读限流

**位置**

- `miniprogram/services/school-home-view.js:148-209`：先读公告（1），再 `Promise.all` 六个协会 × 2 个接口（12），第二轮再读赛季与名录（2）——**一次首页加载约 15 个云函数调用，且六协会那 12 个是并发的**
- `cloudfunctions/data/src/core/rate-limit.js:38`：`LIMITS = { read: 8, write: 3 }`（每账号每秒）
- `school-cloud.js:21`：每个 action 一次 `wx.cloud.callFunction`，**客户端没有批量或排队**

**原因**

限流的粒度是「账号 × 秒 × 读/写」，而首页的读是**按协会数量线性增长**的：六个协会 = 12 个读请求，加上公告与概况共 15 个，全部落在同一两秒内。

**影响**

- 第 9 个之后的请求返回 `fail('请求过于频繁，请稍后再试')`。
- 客户端的每一处都 `try/catch` 后「该协会视为空」（`school-home-view.js:178-185`、`192-206`）：**首页不会报错，而是少显示几个协会的赛事、公告退化成「暂无公告」、概况数字偏小**。这与项目自己的纪律相悖（「失败要拒绝，空列表会让调用方以为成功」）。
- 用户看到的是「首页有时内容不全」，下拉刷新可能又好了 —— 典型的间歇性、难复现缺陷。

**证据强度与验证方法**：这是**代码推演**，不是实测。云函数在并发下可能被调度到多个实例（每个实例有独立的桶），命中概率取决于实例数；单个热容器会稳定命中。**建议第一步就用真机抓包验证**：冷启动首页，看 15 个请求里有几个返回 `ok:false` +「请求过于频繁」。若确认，这属于 P0（核心页面必缺数据）。

**修复方向**

1. 首页改成**一个聚合接口**（服务端一次取齐六协会的近期赛事与概况），请求数从 15 降到 1~2。这是根因解，也和「首页是最高频入口」的定位匹配。
2. 短期止血：客户端把六协会的读**串行化并降并发**（如每批 2 个、间隔 250ms），或对首页路径提高读额度（按账号维度临时 `read: 24`）。
3. 把 `catch → 视为空` 改成「保留上一次结果 / 明确提示部分数据加载失败」，不要用空数据冒充成功。

### X-3　每次列表请求重建全校目录（41 次 RPC）

**位置**

- `miniprogram/services/school-actor.js:60-90` —— `buildDirectory`：`schoolMembers.list()` + `colleges.list()` + `users.listByIds(全部在册成员)`
- `miniprogram/services/school-match-service.js:304-311` —— 比赛列表每次 `buildDirectory`
- `miniprogram/services/school-home-view.js:171` —— 首页每协会一次 `listSchoolMatches`

**原因**

第二轮把「逐行串行读比分」改成了批读、把分页下推到了数据库，但 `dir` 仍然是每次请求现读：2000 人的学校 = `schoolMembers` 20 页 + `users` 20 批 + 学院 1 页 = **41 次 RPC**。而这一页真正用到的只有 `nameResolverOf(dir)`（把参赛者编号换成昵称，一页 ≤100 场 ≈ 200 人）。

**影响**

- ① 协会比赛列表：每次翻页固定 41 次 RPC。
- ② 首页：六协会里每个 `listSchoolMatches` 都带一次 41 次 —— **仅目录就是约 250 次 RPC / 次首页加载**，是当前全站最大的一笔固定开销，且随学校人数线性增长（4000 人 = 500 次）。
- ③ 与 X-2 叠加：每个请求既贵又占限流额度。

**修复方向**

### X-5　授权判定排在昂贵读之后（成本型 DoS）

**位置**

| 接口 | 先做的昂贵读 | 之后才判权 |
|---|---|---|
| `publishMeetResults`（`meet-score-service.js:636-645`） | **6 个整届集合**：entries / scores / sessions / assignments / publications + meet | `canPublishMeetResult(ctx)` |
| `setMeetMatchWinner`（`meet-advance-service.js:728-737`） | `sessions.list()` + `events.list()` | `canPublishMeetResult(ctx)` |
| `submitMeetCollegeEntry`（`meet-registration-service.js:493-511`） | `loadEvent` + `candidateSnapshotOf`（≤20 人 × 3 读） | 事务内 `resolveCollege` |

**原因与影响**

权限判定本身只需要上下文（`ctx` 里已有），但它们写在了取数之后。后果是**任何登录账号**（不需要是管理员，甚至不需要是该运动会成员，`meetReadable` 只要求账号有效 + 学校有效）都可以反复调用这三个接口，每次都让服务端读完几千条文档再拒绝。

- 一届运动会 `sportsMeetScores` 上千条 = 10+ 页 RPC；6 个集合合计 **每请求 30~60 次 RPC**。
- 这三个动作都不以 `get/list/search` 开头，被限流算作**写**（3 次/秒）→ 3 × 50 = **150 RPC/秒/账号**，一个账号十几分钟能打空全校日配额。
- 与第二轮 P-6「限流不按成本加权」是同一条链：限流管请求数，这里让每个请求变得极贵。

**修复**：把 `can*` 判权提到所有 `await` 之前（判权只需 `ctx`），并在取数前顺手校验 `meetId`/`eventKey` 归属。这是纯顺序调整，不改变语义。

**影响**：一届运动会成绩 = 项目 × 场次 × 裁判数，数千条 = 数十页；管理员每次撤裁判都付一遍。
**修复**：改 `listBySession`。

### X-11　小组名单读四张全校表

`association-group-service.js:143-156`：`describeMembers` 为几十人的名单读 `colleges.list()` + `schoolMembers.list()` + `schoolRoles.list()` + `memberships.list()`。

**影响**：2000 人学校 = 20+ 页（`schoolMembers`）+ 若干页，只为一个 30 人小组的「昵称 + 学院 + 权限标签」。历史注释（C5）说「四张表各读一次，RPC 从 4N 降到 4」——那是 50 人规模下的正确取舍，2000 人规模下应改为按这批人的键点读（`schoolRoles.listByIds` / `memberships.listByIds` 已存在，`schoolMembers` 可走 `byIds`）。

### X-12　`isMissingDoc` 把 `errCode === -1` 一律当「文档不存在」

`cloud-repo.js:107-113`：

```js
if (code === -1) return true;
return /not exist/i.test(String(err.errMsg || err.message || ''));
```

**风险**：`-1` 是 SDK 的通用失败码，瞬时故障（超时、连接重置、限流）若也带 `-1`，会被读成「这条文档不存在」，随后：
- 读路径：表现为「账号不存在」「赛事不存在」——用户被误导去重新注册；
- 写路径：`buildScoped.write` 用 `current == null` 判断「首次写入 / 更新」，瞬时故障会让 update 走 insert 分支（`school-repository.js:90-99`），或在事务里把「已存在的占位」当空建。

**修复**：`-1` 分支收紧为「`-1` 且 errMsg 命中 not exist」，其余错误照常抛出；或在 `readDoc` 里对 `-1` 做一次重试（1 次）后再判定。

## 五、已核查、确认无问题的点（避免误伤）

- **权限面**：200 个 action 逐个核对，未发现「无任何权限判定」的接口。几个名字看起来像裸奔的（`confirmSchoolMatch` / `rejectSchoolMatch` / `publishCollegeEvent` / `archiveSchoolAnnouncement`）实际都经 `canConfirmIdentity` / `canManageCollegeEvent` / `canPublishAnnouncement` 判定，且写路径在事务内 `freshContext` 重判。
- **归属校验**：顶层 `repo.<collection>.getById(clientId)` 的每一处调用点（`association-notice-service:131`、`association-training-service:278/338`、`school-event-service:390/486/741`、`school-live-service:65`、`school-match-service:392`、`exchange-service` 9 处）随后都有 `belongsToSchoolScope` / `isLiveGroupDoc` / `canSee` 之一。未发现 IDOR。
- **输入上限**：`payload.limit` 21 处全部做了 `Math.min(..., MAX)` 夹取；`rallyId` 有字符集与长度校验（第二轮 S-2 已修）；`cursor` 有结构与时间格式校验（`school-match-service.js:297-303`）。
- **注入面**：全仓无 `eval` / `new Function` / 模板拼接 SQL 类查询；唯一 `new RegExp` 是定长字符集常量（`school-live-service.js:52`），无用户输入拼接，无 ReDoS。
- **提权**：`grantSchoolPermission` 禁止给自己授权、禁止改平台管理员、三档权限逐级收敛、目标必须本校有效身份；`updateSchoolProfile` 只认 `ctx.actorId` 且走 `EDITABLE_FIELDS` 白名单（实名/学号/角色/积分改不动）。
- **隐私收口**：`getSchoolMemberProfile:833` 的学号按「本人或 `reviewMembers`」发放；`getMeetApplicantPool` 的实名只对学院部长/管理员开放（`resolveCollege` 拦截）。
- **凭据**：仓库内无任何硬编码密钥；`CLOUD_ENV_ID` 为空占位；云函数仅依赖 `wx-server-sdk`。
- **登录态**：`getSchoolIdentitySession` 为纯读，不会在「读动作」里懒建账号 —— 这一点很重要，因为 `context-cache.js` 的白名单机制会把 `get*` 当作可缓存的读，若它写库则会出现 5 秒陈旧 + 不失效。
- **客户端定时器**：`setInterval` 仅 `live-watch.js` 一处且有 `pause/off` 生命周期对齐；`cup-home` / `meet-schedule` 的防抖定时器都在 `onUnload` 清理。
