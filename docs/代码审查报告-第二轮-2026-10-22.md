### P-2 的落地方式

上一轮其实实现过 `matches.listRatedSince`（把 `status` 与 `matchTime >= resetTime` 下推），后来因为榜单改走「不读 matches」而删掉了。这次重新加回，但改成**不带 status 过滤**的 `listSince`：

- 名额口径（`countedMatches`）只排除**作废**场次，待确认的照样占名额。若在下推时顺手加 `status: 1`，等于把业务口径改了——过滤仍留在 `countedMatches`。
- 只在 `forScope` 上提供：没有范围字段的同类查询会跨校泄露。

真正省掉全表读的是 `pairUsageOf` 的两条路：先点读这场涉及的最多 4 对计数文档，**全都有就一次台账都不读**；只有缺文档（历史数据）时才回落到本赛季台账。原来无论文档在不在都先读全量台账，练了三年的协会一次录分要翻上百页 RPC。

### B-3 的落地方式与残余风险

原实现下，两个人同时给同一对录「本赛季第一场」时，两个事务里都读不到计数文档，各自拿**同一个台账初值**加一，写成 `count = seed + 1` —— 少记一场，上限被悄悄放宽，且事后从流水看不出来。

改法：把这场涉及的计数文档**预置到事务之前**（`ensurePairCounters`，一次事务写完最多 4 对）。预置写的是 `count = seed`（占位仍在事务内递增），所以重复预置、或预置后提交失败都不会多算；事务内从此一定读到同一份文档，并发递增落在同一行上，云端靠写冲突回滚重试纠正。

**残余风险**：真机上两个事务同时 `set` 同一个不存在的 `_id` 时，若云端报的是「重复键」而不是可重试的写冲突，后到的那次会失败（用户看到「服务异常」），但**不会少记**——失败的那次可以重录。这比原来的「静默少记一场」安全得多。真机验收时建议并发点两次录分，看第二次是「服务异常」还是正常成功。

用例：`tests/match-pair-usage.test.js` 加了三条——预置文档存在且初值可追溯、**手工把计数写满时台账再空也能拦下**（证明文档优先于复算）、并发两场都记上且计数为 2。

### 为什么 P-3 没有上线

批读本身是对的：探针显示同一段代码从 **13366 次点读（21.4 秒）** 降到 **219 次批读（0.6 秒）**，子集 A/B（`--test-name-pattern="比赛页"`）也没有变慢（7.93s vs 8.07s）。

但**整文件回归**背靠背实测：旧实现 98.98s，新实现 174.25s，三次重复一致。逐步排查结果互相矛盾：

- 该步骤本身快 20 秒；
- 子集用例无差异；
- 测试期间 `setInterval` 创建数为 0（排除"轮询定时器累积"）；
- 每次跑下来"最慢的用例"是**不同的随机一组**，符合调度敏感而非某条路径变慢。

结论：这是**测试夹具的时序敏感**，不是产品代码变慢。但"改完测试慢 75%、原因说不清"不能进主干——本项目的 10-20 记录里，团队为把 `page.test.js` 从 267s 压下来专门重写过内存仓储的克隆策略，这类回退会被直接打回。

因此回退，并把结论留在这里：**P-3 的价值成立，但需要先有一轮专门处理夹具时序（或改为在页面侧合并请求），再单独上线。**

## 结论摘要

10-21 那一轮把**读路径的身份放大**（`users.list()` 跨校全表）与**入口限流**解决了，这两块目前确实干净。但还剩三类问题，性质与上一轮不同：

1. **写路径的读放大**：判球、录分、提交名单这些"现场高频操作"，每一次都在读**与本次操作无关的全量数据**（全院名单、全部历史比赛）。上一轮只处理了读接口，写接口没动。
2. **事务预算与业务上限不自洽**：运动会团体项目允许配到 200 人，提交名单按人循环写 ≈ 9 次操作/人 —— **≥10 人的团体项目必然提交失败**，报错文案是"事务读写总操作预算不足"。这是确定性故障，不是概率问题。**（已修，见上表 B-1）**
3. **两类没有上限的客户端入参**：`rallyId`（写进文档）与 `interests` 全量读，前者可把某场比赛的实时计分台写死。**（`rallyId` 已修，`interests` 已加上限）**

一句话：**上一轮的病在"身份解析"，这一轮的在"业务数据装载"；前者修完仍不够，因为每次判一球都要重新装载一遍全校名单。**

# 一、性能：写路径的读放大（大用户量下最先崩的地方）

## P-1　判一球重建一次全院名单（每球 ≈46 次 RPC）

**位置**

- `cloudfunctions/data/lib/services/school-live-service.js:56-64`
  ```js
  async function guard(payload, ctx) {
    if (!ctx.actorId) return { error: '请先登录' };
    if (typeof payload.matchId !== 'string' || !payload.matchId) return { error: '缺少比赛编号' };
    if (!canReadAssociationSpace(ctx)) return { error: '没有读取协会空间的权限' };
    const dir = await buildDirectory(ctx);      // ← 每一次判球都走这里
    const target = await liveTarget(ctx, payload.matchId, dir);
  ```
- `cloudfunctions/data/lib/services/school-actor.js:60-69` —— `buildDirectory` 读 `schoolMembers.list()` + `colleges.list()` + `users.listByIds(全部成员)`

**原因**

`recordSchoolRally` / `undoSchoolRally` / `finishSchoolLiveScore` 三个接口都以 `guard()` 开头，`guard()` 为了拿 `recordOptions(ctx, dir)` 的学院名，把**全校在册名单**连同**这批人的账号**全读一遍。而判球真正需要的只是「操作者自己的角色 + 学院」——`ctx.schoolMember` 与 `ctx.membership` 里已经有了。

每球的实际开销（2000 人规模的学校）：

| 阶段 | RPC |
|---|---|
| `buildSchoolContext`（学校/协会/账号/学籍/角色/membership） | 6 |
| `buildDirectory` → `schoolMembers` 20 页 | 20 |
| `buildDirectory` → `users.listByIds` 20 页 | 20 |
| `liveScores` 读 + 写 | 2 |
| **合计** | **≈ 48** |

**影响**

- 一场 50 球的匹克球 = **约 2400 次 RPC**；同场 4 个场地并行 = 近 1 万次。云开发日读配额 5 万次，**5 场球就见底**。
- 单球响应时间随学校人数线性增长（2000 人 ≈ 40 页翻页），裁判按下"得分"到界面回显会明显迟滞 —— 这是计分台最不能慢的动作。
- `rate-limit.js` 的 3 写/秒挡不住它：3 × 48 = **144 RPC/秒**，单个裁判账号即可打满配额。

**修复方向**

1. `guard()` 不需要 `buildDirectory`。`canRecordScore` 只用 `role / college / collegeOf`，而 `ctx.schoolMember.collegeId` 与 `ctx.membership` 已在上下文中：
   ```js
   // school-live-service.js
   const dir = {
     collegeIdOf: id => (id === ctx.actorId ? (ctx.schoolMember || {}).collegeId || '' : ''),
     collegeNameById: () => '', actorCollege: '',
   };
   ```
   真需要学院名用于提示文案时，只在出错分支里点读一条 `colleges`。
2. 若保留 `buildDirectory`，就给它一个容器级缓存，键 = `schoolId`，值 = 目录，TTL 60 秒 + `seasons.version` 失效（写路径仍在事务内 `fresh*Context` 重判，读侧延迟可接受）。
3. 判球是写动作，建议在 `guardRate` 里对 `recordSchoolRally` 单独降额（如 2 次/秒），与"人手速度"对齐。

## P-2　录分页与录分提交全量读历史比赛台账

**位置**

- `cloudfunctions/data/lib/services/school-match-service.js:317-322`（录分页取数）
  ```js
  const [dir, season, ledger] = await Promise.all([
    buildDirectory(ctx), loadSeason(ctx), ctx.repo.forScope(ctx).matches.list(),
  ]);
  ...
  pairInfo: { counts: seasonPairCounts(ctx.actorId, ledger, { seasonStart: season.resetTime }), ... }
  ```
- `cloudfunctions/data/lib/services/school-match-service.js:376-380`（录分提交）
  ```js
  const [ledger, season] = await Promise.all([
    ctx.repo.forScope(ctx).matches.list(),   // 为了算 seedUsage
    loadSeason(ctx),
  ]);
  const seedUsage = tallyPairUsage(ledger, { seasonStart: season.resetTime });
  ```

**原因**

两处都为了"本赛季与每个人的交手次数"把**本协会全部历史比赛**读进内存再算。而 `pairCounts` 集合就是为这件事建的：`school-match-service.js:142-173` 的 `occupyPairUsage` 已经按「每对一条」维护计数（`pairUsageKeyOf`）。读路径却退回全量台账，等于把索引好的聚合计抛弃不用。

**影响**

- `matches` 是**只增不减**的集合。假设一个协会一学期 3000 场，三年 1.8 万场 → `matches.list()` 需翻 **180 页 RPC**，一次录分页打开就耗掉日配额的 0.36%，20 次打开就用掉 7%。每年叠加，**越用越慢，且不会自愈**。
- 录分是现场操作：裁判在场地边上打开录分页，等 180 次串行翻页（`readAll` 是 `for (;;) await`，**完全串行**）≈ 3~5 秒，`config.json` 的 `timeout: 20` 迟早被吃穿。
- 与 P-1 叠加：录分页 = 6（身份）+ 100（目录）+ 180（台账）≈ 286 RPC。

**修复方向**

1. 读路径改读 `pairCounts`：新增 `repo.forScope(ctx).pairCounts.list()` 一次范围查询（键含 `schoolId + association + seasonStamp`），得到 `{pairKey, count}` 后按 `counts[pairKey]` 组装，语义与 `seasonPairCounts` 一致，RPC 从 180 降到 1~2。
2. `submitSchoolMatch` 的 `seedUsage` 只在「`pairCounts` 文档尚不存在」时兜底（见 `occupyPairUsage:153-154`），可改为「文档缺失即从 0 起算 + 首次迁移脚本回填」，彻底去掉事务外的全量读。
3. 若短期不想动读模型，至少在 `matches` 上把 `matchTime` 下拉进查询条件（`_.gte(season.resetTime)`），把"全历史"收窄成"本赛季"，配合已有 `schoolId+association+status` 复合索引。

## P-3　比赛列表：分页只截回包，不截数据库读；且逐行串行读实时比分

**位置**

- `cloudfunctions/data/lib/services/school-match-service.js:290` —— `matches.list()` 全量读
- `cloudfunctions/data/lib/services/school-match-service.js:305-311`
  ```js
  const limit = ... Math.min(payload.limit, MATCH_LIST_MAX) : MATCH_LIST_LIMIT;   // 100
  const offset = ...;
  const matches = [];
  for (const doc of rows.slice(offset, offset + limit)) {
    matches.push(await withLive(matchSummary(doc, ctx, dir), ctx));   // ← 逐行串行 await
  }
  ```
- `cloudfunctions/data/lib/services/school-match-service.js:279-283` —— `withLive` 每条一次 `liveScores.getById`

**原因**

1. `offset / limit / hasMore` 是在**内存里**做的：`rows` 已经是全量，`slice` 只减少了回包体积。注释写"无上限时一个畸形入参就能把整库比赛全量拉回来"，但**有上限时也没有减少一次数据库读** —— 保护的是带宽，不是耗时与配额。
2. `withLive` 在循环里 `await`：一页 100 条 = **100 次串行 RPC**。而 `liveScores.listByIds` 已经存在（`cloud-repo.js:403-414`），一次 `_.in` 即可。

**影响**

- 列表页（高频入口）在 1.8 万场的协会里：180（台账）+ 100（比分）+ 100（目录）= **380 RPC，且其中 280 次是串行的**，几乎必然撞 20 秒超时或小程序端 10 秒网络超时。
- 用户看到的是"列表加载失败，请下拉重试"，而每次重试又打一次 380 RPC —— 故障期形成自我加重的循环。

**修复方向**

1. 查询下推：`matches` 的过滤条件（`pool` / `eventId` / `status` / `userId` 参与）改为 `where`，排序 `matchTime desc` + `limit`，用游标（`matchTime + _id`）翻页。`isParticipant` 这类数组包含条件可用 `teamA: _.in([userId])` 之类的等价写法，或单独建"我的比赛"索引表。
2. 实时比分改批读：
   ```js
   const states = await ctx.repo.liveScores.listByIds(page.map(d => schoolLiveKey(d._id, ctx)));
   const liveById = new Map(states.map(s => [s.matchId, s]));
   const matches = page.map(doc => summaryWithLive(doc, liveById.get(doc._id)));
   ```
   RPC 从 100 降到 1，且 `listByIds` 自带 100 一批的分片。
3. `total` 若只是用于展示，改成 `count()` 聚合查询，别为了 total 读全表。

## P-4　赛程页逐裁判串行点读

**位置**：`cloudfunctions/data/lib/services/meet-schedule-service.js:646-652`

## P-6　限流按"次数"计，不按"成本"计

**位置**：`cloudfunctions/data/src/core/rate-limit.js:38, 85-100`

# 二、安全：隐私下发与输入校验

## S-1　全体会员 `realName` 下发给任一"可录分"者（补充点位）

**位置**：`cloudfunctions/data/lib/services/school-match-service.js:323-327`

## S-2　`rallyId` 无长度/字符校验，可把计分台写死

**位置**：`cloudfunctions/data/lib/services/school-live-service.js:89`

```js
const rallyId = String(payload.rallyId || '');   // 无任何校验
```

落库路径：`applyRally`（`live-score.js:401-406`）把 `rally.id = rallyId` 塞进 `rallies` 数组，随 `tx.liveScores.set(id, next)` **整条文档**写回。

**影响**

- 一条 1 MB 的 `rallyId`：`liveScores` 文档超出云数据库单文档上限 → 写入报错；此后该场**每次判球都整条重写**这份超大文档，超时/失败 → 这场比赛永久无法计分、无法撤销、无法定稿，只能改库修数据。
- 由于 `applyRally` 每次都整条 `set`（含 `rallies` 全量），单球写入量 = 文档大小，1 MB 的 id 让**每一球**都变成 1 MB 写。

**修复**

```js
const RALLY_ID = /^[A-Za-z0-9_-]{1,64}$/;

if (raw && !RALLY_ID.test(raw)) return ok(refused('判球编号无效', { live: null }));
```
并在 `applyRally` 里对 `rallyId` 再 `slice(0, 64)` 兜一层（纵深防御），与 `MEMBER_ID_PATTERN`（`association-group-service.js:56`）保持同一口径。

## S-3　「集合不存在」判据正则过宽，会掩盖真实故障

**位置**：`cloudfunctions/data/src/adapters/cloud-repo.js:51-56`

```js
return code === -502005 || /collection|db or table/i.test(msg);
```

**问题**：`/collection/` 会命中任何提到 collection 的错误文案（如权限不足、非法查询、超时提示里带 "collection"）。一旦命中，`readDoc` 会抛出"数据库集合 X 不存在（错误码 -502005）：请先在控制台按 README §三 建齐全部集合" —— 把**鉴权失败 / 查询语法错误**误报成"集合没建"，排查方向被彻底带偏（这正是 10-17 审计 C3 想修的那类问题，只修了一半）。

**修复**：只认错误码，文案作为辅助但必须同时满足：
```js
return code === -502005 || /(collection|db or table)[^.]{0,20}not exist/i.test(msg);
```

# 三、边界情况与输入校验缺失

## B-1　运动会团体项目 ≥10 人：提交必然失败（确定性故障）

**位置**

- 人数上限：`cloudfunctions/data/lib/services/meet-service.js:572-573`
  ```js
  const members = isMulti ? intOf(payload.members === undefined ? template.defaultMembers : payload.members, 0, 200, '每队（组）人数') : ...
  ```
  → 管理员可为团体项目配置**最多 200 人**（拔河、团体操、接力替补都很容易超过 12）。
- 提交路径：`cloudfunctions/data/lib/services/meet-registration-service.js:385-399`（校验循环，每人 4 读）
- 写入路径：`meet-registration-service.js:452-472`（每人 3 写 + 1 读）
- 预算：`cloudfunctions/data/src/adapters/cloud-repo.js:33, 549-553`
  ```js
  const TX_OPERATION_BUDGET = Math.min(100, ...);   // 100
  if (stats.reads + stats.writes > TX_OPERATION_BUDGET) throw new Error('事务读写总操作预算不足…');
  ```

**推导**：固定开销约 14 次（`freshMeetContext` 6 + meet/event/college/quota 4~5 + 序号探测 ≥1 + `touchEvent`/`touchCollegeScope` 2~3），**每人 9 次**（校验阶段 4 读：`schoolMembers`、`users`、`claim`、`interest`；写入阶段 5 次：`claim` 写、`counterOf` 读、`counter` 写、`interest` 读、`interest` 写）。可用额度 `100 - 14 = 86`，**86 / 9 ≈ 9~10 人**。

**影响**：配了 10 人及以上的团体项目，学院部长点"提交名单"必然收到"事务读写总操作预算不足：请缩小本次处理范围"——这句文案是给开发者看的，部长无法理解，也无法通过任何界面操作绕过。等级 **P0（功能不可用）**。这也解释了为什么 10-21 报告把 P2-9 判为"有意不改"是对的（`association-group` 30 人 91 次确实卡在边缘），但**运动会这条路没人算过**。

**修复方向（按成本排序）**

1. 校验循环整体移出事务：事务外 `schoolMembers.listByScope` + `users.listByIds` + `sportsMeetParticipantClaims`/`Interests` 条件查建 Map，事务内只保留"重判权限 + 校验计数快照 + 写"。操作数从 `8N` 降到 `3N + 12`，200 人也只有 612 —— 仍超 100，所以必须配合第 2 条。
2. **改为分批事务**：名单按 ≤20 人一批提交，每批一个事务，最后统一置 `status`。这是 `association-group` 注释里提到的正确方向。
3. **最省事的止损**：把 `meet-service.js` 的人数上限按"单事务可承受"收紧（如多人项目 ≤10 人），超出的走"分多组报名"。这条当天就能上，但限制产品表达。
4. 报错文案改为业务语言：「单个团体项目最多 10 人，超出请分成多组报名」。

## B-3　交手名额：首次并发导致丢更新（上限可被突破）

**位置**：`cloudfunctions/data/lib/services/school-match-service.js:150-157`

```js
const doc = await tx.pairCounts.getById(id);
const used = doc ? Number(doc.count || 0) : Number((seedUsage && seedUsage.get(pair.key)) || 0);
```

**风险**：某对选手**本赛季第一次**交手且并发提交两场时，事务内读到 `doc === null`，两边都退回事务外拍下的 `seedUsage`（同一个值），各自写 `count = used + 1` → 实际应为 `used + 2`，**少计一场**。后果是"每对每赛季上限"可被并发突破一次，而等级分是零和的，这类偏差事后无法从流水看出。等级 P2（概率低、影响中）。

**修复**：`doc` 缺失时不要退回 seedUsage，而是以 `count = 1` 起算并记一条 `origin: 'lazy'`，同时在赛季重置时用一次性脚本回填 `pairCounts`（重置是低频动作，适合做全量重建）。

## B-4　逐球流水无上限；`rallyId` 可缺省导致重复计分

**位置**：`cloudfunctions/data/lib/services/live-score.js:399-406, 449-453`

```js
const rallies = [...(state.rallies || []), rally];
return { ...state, rallies, ...derivedFields(replayRallies(rallies, state)) };
...
return (state.rallies || []).some((rally) => rally && rally.id === id);
```

**三个问题**

1. `rallies` 无上限：网球抢七长局可达 200+ 球，每次判球 O(n) 重放 + 整条文档重写，单场写放大 O(n²)。当前量级无感，但它是"文档只增不减"的模式，与 `matches` 同类风险。
2. `rallyId` 可缺省：客户端不传时 `applyRally` 不写 `id`，`hasRally` 永远判不出重复 → 断线重发、连点会**真加一分**。服务端把所有去重责任交给了客户端的自觉。
3. `hasRally` 是 O(n) 线性扫描，随流水长度增长（与第 1 条同源）。

**修复**

1. `recordSchoolRally` 要求 `rallyId` 必填（与 `submitSchoolMatch` 的 `requestId` 同一口径）。
2. `rallies` 只保留最近 N 条（如 200）用于撤销，更早的折叠成「已结算局摘要」`settledGames: [{a,b}]`。`replayRallies` 从摘要起算，撤销只可能发生在最近几球，语义不受影响。
3. 去重改用 `Set` 或把最近 20 个 id 记在 `recentRallyIds` 字段里，O(1)。

## B-5　`cursorCond` 的 `_id` 分支是死代码（潜在正确性隐患）

**位置**：`cloudfunctions/data/src/adapters/cloud-repo.js:122-129`

```js

return cmd.and([base, next]);      // ← 目前无任何调用能走到这里
```

**问题**：`db.command.and` 期望的是「查询命令数组」，把普通对象 `{schoolId, association}` 直接塞进去，在 wx-server-sdk 下不保证等价于"两个条件和"。已核查现有调用（`listByScope` / `listByEvent` / `exchangeSignups.listByEvent`）**都不带 `_id` 条件**，所以这条分支从未被执行 —— 既是死代码，也是将来第一个"带 `_id` 条件 + 翻页"的查询会静默出错的地方（可能报语法错，也可能退化成全表）。

**修复**：改成数组条件形式并补测试：
```js
return cmd.and([cmd.where ? base : base, next]);   // 或直接用 where({...}) 的两段合并
```
更稳妥的做法：既然当前没有调用方，就**删掉这条分支并显式抛错**（"cursorCond 不支持带 _id 的条件，请改用 listByIds"），等真有需求时再实现。已在 `tests/for-scope-contract.test.js` 覆盖两端方法面，加一条用例即可锁住。
