第一批修的是「会静默算错数据 / 让数据自相矛盾」的高危缺陷（见 `高危缺陷修复记录.md`）。这一批接着往下清，处理的是同一类性质、但触发条件更窄的四条，外加一条云端读取的健壮性缺陷。

- **修复日期**：2026 年 9 月 17 日
- **测试状态**：1866 通过 / 0 失败（169 个套件）
- **云函数镜像**：已 `npm run sync:cloud`，`lib/` 与源同步

## 总览

| # | 缺陷 | 影响面 | 修法 |
|---|---|---|---|
| 1 | 退过赛的人重新报名绕过名额上限 | 有效人数超出上限，抽签凭空多一人 | 名额判定去掉「有记录就豁免」 |
| 2 | 回放排序不是全序，同刻比赛按扫描顺序排 | 等级分随读库顺序漂移 | 补齐次级键，排成全序 |
| 3 | 实时比分定稿后仍能撤销判球 | 实时态与正式比分各说各话 | 定稿盖章，之后只读 |
| 4 | 学院赛撤销小场不回滚大场 | 大场记着已退回去的胜负 | 撤销时回滚，决定性的一场拦下 |
| 5 | 云端分页读没有 `orderBy` | 翻页可能跳条、重条 | 两次读取都按 `_id` 定序 |

## 一、退过赛的人重新报名绕过名额上限

### 现象

赛事名额 2 人，a 报了名、b 报了名（满）；b 退赛让出位子，c 补上；b 又想报一次——**报得进去**。抽签时名单上多出一个人，签位与人数对不上。

### 根因

`event.js` 的 `canSignUp` 里，名额检查写作：

```js
if (quota > 0 && signupCountOf(event, options.signups) >= quota && !signup) return false;
```

`!signup` 的本意是「他已经报过名了，不必再查名额」。但上一行已经把「非取消状态」的报名挡掉了：

```js
if (signup && signup.status !== SIGNUP_STATUS.CANCELED) return false;
```

于是走到名额检查这一行的人，只可能是**从没报过名**（`signup` 为空）或者**退过赛**（`signup.status === CANCELED`）——而 `!signup` 恰好把「退过赛」这一类整个豁免了。退赛退掉的是名额，重新报名就是重新占位，与新人同一条尺子才对。

### 修法

去掉 `&& !signup`，名额判定与新人完全一致。`signupCountOf` 本身已经把取消的排除在外，不必再减。

### 守着它的测试

`tests/event.test.js`：名额 2、名单 `[a 在册, b 已取消, c 在册]` 时，b 重新报名被拒；名额放宽到 3 时又能报。

## 二、回放排序不是全序

### 现象

同一批比赛，换个顺序读进来，算出来的等级分不一样。

### 根因

等级分不落库，靠按时间回放推导（见 `derive.js`）。回放前要排序，而原来的比较器只比一件事：

```js
[...matches].sort((a, b) => new Date(a.matchTime) - new Date(b.matchTime));
```

时间相同时它判等，`Array#sort` 稳定，于是**保留输入顺序**。而输入顺序取决于读库顺序，读库顺序又不保证稳定——同一次读，翻页边界一变，顺序就可能变。

这不是理论问题：抽签生成的整张签表**共用同一个 `matchTime`**（`draw.js` 的 `draftsFromPairs` 写的是 `event.startTime`）。一轮里的几场、以及陆续推进出来的下一轮，时间全一样。谁先谁后，全看扫描顺序。半决赛排在决赛之后重放，决赛用的就是错的赛前分。

### 修法

在 `replay.js` 里加一个真正的全序比较器 `compareForReplay`，逐级判到能分出先后为止：

1. **时间**——缺时间 / 时间非法的排到最后（旧行为：`NaN` 参与比较恒为假，位置随机）；
2. **签表归属**——`eventId || collegeEventId`，不属于同一张签表的（含日常约球）互不依赖，给个确定次序即可；
3. **小组优先**——小组循环排在淘汰阶段之前（兼项赛制里两者都不能跨阶段依赖）；
4. **轮次**；
5. **阶段**——胜者组 → 败者组 → 总决赛（`STAGE_TIEBREAK`）；
6. **签位**；
7. **`_id`**——最后的兜底，保证任意两条都能分出先后。

第 7 条是「全序」二字的关键：前面的键都相同时，仍然给出确定的次序，排序结果就与输入顺序彻底无关。

### 守着它的测试

`tests/replay.test.js` 三条：

- 同一时刻的三场（半决赛两场 + 决赛）按 轮次 → 签位 定序，正序、逆序、任意打乱都给出同一个次序；
- 缺时间 / 时间非法的排到最后，不搅乱正常场次的先后；
- `replaySeason` 的结果不随输入顺序变化——把同一批比赛反过来喂进去，四人的单打等级分必须一模一样。

第三条做过「把比较器换回旧写法 → 测试转红 → 换回来」的验证，确认不是空跑。

## 三、实时比分定稿后仍能撤销判球

### 现象

逐球判到 2:0 赢下整场，点「定稿」把正式比分交出去（比赛转「待确认」）。此时再点「撤销」——**撤得掉**。查看端随即看到一场「进行中 · 10 : 0」的比赛，而备战表里它已经有成绩了。

### 根因

`status === 'finished'` 表示「打完了」，`undoRally` 只看有没有球可撤，不看是否已经定稿。但「打完」与「定稿」是两件事，中间隔着一段时间：

- 打完还能撤掉制胜那一球重来——这是正常的临场更正；
- 定稿之后正式比分已经写进比赛记录，再撤就会让两处各说各话。

更麻烦的是比赛被对手确认之后（`status` 转已生效），实时台就永远停在「进行中」，再也定不了稿。

### 修法

在实时态上加一个 `finalizedAt` 章：`finishLiveScore` 写它，`isFinalized(state)` 读它。

- `undoRally`：已定稿一律拒绝；
- `finishLiveScore`：已定稿不许重复交（否则白 bump 一次赛季）；
- 页面 `canUndo` / `canFinish`：跟着置灰。

**为什么不看 `status`**：`status` 是「这场比赛打完了没有」，`finalizedAt` 是「正式比分交出去了没有」。前者会随着撤销而回退，后者是一次性的、不可逆的。

### 守着它的测试

`tests/live-score.test.js`：

- 纯谓词：`{}` 与 `{ status: 'finished' }` 都判 false，只有盖章的才判 true；
- 内存数据源：定稿后撤销被拒（且比分一分不动）、重复定稿被拒；
- 云端：同样两条。

## 四、学院赛撤销小场不回滚大场

### 现象

学院赛某大场（两个学院之间的一轮对抗）里，管理员撤掉一场打错的小场。个人等级分正确地退回去了——但**大场还记着那一场赢了**，汇总照旧算它一场胜，大场照样「已结束 + 胜者」，下一轮照样顶着这个人晋级。

### 根因

`tie.legs[]` 不是实时读比赛记录，而是小场确认那一刻抄下来的一份**快照**（见 `college-tie.legResultOf`）。撤销走的是个人赛那条通路（`revokeMatch`），它只改 `matches`，完全不知道大场那一侧还有一份副本。

### 修法：撤得动的跟着退，撤不动的拦下来

**没有选择**「撤销时把大场一并退回进行中」这一条通吃，因为小场作废是终态：编号是确定的（`collegeLegKey`），既不能重录（录分只认「待确认」），也不能重新开台（`startTie` 只补不覆盖，且进行中的大场不给再开）。一旦把**决定性的那一场**退回去，这个大场就再也打不完，赛事也跟着结束不了——把人从「数据自相矛盾」直接推进「死局」。

所以按能不能退分两路：

- **大场没结束过**：没有结论可推翻，把这一场的结果从 `tie.legs[]` 里收回去（清胜负、比分文本、累计局分；`matchId` 留着，详情页还点得进去）；
- **大场已结束**：重算一次，结论仍成立（撤的是无关紧要的一场）就把这一场收回去、胜负照旧；结论站不住就**拒绝**，提示改用名次更正（`finishCollegeEvent` 的名次本来就是管理员填的，允许与签表不同）；
- **结果已经排进下一轮**（下一轮大场已按胜者落成真实记录）：拒绝，要求从最后一轮往前撤——与个人赛的 `findDependentMatches` 同一个道理。

### 为什么拦截要分两处

个人赛的签表依赖在 `matches` 里，`findDependentMatches` 够得着；学院赛小场的下游在 `ties` 里，够不着，得单独拦一道（`collegeLegRevokeBlocker`）。

### 守着它的测试

- `tests/college-tie.test.js` —— `revertLegResult` 纯函数四条：未结束的大场只清那一场、决定性的一场返回 `blocked`、无关紧要的一场保留胜负、序号对不上给 `null`。
- `tests/college-score.test.js` —— 端到端三条：撤销后大场里那一场的胜负与比分跟着作废（大场结论不受影响，剩下的场次照常录）；撤决定性的一场被拒且一分不动；结果已排进下一轮被拒。
- 两条拦截路径在 mock 与云端各一份实现，规则一字不差。

## 五、云端分页读没有 `orderBy`

### 现象

理论上：集合超过一页（`PAGE_SIZE`）时，翻页读出来的数据可能**跳过几条、又重复几条**。

### 根因

`cloud-repo.js` 的 `readAll` / `readWhere` 用的是 `skip(offset).limit(PAGE_SIZE)`。`skip` 是**位置**语义，不是游标语义——它假设两次查询之间集合的顺序不变。云数据库不保证这一点，没有显式 `orderBy` 时每次查询的默认顺序可以不同。

### 修法

两次读取都加上 `.orderBy('_id', 'asc')`。`_id` 唯一，排序结果确定，翻页的边界才是稳的。

> 这一条是**潜在缺口**而非已复现故障（需要集合超过一页才可能触发），但代价是数据读错，且排查起来极难，值得提前堵上。这个改动没有直接的单测覆盖——真实的云数据库无法在测试里联调，只能靠约定与代码审阅守住。
