## 一、云函数隐患详表

### C1｜时区：naive 时间串 × 云端 UTC（高，阻塞上云）

**事实链**（每一环已实证）：

1. 官方文档明确云函数容器时区 **UTC+0**；小程序端为 UTC+8。
2. 客户端四处把时间组成 **naive 本地串**（无时区后缀）发送：
   - 录分：`miniprogram/services/match-entry-view.js:198` → `` `${form.date}T${form.time}:00` ``
   - 个人赛事：`pages/event-edit/event-edit.js:453-457`（:467 发送）
   - 学院赛：`pages/college-event-edit/college-event-edit.js:378-382`（:392 发送）
   - 训练：`components/association-space-panel/association-space-panel.js:50,1027-1028`（`localMoment`）
3. 服务端对这些 naive 串做「与绝对时间比较」的判定：
   - 录分：`match-record.js:498-505`，`new Date(matchTime)`（按运行时区解析）vs `ctx.now`（绝对）
   - 训练发布：`association-training-service.js:438-440`，`startMs <= nowMs` 报「开始时间必须在未来」
   - 训练报名：`association-training-service.js:629`，`now < Date.parse(training.startAt)` 判「报名已截止」
   - 赛事报名：`event.js:356/412`，`now` vs `startTime`
4. **爆炸半径边界**（子代理指出、已采信）：已落库的 ISO 绝对串（`...Z`）在 UTC 与本地解析一致，**存量数据不受影响**；受污染的只有「新进入的 naive 串」及其衍生计算。

**三种后果**：

- **误拒（录分，最高频）**：`time > now` → 「比赛时间不能晚于现在」。北京时间白天/傍晚录入当天比赛，naive 串的 UTC 钟点 > 当前 UTC 钟点即触发。例：北京时间 19:30 录入刚打完的比赛 → 云端 now=11:30Z，matchTime 解析为 19:30Z → 拒绝。
- **静默偏移 8 小时**：通过校验后 `matchDocFromRecord` 以 `iso(record.matchTime)` 落库（`school-match-service.js:736`）→ 存成的绝对时刻晚 8 小时（晚场）或早 8 小时（晨场）。连带：回放排序、`rating-cap.js:126-133` 的赛季名额切分（`seasonStart` 恰为 naive 锚点时更严重）、训练积分赛季切分（`training-points.js:105`，`effectiveAt` 与 `resetTime` 混用两种基准）。
- **训练链路全错**：发布「今晚 19 点」的训练 → 校验过、落库晚 8 小时；`inCheckInWindow`（:98-104）按错误时刻开闭 → 用户到点签不了到；`registerTraining`（:629）把合法培训判「报名已截止」；`draw.js:880` 再把赛事 `startTime` 原样写进比赛 `matchTime`（naive 串直入流水，C11）。

**为什么本地测试发现不了**：本地跑在 UTC+8，naive 串解析与客户端一致；内存仓储不做时区转换；2214 条用例中仅 1 条与时区相关且恰好同处 UTC+8；演示数据（`school-seed.js`）与系统生成时间一律走 `iso()` 绝对串，演示链路看起来完全正常。

**修法**（互不排斥，建议都做）：
1. **治本**：新增 `cloudfunctions/data/config.json` 设 `TZ=Asia/Shanghai`（官方推荐），naive 串即按北京时间解析；顺带在同文件设 `timeout`（见 C2）。
2. **治标**：把 4 处 naive 串改为仓内已有正确样板 `pages/school-exchange/school-exchange.js:223-224` 的写法（`new Date(naive).toISOString()` 后再发送）。
3. 验证：`TZ=UTC node --test tests/*.test.js`（当前 1 条红，治本后应转绿）。

### C2｜读放大 × 默认 3 秒超时（高，随数据量阻塞）

**事实链**（已实证）：

1. S2 排名路径**有意不落快照**——`school-rank-service.js:17-22` 自证：「本模块当前每次都现算……云端真要上量时，再按 derive.js 的办法加一层按范围的快照即可」。
2. `getSchoolRanking`（:301）、`getSchoolMemberStats`（:360）每次读都走 `replayScope`（:191-198）：`users.list()`（**整个 users 集合、全部学校**，:136；`school-actor.js:64,111` 同款）+ 本范围 5 个 `list()`（schoolMembers/matches/events/associationTrainings/trainingRegistrations）+ 完整 ELO 回放。
3. 每次 `list()` 在云端是 `ceil(N/100)` 次**顺序** RPC（`cloud-repo.js:72-86` 翻页循环）。
4. `getSchoolMemberStats` 是**应用启动路径**（`association-usage.js:52` 经 P10 子批 10 改接它）+ 赛事面板（`school-events-panel-view.js:19`，`{}` 全量）——最热的两个入口都是全量重放。
5. 云函数目录**无 config.json** → 超时 3 秒、内存 256MB。冷启动另计 `wx-server-sdk` + 27 个服务模块加载（实测模块图 ~89ms，SDK 另计）。

**量化参考**（单次排名读）：上下文 3 + 判权目录 3 + 赛季 1 + 成员/流水/赛事/训练/报名 5 组翻页 ≈ **40–50 次 RPC 起步**；100 会员 + 2000 场 ≈ 2 秒；700 场 + 50 会员 ≈ 0.7 秒。**首次读、每次 `seasons.version` 变化后、每个新冷容器**都触发全量重放。users 表还随接入学校总数增长。读配额同步放大（官方 5 万次/天 ÷ 每次 10–30 ≈ 1700–5000 次排名读/天）。

**本地盲区机制**（子代理指出、已采信）：`school-memory-repo.js:109` 的 `list()` 是 Map 全量返回，**零 RPC、零成本、永不超时**；`cloud-repo-contract.test.js` 的手写 db 桩（:47-58）也是内存翻页。数据量只有几条到几十条，任何超时都不可能触发。

**缓解方向**（按成本）：① `config.json` 设 `timeout`（如 20 秒）——立即消除误杀；② `users.list()` 范围化 / `getByIds` 批读（上轮审计 H3 后半，已列缓做）；③ 按范围落 `rankings` 快照（模块注释自证的既定演进路径）；④ 容器级记忆化 + `seasons.version` 失效。

### C3｜少建集合时「读静默、写才炸」（中）

**事实链**（已实证）：

1. `cloud-repo.js:35-40` 的 `isMissing` 用 `/not exist/i` 匹配 errMsg。
2. 集合不存在的官方错误 errCode **-502005**、errMsg `database collection not exists` / `[ResourceNotFound] Db or Table not exist`——**命中该正则** → `readDoc` 当「文档不存在」返回 `null`。
3. 本地仓储与测试桩**都不抛这个错**：`school-memory-repo.js:112-115` 读不到返回 `null`；`cloud-repo-contract.test.js` 桩的 `doc.get()` 返回 `{ data: null }`。所以「集合未建」在测试里与「文档不存在」完全同形。

**后果**：README 要求建齐 30 个集合，少建任何一个时——读路径**静默返回空**（`users.getByOpenId`→null「账号不存在」、`schools.getById`→null「学校不存在或已停用」、榜单/名录为空），写路径才炸（set/insert 无兜底）→「服务异常」。与 README §三「少建一个，读写它的那一步都会直接报错」的承诺不符，且排查方向被带偏。

**建议**：`isMissing` 前先判 `code === -502005` 并包成明确中文（「集合 XX 未创建」）；文档不存在改用官方 `cloud.database({ throwOnNotFound: false })` 语义或按 errCode 精确判断。补一条测试：桩上让 `doc.get()` 对未建集合抛 -502005。

### C5｜N+1 与风群并发读（中，规模化时）

云端 QPS 30（官方配额），`Promise.all` 100 个 `getById` 直接触发限流；本地内存仓储每次 get 是 Map 查找，零成本零延迟。已实证的路径：

- `association-group-service.js:114-137`（`describeMembers`）：**每个成员 4 次 getById**（user / schoolMember / membership / association），50 人 = 200 次；
- `school-membership-service.js:368-383`（`getSchoolApplications`）、`:465-479`（`getSchoolMembers`）：循环 `getById` + `Promise.all` 风群；
- `school-rank-service.js:162`（`findCappedMatchIds`）：全量 matches 循环 `getPoolRating`（纯 CPU，无 RPC）；
- `association-training-service.js:356,394`（签到/训练 N+1，注释已标 TODO）；
- `school-actor.js:62-64`（`buildDirectory`）：每次判权都读 `users.list()` 全表（上轮审计 H3 的「前半」只修了 school-member 等三处，这里仍在）。

**建议**：沿用仓内已有的「先 list 建 Map」模式（`school-member-service.js:68` 即是样板）改造热点路径；风群加并发上限（如 10）。

### C7｜错误上下文丢失（低）

`index.js:61-66` 的兜底只记 `event.action`，不记 `schoolId`/`association`/`openId`；业务 throw（`school-context.js:14-18` 学校不存在、`utils/school.js:16-18` schoolId 非法）与基础设施故障（DB 连不上）被兜成同一句「服务异常，请稍后再试」，日志里查不到是哪所学校哪个协会。客户端也无法区分「学校不存在」与「数据库故障」。建议兜底日志补 scope 与 openId，业务条件改走 `fail(...)` 信封。

### C8｜回包可超 1MB（低，会员上千时）

`listSchoolMatches`（`school-match-service.js:311-315`）、`getSchoolLiveScores`（`school-live-service.js:181-186`）、`getSchoolApplications`/`getSchoolMembers`/`getSchoolDirectory` 都是全量返回；`getSchoolLiveScores` 每场还附完整 rallies 数组。按每条约 1KB 估算，1000 场比赛 ≈ 1MB，触及 `callFunction` 回包上限即整包丢失。本地测试数据仅几条，永不觉醒。建议 list 类接口补分页或上限。

### C9｜同名字段跨集合类型漂移（低）

`startTime` 在库里有三种表示：naive 串（C1 污染源）、ISO 绝对串（`school-event-service.js:644` 等）、**Date 对象**（`college-event.js:137`、`draw.js:576` 的 `drawnAt`、`school-rank-service.js:563` 的 `updatedAt`）。JS 侧 `new Date(x)` 两种都吃所以功能不崩；但云数据库同名字段按 BSON 类型排序（String < Date），一旦有云端 `orderBy` 落到这些字段、或将来做 console 聚合 / 数据导出，就会静默错序。建议统一为一种表示（推荐 ISO 绝对串）。

### C10｜死代码与孤儿文件（低）

## 三、本地测试为什么照不出来（结构性盲区）

2214 条全绿与云端行为之间存在**六道系统性盲区**，本次全部实证：

1. **时区盲区**：测试跑在 UTC+8，云端 UTC。`TZ=UTC` 重跑立刻转红 1 条——这就是云端。
2. **错误形态盲区**：本地仓储读不到返回 `null`、测试桩返回 `{data:null}`；云端读不到**抛错**（缺集合 -502005 / 缺文档 not exist）。「缺集合」在测试里与「缺文档」完全同形。
3. **成本盲区**：内存 Map 的 `list()` 零 RPC 零延迟；云端每次是 `ceil(N/100)` 次顺序 RPC，且有 3 秒超时与 QPS 30。
4. **事务上限盲区**：内存事务无操作数上限、无大小限制；云端上限未公示。
5. **序列化盲区**：Map 原样保存 `undefined` / `Date` / 混合类型；云端会拒绝 `undefined`、按 BSON 类型排序、单文档 16MB / 单次出包 16MB（官方配额页）。
6. **容器状态盲区**：本地每次 `require` 都是全新模块；云端容器热复用、可并发多请求。已核查云函数侧无跨请求可变缓存（`index.js` 仅缓存 db 句柄单例）；但 `live-watch.js:40` 的模块级 `session` 是小程序端共享态，多页面并发订阅的行为未经云端验证。
