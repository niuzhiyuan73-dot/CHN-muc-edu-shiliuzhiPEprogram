### 1.2 依赖分析（关键发现）

从主包入口（`app.js` + 主包 `pages/` + 主包 `components/`）做 require 可达性遍历，得到三个数字：

1. **主包页面实际 require 到的 services：94 个文件 / 1767 KB**（几乎等于 services 全量）
2. **从 `services/school-mock.js` 出发的可达子图：94 个文件 / 1814 KB**
3. **只有分包才用到的 services：19 个文件 / 131 KB**

第 1 和第 2 条几乎重合，说明一件事：**整个业务层被 mock 那条边串起来了**。`app.js → school-identity.js → school-mock-loader.js → school-mock.js` 这一条链，把 team / meet / college / exchange / training / membership 全部拖进了主包。

> ⚠️ 但要认清一个机制：**微信打包是按目录物理打包，不是按依赖图摇树**。文件只要躺在 `miniprogram/` 下（且不在分包子目录里），就会进主包，哪怕没有一行代码 require 它。`lazyCodeLoading: "requiredComponents"` 只影响组件**按需注入**，不减包体积。
>
> 所以「断依赖」不等于「减体积」，必须**物理动文件**，或者**上传时忽略**。

### 1.4 首页请求放大（最贵的那个数）

`services/school-home-view.js` 的取数结构：

```
collectAnnouncements()        → 循环翻页直到取完（for(;;)，每页 LIMIT 条）
Promise.all(6 个协会)          → 每个协会内 Promise.all([
                                  listSchoolEvents, listSchoolMatches,
                                  listSeason,     listSchoolMembers
                                ])
```

单次 `loadSchoolHomeView` ≈ `1×翻页数 + 6×(1+4)` = **30+ 次云端读取**。
而 `pages/index/index.js` 的 `onShow` 只要 `this.loaded` 为真就 `refresh()` 一次——用户在协会页和首页之间点两下，就是 60+ 次读取。

云开发每日读配额是「万次」量级。按这个模型，**几十个活跃用户就能把日配额打满**，表现为「用着用着首页白屏 / 一直转圈」。

## 二、审核常见驳回原因 → 本项目的实际对照

下面每一条都是「审核员会点进去看的地方」，并给出本项目的确切状态。

### 2.1 🔴 驳回原因：功能不完整 / 内容为演示数据

**本项目现状（高危）**：
- `miniprogram/config.js` → `CLOUD_ENV_ID = ''`，启动即 `DATA_SOURCE.MOCK`，所有数据存内存，**关掉小程序就没了**。
- 页面有 6+ 处显式文案：`当前为本地模拟数据，用于开发预览，并非真实成绩`（`events-panel`、`match-panel`、`rank-panel`、`college-entry-review`、`college-event-detail` 等）。
- 存在「切换演示身份」入口（`app.switchDemoActor` / `DEMO_ACTORS`），审核员点一下就能在「管理员 / 普通会员 / 外校学生」之间任意切换。

**为什么必被驳回**：审核员无法判断功能是否真的可用。看到「演示数据」「切换身份」，直接判「功能未完成」或「内容不真实」，且这类驳回通常要求**整改后重新提交完整审核**，不是补材料能过的。

> ### ✅ 2026-10-21 复核修正（重要）
>
> 初次体检时我判定「演示入口需要单独下线、mock 文案需要构建开关隔离」。**逐个核对后这条不成立，代码不用改。**
>
> 全部 20 处「当前为本地模拟数据…」文案，以及 `school-exchange` 的「切换体验身份」picker，**都写在 `wx:if="{{isMock}}"` 里**：
>
> ```xml
> <!-- components/events-panel/events-panel.wxml:148 -->
> <view wx:if="{{isMock}}" class="mock-note">
>   当前为本地模拟数据，用于开发预览，并非真实成绩
> </view>
>
> <!-- packageMember/school-exchange/school-exchange.wxml:6 -->
> <picker wx:if="{{isMock}}" range="{{actors}}" bindchange="onActorChange">
>   切换体验身份
> </picker>
> ```
>
> `isMock` 取自 `identity.isMockNow()`，云端模式下为 `false`，这些元素**一条都不会渲染**。而 `switchDemoActor` 本身也有 `if (!identity.isMockNow()) throw` 的硬保护。
>
> **结论：只要 `CLOUD_ENV_ID` 填上，演示痕迹自动全部消失，不需要删任何代码。**
> 我在初版报告里把「现象」误判成了「需要整改的代码问题」，实际根因只有一个——数据源没切。

**改法**：

1. 填 `CLOUD_ENV_ID`，部署 `cloudfunctions/data` —— **这一步同时解决演示文案与演示身份入口**，无需改代码。
2. 首次提交前，数据库至少要有 **3 个协会、20 名会员、10 场比赛、5 条公告** 的真实结构数据，让审核员点得开每一个页面。
3. 真机上自查一遍：全项目搜「并非真实成绩」，界面上应一处都看不到。

> ### ⚠️ 修正初版报告的错误
>
> 初版报告让填「**头像、昵称、学号、真实姓名、性别、相册（仅写入）**」，**这是错的，照填会被驳回。**
>
> 原因：`wx.chooseAvatar` 从相册选图**不需要** `scope.writePhotosAlbum`。「相册（仅写入）」对应 `wx.saveImageToPhotosAlbum`，本项目一次都没调用。
>
> 微信会拿「声明项」与「代码实际调用」比对。**声明了没用的接口，属于描述与实际不符**，是社区里最高频的驳回原因之一。
>
> **正确做法：只勾「收集你的昵称、头像」一项。**

学号、真实姓名、性别、学院是**表单输入**，不属隐私接口，不进「开发者处理的信息」勾选项。要说明就走「补充文档」（txt，≤100 KB）。

#### 2.2.3 光配后台不够，客户端也得接

**最容易忽略的一点**：用户未同意隐私协议前，点「换头像」会**直接失败**（`errno 112` / `privacy permission is not authorized`）。

当前代码里 `__usePrivacyCheck__`、`onNeedPrivacyAuthorization`、`requirePrivacyAuthorize`、`openPrivacyContract` **全部为 0**。后果是：用户在登录页点「换头像」→ 被系统拦截 → 无人处理 → 界面毫无反应。**即便后台配好，新用户第一次仍会卡在这里。**

要补三样：

```json
// app.json —— 开发期打开隐私检查（发布后由平台强制）
{ "__usePrivacyCheck__": true }
```

```js
// app.js —— 拦截隐私授权，弹出自己的授权框
onLaunch() {
  if (wx.onNeedPrivacyAuthorization) {
    wx.onNeedPrivacyAuthorization((resolve) => {
      this._privacyResolve = resolve;            // 等用户点「同意」再 resolve
      this.setData ? null : null;
      this.globalData.privacyPending = true;
    });
  }
}
```

```xml
<!-- 同意按钮必须用这个 open-type，否则不生效 -->
<button open-type="agreePrivacyAuthorization" bindagreeprivacyauthorization="onAgree">同意</button>
```

```js
wx.openPrivacyContract({});   // 打开官方协议页，不必自己写页面
```

> 基础库 2.32.3+ 另有 `wx.requirePrivacyAuthorize()`，可不由自己接管 `onNeedPrivacyAuthorization`。本项目 `libVersion` 为 3.14.2，两种都能用。

**另外**：`pages/profile/profile` 底部建议加一个常驻的「隐私政策」入口，调用 `wx.openPrivacyContract()`。审核员会找这个。

**几个设计取舍**：

1. **状态不放在组件里，放在 `services/privacy.js`。** 挂起的那次调用属于 app，不属于某个页面；两个页面都可能弹框，状态必须共享。
2. **「同意」按钮的 `open-type` 是关键，不能改成 `bindtap`。** 改了一样能点、一样能关弹窗，但微信不认那次授权，接口照样失败——所以专门写了静态用例守住它。
3. **用户协议自己写，隐私指引不自己写。** 隐私指引内容由后台维护、随授权项变化，抄一份到本地必然过期，一律 `wx.openPrivacyContract` 打开官方最新版；用户协议是自有条款，才需要本地页面。
4. **协议入口未登录也显示。** 条款不是登录后才生效的。

### 2.3 🔴 驳回原因：类目与资质不匹配

**本项目定位**：校内体育协会的等级分账本 + 赛事管理，用户是**校内师生**，含学院团体赛、校运会、跨校邀请赛。

**建议类目**（按优先级）：

| 方案 | 类目 | 需要的材料 | 适配度 |
|---|---|---|---|
| A（推荐） | **教育 → 教育信息服务** | 学校/学院出具的授权书或事业单位证明 | 最贴合「校内」属性，审核员一看就懂 |

| C | 体育 → 体育服务 | 可能要求体育经营/培训资质 | ❌ 不建议，容易被打回 |

**关键风险点 — 校名使用**：

### 2.4 🔴 驳回原因：UGC 内容未做安全检测

**本项目现状**：公告内容（`announcement-edit`）、昵称、头像均可用户自由填写；已有**人工审核**（`member-review`、`college-entry-review`、`announcement-manage`），但**未接入机审**：
- `msgSecCheck`：0 处
- `imgSecCheck`：0 处

**为什么是问题**：微信对含 UGC 的小程序，要求具备内容安全能力。有人工审核不算「具备」，因为审核滞后。审核员会检查是否调用内容安全接口。

**改法**（云函数侧调用，key 不下发到客户端）：

```js
// cloudfunctions/data/src/core/content-security.js
const cloud = require('wx-server-sdk');

/** 文本机审。不通过则拒绝写入，返回 false */
async function checkText(content, openid) {
  if (!content || !content.trim()) return true;
  try {
    const res = await cloud.openapi.security.msgSecCheck({
      content: content.slice(0, 2500),
      version: 2,
      scene: 2,          // 2 = 评论/公告
      openid,
    });
    return res.result && res.result.suggest === 'pass';
  } catch (err) {
    // 87014 = 内容含违规信息
    if (err.errCode === 87014) return false;
    throw err;
  }
}

module.exports = { checkText };
```

在 `announcement` 写入、`schoolMember` 昵称写入、`team` 名称写入三处调用。头像图片用 `mediaCheckAsync`（异步）或先落云存储再 `imgSecCheck`。

### 2.5 🟠 驳回原因：权限声明与实际使用不符

**现状**：`app.json` **没有** `permission`、**没有** `requiredPrivateInfos`。

- 🟢 好消息：项目**没有**使用 `wx.getLocation` / `wx.chooseLocation`。若用了却没声明 `requiredPrivateInfos`，或声明了却没在页面上给出可见用途，是高频驳回项。本项目**绕过了这个坑**。
- 🟠 需处理：`wx.chooseAvatar`（头像）+ `wx.cloud.uploadFile`（相册选图）需在隐私指引里声明；若后续加「比赛地点」「球馆导航」，**必须**同步加 `requiredPrivateInfos: ["getLocation","chooseLocation"]` 并在页面上有可见的选址场景。

### 3.2 启动加载速度

#### 3.2.1 合并会话请求（4~6 次 → 2 次）

当前 `loadSchoolSession()` 是两次串行：`getSchoolIdentitySession` → `getSchoolMember`。这两个在服务端都按 `openid + schoolId + association` 解析，完全可以一次返回。

**云函数侧**：给 `school/identity` 动作加一个 `withMember: true` 参数，在同一个 handler 里把会员档案一起查出来放进 `data.profile`。**客户端侧** `loadSchoolSession` 只发一次请求。

```js
// services/school-session.js 侧（示意）
async function loadSessionWithProfile(scope) {
  const { data } = await call('school/identitySession', {
    ...scope,
    withMember: true,   // 服务端一次查齐
  });
  return data;          // { session, profile }
}
```

#### 3.2.2 协会校正与登录校正并行

`onLaunch` 里现在是：

```js
this.refreshSession().then(() => this.syncAssociationForUser());
```

作者注释解释了「为什么串行」——因为 `associationScope` 是模块级单例，并行会互相读到对方切到的协会。**这个约束是真的**，但可以换成**显式传参**解掉：

```js
// 把 association 作为参数显式传入，而不是依赖模块单例
async refreshSessionFor(associationId) { ... }
async syncAssociationForUser() { ... }

// onLaunch
const assoc = this.getAssociation();
Promise.all([
  this.refreshSessionFor(assoc),
  this.computeDefaultAssociation(),   // 只算，不写单例
]).then(([, target]) => {
  if (target && target !== assoc) this.applyAssociation(target);
});
```

改造成本中等（要动 `associationScope` 的调用点），收益是**冷启动少 1 轮往返**。如果 P0 已经压得很紧，这条放 P1。

#### 3.2.3 首屏骨架 + 缓存先行

`pages/index/index.js` 现在 `loading: true` 白屏等云端。改为**缓存优先渲染**：

```js
onLoad() {
  const cached = wx.getStorageSync('home_view_cache');
  if (cached && Date.now() - cached.ts < 5 * 60 * 1000) {
    // 先用缓存渲染，用户立刻看到内容
    this.setData({ view: cached.data, loading: false, stale: true });
  }
  return this.refresh({ silent: Boolean(cached) });  // 后台刷新，回来了再覆盖
}
```

配合 `refresh` 成功后 `wx.setStorageSync('home_view_cache', { data, ts: Date.now() })`。
**感知启动时间从「等接口」降到「读缓存」，通常 300~800 ms → 50 ms 以内。**

#### 3.2.4 预下载规则补全

`app.json` 现在只有一条。补上高频路径：

```json
"preloadRule": {
  "pages/index/index":     { "network": "all", "packages": ["packageEvent", "packageMeet"] },
  "pages/association/association": { "network": "all", "packages": ["packageTeam", "packageCollege"] },
  "pages/profile/profile": { "network": "all", "packages": ["packageMember"] }
}
```

> `network: "all"` 比 `"wifi"` 更实用——4G 下预下载 300 KB 用户基本无感，但换来的是「点进去就开」。
> 注意**预下载总量上限 2 MB**，别全配上。

### 3.3 页面渲染效率

#### 3.3.1 拆掉 58 KB 的 `association-space-panel`

这是全项目最重的前端组件（JS 58 KB + WXML 34 KB + 82 处 setData）。它把「公告 / 训练 / 成员 / 小组 / 赛事」等多个页签全塞进一个组件，切页签时所有 `wx:if` 分支都在 diff。

**改法**：按页签拆成子组件，用 `wx:if` 只在激活时渲染：

```
components/association-space-panel/
├─ index.js / .wxml            # 只保留外壳、页签栏、数据分发
└─ panels/
   ├─ notice-panel/            # 公告
   ├─ training-panel/          # 训练
   ├─ member-panel/            # 成员
   └─ group-panel/             # 小组
```

预期：单次切换渲染数据量降 60%+，`setData` 调用点从 82 降到每面板 10~15。

#### 3.3.2 `team-event-detail` 的 95 次 setData

高发模式是「一次操作 → 多次 setData」。典型改法：

```js
// ❌ 现在（3 次跨线程）
this.setData({ busy: true });
this.setData({ notice: '' });
this.setData({ noticeError: false });

// ✅ 合并（1 次）
this.setData({ busy: true, notice: '', noticeError: false });
```

再进一步：**只传变化的最深路径**，不要传整个对象。

```js
// ❌ 全量 map + 全量传输
this.setData({ rounds: this.data.rounds.map(r => ({ ...r, expanded: false })) });

// ✅ 只改需要改的那一项
this.setData({ [`rounds[${i}].expanded`]: false });
```

**验收标准**：单页面单次交互的 `setData` ≤ 3 次，payload < 100 KB。

#### 3.3.3 长列表分页

排行榜（`rank-panel`）、比赛流水（`match-panel`）、赛事列表当前都是全量 `wx:for`。数据一旦上千条，渲染必然卡。

**最小改动方案**（不需要引入 `recycle-view`）：**分批渲染**

```js
data: { list: [], renderCount: 20 },
onReachBottom() {
  const next = this.data.renderCount + 20;
  if (next >= this.data.list.length) return;
  this.setData({ renderCount: next });   // 只扩大渲染窗口
}
// WXML: wx:for="{{list.slice(0, renderCount)}}"
```

如果榜单要上 1000+，再考虑官方 `recycle-view`（Skyline 下有原生 `scroll-view` 虚拟列表）。

#### 3.3.4 图片

虽然图片不是瓶颈，但列表里的头像用 `lazy-load` 是零成本的：

```xml
<image src="{{item.avatar}}" mode="aspectFill" lazy-load />
```
另外云端头像建议在 `wx.cloud.getTempFileURL` 后加 `?imageView2/1/w/120/h/120` 缩放参数（云存储支持），别把原图拉下来渲染 40 px 的圆圈。

### 3.4 接口请求优化（收益最大的一块）

#### 3.4.1 首页改成一次聚合请求

**这是全项目最该改的一处。** 现状 30+ 次读取 → 目标 **1 次**。

在云函数加一个 `school/homeView` 动作，服务端内部并行查询、聚合、裁剪成首页需要的视图模型：

```js
// cloudfunctions/data/src/core/home-view.js（示意）
async function homeView(repo, { schoolId, limit = 20 }) {
  const assocIds = await repo.listEnabledAssociations(schoolId);

  const [announcements, ...perAssoc] = await Promise.all([
    repo.listAnnouncements(schoolId, { limit }),
    ...assocIds.map(id => repo.listRecentEvents(schoolId, id, { limit: 5 })),
  ]);

  // 服务端裁剪：只返回首页要的字段，避免把整条文档传回客户端
  return {
    announcements: announcements.map(toAnnouncementCard),
    events: perAssoc.flat().map(toEventCard).slice(0, limit),
    counts: { ... },
  };
}
```

客户端 `services/school-home-view.js` 改成一次 `call('school/homeView')`。

**收益**：
- 网络往返 30 → 1
- 云端读配额消耗降 **95%**
- 首页首屏从「6 个协会全查完才渲染」变成「一次拿齐就渲染」
- 客户端不再有聚合逻辑，`school-home-view.js` 从 40 KB 级瘦到十几 KB（顺带减包）

> 云函数单次执行上限 20 秒、单次 `Promise.all` 并发不要超过 10。上面这个结构 6 个协会完全可控。

#### 3.4.2 加一层 SWR 缓存

所有「列表类」读操作统一走一个缓存包装：

```js
// utils/cache.js
const TTL = { short: 30 * 1000, normal: 5 * 60 * 1000, long: 60 * 60 * 1000 };

function swr(key, ttl, fetcher) {
  const hit = wx.getStorageSync(key);
  const fresh = hit && Date.now() - hit.ts < ttl;
  if (fresh) return Promise.resolve(hit.data);

  const p = fetcher().then(data => {
    wx.setStorageSync(key, { data, ts: Date.now() });
    return data;
  });
  // 有旧值：先给旧值，后台继续刷新
  return hit ? (p.catch(() => hit.data), Promise.resolve(hit.data)) : p;
}
```

**适用**：排行榜（30s）、赛事列表（30s）、公告（5min）、协会信息（1h）。**不适用**：比分/实时计分（必须实时）。

#### 3.4.3 `onShow` 收敛

`pages/index/index.js` 现在「从任何页面返回都刷新」。改为**按需刷新**：

```js
onShow() {
  if (!this.loaded) return;
  // 只在登录态或协会变化时重取；单纯返回不发请求
  const sig = `${app.isLoggedIn()}|${app.getAssociation()}`;
  if (sig !== this.lastSig) {
    this.lastSig = sig;
    return this.refresh({ silent: true });
  }
  return undefined;
}
```

配合 3.4.2 的缓存，用户来回切页签**几乎不产生请求**。

#### 3.4.4 确认线上索引已建

`docs/数据库索引清单.md` 列了 21 个集合的组合索引。**这些索引没建，上面所有优化都白搭**——每次 `where` 都是全表扫。

上线前在云开发控制台 → 数据库 → 索引管理，逐个核对；或在云函数启动时跑一次 `db.collection(x).where(...).explain()` 看是否走索引。
