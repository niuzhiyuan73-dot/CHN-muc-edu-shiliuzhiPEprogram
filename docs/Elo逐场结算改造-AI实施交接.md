## 1. 任务与背景：先读这一节

用户希望将当前 Elo 全量回放体系改成「当前评级落库、确认比赛时逐场结算」，并取消比赛撤销功能。用户已明确：项目尚未实际上线，没有真实历史数据的继承问题，可以不保留旧回放引擎。本文件是实施交接，不代表改造已经完成。

下一位 AI 应完成代码、仓储、页面、模拟数据、测试和开发文档的整套改造，而不是只给建议、只增加一个 elo 字段，或者只隐藏撤销按钮。

当前本轮仅产出本文档；未修改业务代码、未访问云端数据库。不得将「没有历史数据问题」解释为可以自行删除云环境中的所有集合、账号、学校配置或其他项目数据。

### 1.1 已明确的方向

- 用户当前 Elo 必须持久化，在线读成绩不再全量回放比赛。
- 删除旧的两遍回放引擎，不维护新旧双轨，不做生产历史回填。
- 已结算比赛不可撤销。
- 保留历史比赛及结算明细，以支持战绩、走势图、审计和核账。
- 保留单场 Elo 公式与现有非相关功能。

### 1.2 本交接采用的实施默认值

以下是根据上述方向给出的具体设计，属于实施建议，不要对用户声称这些细节都曾被逐条确认。若用户没有另行修改，按这些默认值实施，不必为了普通命名或可逆技术选择反复确认。

1. 新人采用固定起评分，删除「用前几场对手反推起评分并重算历史」的逻辑。
2. 使用服务器实际结算顺序，而不是用户填写的比赛发生时间计算 Elo。
3. 保留待确认驳回；已结算后禁止修改比赛结果和参赛人。
4. 不新增高 K 新人规则。本次保留现有公式参数，避免夹带算法改动。
5. 单场评级结算同步完成，和比赛生效在同一个事务中提交。
6. 积分从 Elo 中解耦；本次优先继续根据赛事与训练事实单独聚合积分，避免把积分账本重建扩大成另一项大型任务。
7. 不新增复杂的历史纠错后台。若现有可达的管理员改分功能存在，就接入有审计的当前评级调整；若仅旧代码残留，不为此新增管理页面。
8. 不将跨校交流赛擅自纳入个人 Elo。核实其当前规则，保留不计 Elo 的边界。

## 2. 当前实现与关键事实

## 4. 新业务规则的明确语义

### 4.1 初始化与定级

- 每个「学校 + 协会 + 用户 + 池」有独立起点评级。
- 推荐在首次结算时事务内惰性创建；无比赛时读取端可返回默认展示值，但不得在读取请求中偷偷写库。
- 若保留管理员预设初始分，应按范围/池保存；首场结算前可改，之后只能走明确的当前评级调整。
- 第一次初始化必须冻结 `startElo` 和实际采用的初始化配置。以后修改性别、默认初始分，不得重置已存在评级。
- 删除真实的对手推导定级；若 UI 仍需要新人标识，可按场次显示「新选手/样本较少」。不要留下暗示起评分会被重新推算的说明。
- 不因为取消追溯定级就把 K 改成 32，也不擅自改变单场计算函数。

### 4.2 计分顺序与日期

- `matchTime`：比赛发生时间，供记录与展示。
- `settledAt`：服务端结算时间，不能由客户端指定。
- `settlementSeq`：学校/协会范围内递增的结算序号，决定 Elo 变化链的顺序。
- 第一版可以在独立的范围级计数文档中分配序号，并在结算事务中原子更新。这会让同范围确认串行竞争，但在当前规模下可接受，必须记录该取舍。
- 单靠毫秒时间或客户端时间不能提供确定顺序。
- 补录旧比赛按当前结算位置处理，不插入历史、不改已结算快照。
- 图表的 Elo 链按结算顺序；比赛列表可按发生时间。页面应说明「按确认顺序计分」，不能把两条时间轴混为一谈。
- `lastMatchTime` 建议表示实际发生时间最大值，另存 `lastSettledAt`；补录旧比赛不能把活跃时间倒退。

### 4.3 状态与不可变性

- 待录入/待确认阶段可以按原权限编辑和驳回，继续保留防刷分额度预占/释放。
- 已生效的计分比赛一旦结算，不允许改分、改胜方、改参赛人、改计分池、撤销、删除或改为弃权。
- 不计 Elo 的比赛也保存一次性「不计分」结算决定及原因，避免后来修改规则使其突然获得分数。
- 不要用「是否有 players 数组」作为唯一结算标识，应有显式结算状态与稳定 ID。
- 成绩确认之前必须有可见的结果核对和「确认后不可撤销」提示；已有确认弹窗可以复用，避免增加冗余步骤。
- 赛事等级/规则变化不改变已结算比赛所使用的 K；快照中保存实际参数。

### 4.4 防刷分、赛季与补录

- 保留提交即占额度、待确认驳回释放的设计；不要改为仅确认时计额度造成批量提交绕过。
- 新计分资格不再在读榜单时调用 `findCappedMatchIds` 动态筛选。
- 每条新提交日常比赛保存服务端确定的额度赛季标识；建议使用提交时当前赛季。旧日期补录也占当前提交赛季额度，不能伪造日期逃避上限。
- 跨赛季未确认比赛保留提交时的额度归属，不在确认时再次占用新赛季额度。
- 赛事正式比赛继续沿用现有额度豁免范围。
- 已结算比赛不释放额度；驳回只能释放自己确实占用的额度一次。
- 新赛季编号递增；建议不允许通过任意历史 resetTime 重写已确定的赛季边界。保留测试注入时钟即可，不将测试便利暴露为生产绕过。
- Elo 表主键不包含 seasonId；交手额度与积分按赛季，评级跨赛季连续。

## 5. 数据结构与仓储

以下集合名是建议；实施者可按现有约定调整，但隔离维度和不变式不能删。

### 5.1 `memberRatings`（数据库物理名称统一记录）

```js
{
  _id: ratingKey({ schoolId, association, userId, pool }),
  schoolId, association, userId,
  pool: 'singles', // 或 doubles
  elo: 1450,
  startElo: 1450,
  matchCount: 0, wins: 0, losses: 0,
  lastMatchTime: null,
  lastSettledAt: null,
  lastSettlementSeq: null,
  lastLedgerId: null,
  version: 0,
  algorithmVersion: 'elo-v2',
  createdAt, updatedAt
}
```

- 不把评分直接写为全局 `users.elo`。
- 使用项目现有的确定性键编码约定，避免简单拼接带分隔符的任意用户输入造成碰撞。
- 核心金额式状态必须校验有限数字。已有评级损坏时拒绝结算并报告，不允许悄悄当作初始值覆盖。
- 数据库存储精度沿用算法输出；页面展示取整不能反写入评级。
- 每次比赛结算该池 version +1；双打更新四人。其他池不变。
- 转校、停用、离校只影响可见性与操作权限，不删除旧校评级，不重算对手。

### 5.2 比赛上的结算快照

```js
settlement: {
  id: /* 由比赛 ID 确定的稳定 ID */,
  status: 'rated', // 或 excluded
  exclusionReason: null,
  settledAt,
  settlementSeq,
  algorithmVersion: 'elo-v2',
  configSnapshot: { /* 实际 divisor、K、zeroSum 等必要参数 */ },
  pool,
  expectedA, expectedB,
  players: [
    { userId, side, pool, isWin,
      eloBefore, eloDelta, eloAfter,
      ratingVersionBefore, ratingVersionAfter }
  ]
}
```

- 沿用 stats 构建器需要的 DTO 时，可在适配层映射成顶层 `players`，不必让前端全面改数据形状。
- 比赛快照是比赛结算的不可变依据；不要再由当前评级反推历史赛前分。
- 不计分比赛必须写明确原因，例如 forfeit、college_doubles。不要产生伪造的 0 分计分场数。
- 确定同一批配置的语义版本；仅存一个版本名字而没有参数或对应代码记录，不足以解释历史。

### 5.3 管理员评级调整（仅当接续现有功能时）

- 以独立 adjustment 记录保存 userId/pool/scope、before、after、delta、原因、操作者、请求幂等键、序号和时间。
- 和评级更新放在同一个事务，复用范围序号以解释图表中的分数跳变。
- 不改场数与胜负，不把 adjustment 伪装成比赛，不修改既有比赛快照。
- 取消旧 `eloOverrides` 时间线回放。首次出场前的初始分设置和出场后的当前分调整应有明确区别。
- 若没有当前可达入口，不因这个设计额外扩张产品范围；删除确认为废弃的旧入口/台账引用即可。

### 5.4 仓储与索引

- 同时扩展云端和内存仓储，支持按确定 ID 读写评级、范围计数。
- 评级范围列表、按用户/池取评级、个人结算比赛分页应在数据库侧约束 scope。
- 新集合加入 `forScope` 的隔离检查；按 ID 读取后仍校验学校/协会。
- 不在事务中做集合条件查询；当前 cloud-repo 明确禁止此用法，应先用可推导的主键读文档。
- 个人战绩建议新增可索引 participantIds 并按 scope/user/seq 读取；根据实际云数据库查询能力制定索引，不能假定所有组合索引都支持。
- 如需要全榜计算准确名次，可以先读取本范围评级再排序；这是可接受的第一版。不得为了一个人成绩读取全部比赛。
- 排名时还需过滤有效会员与性别，保证名次、总人数、百分位口径一致。不要仅查评分前十后再过滤导致人数错误。
- 云端事务当前有内部写预算配置，不能把注释里的预算当成云平台官方限制。真实 SDK 事务能力、重试与索引限制需要实施时查官方资料或实际验证。

## 6. 核心结算流程

推荐新增服务 `school-rating-service.js`，将「纯计算」与「事务读写」分开。文件名可调整。

外层确认流程示意：

```text
检查请求形状
→ 开启事务
  → 重读有效身份、角色、学校/协会与比赛
  → 校验范围与读取权限
  → 若已有最终结算：鉴权后返回既有结果，不加分
  → 校验本次确认权限、待确认状态、有效比分和父赛事状态
  → 校验参赛者与不计分条件，读取规则/赛事等级
  → 点读全部评级与范围序号文档
  → 缺失评级按固定起点初始化，存在则严格校验
  → 纯函数计算一次赛前快照和分差
  → 原子写评级、比赛 ACTIVE+结算快照、序号、审计
→ 事务成功
→ 幂等推进个人赛事/学院大场/下一轮
→ 返回既有接口需要的结果
```

实施约束：

1. `settleMatchInTransaction(tx, ...)` 不得自己再开启嵌套事务。
2. 使用现有 `calculateMatchRatings`；给它事务内读取的最新参赛者分数与场次。
3. 不用事务外读取的 Elo 计算后直接覆盖数据库。
4. 同一选手同时确认两场，后一事务应冲突重试并重新读取计算；不能两次都从同一旧值计算后丢掉其中一场。
5. 不只依赖接口请求 ID 防重；相同比赛换一个请求 ID 也只能结算一次。
6. 已结算重复确认要保证有权限的重试能成功获取结果，同时不能绕过 scope/账号访问检查。
7. 事务回调可能被 SDK 重试，禁止在回调里发送消息、推进下一轮、写外部日志服务等非事务副作用。
8. 校验 2/4 人、去重、队伍合法、结果合法、类型映射与赛事归属；失败时所有写入一起回滚。
9. 同场若等级取自 match.level 优先还是 event.level，保留当前优先级并写快照；不得相信未验证的客户端 level。
10. 弃权和其他不计分路径也要经过最终状态封口，避免 ACTIVE 记录缺少结算决定。
11. 晋级失败不回滚已提交 Elo。重复确认/重试任务应能再次调用幂等推进，并返回可理解的结果。
12. 不要通过允许已生效比赛重新写比分来修复晋级失败。

## 7. 取消撤销：服务端与 UI 都要完成

### 7.1 必做范围

- 从 action 白名单、云端注册、mock 注册、客户端门面和写操作清单移除 `revokeSchoolMatch`。
- 删除对应实现、导出、权限按钮与事件处理。
- 移除学院赛「撤销后回收大场结果」的专用依赖，确认无其他调用后再删除辅助函数。
- 保留待确认驳回、拒绝理由和额度释放，必要时将状态语义改名为 REJECTED；若沿用 REVOKED 常量则明确只用于未生效拒绝，不保留已生效撤销能力。
- 不保留可通过旧 action 或内部导出调用的撤销后门。
- 全局检查实时比分提交、赛事编辑、学院赛结算是否还能间接修改已生效结果。

### 7.2 交流赛与非比赛撤销

用户提出取消比赛撤销功能，需检查 `pages/school-exchange` 的撤销比分入口。其业务实现可能独立于个人 Elo：若是已确认比赛结果撤销，按同样不可撤销规则删除；若是确认前的草稿清空，应保留但明确标成编辑/清空草稿。

不要误删撤回报名、取消训练、撤回申请等非比赛结果功能。不要为了统一代码把交流赛加入 Elo。

## 8. 改造读取与积分

### 8.1 成绩与战绩

- `getSchoolRanking`：从本范围会员与评级建立榜单；保留原榜单字段、男单女单双打分类、无场次不上榜规则。
- `getSchoolMemberStats`：按请求用户取得两池评级及积分；未出场用户正常显示初始值，不强制建立数据库记录。
- `getSchoolMemberProfile`：评级来自评级表，历史和走势来自结算快照；交锋、搭档、近期状态复用原纯构建器或轻量适配。
- 读取权限与会员可见性继续执行；历史里离校/停用选手可用脱敏/保留名称展示，不因名单里缺人导致别人的战绩读取失败。
- 稳定排序：Elo、既有次级规则和 ID，确保分页/并列名次不抖动。
- 即使用户档案改变、赛事名称改变，已结算分差不变。
- 优先保持前端 DTO，修改来源而非无必要重写整套 UI。
- 必须移除所有在线成绩请求中的 replaySeason 调用，而不是把回放换个函数名继续藏在读取端。

### 8.2 积分独立聚合

推荐提取 `school-points-service.js`：输入范围、赛季、赛事结果、训练事实，输出每个会员的当前赛季积分。

- 赛事积分按已结束赛事最终名次计算，保留现有等级规则与双打不发赛事积分的规则。
- 按实际结束时间 `finishedAt` 等既有时间优先级处理赛季，不直接拿计划开始时间替代。
- 无已确认小场但存在有效最终名次时仍可获得赛事积分；不要引入「必须有 Elo 快照才发积分」的新限制。
- 训练积分继续使用已确认签到事实，保持去重与原权限规则。
- 赛季重置只改变积分统计范围和额度赛季，不改评级。
- 原先比赛 `players.pointDelta` 是派生展示位置，不能迁入不可变 Elo 快照后期待赛事结束再改它。应在读 DTO 时关联赛事积分，或明确将积分展示为独立条目。
- 如果沿用原「赛事分挂在该用户赛事最后一场」展示，定义确定的最后一场与唯一挂载位置；积分总数不能因为无法挂载而漏发。
- 积分聚合可以读本范围积分事实，但不得为了它重新加载所有 Elo 比赛。

## 9. 删除旧回放与替换开发工具

等新链路接通并验证后再删除，避免中途靠大量 stub 让测试假通过。

### 9.1 应删除或重构的内容

- `miniprogram/services/replay.js` 与其云端镜像。
- `runReplay`、`replaySeason`、`planInitialRatings`、仅服务旧追溯定级的观察采集与配置。
- 不再使用的 `eloOverrides`、本地 Elo 时间线台账及旧缓存构建逻辑。
- 仅为回放锚点存在的逻辑/字段；先辨别它与积分赛季边界不同，不能把 resetTime/seasonNumber 一起删除。
- `rating.js` 中若不再有合法用途的 `revertMatchResult`。
- 仅验证旧业务的测试应改为新规则测试，不能无解释批量删测试来凑通过率。

### 9.2 隐性依赖必须接续

- `rating-cap.js` 当前从 replay.js 导入 `compareForReplay`。如果额度/列表仍需排序，将必要排序函数独立到 match-order 模块；不得为了一个 comparator 保留整套回放。
- `stats.test.js`、`seed.test.js`、导入测试、训练积分测试可能调用回放制造夹具，改为通过新结算内核生成合法快照。

- 推荐演示生成器按确定顺序逐场调用同一个纯结算内核累积数据，首次初始化时一次完成。它是新业务的夹具生成，不是旧两遍回放的保留。
- 若 mock 初始化变成异步，所有读取必须等待初始化完成，避免首屏空榜与偶发竞态。
- 导入工具不应直接产出可绕过结算的 ACTIVE 文档。选择改为待确认导入，或者受控工具调用同一新结算服务；在工具说明与测试中固定一种方式。
- 没有生产历史迁移需求，不要新写大规模旧引擎回填框架。
- 算法实验脚本若依赖旧定级语义，更新到新结算或明确退役，不能留下运行即找不到模块的脚本。

### 9.3 镜像同步

业务源代码主要在 `miniprogram`，`cloudfunctions/data/lib` 是镜像。不要手工维护两套。

更新 `tools/sync-cloud-lib.js` 的清单，加入新服务，移除 replay。确认同步脚本是否会清理已移除清单的旧文件；如果不会，准确删除旧镜像文件。

更新镜像测试，不再 require 已删除 replay。保留字节一致、模块可独立加载和新算法行为一致的检查。

## 11. 必须覆盖的验收用例

测试应断言业务结果和持久化事实，不只检查实现细节或 mock 调用次数。

### 11.1 数学与状态

- 同分单打、强弱胜负、双打、赛事 1/2/3 级与日常 K，保持原算法结果。
- 单双打隔离、男女榜共享单打池、学校和协会隔离。
- 首场初始化正确；无场次展示正确；后续改性别不重置分数。
- 新人第二/第五/第六场不会修改已经保存的第一场快照。
- startElo、场数、胜负累计正确；新赛季不清 Elo。
- 弃权/学院双打不计 Elo，也不增加评级场数；普通双打按既有规则计分。

### 11.2 并发与原子性

- 同一场重复确认、多请求 ID 重复确认，只有一次分数变化和一份结算事实。
- 同一用户并发确认两场，最终状态等价于两种合法串行次序之一，绝无丢失更新。
- 两场无共同用户并发确认仍获得唯一序号。
- 在写第二名/第四名评级、写比赛、写审计时注入失败，全部回滚。
- 事务回调重试不会重复生成外部副作用。
- 已提交但响应丢失后重试返回已结算结果；晋级失败可补做，Elo 不重复。
- 内存仓储需要真实模拟隔离/回滚/冲突，不能用 `transaction(fn) => fn(repo)` 证明并发正确；无法本地验证的 SDK 行为单独列明。

### 11.3 权限与不可变

- 停用账号、失效学籍、无权限用户不能确认或调整评级。
- 跨校/跨协会伪造 ID 无法读写。
- 老撤销 action 被拒绝，UI 不提供撤销已生效比赛。
- 已结算比赛不能经录分、实时比分、弃权、赛事编辑、学院大场操作变更结果。
- 交流赛的已确认结果同样不可撤销，但不因此产生个人 Elo。
- 待确认驳回仍有效，理由保留，额度只释放一次。

### 11.4 日期、额度、赛季

- 倒序确认的比赛按结算顺序连接分数；历史补录不会改已有快照。
- 补录不回退 lastMatchTime，不可借旧 matchTime 绕过当前提交赛季额度。
- 双打四组跨队额度保持一致；赛事豁免不变。
- 跨赛季 pending 确认/驳回使用原预占归属，无重复占用/释放。
- 并发提交最后一个额度不会超限。

### 11.5 读端与积分

- 排行榜与会员详情 Elo 一致；个人曲线前后衔接；分页无重复/遗漏。
- 排榜过滤离校/停用会员，但其历史对手的分数与战绩不改变。
- 只读请求不写库，不调用旧回放，不扫描所有学校比赛。
- 赛事积分、训练积分、新赛季边界、无可挂载比赛的赛事名次均正确。
- Elo 快照不因后来发赛事积分而被重写；展示积分不重复。
- mock 和云端共享相同新结算业务实现；演示入口、榜单、个人页不空白/崩溃。
