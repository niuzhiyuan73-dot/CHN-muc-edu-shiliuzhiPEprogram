## 1. S0 冻结的试点规则

用户已同意按建议实施，第二所模拟学校指定为北京航空航天大学。本轮采用以下规则：

| 项目 | 本轮约定 |
| --- | --- |
| 学校 | `muc` 中央民族大学、`buaa` 北京航空航天大学；北航为模拟试点 |
| 项目 | 保留 `pkb / tt / bd`，与 schoolId 共同定位学校协会 |
| 学校接入 | 受控目录配置；不开放用户自助创建 |
| 身份 | 全局账号唯一，一个有效主要学校身份；历史身份保留 |
| 参与资格 | 本校有效身份可参与本校启用项目；浏览外校不产生资格 |
| 管理权限 | 平台、学校、协会、学院四级明确授权；不自动继承旧数值 ADMIN |
| 跨校计分 | 以后通过邀请赛开放，首版不进入校内 ELO 或积分；S1 不开放跨校参赛 |
| 学院目录 | 民大沿用当前 COLLEGES；北航为模拟样本，不代表其正式组织设置 |
| 公开范围 | 校内名单默认受限；公开投影与赛事例外权限在 S2/S4 实现 |

平台管理员管理外校资源不等于取得该校参赛资格。新权限函数将管理能力和参赛身份分别判断。

## 2. S0 字段与主键字典

字段名和状态值按本轮代码固定。新模型的状态使用字符串，不能将旧 USER_STATUS 数值直接写入新集合。

| 对象 / 数据库集合 | 关键字段 | 主键与约束 |
| --- | --- | --- |
| schools | schoolId、name、shortName、status、configVersion | `_id = schoolId`；学校 ID 使用小写字母、数字、下划线、连字符，首位字母，最长 40 |
| school_associations | schoolId、association、name、status | `schoolAssociationKey(scope)`；一校一项目一个协会 |
| colleges | schoolId、collegeId、name、status | `collegeKey(schoolId, collegeId)`；名字可重复，ID 按校隔离 |
| users（新增字段） | platformStatus、platformRole、primarySchoolId | 用户原 ID / OpenID 不变；新权限不读取旧 role 数值作为平台角色 |
| school_members | userId、schoolId、collegeId、studentId、status、appliedAt | `schoolMemberKey(userId, schoolId)`；学号为字符串，不丢失前导零 |
| school_roles | userId、schoolId、role、status | `schoolRoleKey(userId, schoolId)`；当前校级角色为 admin |
| memberships（新范围行） | userId、schoolId、association、role、collegeId、status | `schoolMembershipKey(userId, scope)`；角色 leader / staff；staff 带学院 ID |
| member_ratings | userId、schoolId、association、initialElo、currentElo | `ratingKey(userId, scope)`；currentElo 每池为完整 `{value, at}` 事件数组，at 为毫秒时间戳 |

学校/组织/授权状态：`active / disabled`。学校身份状态：`pending / active / rejected / left / disabled`。平台状态：`active / disabled`；平台角色：`member / admin`。

本轮的学校目录生成器每次返回独立对象，不能通过修改一份结果污染后续测试。学院 c01 等编号只用于试点种子；生产目录必须固定保存 ID，不得每次按名称排序重新编号。

`schoolScope({schoolId, association})` 校验显式范围并返回冻结对象。缺失学校或未知项目直接报错。`belongsToSchoolScope` 不把旧的无学校记录默认划进任何学校。

`schoolKey` 对各组成段分别转义，避免分隔符造成同键。派生角色、评级、缓存键都可区分两校同一用户、同一项目。

### S2 必须实现的身份一致性约束

模型已留出字段，但本轮没有开放身份审批写入口，以下不宣称已完成：

- 同一用户最多一个有效主要学校：审批事务同时更新 primarySchoolId 和学校身份。
- 同校学号唯一：增加事务内唯一占用记录，配合审批、转校及重新绑定规则；不同学校相同学号合法。
- 审核操作人、审核时间与理由、转校历史、授权变更记录必须落审计日志。
- 离校/转校的旧权限失效，进行中赛事的参赛归属按既定规则处理。

新增纯模型、申请和权限模块纳入共享库同步，云函数镜像共 34 个文件。

### 仓储用法

```js
const scope = { schoolId: 'buaa', association: 'pkb' };
const local = repo.forScope(scope);
const matches = await local.matches.list(); // 数据库条件查询，自动读完本范围各页
const match = await local.matches.getById(id); // 外校或其他项目返回 null

await local.transaction(async (tx) => {
  await tx.events.insert({ _id: eventId, title: '模拟赛事' });
  // 仓储盖上学校与项目，拒绝覆盖已有外校同 ID 的记录。
});
```

范围接口提供 list / getById / insert / set / update。新集合原始接口提供 list / getById / set。原有单校方法保留，S2 逐处理器替换，避免本轮改变旧页面行为。

范围外记录不可读，已存在的范围外同 ID 记录不可覆盖。写入学校字段与绑定范围冲突、记录 ID 不一致、更新不存在的记录、重复 insert 都拒绝。归属检查和写入在同一事务；事务内禁止集合查询。

学校身份、校级角色和学院按学校查询，不额外要求 association。比赛、赛事、名单、排阵、实时比分、评级、赛季及快照同时按学校与项目查询。

**仓储范围保护不等于用户授权。** S2 处理器必须先通过 school-context 与具体能力检查，验证父赛事/比赛的归属及业务状态，再进行仓储写入。原始仓储仅供可信服务代码、迁移与测试使用，不直接暴露给客户端。

### 本地模拟数据

`createSchoolDemoSeed()` 提供民大/北航各一位模拟校管理员和普通会员。所有账号的平台角色均为 member，校管理权来自 schoolRoles；两校故意使用相同测试学号，以验证它不是全平台唯一。

模拟 OpenID 以 `mock_openid_` 开头，仅用于测试。该生成器不写真实云数据库，不接管现有 mock.js 的默认账号，也不把北航数据混进现有页面。

## 4. 验证与已知边界

新增 30 项测试，覆盖：

- 双校目录、同名学院、相同学号样本，以及主键和范围校验。
- 17 类范围集合的列表、直接 ID 读取、跨校写入拒绝与本校更新。
- 项目、评级、赛季、榜单缓存命名空间与异步内存容器隔离。
- 事务回滚、事务内禁止列表查询。
- 校级/协会/学院权限、停用/离校/转校指针、错误归属角色、访客与平台管理员参赛限制。
- 云适配器按学校/项目下推条件，完整读取 205 条本范围记录；缺学校的旧记录不会被纳入。

```powershell

node --require ./.review/baseline-preload.cjs --test "tests/**/*.test.js"
```

全套基线使用原测试演示账号 u06，工作区 u01 设置保持不变。本轮全套测试数为 2139。

云适配器测试使用 SDK 形状的本地替身，验证查询、分页和事务调用契约，不代表真实云端锁冲突、索引或部署已验证。内存仓储沿用原测试实现，不模拟数据库并发重试。

本轮尚未接入客户端门面 `forScope`、学校切换界面、旧业务 dispatcher、会员审批、全量计分迁移或跨校赛事；它们属于 S2 及以后。不能据此直接开放第二所学校的真实业务。

## 5. S2 接续清单

1. 盘点现有读写 action，逐一标明学校、项目、父资源与可见字段，替换旧全局有效角色判定。
2. 接入学校身份申请/审批事务、唯一学号占用、主要学校指针、审计及版本失效。
3. 客户端 forScope 与 mock 全台账双范围化；学校目录接入页面，处理旧请求回流。
4. 校内比赛、赛事、学院赛、实时比分的父子归属校验，按范围读取完整回放输入。
5. 迁移旧角色、评级配置与赛季；将原 users 的身份字段逐步迁入 schoolMembers。
6. 云环境建立新集合，按 schoolId / association / _id 等实际查询创建索引并测分页；真实旧数据盘点、备份及学校映射在 S3 上线前完成。

原单校流程继续走旧入口。S2 必须整条业务链闭环并通过权限测试后，才切换到新上下文；不能只在旧请求上增加 schoolId 就宣布完成多学校支持。
