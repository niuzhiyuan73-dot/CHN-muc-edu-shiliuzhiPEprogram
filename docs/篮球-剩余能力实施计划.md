# 篮球：剩余能力与缺陷修复实施计划

日期：2026-10-20
前置：`篮球协会-需求与实施规划.md`（A–D 期已落地）、103 项篮球测试全绿
范围：**不含**云端部署与真机验收；三人制、小组赛接淘汰赛、逐球事件流水均为明确非目标

---

## 一、结论先行

现有 103 项测试全绿，但其中 4 条缺陷属于「测试没覆盖到真实并发与真实可见性」，
不是新需求。因此实施顺序不能按功能清单从上往下做，而要**先让已交付的能力可信**：

1. **P0 可信性**（本轮）：并发闭环、统计准确性、发布隔离。这三项不修，
   后面新增的赛程、名单、荣誉都建立在会算错的数据上。
2. **P1 赛程管理**：逐场时间 / 场地 / 裁判 / 记录员，是「办赛」真正缺的那一段。
3. **P2 报名与出场名单**：选人、球衣号、单场实际出场。
4. **P3 个人与球队成绩**：我的球队、参赛经历、团队荣誉、跨赛事累计、球队战绩页。
5. **P4 实时协作**：主记录员占用、交接、实时同步、冲突恢复。

P0 与 P1 之间没有依赖倒置风险；P3 依赖 P0 的统计口径（未记录 ≠ 0）；
P4 依赖 P0 的版本号闭环（否则同步只是把冲突放大）。

## 二、P0：四处缺陷的根因与修法

### 2.1 并发保护没有真正闭环

**现象**：`recordTeamMatch` / `publishTeamMatch` 的读、判、写三步不在同一事务里；
`expectRevision` 可缺省；页面从不传；`matchView` 不返回 `revision`。
本地复现：80:70 被后来的 81:70 静默覆盖。

**根因**（`services/team-event-service.js`）：

- 版本号判定写在统计落库**之后**，即使判失败也已产生副作用；
- 读取用事务外的 `repo`，两个请求各自基于同一份旧快照，后写者覆盖先写者；
- 判定的写法是「只有调用方传了才检查」，等于默认不设防。

**修法**：

- 录分 / 发布 / 统计保存全部改为 `ctx.repo.forScope(ctx).transaction(...)`，
  事务内 `getById` 重读比赛与赛事，权限按最新会籍重判；
- `expectRevision` 与事务内读到的 `revision` 比较，**先判后写**，判不过直接返回；
- `matchView` 返回 `revision`；页面录分、发布、统计都带上打开面板时的版本号；
- 统计的两个队文档在同一事务内写，避免「A 队写成功、B 队失败」的半截状态。

**验收**：两个请求带同一 `expectRevision` 并发提交，只有一个成功，另一个得到
「刚被改过，请刷新」；成功后 `revision` +1。

### 2.2 未统计的指标显示为 0

**现象**：只填得分，榜单的篮板 / 助攻显示 0。

**根因**（`getTeamEventPlayerStats`）：累加器初始化成 `0`，输出时
`out[field] = acc[field]` 无条件回填；`null`（未记录）与 `0`（确认 0）在累加时
被抹平。

**修法**：每个指标单独维护「有值场次」计数；计数为 0 → 输出 `null`，
页面显示 `—`；场均只按「该指标有记录的场次」计算，不按总场次摊薄。
服务端同时下发 `pointsText` 等展示文本，页面不写下标取值。

**验收**：只录得分的球员，榜单篮板 / 助攻为 `null`、显示 `—`；
同一指标两场有值一场没记，场均按两场算。

### 2.3 按节统计的个人合计返回错误

**现象**：两人分别 10 分、3 分，读回来每人都是 13 分。

**根因**（`getTeamMatchStats`）：`totalsOf(rows)` 对**整队**的行求和，
再把同一个 `totals[field]` 填给队里每个球员。

**修法**：按 `userId` 分组后再求和，每人只取自己的行；队级合计另行计算，
仅用于差额提示。

**验收**：两人 10 / 3，读回各自 10 / 3；队级合计 13 只出现在提示里。

### 2.4 公开成绩与审核状态没有隔离

**现象（两处）**：

1. 普通成员在赛事详情能看到「待审核」比分；
2. 已发布比赛的统计仍可直接改，改完立刻影响球员榜——等于绕过了审核。

**根因**：

1. `matchView` 无可见性分层，`getTeamEvent` 把 `reviewing` 的比分原样下发；
2. `team_match_stats` 只有一份工作副本，`saveTeamMatchStats` 对已发布比赛不加限制。

**修法**：

- **比分可见性**：`matchView` 增加 `canSeePending`；非管理者、非参赛队队长看到的
  `reviewing` 比赛只显示「待审核」，比分、胜方、弃权一律不返回；
- **统计审核版本**：统计文档增加 `status`（`draft` / `pending` / `published`）与
  `published` 快照。已发布比赛的统计修改写入 `pending` 工作副本，**对外仍读
  `published` 快照**；新增 `reviewTeamMatchStats`（管理员）通过或退回后才切换指针；
- **发布即发布统计**：`publishTeamMatch` 通过时把当时的统计工作副本一并转成
  `published` 快照（发布一场 = 发布这一场的比分与统计），驳回时两者一起退回；
- 球员榜只读 `published` 快照，永远与公开页面一致。

**验收**：普通成员看不到待审核比分；已发布比赛改统计后，球员榜数值不变；
管理员「通过」后才变；「退回」后回到原快照。

## 三、P1：单场赛程管理

**现状**：抽签能自动生成对阵，但每场只有建赛时的统一时间与地点，没有裁判、记录员入口。

**交付**：

| 能力 | 说明 |
|---|---|
| `updateTeamMatchSchedule` | 逐场改 `matchTime` / `location` / `refereeId` / `recorderId`，带 `expectRevision` |
| 裁判、记录员候选 | 本协会正常在册会员；记录员需为协会成员，裁判不得同时是两队队长（避免自判） |
| 赛程页入口 | 每场「改期 / 换场地 / 指派」浮层，管理员可见 |
| 批量顺延 | 同一轮统一顺延，避免逐场改二十次 |

**验收**：非管理员改不了；指派非在册会员被拒；改期不改变签表与比分；
并发改同一场只有一次生效。

## 四、P2：报名名单与单场出场名单

**现状**：报名直接带入全部在队成员，没有选人、球衣号、单场实际出场。

**交付**：

| 能力 | 说明 |
|---|---|
| 报名选人 | 队长在报名时勾选参赛队员（默认全选，至少 `rosterMin`），不再强制全队 |
| 球衣号码 | 报名名单内唯一，0–99；重复即拒 |
| 单场出场名单 | `team_matches.lineups[side]`：从报名名单里勾「本场实际出场」，开赛即定 |
| 统计面板按出场名单列人 | 未出场者不出现在录分格里，避免「没上的人也记 0 分」 |

**验收**：未报名者不能出现在出场名单；号码重复被拒；统计面板只列实际出场者。

## 五、P3：个人与球队成绩展示

**现状**：赛事内有球员榜；个人页缺「我的球队 / 参赛经历 / 团队荣誉」，也没有跨赛事累计与球队战绩页。

**交付**：

| 能力 | 说明 |
|---|---|
| `getMyTeamProfile` | 我的球队（含队长标记）、参赛经历（赛事 / 名次 / 场次）、团队荣誉 |
| 跨赛事累计 | 从已发布单场聚合，不落表；按赛事分组，避免不同届混算 |
| 球队战绩页 | 一支球队的历史赛事与胜负，归档后仍可查 |
| 个人页分区 | 技术统计与球拍运动的等级分**分栏**，不混算 |

**验收**：退队后历史仍显示；跨赛事累计只算已发布；普通成员能看到自己的，看不到别人的私密信息。

## 六、P4：多记录员实时协作

**现状**：打开—填写—保存的离线口径，没有占用、交接、同步。

**设计要点**：

| 问题 | 处理 |
|---|---|
| 谁在录 | `team_matches.recorder` 记录**主记录员**，带 `leaseUntil` 心跳租约（默认 60 秒） |
| 抢录 | 第二人进入只读模式，可「申请接管」；主记录员超时未续租自动释放 |
| 交接 | 主记录员主动交接给指定人，交接写审计（谁交给谁、何时） |
| 实时同步 | 轮询 `getTeamMatchStats`（带 `revision`），版本变了就提示「有人改了，已刷新」 |
| 冲突恢复 | 保存带 `expectRevision`，失败时保留本地输入并提供「以服务端为准 / 重新提交」两条路 |
| 弱网 | 写动作幂等 `requestId`，重试不重复加分 |

**非目标**：逐球事件流水（谁在哪投了两分）——首版明确不做，仍按「每节每人一行」。

## 七、明确不做的

- 三人制（仅保留 `sportFormat` 扩展点）
- 小组赛接淘汰赛（建赛接口直接拒绝，不静默降级）
- 逐球事件流水
- 云端部署与真机验收（本轮排除）
- 篮球接入球拍运动的逐球计分台（`live-score.js` 是球拍专用，团队赛不复用）

## 十一、P2 实施记录（2026-10-20）

| 项 | 落点 |
|---|---|
| 报名选人 | `submitTeamEntry` 接受 `roster: [{ userId, no }]`；不传时保持旧口径（全队在队成员），老调用方与演示数据不受影响 |
| 球衣号 | `no` 0–99，同队唯一；空号允许（先报名后补号），存进报名快照 |
| 报名面板 | `getTeamEntryRoster`：本队在队成员 + 已选与已填号码（队长或协会负责人） |
| 重新审核 | 改动「已通过」的报名会退回 `submitted` 并清掉原审核签字（内容变了，签字不算数） |
| 出场名单 | `getTeamMatchLineup` / `saveTeamMatchLineup`：按 A/B 侧存 `match.lineups`，默认全选，队长只能定自己一侧 |
| 统计收敛 | 定过出场名单后，`getTeamMatchStats` 只列出场者；`saveTeamMatchStats` 与 `recordTeamMatch` 也只认出场名单上的人 |

口径：
- 出场名单只能从**报名快照**里挑，不能拿「现在队里有谁」顶替；
- 人数下限取规则快照的 `minOnCourt`（默认 2）——低于它就是自己判负；
- 已发布的比赛出场名单锁定，不能再改；改名单与改比分一样带 `expectRevision`；
- 出场名单面板只开给当事两队与协会负责人（面板里的 `matchView` 会带待审核比分）。

测试：`tests/team-event-lineup.test.js` 10 条（选人、人数边界、重号、非本队、重新审核、
默认全选、跨侧越权、名单外的人、统计只列出场者、发布后禁改），页面侧 +3 条与 1 条改写。
