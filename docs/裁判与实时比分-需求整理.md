## 一、需求原文

> 现在我想要给每场赛事里的比赛都加上裁判功能，就是管理员在每个小场（学院赛是大场）录分之前可以指定一个裁判，不指定裁判的局和之前完全一样，指定裁判的局只有裁判和管理员才能录分和确认，然后增加一个实时比分功能，我需要一个事实录入当前比分的功能，录入比分时处于横屏，每一球判给一边得分，同时把当前比分实时更新在外面的界面上，这些都是很大的功能增加，把这些需求整理一下，给出建议和方案，成为一个新的word文档，然后找我确认。

两点理解已与需求方对齐：

1. 「事实录入当前比分」理解为**实时录入当前比分**（逐球记录，而非赛后一次性补录）；
2. 「外面的界面」= **现有小程序里所有显示该场比赛的界面**（赛事页 → 学院赛 → 对应比赛、比赛页），其他用户在自己手机上实时看到比分，位置就是现在显示终局比分的位置。详见 §3.4 与 Q6。

## 二、需求拆解

| 编号 | 需求 | 涉及体系 | 类型 |
|---|---|---|---|
| 1 | 管理员在「小场」录分**之前**指定一名裁判 | 个人赛 + 学院赛 | 新增字段 + 新增写接口 |

## 三、现状与根因

### 3.1 录分与确认是两把不同的尺子

现有两套权限，都是一场比赛一个判定：

- **录分权** `canRecordScore`（`services/match-record.js:116`）：参赛者本人，或管理员，或**本学院有人上场的干事**。
- **确认权** `canConfirm`（`services/match-record.js:151`）：**对手方**（站在录入者对面的人），或管理员；mock 下放宽为「参赛即可」。

一个特殊口径值得留意：录入者不在场上时（例如学院赛小项由**干事代录**），`canConfirm` 会退化成「**参赛者任一方都能确认**」（`match-record.js:161-162`）。也就是说学院赛小项的确认，今天并不严格是「对手确认」。

无论哪种口径，判定依据都是「你是不是这场的人 / 你这个学院有没有人上场」。**裁判这个新角色不属于任何一方**，现有两个函数都表达不了它——这是本次要改的第一处根因。

### 3.2 学院赛的三级结构决定了裁判的粒度

学院赛是 `赛事 → 大场(tie) → 小项(leg) → 比赛(match)`。一个大场包含男单 / 女单 / 男双 / 女双 / 混双若干**小项**，每个小项落成一场独立的 `matches` 记录（`_id = l_{eventId}_{tieId}_{legNo}`，见 `services/college-tie.js:209`、`:266`）。

需求说「学院赛是大场」，即**一名裁判管一个大场的全部小项**。于是：**指派动作发生在大场层**（一个界面、一次操作），但**权限判定发生在比赛层**（真正被读写的 `matches` 记录）。中间的「大场裁判 → 小项比赛」怎么落，是本次要定的第二处口径。

### 3.3 项目当前没有任何实时能力（本次最大的技术缺口）

全仓库排查结果：

- **没有** `db.collection().watch` / `onSnapshot` / WebSocket / `connectSocket`；
- **没有**订阅消息（`requestSubscribeMessage` / 模板消息）；
- **没有**任何定时器（`setInterval` / `setTimeout`；云函数无 `config.json`，无触发器）；
- **没有** event bus / storage 监听；
- 数据新鲜度**完全靠**「页面 `onShow` 重新拉一次」+ 下拉刷新（如 `pages/match/match.js:73-84`）；
- 客户端云调用是**单次 `callFunction`，无重试、无超时、无并发控制**（`services/cloud.js:32-46`）；
- 全项目**没有一个横屏页面**，`app.json` 无 `pageOrientation`，也未分包。

所以「把当前比分实时更新在外面的界面上」不是加个字段就能成的事，**必须新引入一条跨设备同步通道**，取舍见 §6.3（Q2 已拍板）。

### 3.4 「外面的界面」= 现有页面，不新开大屏页（Q6 已拍板）

已与需求方对齐（见 §5.1 Q6）：**不新开专门的大屏页**。比分就落在**现有那些显示该场比赛的页面**上——赛事页 → 学院赛 → 对应比赛、比赛页——位置与今天显示的终局比分**完全同一处**，只是内容从「终局」变成「实时」。

这带来两个结论：

- **场景仍是跨设备的**：看的人是**另一位用户、在另一台手机上**（不是裁判自己切页面）。因此同步通道依然必需，只是**消费端是既有页面**，不需要新页面、不需要二维码 / 投屏。
- **改动方式变成「就地替换」**：这些页面本来就通过 `getMatches` / `getCollegeEvent` 之类的读接口拿到 `scoreA` / `scoreB` 并渲染。实时比分只需在**服务端读接口**里把「该场正在进行的实时比分」并进返回结果，页面拿到的字段位置不变，**页面渲染代码几乎不用改**（见 §6.3）。

顺带一提，投屏 / 二维码那类「第二块屏」的玩法并未被否决，只是**不在本次范围内**（见 §九）。

### 3.5 为什么不能把实时比分直接写进比赛记录

`matches` 是**回放计分的输入**：`winner` 由 `validateMatchScore` 从比分推出，`isEloEligibleMatch` 只认 `ACTIVE` 且非弃权（`college-tie.js:366`），写库后 `bumpSeason` 让整季回放缓存失效。如果每打一球就往 `matches` 里写一次：

1. 每球一次 `bumpSeason`，整季回放缓存每球失效一次，开销不可忽略；
2. 一条「打了一半」的记录一旦被误判成 `ACTIVE`，就会喂给回放一个半场比分；
3. `matches` 的语义是「已发生的事实」，不该承载「正在发生的过程」。

结论：**实时比分单开一个集合**（§6.2），比赛记录仍然只在「整场结束、裁判定稿」时写一次。

### 5.2 按默认执行

1. **零回归优先**：未指定裁判时，`canRecordScore` / `canConfirm` 的返回值必须与今天**逐字一致**，由现有测试守住。
2. **失败关闭**：指定裁判后，非裁判非管理员一律拒绝，并给明确文案（如「本场由 XX 裁判执法，仅裁判与管理员可录分」），不做灰按钮、不做静默降级。
3. **管理员兜底永远在**：无论是否指定裁判，管理员始终可以录分、确认、**改派或取消裁判**；裁判临时来不了，管理员取消裁判即回到普通口径。
4. **指派时效**：比赛 / 大场**已生效（ACTIVE）或已结束**后不可改派，避免「改历史」。
5. **历史不回溯**：`referee` 是新字段，历史比赛一律视为「未指定裁判」，行为不变，不回填、不报错。
6. ~~**撤销权跟随录入者**：`canRevoke` 维持「管理员 + 录入者」不变。指定裁判后录入者即裁判，裁定权自然收敛到裁判手上，无需另加规则。~~ **已推翻（后续修订）**：撤销权收归管理员，录入者（含担任裁判的录入者）一并收回。理由与影响见 §10.3。
7. **实时比分只写新集合**：`matches` 只在整场结束定稿时写一次；实时过程全部落在 `live_scores`，且**不触发 `bumpSeason`**。
8. **实时比分沿用现有赛制**：局分、局数直接读该场比赛的 `gamePoints` / `bestOf`，不另设一套规则。
9. **横屏只在录分页**：只有 `pages/live-score`（裁判录分台）强制横屏，写在该页自己的 `.json` 里；查看端是现有页面，布局一律不动。
10. **查看端只读、不打扰**：现有页面显示实时比分时只是把终局比分的位置换成当前比分（并标注「进行中」），不弹窗、不震动、不改变原有交互。
11. **一个真相源**：裁判判定只改 `match-record.js` 一处；实时比分状态机只写在 `live-score.js` 一处；两份都进 `lib/` 镜像，mock 与云端共用。

## 六、建议方案

### 6.1 裁判：一个字段 + 两个判定

**数据落点**——比赛记录加三个字段：

```js
// 个人赛的一场 / 学院赛的一个小项，都落在 matches
referee: '',      // 指定裁判的会员 _id；空串 = 未指定，行为与现在完全一致
refereeAt: null,  // 指派时间（审计用）
refereeBy: '',    // 指派人（审计用）
```

学院赛的大场（`ties`）同时加一个 `referee`，作为指派的界面锚点与改派依据。

**判定改动**——只动 `services/match-record.js`，两个函数各加一道前置闸，其余调用方一律不改：

```js
// canRecordScore：指定了裁判，就只有裁判与管理员
if (match.referee) {
  return actorId === match.referee || Number(role) >= ROLE.ADMIN;
}
// 原有逻辑（参赛者 / 干事本学院 / 管理员）继续往下走

// canConfirm：同样先过裁判闸
if (match.referee) {
  return actorId === match.referee || Number(role) >= ROLE.ADMIN;
}
// 原有「对手确认」（含录入者不在场上时退化为参赛者即可）继续
```

`needsScore`（没比分不能确认）不变。~~`canRevoke` 也不变——裁判录入后就是录入者，本就握有撤销权。~~ **已推翻（后续修订）**：`canRevoke` 改为只认管理员，录入者与裁判都不再能撤；裁判闸不再参与这条判定。见 §10.3。

### 6.3 查看端与实时同步（Q2/Q6 已拍板）

**不新开页面**。查看端就是现有页面，渲染位置与今天的终局比分同一处。

**同步走一个适配器**，页面只认它，不认轮询：

```js
// services/live-watch.js（唯一出口，页面不直接碰 setInterval / callFunction）
// matchIds 变化时自动重订阅；onUpdate 只在比分真的变了才被调用
watchLiveScores(matchIds, onUpdate) -> () => void   // 返回取消订阅
```

适配器内部（当前实现 = 短轮询）：

1. `matchIds` 为空 ⇒ **完全不启表**（没有进行中的比赛就不轮询，这是「不频繁刷新」的第一道闸）；
2. 有比赛时每 **2 秒**（常量）调一次 `getLiveScores({ matchIds })`；
3. 拿到结果先与上一次**逐场比对**，只有**值真的变了**才 `onUpdate`，值没变一个字节都不 `setData`；
4. 页面 `onHide` ⇒ 停表；`onShow` ⇒ 立即补一次再续表（避免后台空转与回前台空窗）；
5. 单次请求失败**静默跳过**这一拍，不弹错、不重试堆积，下一拍照常。

因第 1、3 条，观众端在「没有比赛进行中」时**零请求**，在「比赛进行中但比分没变」时**零重渲染**——这两点是 A 方案不伤体验的关键。

**首屏就有值**：进入页面时既有读接口已带回实时比分（§6.2），适配器只负责后续增量，所以不会出现「先显示 0:0 再跳」。

**查看端只显示**：双方名称（学院名 / 队员姓名）、当前局比分、局数、第几局、进行中 / 已结束。不显示逐球流水、不显示裁判操作。

## 八、工程约束

1. **新增写接口四处同步**：`mock.js`、`cloud.js`、`utils/write.js`、`src/actions.js`；云函数 handler 由 `dispatch.js` 按导出自动登记。四处不一致时 `datasource` / `write` / `cloud-core` 三个测试会红。
2. **权限一律服务端判定**：页面上的显隐只是体验，真正的闸门在 `match-record.js` 纯逻辑（经 `lib/` 镜像被云端复用）。
3. **实时态写库必须幂等**：一球一次写，断线重发 / 连点会重复计分。`recordRally` 带 `rallyId`，服务端按它去重（与既有 `matchNaturalKey` 同一思路）。
4. **并发收敛**：同一场可能两台设备同时判球。写接口在事务内重读当前 `rallies` 长度，不匹配则拒绝、让客户端刷新（与 `confirmMatch` 的「已经处理过了」同一手法）。
5. **每球写不触发 `bumpSeason`**：实时态不进回放，只有定稿提交才 `bumpSeason`。
6. **横屏是页面级配置**：`pageOrientation` 写在新页面自己的 `.json` 里，`app.json` 的 `window` 不动，避免影响其余页面。
7. **零回归有测试兜底**：先补「未指定裁判时 `canRecordScore` / `canConfirm` 与今天一致」的用例，再动实现。
8. **演示要能跑通**：mock 数据源要能完整演一遍「指派裁判 → 横屏逐球 → 查看端同步 → 定稿确认」，与云端同一套纯逻辑。
9. **轮询只在适配器里**：`setInterval` 只允许出现在 `services/live-watch.js` 一处；页面调 `watchLiveScores` 拿取消函数，绝不自建定时器。页面在 `onUnload` 必须调用取消函数，`onHide` 由适配器停表。这样「不频繁刷新」是可被单测覆盖的（假定时器 + 断言「值没变不回调」）。

### 10.3 与原始方案的出入（两处）

**一、学院赛小场首屏实时比分改走批量读。** 方案（§6.2 末）说实时比分「并入既有读接口」，学院赛按 `getMatchRecords({ eventId })` 取。但学院赛小场的 `matches` 有意把 `eventId` 留空（`college-tie.js:296`，小场不计个人赛事积分），按 `eventId` 查台账**永远查不到小场**。改为：详情页把本场所有小场的 `matchId` 收齐后一次 `getLiveScores(legIds)`——与轮询适配器同一个读接口，首屏与增量同源。个人赛仍走台账（其 `eventId` 有值），不变。

**二、撤销权收归管理员（2026-09-14 修订，推翻 §5.2 第 6 条与 §6.1 末）。** 原口径是「管理员 + 录入者」，理由是「谁录的谁最清楚录错了」。但这个理由把**录入者**当成了可信第三方，而录入者根本不是第三方：他是录分时**自己选的**（`buildMatchRecord` 里 `recorder` 取 A 队第一位，录分页也允许挑人）。于是比赛的一方可以自己录分、再自己撤销——不需要伪造比分，只要事后把记录抹掉，等级分照样回到从前。撤销与确认的分量也不对等：确认是**向前**给成绩盖章，撤销是**向后**改写已经计入等级分与积分的账本。

改后：`canRevoke` 只认 `role >= ROLE.ADMIN`（`services/match-record.js`），录入者、干事、裁判一律不放行。

- **不受影响**：**驳回**（`canConfirm`）仍是「对手方 / 裁判 / 管理员」，它在比分**生效之前**，不涉及任何回滚——日常录错了走这条就够了；
- **受影响**：比赛页的「撤销」入口只对管理员显示；学院赛大场页的 `canRevoke` 同源收窄；已指定裁判的场次，裁判也不再能撤销**已生效**的成绩（他仍然能录分、确认、驳回）。

改动落在：`services/match-record.js`（判定）、`services/mock.js` + `src/core/match-handlers.js`（写入端文案与注释）、`tests/{match-record,match-view,datasource,cloud-auth,page}.test.js`。镜像随 `npm run sync:cloud` 同步，云端与本地同一条规则。

其余口径与方案一致，含：每球写不触发 `bumpSeason`（只有定稿才走 `submitMatch → confirmMatch`）、`setInterval` 只在 `live-watch.js`、横屏只写在 `pages/live-score/live-score.json`、Q5 裁判兼参赛在界面上给「兼参赛」提示。计分台页面侧另定了一条方案未写的交互口径：**乐观更新 + 串行队列**，每球带客户端 `rallyId` 幂等，队列排空时才用服务端返回对账。
