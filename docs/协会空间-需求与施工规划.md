## 1. 用户要求与交付边界

### 1.1 用户明确提出的需求

1. 每个协会增加名称为“协会空间”的页签。
2. 空间包含“分组、通知、训练”三个功能。
3. 这三个功能由协会负责人及以上权限的人发起。
4. 分组由发起者选择成员；入组后，成员可以自行退出，负责人也可以移除成员。
5. 原有协会内**赛事**增加可选小组：不限、一个小组、多个小组。管理员（负责人）发布赛事时通过选择小组，规定本次赛事可报名的人员范围；限制小组时，只有被选小组成员可以报名。（**仅赛事**。普通比赛当前只有赛果录入、没有报名，不接小组限制，见 §7.3。此前误写作"比赛和赛事"，已订正。）
6. 通知可以复用公告模板，但发布后仅在所属协会空间内展示。
7. 训练可以复用部分比赛模板。时间、地点必填；人数上限、小组限制选填。
8. 训练详情提供会员报名按钮、签到按钮，并展示已经报名的其他成员。
9. 负责人可以查看所有报名人员。会员点击签到后，还需要负责人再次确认，才算签到成功。
10. 每次训练签到成功，增加 1 点赛季积分。

### 1.1.1 负责人第二轮反馈（2026-10-14，覆盖上表相应条目）

1. **小组限制只加在"赛事"上**（对应上表第 5 条）。此前的"比赛和赛事"是笔误。发布赛事的负责人（管理员）通过勾选小组限定本次赛事**可报名的人员范围**；普通比赛没有报名流程，不加小组。
2. **空间二级默认展示"训练"**，因为训练最常用。
3. **"协会空间"并入工作台顶层四个页签，排在第一个，且每次进入协会即默认展示它**；绑定沿用**全局当前学校**（与排行榜 / 比赛 / 赛事同一把学校开关，不另设学校选择）。
4. 不存在"是学院负责人但不是会员"的情况（学院负责人的身份以在册会员为前提）。若实现中出现该状态，按缺陷上报，不当作需求。
5. 候选成员**多选列表**里不应出现不具备资格的人（如非本协会在册会员）；这是预期行为，保留。
6. 训练积分 / 赛季归属算法的具体实现由本文给出方案（见 §6.3）。
7. **取消"跨赛季确认"**：赛季重置时若仍有未确认的签到（pending），一律**自动退回**，视为该次未参加，不产生积分。不再允许新赛季补确认上一赛季。
8. 会员丧失本校 / 本协会身份后**仍可暂时占用名额**，但在**确认时被自动移除**；不再有"标记待处理"这一步。
9. 训练场景下的**通知触达**与**人数上限**（capacity）的口径，见 §6.2 与 §5.4 的落实方案。
10. **功能开关与灰度**（`associationSpaceEnabled`）的落地方式，见 §10.3。

#### 新增：协会空间"成员"页签

11. 在协会空间内新增**成员**页签，与"分组 / 通知 / 训练"并列（即空间二级为：分组 | 通知 | 训练 | 成员，默认 **训练**）。
12. 页签顶部是**搜索栏**，样式与现有的排行榜 / 比赛搜索一致；输入即过滤，在下方列出**所有满足条件的成员**（例如输入"张"，按既定顺序列出所有名字含"张"的会员）。
13. 点成员**头像**进入其个人主页，便于成员互相认识，也便于管理员等人分发权限。

### 1.2 本方案的推荐解释

这里的“tag”按页面中的 tab／页签实现：在现有协会工作台中增加第四个页签“协会空间”，不是给全局底部导航再加一栏。

“分组”是长期存在的协会成员小组，例如“新手组”“校队组”。它与赛事赛制里的“小组赛分组”“A 组/B 组签表”完全不同。代码用 `associationGroup` 表示成员小组；限制字段用 `audienceGroupIds`；禁止覆盖现有赛事 `groupCount`、签表分组等字段。

“不限”只表示不限制成员小组，仍需满足本校、本协会、有效会员、赛事原有资格、报名时间和名额条件。它不表示允许所有学校的人参加。

多个小组按**并集**处理。例如选择新手组和校队组，属于任一组即可报名；同时属于两组的人只算一个人、占一个名额、获得一次训练积分。

### 1.3 本期不扩展的内容

本期不实现聊天、论坛、自助申请入组、付费报名、候补递补、循环训练自动生成、定位或扫码签到、微信订阅消息推送。通知是空间内的信息展示，不等于向微信用户发送消息。

跨校邀请赛继续使用独立流程。本期小组只存在于一个学校的一个协会内，不把民大小组 ID 塞进北航或跨校赛事。若未来跨校活动也需要小组限制，应另设计“每个受邀学校自己的可选小组”规则。

本期交付包含本地模拟实现、共享业务规则、云端代码与测试。当前没有部署云环境，应明确交付“代码已实现、本地验证通过、云端尚未部署”；不能把本地演示称为已上线。

## 3. 页面与交互设计

### 3.1 页面结构

```text
底部导航： 首页 / 协会 / 我的
协会 → 选择某学校的某协会 → 协会工作台
  协会空间 | 排行榜 | 比赛 | 赛事          ← 协会空间排第一，进入即默认
              分组 | 通知 | 训练 | 成员     ← 二级；默认训练
```

**顶层顺序与默认页**：协会工作台四个页签从左到右为"协会空间 / 排行榜 / 比赛 / 赛事"。"协会空间"**排在第一**，且每次进入协会工作台都**默认展示协会空间**（与原来的默认"排行榜"相反）。四个页签延续现有的懒挂载机制：只有进过的页签才挂上，来回切换不丢状态。

**二级顺序与默认页**：空间内部二级为"分组 / 通知 / 训练 / 成员"，**默认展示训练**（训练最常用）。二级页签同样懒挂载。

**范围绑定**：空间绑定在**全局当前学校**（`school-session` 的当前学校）上，与排行榜 / 比赛 / 赛事共用同一把学校开关，不再为空间单独加学校选择器；切换学校时空间随之切换（按 §9.4 清缓存重载）。

建议新增组件 `components/association-space-panel`（内含分组 / 通知 / 训练 / 成员四子栏目）。顶部保留当前学校、协会名称，禁止仅显示"匹克球"而无法区分民大与北航。原来的 `components/rank-panel` 等三个面板继续保留，仅把"协会空间"插到 `TAB_DEFS` 最前并调整默认值。

空间页签展示入口不等于授予内容读取权限。未登录、非会员、身份审核中，显示明确的加入或登录提示；不要先把完整成员名单下载到客户端再隐藏。

### 3.2 分组页面

普通会员看到可访问的小组名称、说明、人数、“我已加入”标记。建议默认允许本协会有效会员查看本协会小组基本信息，但仅组内成员与空间管理者查看小组成员名单；不提供“自行加入”按钮。

负责人看到“新建分组”“编辑”“管理成员”“归档”入口。新建时填写组名、说明，从本校本协会有效会员中多选成员，可搜索、分页、显示已选择人数。不能只允许选当前第一页。

创建者不自动入组；如果本人需要加入，应在选择名单时显式勾选。创建者可以继续添加成员；其他当前有空间管理权限的人也可以维护。记录创建者用于审计，不赋予永久特权。

成员点击“退出小组”后，本人关系变为已退出，不能退出其他人。负责人移除时记录操作者与时间。退出或移除不删除历史关系与活动报名快照。重新加入必须由管理者再次选中。

### 3.3 通知页面

通知列表按“置顶优先、发布时间倒序、ID 稳定排序”展示；内容包含标题、正文、分类、发布人、发布时间与修改时间。只提供列表和详情即可；分类优先复用原公告分类，不强行增加附件能力。

负责人提供发布、编辑、撤回、置顶；会员只读。被撤回的通知对普通会员不再可读，管理端保留审计记录。

新通知不得进入首页公告列表、旧公告中心、全站公告数量、其他协会空间及其他学校空间。分享直达链接也必须经过同样的后端范围和权限检查。

### 3.4 训练页面

列表区分“可报名 / 进行中 / 已结束 / 已取消”，展示标题、时间、地点、报名人数、名额和小组限制摘要。“进行中”可由服务器时间推导，不必维护额外可漂移状态。

详情会员视角：

- 训练说明、时间、地点、人数限制、小组限制。
- 未报名：显示报名按钮；不满足条件时显示原因。
- 已报名且未开始签到：显示“已报名”和允许时的“取消报名”。
- 签到窗口内：显示“点击签到”。提交后显示“待负责人确认”，不能显示“签到成功”。
- 被退回：显示退回原因，并在签到窗口内允许重新提交。
- 已确认：显示"签到成功"；本赛季计入时显示"本赛季 +1"。已取消"跨赛季确认"（见 §6.3），因此不出现"往季补确认 / 归属原训练时间"这类文案。
- 已报名成员列表：昵称、头像及必要的报名状态，不显示学号、OpenID、手机号、内部权限字段。

详情管理者视角：

- 全部报名记录，可分页筛选“有效报名 / 已取消 / 待确认 / 已确认 / 已退回”。
- 显示对应成员的学校内身份信息，仅限管理需要；默认不额外暴露完整学号。
- 待确认成员逐人提供“确认签到”“退回”按钮；首版不做批量确认。
- 已确认记录可“撤销确认”，必须填写原因；同时撤销对应训练积分资格。
- 不提供“直接给未报名人员加分”的入口。管理者若本人参加，也要按会员资格报名并主动签到。

所有提交按钮有提交中状态，网络失败允许重试。按钮防连点不是后端幂等替代品。

### 3.5 成员页面

顶部一个**搜索栏**，交互与视觉沿用排行榜 / 比赛页现有的搜索框（同一组件或同一样式类），不另造一套。

- **输入即过滤**：输入关键词后，下方列出**本协会在册会员中所有匹配的人**。匹配口径为**昵称或真实姓名包含关键词**，与排行榜 / 比赛搜索完全一致（见 §4.5 的排序与匹配规则）。
- **列表项**：头像、昵称、必要标签（如学院名、角色徽标"协会负责人 / 学院负责人"）。**不得**显示学号、OpenID、手机号等隐私字段（与 §5.6 的隐私口径一致）。
- **点头像 / 整行**进入该成员的**个人主页**（复用现有 `pages/member` / `profile-detail`）。**不能**点进外校或不存在的人——空间成员一律来自本校本协会。
- **空态**：未输入时，**默认直接列出全部在册会员**（按 §4.5 默认序），不给"先输入再查"的挡板；输入后无匹配时给"没有找到匹配的成员"。
- **分页**：成员可能超过数据库单次返回条数，列表必须分页（滚动加载或分页器），不能只给第一页就宣称"列出所有满足条件的成员"。

成员**列表**本身不提供任免 / 入组等批量写操作。**授权落在个人主页**：进入某人主页后，具备授权资格的人（判断口径与可授予档位来自 `school-identity` 的 `canGrantPermission` / 服务端返回的 `grants`）在该页的**「指定权限」入口**发起授权 —— 即把 `pages/school-identity` 上那份「指定权限」`onGrant` 逻辑复用到个人主页，不另造一套。查看者无授权资格（`grants` 为空）或在跨校只读浏览时，该入口隐藏。

## 4. 范围、权限及资格

### 4.1 固定范围

每个分组、成员关系、通知、训练、报名、签到和相关审计记录，必须同时绑定 `schoolId` 与 `association`。服务端同时验证：

1. 登录身份来自可信服务端会话，云端从 OpenID 解析，不能相信 payload 的 actor/role。
2. 学校、该校协会处于启用状态。
3. 目标记录的两个范围字段与请求上下文完全一致。
4. 关联资源（小组、用户学校身份、训练、赛事）同范围。
5. 每次写操作重新检查权限；不能信任打开页面时的旧权限快照。

### 4.2 权限矩阵

“空间管理者”＝本协会负责人、本校学校管理员、平台管理员。学院负责人不属于“协会负责人及以上”。

| 操作 | 本协会有效会员 | 学院负责人 | 本协会负责人 | 本校学校管理员 | 平台管理员 |
|---|---|---|---|---|---|
| 读取本协会空间内容 | 是 | 是，需会员资格 | 是 | 是 | 是 |
| 读取本协会成员名录（成员页签） | 是 | 是，需会员资格 | 是 | 是 | 是 |
| 创建/维护分组、选入/移除成员 | 否 | 否 | 是 | 是 | 是 |
| 本人退出小组 | 本人已入组即可 | 同左 | 同左 | 同左 | 同左 |
| 发布/编辑/撤回空间通知 | 否 | 否 | 是 | 是 | 是 |
| 发布/编辑/取消训练 | 否 | 否 | 是 | 是 | 是 |
| 训练报名、提交本人签到 | 需活动资格 | 需活动资格 | 需活动资格 | 需活动资格 | 需活动资格 |
| 确认、退回、撤销训练签到 | 否 | 否 | 是 | 是 | 是 |
| 读取已取消报名等管理明细 | 否 | 否 | 是 | 是 | 是 |

实现空间管理权时复用 `canSchoolAction(ctx, 'manageAssociation', resource)`。但是它的 `participate` 当前主要判断本校有效身份，**不能单独用来证明本协会会员资格**。新增 `canParticipateInAssociation`：有效平台账号 + 本校有效学校身份 + primarySchoolId 匹配 + 本协会有效 membership。活动小组判定在此基础上叠加。

建议默认空间内容只向本协会有效会员和空间管理者开放。现有 `canReadSchool` 允许更广的学校浏览，不能直接用它放行内部通知与名单。外校管理员只能管理自己的学校；平台管理员的管理权不自动赋予任意学校参训资格。

退出小组是特殊自助操作：即使后来失去会员身份，只要账号仍可登录且关系属于本人，也允许退出；不能因此授予内容读取、报名或重新入组权限。

### 4.3 小组限制的统一规则

```js
// 写入时使用的规范形式
{ audienceMode: 'all', audienceGroupIds: [] }
{ audienceMode: 'groups', audienceGroupIds: ['group_a', 'group_b'] }
```

`groups` 必须至少有一个去重后的合法 ID。`all` 必须为空数组。混合非法状态一律拒绝新写入，不能静默降级为不限。缺字段的旧活动仅在兼容读取层解释为不限，不能把客户端明确传入的空限制错误也当成旧数据。

小组资格判断：目标用户在所选小组中至少有一条 active 成员关系。所有小组都必须来自本活动学校协会；提交别校、小组不存在、伪造 ID 时整个请求失败。

保留原有性别、学院、赛制、队伍人数等限制：最终资格是“原有条件 AND 学校协会会员资格 AND 小组并集资格”，不能用小组校验替换原来的校验。

### 4.4 建议默认的边界规则

| 问题 | 本方案默认规则 |
|---|---|
| 同一个人能否加入多个小组 | 可以；报名和积分均按用户去重 |
| 退出小组是否退出协会 | 否；两个身份互不替代 |
| 报名后退出/被移出小组 | 保留已经成功的报名，小组资格按报名时快照确认；以后新的报名按最新关系判断 |
| 报名后失去本校或本协会身份 | 不能新签到；**仍可暂时占用名额**，但负责人在**确认时**会被拒绝并**自动移除该报名**（不再有"标记待处理"环节，见 §8.2）；移除**不向该会员发提示**，只写审计；已确认的历史积分不因身份变更自动删除 |
| 学院负责人是否必然是会员 | 是。学院负责人以在册会员身份为前提，不存在"是学院负责人但不是会员"。若实现中出现该状态按缺陷处理 |
| 候选成员多选 / 训练报名名单里出现不合格的人 | 属缺陷。多选只列本校本协会**在册且合格**的会员，不在列表里显示的人不应被选入 |
| 是否自动把失效报名从人数中扣除 | 不自动扣。未取消记录仍占位，避免计数与台账分叉；管理者移除时事务扣减 |
| 有人报名后更改限制小组 | 不允许；普通赛事开始有报名、学院赛开始有名单提交、训练开始有报名后，限制即冻结，即使后来全部取消也不解冻 |
| 归档小组 | 不可新选入活动、不可新增组员；保留关系，已引用的活动仍按现有 active 关系接收报名；允许成员退出和管理者移除 |
| 管理者是不是可以绕过小组限制报名 | 不可以；管理权与参加资格分别判断 |
| 负责人能否确认自己签到 | 建议首版允许，用户未要求双人审核；必须先本人签到、再在管理端明确确认，并完整记录操作者。若改为禁止自确认，需补唯一负责人无人可确认的流程 |
| 小组限制是否限制活动可见性 | 不限制本协会成员看活动基本信息，只限制参加；空间读取权限仍按本节执行 |

上述保留报名规则是"报名时资格"的明确选择。若产品改为退出即取消，必须一起改计数、通知、队伍完整性、抽签及测试；不能只在签到按钮处临时加个小组判断，造成已占位用户突然无法签到。

### 4.5 成员页签的取数、匹配与排序

**取数范围**：只取 `schoolId + association` 范围内的**在册会员**（`school_members.status === active` 且 `primarySchoolId` 与范围一致），与空间其它内容同一把范围锁。不复用跨校只读的 `canReadSchool`——外校人不能靠成员页把别校名单拉走。

**匹配规则**：
- 关键词先 `trim`，空串视为"未过滤"（此时列出全部在册会员）。
- 主匹配为**昵称包含 或 真实姓名包含**（`nickName.includes(kw) || realName.includes(kw)`），与排行榜 / 比赛 / 学院赛的搜索保持同一口径（现有 `components/match-panel`、`pages/college-event-detail`、`services/events-view.js` 都按"昵称与真实姓名都能搜到人"实现）。
- **学号不参与匹配**（含学号搜索会泄露"某学号是否在册"）；拼音 / 首字母可作后续增强，首版不做。
- 大小写与全半角归一后再比对；中文按原字符包含即可。

**排序规则（需固定以保证"按一定顺序"可复现）**：
1. 前缀命中优先于中间命中：**昵称或真实姓名以关键词开头**的排在**仅包含关键词**的前面（搜"张"时，"张宇轩"排在"小张"前）。
2. 同一档内按**昵称的稳定字典序**（`Intl.Collator` 或按 Unicode 码点）升序；昵称相同再比真实姓名。
3. 再以 `userId` 升序做**最终稳定键**，避免同名 + 无前缀差异时顺序漂移。

**分页**：`cursor + limit`，`limit` 建议 20～50；游标与排序键一起编码，保证翻页不重不漏。搜索关键词变化时重置游标。

**隐私**：只下发 `userId / nickName / realName / avatarUrl / collegeId / collegeName / permissionLabel`。`realName` 与现有排行榜 / 比赛一致，**只参与搜索匹配、不作为主渲染字段**。**不下发**学号、手机号、OpenID、平台角色等。这与 `getSchoolMembers` 现有口径一致，成员页直接复用其 DTO 即可（可再加 `keyword` / `cursor` 参数）。

**实现落点**：新增 `listAssociationMembers`（见 §8.2），服务端做匹配与分页；页面只负责输入与渲染，不在前端拉全量再过滤。

## 5. 数据模型与不变量

以下集合名和 API 名是建议新增名称，不表示仓库已经存在这些文件或接口。实际使用数据库前缀时统一在仓储层映射。

### 5.1 公共字段

所有新业务主记录使用 `_id, schoolId, association, createdBy, createdAt, updatedAt, revision`。时间用服务器 UTC 时间戳或统一 ISO 串持久化；界面按 Asia/Shanghai 展示。不要混存本地格式日期字符串。

ID 由服务端生成或由服务端根据稳定业务键计算。不得将任意客户端提供的 ID 直接用于覆盖数据库已有记录。

### 5.2 小组与成员关系

`association_groups`：

- `name`：必填，去首尾空格后建议 2～30 字；同范围 active 小组不重名。
- `description`：选填，建议最多 300 字。
- `status`：`active | archived`。
- `memberCount`：active 关系数的事务维护缓存，不是资格判断的事实来源。
- `membershipRevision`：成员变化和受限报名资格串行化使用的版本。

`association_group_members`：

- `_id`：服务端以 scope + groupId + userId 生成稳定唯一键。
- `groupId, userId`。
- `status`：`active | left | removed`。
- `joinedAt, addedBy, leftAt, removedAt, removedBy`；每次变化另记审计。
- 重复添加 active 成员为幂等成功，不增加人数；重新加入更新同一关系，清理不适用的当前状态时间字段，历史由审计保存。

组名唯一应使用同范围名称占位键或经验证可用的数据库唯一约束。不能用“先查重再插入”当成并发安全。重命名时在同一事务释放旧占位、取得新占位。

首版创建分组及选定初始成员必须明确事务规模上限。建议单次最多 50 名初始成员；更多成员通过详情页分批添加，每批返回成功/失败状态。不要静默截断第 51 人。实际部署前验证数据库事务限制，必要时调低公开的上限。

### 5.3 空间通知

`association_notices`：

- `title, content, category, pinned`：可复用公告纯校验规则。
- `status`：`published | withdrawn`。
- `publishedAt, withdrawnAt, withdrawnBy`。

建议独立集合，避免旧公告读取端漏过滤导致全站展示。复用“模板”不等于复用旧公告发布 API、旧权限或旧集合。若复用表单组件，明确传入模式并绑定独立提交函数。

### 5.4 训练

`association_trainings`：

- `title`：必填，建议 2～30 字；用户只明确要求时间地点必填，此项为列表可辨识所需的推荐补充。
- `description`：选填，建议不超过 1000 字。
- `startAt`：必填；建议新增时必须在未来。
- `endAt`：可选，但服务端总要得到有效结束时间；省略时建议默认为 startAt + 2 小时，并在发布预览里明确展示。
- `location`：必填，去空格后建议 1～100 字。
- `capacity`：`null` 表示不限；其他值必须为正整数。建议首版 UI 上限 1000；0、负数、小数不是不限。
- `audienceMode, audienceGroupIds`：按第 4 节。
- `status`：`published | finished | canceled`。
- `signupCloseAt = startAt`、`checkInOpenAt = startAt - 30 分钟`、`checkInCloseAt = endAt`：建议首版服务端自动计算，不加复杂表单。
- `signupCount`：有效报名人数；`audienceLockedAt`：首次报名后设置且不清空。
- `canceledAt, canceledBy, cancelReason`。

报名人数不限不等于一次读取全部数据。所有列表必须分页。

### 5.5 报名、签到、积分事实

`training_registrations`，建议将报名与签到放在同一用户记录，避免跨表状态错位：

- `_id`：scope + trainingId + userId 的稳定唯一键。
- `trainingId, userId`。
- `signupStatus`：`registered | canceled`。
- `signedAt, canceledAt, canceledBy, cancelReason`。
- `eligibilitySnapshot`：报名时 `audienceMode`、命中的小组 ID、活动限制版本、校内会员身份版本。用于解释历史报名，不把它当成当前学校身份的永久通行证。
- `attendanceStatus`：`not_submitted | pending | rejected | confirmed`。
- `requestedAt, confirmedAt, confirmedBy, rejectedAt, rejectedBy, rejectionReason`。
- `pointEffectiveAt`：成功确认时从不可变的训练 startAt 复制。
- `revision`：管理操作的 expectedRevision 校验。

**积分唯一事实来源：有效报名记录上的 confirmed 状态。** 首版不再维护一份可独立增减的训练积分余额或第二套积分账本。重算时将 confirmed 记录映射成 `{sourceType:'training', sourceId: trainingId, userId, amount:1, effectiveAt}`。历史审计不是积分来源。

同一次训练、同一用户最多一个有效事实；禁止以签到点击次数、审计条数、加入小组数量计分。取消训练后的记录不计分，撤销确认后的记录不计分。重复确认只能返回现状。

`association_space_audits`：记录 scope、actorId、action、resourceType、resourceId、targetUserId、前后状态摘要、原因、服务器时间、requestId。不得把学号等无关资料整份复制进审计。

### 5.6 索引与查询要求

至少准备并验证这些复合查询的索引：

| 集合 | 查询字段顺序（尾部增加稳定 ID 排序） |
|---|---|
| groups | schoolId, association, status, createdAt |
| group_members | schoolId, association, groupId, status, userId |
| group_members | schoolId, association, userId, status, groupId |
| notices | schoolId, association, status, pinned, publishedAt |
| trainings | schoolId, association, status, startAt |
| registrations | schoolId, association, trainingId, signupStatus, signedAt |
| registrations | schoolId, association, trainingId, attendanceStatus, requestedAt |
| registrations | schoolId, association, userId, attendanceStatus, pointEffectiveAt |
| audits | schoolId, association, resourceId, createdAt |

索引声明需适配实际云数据库能力，不能把此表原样当作可执行语法。重算扫描所有有效积分事实时也要内部翻页，不能受数据库默认单次返回条数限制。数据库规则禁止客户端绕过云函数直接写业务集合。

## 6. 训练状态、时间与计分

### 6.1 报名与签到转换

```text
未报名 → registered / not_submitted
registered / not_submitted → canceled / not_submitted （开始前取消）
canceled / not_submitted → registered / not_submitted （重新验证全部报名条件）
registered / not_submitted → registered / pending （本人在窗口内点击签到）
registered / pending → registered / confirmed （负责人确认）
registered / pending → registered / rejected （负责人退回并给出原因）
registered / rejected → registered / pending （本人在窗口内重新提交）
registered / confirmed → registered / pending （负责人撤销确认，填写原因）
```

待确认和已确认状态不得直接取消报名。需要移除时先走退回/撤销确认，再由管理者按明确流程取消记录；移除接口也可以在一个事务内同时撤销资格并取消，但必须生成完整审计，不能绕过积分失效。

训练取消是独立整体操作：使其所有报名与签到失效，人数对外显示为不再接受报名；保留历史注册记录和历史计数供审计，不为每个人批量物理删除。重算按训练 canceled 状态排除积分。取消前若有确认人数，界面必须说明将影响这些人的积分。

### 6.2 时间边界

- 报名和自主取消：服务器 now < startAt，且训练 published。
- 本人提交签到：`checkInOpenAt <= now <= checkInCloseAt`，且报名有效、会员资格仍有效、训练未 canceled/finished。
- 负责人确认：必须存在 pending 请求，且服务器 now >= startAt。建议允许训练结束后**在同一赛季内**补确认已提交请求，避免负责人当天忙碌漏确认；finished 训练也可处理已有 pending。但**跨赛季不再补确认**：赛季一旦重置，上一赛季的 pending 在重置事务中被自动退回（见 §6.3）。
- 普通会员不能在窗口结束后首次补签到。首版不提供手工补签；需要时另加带理由、完整审计的操作，不能复用确认接口造一个 pending。
- 结束训练：now >= endAt 才可 finished；不自动批量确认 pending。
- 新训练发布时 startAt < endAt，服务器拒绝无效日期。所有临界值使用同一服务器时钟。

训练在首次报名后锁定 startAt、endAt 和小组范围；需要改期建议取消重发。地点、说明仍可编辑并显示“已更新”；人数上限可增大，也可减小但不得低于 signupCount。用户尚未要求推送提醒，修改不能假称已通知所有人。

### 6.3 赛季积分归属（取消"跨赛季确认"）

积分仍按**训练发生时间 startAt**归属赛季，不按负责人确认时间归属——这一点保留。**但不再允许"上一赛季的训练在新赛季补确认"**（原方案允许，现按负责人第二轮反馈取消）。

规则如下：

1. **赛季重置时清理未确认**：赛季重置（`resetTime` 推进）时，若存在**上一赛季的 pending 签到**（`attendanceStatus === 'pending'` 且训练属于重置前），一律**自动退回**为 `not_submitted`（写 `rejectedAt / rejectedBy = 系统 / rejectionReason = '赛季已重置，未确认自动退回'`，并记审计）。该次训练视为**未参加**，不产生任何积分。
2. **不再补确认**：新赛季不再提供任何"补确认上一赛季"的入口；确认接口拒绝确认属于已重置赛季的 pending。负责人若在重置前没来得及确认，即视为放弃。
3. **计分边界**：若存在有效 `resetTime`，仅统计 `pointEffectiveAt >= resetTime` 的 confirmed 事实；没有 `resetTime` 则统计全部有效训练事实。边界等于 `resetTime` 算新赛季。由于 1 已清掉旧赛季所有 pending，这个过滤不会把旧赛季的确认误计入新赛季。
4. **历史可读**：保留历史训练事实与时间，不要求本期新增完整往届排行榜。旧赛季的已确认记录仍显示为历史（不计入当前赛季）；**不要伪造当前仓库没有的历史 seasonId**。

**算法落点（对应反馈第 6 条）**：赛季重置流程（现有 `resetSeason`）在同一事务里，除推进 `resetTime`、升级赛季版本、使缓存失效外，再扫一次本范围 `attendanceStatus === 'pending'` 的报名记录，逐条写成"自动退回"并记审计。这与 §9.3 的确认事务共用同一把训练主记录 / 报名记录的冲突点，保证"重置"与"确认"不会并发各改一半。扫描需内部分页，不能受数据库单次返回条数限制。

计分实施要求：

1. 为 `replaySeason` 增加可选 `trainingPointFacts = []` 参数，旧调用默认行为不变。
2. 建议在最终回放结果得到后统一叠加训练积分，避免两遍回放重复累加；也可在内部纯函数计算，但必须证明最终只计一次。
3. 训练只改变该校该协会的 `points`，不改变 singles/doubles ELO、不增加比赛场数、胜率、对手次数、定级场数，不伪造比赛记录。
4. 训练积分不是“每个等级分池 +1”。用户总分只加一次；不同榜单引用同一总分时不得重复结算。
5. mock 构建缓存与云端 derive 都传入同样事实，重启后依然可重建积分。
6. 确认/撤销/取消训练与该 scope 的赛季版本失效在同一事务中完成，升级算法缓存版本，确保旧排行榜快照不能复用。
7. 个人页提供“赛事积分 + 训练积分”的来源说明。原“所有积分都能挂在某场比赛上”的文案需要改掉；训练积分不挂在任意虚构比赛上。
8. 保持旧赛事名次计分规则、双打赛事不计分规则不变；新增加分来源是训练。
9. 成员被冻结后仍保存历史事实，按原排行榜对停用人员的展示规则处理；不能为了过滤名单把历史流水删掉。

## 7. 原有比赛、赛事接入小组限制

### 7.1 普通赛事（已有个人报名）

在 `event-edit` 增加共用小组选择器；详情展示“不限小组”或所选组名。发布端持久化两个限制字段，报名事务调用统一资格服务。

必须覆盖：`signUpEvent`、重新报名、管理员代报名（若执行时已有）、双打搭档加入、后续补入参赛者等所有产生新参加资格的入口。不能只校验操作者；实际参赛的每一人都要校验。双打若当前报名模型分阶段组队，则每个人各自取得资格，在组队/锁签表时检查每名队员有有效报名资格；禁止直接塞入未报名搭档。

抽签、排阵、录分不重复按“现在还在不在小组”否定历史合法报名，但必须确认选手来自有效报名快照、身份未失效。中途新补入的人按补入时的最新资格验证。

### 7.2 学院赛（由负责人提交名单）

`college-event-edit` 同样增加限制字段。`college-entry` 候选名单过滤后端返回的合格成员；提交端再逐人验证。一个人不合格时拒绝整份提交，返回可理解的失败成员和原因，不悄悄删人后提交。

初次提交后冻结该赛事小组范围。已通过合法提交的成员保留小组资格快照；修改名单时，对新增成员按最新小组关系检查，保留成员按已有有效快照检查，取消后重加视为新增。学院资格、人数、性别、项目及替补规则继续独立执行。

排阵与替补只能从有效名单选人；禁止管理员直接写 lineup 绕开学院名单。自动生成的小场继承赛事资格约束，不新增可自由修改的小组范围。

### 7.3 普通比赛（当前只有赛果录入）—— 不加小组

**负责人第二轮反馈已明确：小组限制只加在"赛事"上，普通比赛不加。** 现有 `match-entry` 是赛果录入，不是"发布比赛并接受报名"，没有"报名范围"可言，故本期**不给普通比赛增加小组选择器**。此前 1.0 版把小组限制扩到普通比赛的想法作废，原"唯一范围分叉"问题随之解决：不需要新建"约球发布 → 报名 → 组队"的 match activity 流程。

唯一保留的一条约束：**赛事自动生成的比赛**（带 `eventId`）沿用其父赛事已限定的有效参赛名单，录分人不能借录分环节把不在名单里的人塞进去。旧比赛改比分、审核确认、重算积分时，不因后来退出小组追溯判为非法；历史比赛不补小组。

### 7.4 向后兼容

- 历史活动缺少限制字段，读取为不限，不追溯删报名。
- 所有新活动显式写出规范字段；旧客户端未传字段的新建请求可按不限兼容，但新接口发现格式错误必须拒绝。
- 老接口若能操作已限制小组的活动，必须接入同一校验或拒绝并提示升级；不能让协议 1 成为绕过协议 2 的后门。
- 旧客户端改赛事时未传限制字段，应保留原值，不得覆盖成不限。
- 修改比分不能携带并覆盖小组范围；父赛事 ID 不能任由新录分请求伪造以绕过校验。

## 9. 事务、并发和缓存：不可省略的实现细节

### 9.1 报名事务

```text
由可信身份构建固定 scope
进入事务：
  读取训练主记录、本人报名记录、学校/协会身份
  若是同一次已成功报名的重试，返回已有结果，不重复加人数
  验证状态、时间、会员资格
  若选择小组，读取最新成员关系并验证任一命中
  验证 capacity 为空 或 signupCount < capacity
  写/恢复报名记录及 eligibilitySnapshot
  signupCount += 1；首次报名设置 audienceLockedAt
  更新训练 revision
  写审计及必要的幂等结果
提交
```

同一个最后名额只能被一个事务取得。取消报名在同一事务修改用户记录并减训练计数；重复取消不再次扣减。训练取消与新报名均写同一训练主记录，不能并发产生取消后仍成功的报名。

### 9.2 资格竞争

报名与“移出小组”并发时，业务顺序必须确定：报名先成功则按快照保留；移除先成功则报名失败。不能仅在事务外查成员资格。

使用当前数据库支持的事务冲突机制，保证相关成员关系读写冲突会重试；若仅只读文档不足以提供该保证，报名事务同步更新所命中小组的 `membershipRevision`，成员变更也更新同一主记录。多组验证按稳定 ID 顺序读写，减少冲突。

学校身份/协会 membership 被撤销与参加操作也须有同等竞争保护；不能只锁小组而忽略基础身份。P0 需验证真实适配器的事务语义，测试内存仓储同样模拟冲突/串行化。

> 2026-10-14 核对：`tests/helpers/memory-repo.js` 目前**尚未**模拟 conflict / revision，本项要求未落实，P0 需补。

### 9.3 确认签到事务

```text
事务内重新读取当前管理权限、训练、目标报名与目标身份
确认资源范围一致、训练未取消、目标有效、报名 registered
若已 confirmed 且为重复确认，返回现状，不再加版本/审计
必须 attendanceStatus = pending 且 now >= startAt
检查 expectedRevision；过期则要求刷新
写 confirmedAt/confirmedBy、pointEffectiveAt = training.startAt
写审计
更新该 schoolId + association 的积分缓存版本
提交
```

不要在事务成功后再单独加分。积分从事实派生；事务中的状态和缓存版本必须一起成功或一起失败。确认与取消、撤销、退回的竞争也应共享训练主记录或相应冲突点。

### 9.4 客户端缓存

缓存键至少包括 schoolId、association、当前身份和资源 ID；管理列表不能被会员会话复用。切学校、切协会、退出登录、切演示身份时销毁旧 client 或使请求代际失效，旧请求返回后不得覆盖当前页面。

空间面板隐藏后停止不必要的刷新；学校范围变化后即使面板曾懒挂载，也必须清空并重载，不能沿用旧成员列表。训练报名/签到后刷新详情和当前用户状态，积分确认后刷新积分相关页面的数据版本。

## 10. 老数据、学校隔离与部署准备

### 10.1 迁移原则

1. 新集合初始为空；不得自动替所有协会创建真实成员关系或历史训练积分。
2. 现有历史比赛与赛事的缺失限制字段兼容为不限。
3. 核查旧记录学校来源。仅当有依据证明属于原民大数据集时，迁移为 `muc`；来源不明的记录单列报告，不能默认塞进当前浏览学校。
4. 迁移 scripts 提供 dry-run，输出按集合、学校、协会的记录数量、冲突和孤立引用；有真实数据时先备份再执行。
5. 同一全局 userId 在不同学校协会的训练事实、赛季版本和缓存必须分开；不把新空间小组数组直接挂到全局 users 上。
6. 暂未迁移的旧 action 继续有明确边界；仅允许默认学校兼容时，在服务端绑定并校验默认学校，不能接受任意 schoolId 然后忽略它。
7. 任何接入本期限制的老比赛/赛事读写，必须由同范围适配器执行。要么完成协议 2 迁移，要么提供严格默认校适配；没有隔离就不得开放第二学校写操作。

### 10.2 演示数据

使用中央民族大学 `muc`、北京航空航天大学 `buaa`。每校至少为匹克球协会准备负责人、普通会员、学院负责人、学校管理员，并增加另一个协会验证隔离。

每校创建“新手组”“校队组”；同名允许跨学校存在。示例：A 在新手组，B 在校队组，C 同时在两个组，D 不在任何组。准备不限训练、单组训练、多组训练、满额训练、待确认签到、已确认签到、已取消训练。演示用户与旧 mock 用户的映射要明确，禁止仅靠同名匹配。

### 10.3 发布与回滚

新增集合、索引、迁移、云函数版本、客户端版本分别列入部署清单。由于当前未部署云环境，代码阶段只生成这些清单并本地验证。

建议使用 `associationSpaceEnabled` 功能开关，默认演示开启、生产按迁移完成状态开启。回滚首先关入口和新增写操作，保留事实与审计。已产生训练积分后，不能直接降级到完全忽略训练事实的旧重算器，否则积分会消失；需要保留兼容读/计分版本，或先部署专门的兼容回滚版本。

| T16 | startAt 恰等于 resetTime | 算新赛季；更早的训练不计当前赛季 |
| T17 | 用户同时属于两个选中组 | 一次报名、一次确认、总分 +1 |
| T18 | 冷启动、清缓存、完整重算 | 训练积分不丢、不重复；ELO/胜率/比赛场数不变 |
| T19 | 同用户参加不同训练 | 每个训练成功签到各 +1 |
| T20 | 民大匹克球训练签到 | 不改变北航或民大羽毛球积分 |
| T21 | 超过 100 条报名/积分事实 | 管理者翻页能看全；重算不只算第一页 |
| T22 | 确认事务中途故障 | 签到事实、版本、审计一起回滚 |
| T23 | 无任何比赛但有一次确认训练 | 用户积分为 1，等级分保持初始值 |
| T24 | 重置赛季后读取旧持久化排行榜快照 | 不复用旧快照，积分按新边界重算 |
| T25 | 已报名后失去会员身份，负责人来确认 | 拒绝确认并在同一事务自动移除该报名、释放名额、记审计（不再"标记待处理"）|

## 14. 下一位 AI 的执行提醒与需要确认的选择

执行时遵守以下顺序：先有统一权限与资格服务，再写事务，再接页面；先证明学校隔离，再开放第二学校写操作；先有可重算的训练事实，再展示成功加分。

不得做这些“看似完成”的实现：

1. 仅隐藏按钮，不在服务端判权。
2. 仅筛选第一页会员，或仅在页面过滤小组。
3. 用赛事小组赛的 groupId 代替协会成员小组。
4. 普通会员点击签到立刻显示成功、立刻加分。
5. 直接给持久化 user.points 加 1，没有事实来源。
6. 所有学校共用一个训练列表、一个赛季版本或一个本地存储键。
7. 新通知仍走旧公告发布，导致首页出现。
8. 将现有普通赛果页描述为已经具备活动报名能力。
9. mock 有功能、云接口没有对应动作，却宣布可部署。
10. 修改生成库但不修改源文件，或把本地演示验证称为真实云端上线。
11. 成员页签把学号 / 手机号 / OpenID / 平台角色下发给客户端，或把外校名单混进来。
12. 成员搜索只在客户端过滤，等于先把全量名单拉到本地再隐藏。

正式实施前向产品集中说明这些推荐默认：空间只对会员/管理者可读；多组取并集；退出组保留已有报名；训练默认两小时、提前半小时可提交签到、开始后才可确认；训练按发生时间归属赛季；负责人允许确认本人已提交的签到；人数与标题长度等上限是实现建议。成员页默认：列表只读、默认列出**全部**本协会在册会员、按"昵称或真实姓名包含关键词"匹配并按前缀优先 + 稳定字典序排序（§4.5）；**授权在个人主页的权限入口处发起**。用户未提出调整时按文档默认推进，不在每个小步骤反复询问。

其中“普通比赛是否要新建发布与报名流程”会明显改变工程范围，应在 P4 前取得明确口径。其他阶段的分组、通知、训练和已有赛事限制可以独立继续，不必等待该问题才开始。

最终交付报告至少包含：实现阶段、实际改动、验证命令及结果、人工演示结果、历史数据迁移状态、云端部署状态、仍未完成项。只有全链路与验收完成，才可把对应阶段标为完成。
