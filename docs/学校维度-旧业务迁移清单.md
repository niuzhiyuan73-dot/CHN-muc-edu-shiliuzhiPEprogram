# 学校维度：旧业务迁移清单（方案 B 施工文档）

日期：2026-10-14
状态：**盘点文档，待实施**。本文只列“现状与差距”，不代表功能已完成。
代码基线：`5a4ba32`（协会空间 P2/P3）。

## 0. 这份文档解决什么

用户要求（方案 B）：**把以前的所有业务全都走学校维度，涵盖以前的全部内容**。

当前仓库里同时存在两套身份/数据栈：

- **旧栈（协议 1 / protocol-1）**：`services/index.js` 门面 → `services/mock.js` / `services/cloud.js`。
  身份是 `getCurrentUser()` 读的编译期常量 `DEFAULT_CURRENT_USER_ID`（演示账号 `u01`–`u24`）。
  数据模型没有 `schoolId`，只按 `association`（协会）分桶。
- **学校维度栈（协议 2 / protocol-2）**：`services/school-identity.js` 门面 → `services/school-mock.js` / `services/school-cloud.js`。
  身份是 `school-context.js` 从 `users` + `schoolMembers` + `schoolRoles` + `memberships` 组装出来的上下文。
  所有业务主记录同时绑定 `schoolId` + `association`。

**“不兼容学校维度”= 页面/服务的数据读写仍走旧栈、或其数据模型里没有 `schoolId` 这一维。**
只要某页面的数据整条链路（页面 → 视图 → 服务 → 仓储）拿不出“当前学校”这一维，
它在多学校下就会把两所学校的数据混在一起，就属于本文要列的迁移对象。

> 桥接点说明：`school-mock.js` 的 `attachLegacyMembers()` 已把演示账号 `u01`–`u24`
> 回溯登记进中央民族大学（`LEGACY_SCHOOL_ID = 'muc'`），且默认演示身份跟随
> `mock.js` 的 `DEFAULT_CURRENT_USER_ID`。**这只是把旧账号“单向喂进”了 S2 仓储，
> 页面层并未因此接入 S2**——两套栈仍是并行的。

## 7. 数据模型与集合的差距

| 集合（旧栈概念） | 现状 | 迁移要求 |
|---|---|---|
| `users` | 有学院、学号、审核状态 | 学号/学院/在校状态应归 `schoolMembers`；平台停用与学校停用分开 |
| `memberships` | 只按 `userId + association` 记角色 | 角色键必须含 `schoolId`（S2 已用 `schoolMembershipKey`） |
| `events` / `matches` / `colleges` | 只按 `association` 分桶 | 全部加 `schoolId`，查询本身带范围 |
| `seasons` / `rankings` / 派生缓存 | 按 `association` 分桶 | 加 `schoolId`，避免两校共用缓存/赛季/报名自然键 |
| 学院目录 `COLLEGES` | 全平台固定一份，名称参与判权 | 每校独立学院目录，改用稳定 `collegeId` |
| `users.currentEloByAssoc` / `initialElo` | 按协会保存 | 按学校 + 项目 + 等级分池定位 |
| 首页 / 公告 / 个人统计 | 跨协会汇总 | 默认只汇总当前学校的协会 |

## 8. 云端 action 现状

- `cloudfunctions/data/src/core/school-request.js` **只分发协议 2 的学校身份 / 协会空间 / 跨校交流 action**。
- 旧协议 1 的 action（`submitMatch`、`publishEvent`、`publishCollegeEvent`、
  `publishAnnouncement`、`approveMember` 等）**未进入学校路由**，仍是原单校入口。
- `cloudfunctions/data/src/school-repository.js` 已有 `forScope({schoolId, association})`
  基础能力，但**尚未覆盖旧业务集合的范围保护**。
- 结论：**旧业务在云端根本没有学校隔离**。第二所学校的写操作若借旧门面，
  会直接写进“默认学校”，必须堵死（见 §10.7）。

## 9. 迁移影响面（谁会被牵连）

1. **计分**：`replay.js` / `season.js` 是等级分与积分的唯一事实引擎。加 `schoolId`
   意味着“同一全局 userId 在不同学校的等级分、积分、赛季版本必须分开”，
   排行榜快照缓存键也要加学校。P5 的训练积分正是在这个引擎里叠加。
2. **自然键**：报名、签到、抽签、名次、小组等所有“稳定主键”当前只带
   `association`，加学校后必须一并带 `schoolId`，否则两校同场景主键相撞。
3. **导航与演示**：`school-demo.js` 是外校**只读演示**，不是隔离。迁移完成后
   外校数据应由真实链路（按 `schoolId` 查询）提供，`school-demo` 可作为空态兜底。
4. **演示账号**：`u01`–`u24` 已进 `muc`（`attachLegacyMembers`）。旧页面改走
   S2 后，“当前登录是谁”会从 `DEFAULT_CURRENT_USER_ID` 自然过渡到 S2 的
   上下文（同一批人，同一 `muc`）。
5. **测试**：`tests/page.test.js`、`events-view`、`college-*`、`replay`、`season-reset`
   等大量用例建立在旧栈上。迁移时这些用例需增补 `schoolId` 夹具，不能只改断言。

## 10. 迁移建议（方案 B 分期）

### M0：盘点与地基（本文件 + 补测）

2. 为旧栈的“范围”补一层适配器：门面新增 `forScope({schoolId, association})`。

- 每行下发 `userId / nickName / realName / avatarUrl / gender / collegeId /
  collegeName`；**带 `gender`**（性别项目报名、单打榜过滤要用），隐私字段（学号 /
  手机号 / OpenID / 平台角色）一律不下发（与 `getSchoolMembers` / `listAssociationMembers`
  同口径）。可选 `collegeId` 只取某学院；平铺一次取齐，不做分页与权限标签。
- 读权限复用协会空间那把锁（`canReadAssociationSpace`）：本协会有效会员或空间管理者
  （含平台管理员）；外校人读不到（`getSchoolMember` 对别校用户按「找不到」处理，
  不泄露其存在）。平台管理员可跨校读。
- **会员审核无需另建**：入会申请 → 通过 / 驳回已由 `school-membership-service` 的
  `getSchoolApplications` / `reviewSchoolMembership` 覆盖（学校身份页在用），本片只
  补审核通过后的档案读取；审核时手工指定初始等级分归 M4（等级分随 M4 加学校维度）。

  注册表、`tools/sync-cloud-lib.js` 清单均已加入（同步 53 个文件）。
- 测试：`tests/school-member.test.js`（5 条）——名录成员筛选（本校 / 在册 / 平台启用 /
  归属本校；停用与平台管理员不入册）、每行带 gender / collegeName 且不下发隐私字段、
  按学院过滤、跨校（外校读不到 / 平台管理员可跨校）、单档案（按编号取 / 不存在 /
  别校用户为拒）。
