# 云开发控制台操作指南

| 项目 | 说明 |
|---|---|
| 适用对象 | 需要进云开发控制台的人：首次部署、审核会员、调角色、换赛季、数据救急 |
| 云函数 | `data`（唯一一个，承载全部 **200** 个 action：身份 13 + 协会空间 119 + 跨校邀请赛 15 + 运动会 53） |
| 数据库 | **52 个业务集合**，全部对小程序端关闭，读写只走云函数 |
| 核心原则 | 小程序里的每一步都有权限与校验；控制台直接改库**没有护栏**，能走小程序就不要改库 |
| 最容易忘 | 改完代码必须重新「上传并部署」`cloudfunctions/data`，否则线上还是旧包 |

> 本指南里的集合名、字段名、action 名都与仓库代码一一对应（`miniprogram/utils/constants.js` 的 `COLLECTION`、`cloudfunctions/data/src/core/*-handlers.js`）。控制台界面以微信开发者工具当前版本为准。

---

## 一、入门

### 1.1 从哪里打开

1. 用管理员微信登录「微信开发者工具」，打开本项目。
2. 点顶部工具栏「云开发」进入控制台（首次需开通并实名）。
3. 左上角确认环境。环境 ID 写在 `miniprogram/config.js` 的 `CLOUD_ENV_ID`；**留空时小程序走本地模拟数据**，此时控制台里没有任何业务数据——这是排查「线上没数据」的第一个检查点。
4. 小程序管理后台（mp.weixin.qq.com）里没有云开发控制台，必须从开发者工具进入。

日常只用到四块：数据库、云函数、存储、设置。

### 1.2 权限模型：三层闸门

| 层面 | 能做什么 | 说明 |
|---|---|---|
| 小程序端 | 不直接读写数据库 | 页面只调云函数，不持有集合权限 |
| 云函数 `data` | 全量读写 | 以管理员身份运行，不受安全规则限制；所有业务校验都在这里 |
| 云控制台 | 全量读写 | 人工操作，绕过一切校验 |

请求信封固定为：

```
{ protocolVersion: 2, schoolId, association, action, payload }
```

不带 `protocolVersion` 的旧协议请求一律返回「请升级客户端」——旧协议已完全下线，控制台「云端测试」里手调 action 时也必须带 `protocolVersion: 2` 与 `schoolId`。

> 控制台改动没有护栏。小程序里「已生效不可撤销」这类规则，在控制台里是不存在的——改错了没人拦你。

## 二、数据模型：五层账号 + 52 个集合

### 2.1 先理解账号的五层

一个人可以同时是「匹克球的学院负责人」和「乒乓的普通会员」，也可以同时在两所学校有会籍。这不是四张平行表，而是五层：

| 层 | 集合 | 主键 | 一条记录代表 |
|---|---|---|---|
| 平台账号 | `users` | `acc:<md5(openId)>` | 一个微信号 |
| 学校会籍 | `school_members` | `sm:<schoolId>:<userId>` | 某人在某校的会籍与状态 |
| 校级角色 | `school_roles` | `sr:<schoolId>:<userId>` | 某人在某校的校级管理员身份 |
| 协会角色 | `memberships` | `mb:<schoolId>:<association>:<userId>` | 某人在某校某协会的 `staff` / `leader` |
| 学校 × 协会 | `school_associations` | `sa:<schoolId>:<association>` | 该校是否启用该协会 |

有效角色是合成的：`schoolAdmin` > `associationLeader` > `collegeLeader` > 会员。「无行即普通会员」，所以普通会员在 `memberships` 里**没有记录**，不要为每个人建行。

### 2.2 集合总表（52 个）

**学校与身份（6）**

| 集合 | 存什么 | 关键字段 |
|---|---|---|
| `schools` | 学校目录 | `schoolId`、`name`、`status('active')` |
| `school_associations` | 学校启用了哪些协会 | `schoolId`、`association`、`status` |
| `colleges` | 每校的学院目录（26 所） | `schoolId`、`name` |
| `school_members` | 学校会籍 | `schoolId`、`userId`、`status`、`college`、`studentId`、`joinedAt` |
| `school_roles` | 校级角色 | `schoolId`、`userId`、`role('schoolAdmin')` |
| `student_id_claims` | 学号唯一占用 | 学号 → 用户，防一人多号 |

**账号与协会角色（2）**

| 集合 | 存什么 | 关键字段 |
|---|---|---|
| `users` | 平台账号 | `openId`（唯一）、`nickName`、`realName`、`gender('M'/'F')`、`role(0/2)`、`status(0/1/2/3)`、`initialEloByAssoc` |
| `memberships` | 协会角色 | `userId`、`schoolId`、`association`、`role('staff'/'leader')` |

**比赛与等级分（4）**

| 集合 | 存什么 | 关键字段 |
|---|---|---|
| `matches` | 比赛流水（个人赛、学院赛小场、日常约球都写这里） | `_id`（自然键）、`schoolId`、`association`、`pool`、`teamA/teamB`、`scoreA/scoreB`、`winner`、`status(0/1/2)`、`competition`、`eventId`、`collegeEventId`、`tieId`、`outcome`、`settlement` |
| `member_ratings` | **等级分当前值**（Elo 逐场结算后落库） | `_id='mr:<schoolId>:<association>:<userId>:<pool>'`、`elo`、`startElo`、`matchCount`、`wins`、`losses`、`lastSettlementSeq`、`algorithmVersion='elo-v2'` |
| `rating_counters` | 结算序号 | `_id='mrseq:<schoolId>:<association>'`、`seq`（事务内原子递增） |
| `pair_counts` | 一对会员本赛季的日常约球场次 | `_id` = 范围 + 赛季 + 两人编号，用于 15 场防刷限额 |

**个人赛与公共（5）**

| 集合 | 存什么 | 关键字段 |
|---|---|---|
| `events` | 协会级个人赛 | `association`、`title`、`format`、`level`、`status(0/1/2)`、`draw`、`results` |
| `event_signups` | 报名与签到 | `eventId`、`userId`、`status(0/1/2)` |
| `seasons` | 赛季锚点 | `_id='<schoolId>:<association>'`、`seasonNumber`、`resetTime`、`version` |
| `audit_logs` | 写操作留痕（关键写操作逐条落库：录分 / 确认 / 驳回 / 授权 / 赛季重置等） | `action`、`actorId`、`schoolId`、`association`、`at` |

**学院赛 / 石榴籽杯（4）**

| 集合 | 存什么 | 关键字段 |
|---|---|---|
| `college_events` | 杯赛本体 | `association`、`title`、`legPlan`（小项序列）、`allowMultiEntry`、`tieAlgo`、`tieNetMode`、`status(0/1/2/3)`、`results` |
| `college_entries` | 各院名单 | `eventId`、`college`、`members[]`、`status(0/1/2)`、`reason` |
| `ties` | 大场 | `eventId`、`round`、`collegeA/collegeB`、`legs[]`、`winner`、`status(0/1/2/3)` |
| `lineups` | 大场排阵 | `tieId`、`college`、`entries[{legNo,players}]` |

**实时计分（1）**：`live_scores`，一场一条（`_id='ls_'+matchId`），只存逐球过程态，定稿后转写 `matches`。

**团队运动 · 篮球（6）**：与个人赛彻底分开，一场 5v5 绝不写 `matches` 与 `member_ratings`。

| 集合 | 存什么 | 关键字段 |
|---|---|---|
| `teams` | 长期球队 | `schoolId`、`association`、`sport`、`name`、`captainId`、`college`（可选）、`status`(pending/active/archived) |
| `team_members` | 队员与入队申请 | `teamId`、`userId`、`role`(captain/member)、`status`(pending/active/rejected/left) |
| `team_events` | 团队赛事 | `rules`（规则快照：节数/节长/犯规上限/报名下限）、`format`、`status`、`draw`（签表与随机种子）、`placements`（结算后的名次） |
| `team_event_entries` | 球队报名 | `eventId`、`teamId`、`status`(submitted/approved/rejected/locked)、`roster`（姓名与号码快照）、`lockedAt` |
| `team_matches` | 比赛 | `eventId`、`round`、`stage`、`slot`、`teamA/teamB`、`scoreA/scoreB`（**数字总得分**，不是数组）、`overtime`、`forfeit`、`winner`、`status`(scheduled/reviewing/published/canceled)、`revision` |
| `team_match_stats` | 单场个人统计（得分 / 犯规） | `matchId`、`teamId`、`players[{userId, points, fouls}]`（**null＝未记录，不是 0**）、`integrity`(basic/none) |

> 报名下限是 **5 人**（本项目口径，不采用 CUBAL 的「不足 8 人不得参赛」），规则快照里另有 `minOnCourt: 2`：犯规离场导致场上不足 2 人时判负。

**协会空间（6）**：`association_groups`、`association_group_members`、`association_notices`、`association_trainings`、`training_registrations`，以及公共公告 `announcements`。

**跨校邀请赛（4）**：`exchange_events`、`exchange_invitations`、`exchange_signups`、`exchange_matches`。这一组**不计个人等级分**。

**运动会（15）**：`sports_meets`（届）、`sports_meet_events`（项目）、`sports_meet_colleges`（学院范围）、`sports_meet_interests`（意向）、`sports_meet_entries`（报名）、`sports_meet_sessions`（场次）、`sports_meet_judge_assignments`（裁判）、`sports_meet_scores`（成绩）、`sports_meet_publications`（发布）、`sports_meet_result_rows`（结果行）、`sports_meet_quota_usage`（配额用量）、`sports_meet_standings`（学院总榜）、`sports_meet_honors`（个人荣誉）、`sports_meet_participant_claims`（参与认领）、`sports_meet_college_leads`（学院部长）。

运动会 15 个集合**一律带** `schoolId + meetId`，跨届读写会被拒。

> **52 个集合全是硬依赖**：少任何一个，走到那一步就报「集合不存在（-502005）」。`live_scores` 与 `pair_counts` 同样必须建——前者是计分台的实时态，后者是 15 场防刷名额的计数（缺它录分直接失败）。

### 2.3 关联键与索引

学校维度的记录一律用确定性复合 `_id`（`utils/school.js` 的 `schoolKey`），所以按主键点读最省事。只有「取一个范围的一批」才需要联合索引：

| 集合 | 联合索引 | 用途 |
|---|---|---|
| `matches` | `schoolId + association + status` | 取某范围已生效流水 |
| `matches` | `eventId` / `collegeEventId` / `tieId` | 按赛事/大场取比赛 |
| `member_ratings` | `schoolId + association` | 取一个范围的评级表 |
| `school_members` / `school_roles` / `colleges` | `schoolId` | 按学校取一批 |
| `memberships` | `schoolId + association` | 按范围取角色 |
| `association_*` / `exchange_*` / `pair_counts` | `schoolId + association` | 按范围取一批 |
| `sports_meet_*` | `schoolId + meetId` | 按届取一批 |
| `team_*` | `schoolId + association` | 按范围取球队 / 赛事 / 报名 |
| `team_matches` | `eventId` | 按赛事取赛程 |
| `team_event_entries` | `eventId` | 按赛事取报名 |
| `users` | `openId`（**唯一**） | 一个微信号只能一条 |

> `users.openId` 的唯一索引是最重要的。没有它，同一微信号可能被写入多条账号，登录态与权限都会错乱。

### 2.4 索引总表（照单建，集合名用控制台里的真实表名）

> 前面 2.3 是「按用途」的表，口径不变；这一节是「按集合」的执行清单，照着建不会漏。
> 共 **49 个集合**需要索引（其中 `matches` 一个集合多条、另有跨集合的按人反查），其余 3 个不需要。

| 类别 | 集合 | 索引字段 | 为什么 |
|---|---|---|---|
| 唯一 | `users` | `openId`（唯一） | 一个微信号只能有一条账号 |
| 范围 | `matches`、`events`、`event_signups`、`college_events`、`college_entries`、`ties`、`lineups`、`live_scores`、`seasons`、`pair_counts`、`member_ratings`、`rating_counters`、`teams`、`team_members`、`team_events`、`team_event_entries`、`team_matches`、`team_match_stats`、`association_groups`、`association_group_members`、`association_notices`、`association_trainings`、`training_registrations`、`exchange_events`、`exchange_invitations`、`exchange_signups`、`exchange_matches`、`memberships`、`school_associations`（共 29 个） | `schoolId` + `association` | 协会空间的每一次「取一批」都按这两个字段过滤 |
| 学校级 | `colleges`、`school_members`、`school_roles`、`sports_meet_college_leads`、`announcements` | `schoolId` | 这些集合只按学校归属，不带协会 |
| 运动会 | `sports_meets`、`sports_meet_events`、`sports_meet_colleges`、`sports_meet_interests`、`sports_meet_entries`、`sports_meet_sessions`、`sports_meet_judge_assignments`、`sports_meet_scores`、`sports_meet_publications`、`sports_meet_result_rows`、`sports_meet_quota_usage`、`sports_meet_standings`、`sports_meet_honors`、`sports_meet_participant_claims`（共 14 个） | `schoolId` + `meetId` | 运动会按届隔离，跨届读写要被拒 |
| 赛事子集 | `event_signups`、`college_entries`、`ties`、`lineups`、`team_event_entries`、`team_matches`、`team_match_stats` | `eventId` | 详情页只取本届 / 本赛事的几十条，不再整表读完再筛 |
| 赛事子集 | `matches` | `eventId`、`collegeEventId`、`tieId`（三条） | 个人赛签表 / 学院赛小场 / 大场查比赛 |
| 赛季区间 | `matches` | `schoolId` + `association` + `matchTime` | 录分页与提交要算「本赛季与每个人的交手次数」（`listSince` 把时间条件下推）。与 2.5 的 `by_scope_match_time` 同前缀——建那一条即可，不要重复建 |
| 按人反查 | `training_registrations` | `schoolId` + `association` + `userId` | 个人主页算训练积分只取这个人的几十条（`listByUser`，2026-10-22 H-2）。训练报名只增不减，不建会退化成整表扫描 |
| 按人反查 | `association_group_members` | `schoolId` + `association` + `userId` | 赛事详情判断「我在不在指定小组」（`listByUser`，2026-10-22 H-3）。不建会把整个协会的小组成员行读回来再筛 |
| 角色反查 | `memberships` | `userId` | 「我在哪些协会有高配角色」 |

不需要建范围索引的只有 3 个：`schools`（一校一条）、`student_id_claims`（按主键点读）、`audit_logs`（只追加、只按主键查）。

建索引时的三条注意：

- 除 `users.openId` 外**全部不唯一**：唯一性由确定性 `_id` 保证，别把业务字段设成唯一索引。
- 一个集合多条索引是正常的（`matches` 就有 8 条：3 条赛事键 + 5 条分页），在控制台里逐条「新建索引」。
- 建完等状态变「可用」再压测；索引没就绪时查询仍走全表，看起来像「建了没用」。

### 2.5 比赛列表分页索引（2026-10-22 新增）

比赛列表已改为在数据库内过滤、排序、分页并计数（一页最多 100 条），实时比分按这一页一次批读。**下面 5 条是它的前置条件**，缺了会退化成整表扫描——接口照样能用，只是每次翻页都在扫全表。

| 索引名建议 | 字段与方向 |
|---|---|
| `by_scope_match_time` | `schoolId ↑`、`association ↑`、`matchTime ↓`、`_id ↓` |
| `by_scope_event_match_time` | `schoolId ↑`、`association ↑`、`eventId ↑`、`matchTime ↓`、`_id ↓` |
| `by_scope_status_match_time` | `schoolId ↑`、`association ↑`、`status ↑`、`matchTime ↓`、`_id ↓` |
| `by_scope_team_a_match_time` | `schoolId ↑`、`association ↑`、`teamA ↑`、`matchTime ↓`、`_id ↓` |
| `by_scope_team_b_match_time` | `schoolId ↑`、`association ↑`、`teamB ↑`、`matchTime ↓`、`_id ↓` |

- 方向不能照抄其他索引：前几个等值字段升序，**`matchTime` 与 `_id` 必须是降序**，否则排序退回内存。
- `teamA` / `teamB` 是数组字段，必须分开建两条；不要把两个数组塞进同一条组合索引。
- 其余筛选（`pool`、状态与参与者叠加等）由上面几条缩小候选后再过滤；等真实慢查询出现再补，不预建所有字段排列。
- 索引未就绪时列表仍能跑，建完等状态变「可用」再压测。

## 三、首次部署：六步

### 3.1 建集合

数据库 → 集合管理 →「＋ 新建集合」，按第 2.2 节建齐 **52 个**。集合名一个字都不能差（区分大小写与下划线）。

若想先跑通主链路（注册 → 浏览 → 录分 → 确认 → 排行榜），最少要建这 **18** 个：`schools`、`school_associations`、`colleges`、`school_members`、`school_roles`、`student_id_claims`、`users`、`memberships`、`seasons`、`matches`、`pair_counts`、`live_scores`、`member_ratings`、`rating_counters`、`audit_logs`、`events`、`event_signups`、`announcements`。缺哪个，走到那一步就报「集合不存在（-502005）」。其余 34 个按功能启用时补齐（团队赛事 6、运动会 15、学院赛 4、跨校 4、协会空间 5）。另有一个历史集合 `rankings`（旧回放缓存）已退役，不要建。

### 3.2 建索引

按 2.3 / 2.4 / 2.5 三节。索引不是启动必需，但比赛列表与录分页在数据量上来后会明显变慢；**2.5 的 5 条是分页查询的前置条件**，不建等于把「数据库内分页」退回「整表读回再切」。

### 3.3 安全规则

选中集合 →「权限设置」→ 自定义安全规则，全部设为：

```json
{ "read": false, "write": false }
```

云函数以管理员身份运行，不受影响。**不要**设成「所有用户可读」——那等于把全量会员与比赛数据公开。

### 3.4 部署云函数 `data`

1. 仓库根目录先跑 `npm run sync:cloud`（把纯逻辑镜像到 `cloudfunctions/data/lib/`），再跑 `npm run check:cloud-sync` 确认一致。
2. 开发者工具右键 `cloudfunctions/data` →「上传并部署：云端安装依赖」。
3. 确认部署到 `CLOUD_ENV_ID` 指向的那个环境。

### 3.5 建学校与协会（新增学校时也要做）

控制台 → 数据库，各插一条：

```json
// schools
{ "_id": "muc", "schoolId": "muc", "name": "中央民族大学", "status": "active" }

// school_associations —— 每个要启用的协会各一条
{ "_id": "sa:muc:pkb", "schoolId": "muc", "association": "pkb", "status": "active" }
```

协会 id 取自 `miniprogram/utils/associations.js`，共 **6** 个：`pkb` 匹克球、`tt` 乒乓、`bd` 羽球、`tn` 网球（球拍类，走个人赛与个人等级分）、`bk` 篮球、`fb` 足球（团队类，走球队与团队赛事，不进个人等级分）。**没建 `school_associations` 的协会，该校用户进去会看到「该校尚未启用此协会」**。排球暂未接入，不要手工建它的协会行。

`colleges` 也要有该学校的 26 所学院（名字须与 `constants.COLLEGES` 完全一致，学院名是学院赛的对阵主键）。

### 3.6 创建第一个管理员

系统里没有内置管理员，第一个只能手工提。推荐：

1. 用管理员的微信在小程序里走一遍注册（会写 `users` + `school_members`，均为待审核）。
2. 控制台 → `users` 找到这条，`role` 改 `2`、`status` 改 `1`。
3. 控制台 → `school_members` 找到对应记录（`_id = sm:<schoolId>:<userId>`），`status` 改 `1`。
4. 控制台 → `school_roles` 插一条校级管理员：

```json
{ "_id": "sr:muc:<userId>", "schoolId": "muc", "userId": "<userId>", "role": "schoolAdmin" }
```

5. 重新打开小程序。

> 只改 `users.role` 不改 `school_members.status`，会出现「明明设了管理员还是没权限」——会籍不在册，权限一律不通过。这是最常见的原因。

## 四、日常操作之一：会员与角色

### 4.1 审核会员

小程序「我的 → 会员审核」就是干这个的，优先用它。控制台只在进不去或批量处理时用。

| 要做的事 | 集合 | 怎么改 |
|---|---|---|
| 通过会籍 | `school_members` | `status` 改 `1` |
| 驳回 / 禁用 | `school_members` | `status` 改 `2`，建议加 `reason` |
| 标记离校 | `school_members` | `status` 改 `3`（不上榜、不可报名，历史保留） |
| 修正学院 | `school_members` | 改成 26 所学院之一的全名 |

状态取值：`0` 待审核、`1` 正常、`2` 禁用、`3` 离校。只有 `1` 能正常使用。

> **不要「删了重建」**。删除会换掉主键，该会员的历史比赛、评级、荣誉全部对不上人。

### 4.2 角色任免

| 想给的权限 | 改哪里 | 改成什么 |
|---|---|---|
| 校级管理员 | `school_roles` | 插 `role='schoolAdmin'`，并确保 `school_members.status=1` |
| 协会负责人（本协会等同管理员） | `memberships` | 插 `role='leader'`，带 `schoolId + association + userId` |
| 学院负责人 | `memberships` | 插 `role='staff'`；另需 `school_members.college` 是学院全名 |
| 退回普通会员 | 两张表 | 删 `memberships` 行 / 删 `school_roles` 行 |

小程序里也有入口：他人主页上的「任免学院负责人」「任免协会负责人」，效果与控制台一致，且**协会负责人只能由校级管理员任免**（防止自己人提自己人）。

### 4.3 初始等级分

Elo 的起评分是**固定**的：男 1450、女 1300（`utils/elo.js`）。管理员可以为某会员在某协会预设一个起始分，写在 `users.initialEloByAssoc`：

```json
{ "pkb": 1600, "tt": 1450 }
```

规则：

- 取 0–3000 的整数；
- **只在首次建档时生效**——该会员在该协会还没打过任何一场计分比赛之前才有意义；
- 一旦出场，评级已落库，再改不会生效；
- 小程序「个人主页 → 调整初始等级分」是同一个字段，带「清除」按钮。

## 五、日常操作之二：赛季更新

### 5.1 它会做什么

只做两件事：写下分界时刻、赛季号 +1。

| 项目 | 变化 |
|---|---|
| 赛事积分 / 训练积分 | 清零重来（分界点之前结束的不计入本赛季） |
| 等级分（Elo） | **完全不变**，跨赛季连续累计 |
| 进步榜起点分 | 不变（只在首次入池时写一次） |
| 历史比赛 / 名次 / 荣誉 | 全部保留 |

### 5.2 怎么调

小程序里没有赛季入口，只能从控制台调云函数：

1. 云开发控制台 → 云函数 → `data` →「云端测试」。
2. 参数：

```json
{ "protocolVersion": 2, "schoolId": "muc", "association": "pkb", "action": "resetSchoolSeason", "payload": {} }
```

3. 点「调用」。需要该账号是管理员（校级管理员或协会负责人）。
4. 返回 `{ ok: true, data: { season: { seasonNumber: N+1 } } }` 即成功。

> 没有撤销。调用一次就多一个赛季，无法回退。请在赛季确实结束、通知到位后再做。

若页面仍显示旧赛季，退出重进小程序；仍不对则检查 `seasons` 里该范围那条记录的 `seasonNumber`。

### 5.3 手工调赛季参数

直接编辑 `seasons` 里 `_id = <schoolId>:<association>` 那条的 `anchorTime` / `resetTime` / `seasonNumber`。

> 手工改完把 `version` 加 1，否则容器里缓存的旧结果还会被沿用。

## 六、数据救急：先搞清「改了会不会重算」

### 6.1 最重要的一条变化

**等级分不再「每次读时重算」，而是确认比分时逐场结算落库。** 所以：

| 你改了什么 | 等级分会跟着变吗 |
|---|---|
| 改 `matches` 的比分 / 胜负 / 状态 | **不会**。评级表里已有结算快照，读接口直接读它 |
| 改 `member_ratings.elo` | 会，立刻生效（但结算链与快照不会跟着改，属于破坏一致性） |
| 改 `events.results`（名次） | 赛事积分会按新名次聚合（积分是聚合出来的），等级分不变 |

结论：**想改一场已结算的比赛，控制台改库做不到「正确回滚」**。正确做法只有两条：

1. 在「待确认」阶段用小程序驳回（此时还没结算）；
2. 找开发者在代码层面按结算链补一笔修正记录（当前没有这个工具）。

### 6.2 改玩家能看到的东西（低风险）

| 想改 | 集合 | 字段 |
|---|---|---|
| 昵称 / 头像 | `users` | `nickName` / `avatarUrl` |
| 真实姓名 | `users` | `realName` |
| 会员学院 | `school_members` | `college` |
| 比赛场地 / 时间 | `matches` | `location` / `matchTime`（不影响分数，但影响列表排序） |
| 赛事置顶 | `events` / `college_events` | `pinned` |
| 公告下架 | `announcements` | `status='archived'` |

### 6.3 清理测试数据

| 删什么 | 连带要删 |
|---|---|
| 个人赛事 | `event_signups`、`matches`（`eventId` 指向它） |
| 杯赛 | `college_entries`、`ties`、`lineups`、`matches`（`collegeEventId` 指向它） |
| 运动会 | 15 个 `sports_meet_*` 里该 `meetId` 的全部记录 |
| 会员 | **不要删**；改 `status` 即可锁定 |

> 批量删除前先在该集合点「导出」留底。孤儿数据比脏数据更难查。

### 6.4 防刷上限（15 场）

一对会员每赛季最多 15 场日常约球计入等级分。上限写在 `constants.RATED_PAIR_LIMIT`，库里没有「已超限」标记。

- 只有**日常约球**受限；带 `eventId` 或 `collegeEventId + tieId` 的比赛不占名额。
- 待确认也占名额，驳回后才还回来。
- 要临时放开只能改常量并重新部署云函数。

## 七、导入历史成绩（高风险，先读再动）

`tools/import-matches.py` 能把历史 Excel 转成 `matches` 文档，且自然键与云端一致（重复导入不会产生两条）。

**但它产出的记录是 `status=1`（已生效）**。在有 Elo 结算链的版本里，这意味着：

- 比赛会出现在列表里，却**没有对应的评级结算与快照**；
- 该会员的等级分不会因为这些比赛而改变；
- 结算序号链里也没有它们的位置。

所以当前版本的推荐做法是：

1. **首选**：在小程序里补录（每场都会正常结算）。
2. 需要批量导入时，先与开发者确认是否要一并生成 `member_ratings` 结算与序号，**不要**直接把 ACTIVE 文档灌进 `matches`。
3. 若确实导入，先在测试环境验证三件事：该会员评级是否变化、`rating_counters.seq` 是否递增、历史列表是否能打开该场。

## 八、更新云函数（每次改代码必做）

```
1. npm run sync:cloud           # 把 miniprogram/ 下的纯逻辑镜像到 cloudfunctions/data/lib/
2. npm run check:cloud-sync     # 确认 86 个文件逐字节一致
3. 开发者工具右键 cloudfunctions/data →「上传并部署：云端安装依赖」
4. 等状态变「部署成功」，再进小程序验证
```

判断是否部署过：控制台 → 云函数 → `data` 的「更新时间」。改了代码没重新部署，这个时间不会变。

> 漏部署的典型症状：新增接口报「该操作尚未支持学校范围」；改过的规则不生效；网球比分被按 11 分制拒掉。

## 九、故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 小程序显示「本地模拟数据」 | `config.js` 的 `CLOUD_ENV_ID` 为空 | 填入环境 ID，基础库 ≥ 2.2.3 |
| 报「该操作尚未支持学校范围」 | `data` 未部署或版本旧 | 重新同步并上传部署 |
| 报「请升级客户端」 | 请求没带 `protocolVersion: 2` | 老客户端；控制台手调时补上该字段 |
| 报「学校不存在或已停用」 | `schools` 缺该学校，或 `status` 不是 `active` | 补建/改正 |
| 报「该校尚未启用此协会」 | 缺 `school_associations` 那条 | 补建 `sa:<schoolId>:<association>` |
| 报「集合不存在 -502005」 | 少建集合 | 按 2.2 节补齐 |
| 设了管理员还是没权限 | `school_members.status ≠ 1`，或缺 `school_roles` 行 | 两处都改 |
| 排行榜上没有某人 | `users.gender` 缺失 | 补 `'M'` / `'F'` |
| 学院负责人交不了名单 | `school_members.college` 不是学院全名 | 改成 26 所之一 |
| 改库后分数没变 | Elo 已落库，不随 `matches` 重算 | 见 6.1：改库无法回滚，需代码层修正 |
| 同一对会员录不进分 | 本赛季日常约球已满 15 场 | 正常限制；或改常量重部署 |
| 运动会某步报错 | 15 个 `sports_meet_*` 少建 | 补齐 |
| 赛季调用被拒 | 调用身份不是管理员 | 用校级管理员或协会负责人身份 |
