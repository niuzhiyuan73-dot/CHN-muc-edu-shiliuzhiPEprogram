## 3 关键口径

**服务端统一、客户端例外一处。** 服务端四组处理器现在只有一种失败形状，符合 `src/envelope.js` 与交接说明「约定 4」。客户端 `forMeet` 仍把业务拒绝抛成异常：6 个运动会页面（meet-detail / meet-schedule / meet-score / meet-setup / meet-standing / meet-college）共 60 余处按 `catch` 写的失败分支，只有 `meet-list` 判过 `ok === false`；直接改成值返回会让「没权限 / 没指定学院 / 报名已截止」静默变空数据，退化比不统一更糟。将来统一个四门面，先改这 6 个页面的失败分支。

**只修契约，不改页面交互。** `listMeetEntries` 保持全量返回，不加分页参数——它的消费方 `meet-college` 是一次性平铺全届报名的校管理员工作台，加分页要连页面一起改，超出本批范围。

## 4 踩坑与纠正

- **第一次验证分页读到旧数据。** 改完 `listMeetColleges` 直接跑探测，`limit: 3` 仍返回 26 条，误以为改动没生效。真因是探测走 `cloudfunctions/data/lib/` 镜像，而没跑 `npm run sync:cloud`。同步后 `{total:26, len:3, hasMore:true}` 正常。这条是本项目最容易静默失败的一处，再确认一次。
- **「失败即异常」不是纯客户端问题。** 一开始把 6 个页面的 `catch` 当成可以顺手改的旧写法，动手前统计了各页 `catch` 与 `ok === false` 的数量（6 个页面 0 处判断），确认改成值返回必然吞提示，才回退到门面层 `throwOnRefused`。如果只按「四域统一」的目标硬改，会是本批最大的回退风险。
- **`seasons.getById is not a function` 不是线上缺陷。** 桩上五个动作报这个错，一度当作线上故障。核对 `school-memory-repo.js` 的逐集合生成与 `cloud-repo.js` 的「三件套补齐」后确认两端都有 `getById`，缺的只是 `tests/helpers/memory-repo.js` 这一层，属测试盲区。3222 条用例全绿本身就是它没被覆盖的证据。
- **审计里「页面取 `.items` 未判空」一条随方案失效。** 该条成立的前提是运动会读接口改成值返回；既然门面仍抛异常，`catch` 照常生效，`meet-college` 不需要额外判空，本批不做。

## 8 回归与反向验证

- **反向 1：归一化不能吞掉真正的请求级失败。** 新增用例专门钉住「协议版本不对 / 未知动作 / 缺学校」仍是顶层 `ok:false`，防止 `acceptResult` 把 `fail()` 也一起包进去。
- **反向 2：DTO 注入不能把 `ok:false` 改成 `true`。** `ok()` 的注入条件是 `data.ok === undefined`，用例里对一次真实拒绝断言 `data.ok === false`。
- **反向 3：运动会页面行为不变。** `meet-pages` / `meet-*` 共 268 条与页面装配 425 条全绿，跑的就是 mock 门面；若 `forMeet` 的抛出被误删，这些用例里的拒绝分支会失去异常入口。
- **反向 4：分页不重叠。** 用例断言第二页与第一页的 `collegeId` 无交集，防止 `offset` 语义写反（改了 `slice(0, 50)` 很容易写成固定窗口）。
