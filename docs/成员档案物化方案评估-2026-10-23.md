# 成员档案物化方案评估（2026-10-23）

**背景**：大用户量复查里还剩三处读放大没根治——榜单（H-6）、个人主页的「项目排名」（H-2 剩余）、协会名录的分页（H-5 剩余）。三处的根因是同一个：**要排序/计数的字段散在两个集合里，数据库无法跨集合 join，所以只能整表读回来在内存里算。**

本文只做方案评估，**没有改动任何业务代码**。要动的是数据模型，需要先拍板。

---

## 一、三处问题各自的现状

以「2000 人在册 / 人均 4 池评级 / 3 年积累」估算，单次请求的 RPC 页数（云端每页 100 条）：

| 接口 | 读什么 | 页数 | 现状 |
|---|---|---|---|
| `getSchoolRanking`（榜单） | 名册 `schoolMembers` 20 + 账号 `users` 20 + 评级 `memberRatings` 80 | **120** | 已去掉积分事实（33 页），剩这 120 |
| `getSchoolMemberProfile`（个人主页） | 同上 120 + 我的比赛 1 + 我的训练报名 1 + 学院 1 | **≈ 123** | 已下推比赛与训练报名，剩这 120 |
| `listAssociationMembers`（名录） | 名册 20 + 账号 20 + 学院 1 | **41** | 权限标签已批读（40 次 → 2 次） |

> 名册那 40 页（`schoolMembers` + `users.listByIds`）三处都要，因为**排序键与展示字段跨集合**：
> 性别、在册状态在 `schoolMembers`；昵称、真名、头像在 `users`。

### 为什么不能直接下推

| 需求 | 排序/过滤键 | 在哪 | 障碍 |
|---|---|---|---|
| 榜单按 elo 排序、按项目（性别）筛 | `elo` + `gender` | 评级表 / 名册 | 性别不在评级表，无法一条查询搞定 |
| 「我在同项目排第几」 | 比我 elo 高的人数 | 评级表 + 名册 | 同上，且要 join 后才能数 |
| 名录按昵称排序 + 关键词匹配 | `nickName` + `realName` | 账号表 | 排序键不在名册集合上 |

`memberRatings` 的主键是 `(userId, pool, scope)`，每人 4 池 = 4 条。2000 人就是 8000 条 —— **80 页**，这是三处里最贵的一项，而真正用得上的只有「该池、该性别、elo 前 10」和「比我高的人数」。

## 二、三个可选方案

### 方案 A（推荐）：给 `memberRatings` 补两个字段

在评级文档里冗余 **`gender`** 与 **`memberStatus`**（在册状态）。评级本来就是「结算时逐场更新」的物化数据，多带两个几乎不变的字段不改变它的性质。

改完之后三条查询都能下推：

| 需求 | 新查询 | 页数 |
|---|---|---|
| 榜单前 10 | `memberRatings` where `{pool, gender, memberStatus: active}` orderBy `elo desc` limit 10 | 1 |
| 我的名次 | `count(elo > 我的)` + 1 | 1（聚合计数） |
| 榜单行的昵称 | `users.listByIds`（前 10 + 我 = 11 人） | 1 |
| 个人主页「我排第几」 | 同上（本人点读 + count） | 2 |
| 名录分页 | 需另补 `schoolMembers.nickName`（见下） | — |

**要改的地方**

1. **写入路径**（`school-rating-service.js` 的 `buildRatingDoc` / 结算）：建档与结算时写入 `gender`、`memberStatus`。建档点在 `materializeRatings`，结算在 `settleMatchInTransaction`。
2. **同步点**（`school-membership-service.js`，5 处）：入会审核通过、退会、转校、恢复、性别变更——每处更新该会员的 4 条评级文档。这些都在事务里，每次多 4 个写操作；事务预算 100，目前这些路径开销不大，可以容纳。
3. **新仓储原语**（两端 + 契约）：`memberRatings.listTop({ pool, gender, limit })`、`memberRatings.countAbove({ pool, gender, elo })`、`memberRatings.listByUser(userId)`。
4. **索引**：`member_ratings` 加 `schoolId + association + pool + gender + memberStatus + elo desc`。
5. **历史回填**：一次性脚本，按 `schoolMembers` + `users` 补齐 8000 条评级文档的 `gender` / `memberStatus`。**回填前不能切换读路径**，否则老文档缺字段会被过滤掉，榜单直接空。

**风险**

- 冗余字段与源数据不一致（改名不会影响这两个字段，但性别/在册状态会变）。所有变更点都在上面 5 处，漏一处就出现「已退会的人还挂在榜上」。**建议加一条对账测试**：随机抽样比对 `memberRatings.memberStatus` 与 `schoolMembers.status`。
- 回填 8000 条需要分页跑（每批 100），一次性执行约 80 批写。

**收益**：榜单 120 → **约 5 页**；个人主页 123 → **约 15 页**（评级与名册都不再全量读）。

### 方案 B：新建 `memberProfiles` 影子集合

每校每人一条，冗余昵称、真名、头像、性别、在册状态 + 各池 elo/胜负/出场数。榜单、名录、个人主页都只读它。

- **优点**：一次解决三处，连名录的排序也一起解决；单次读降到 1~2 个 RPC。
- **缺点**：等于把 `memberRatings` 与 `users` 各复制一份，**三份数据要同步**（改名、换头像、退会、每场结算都要更新）。每场结算多写 2~4 条，而结算本来就在事务预算内。
- **结论**：单看读比 A 好，但读写合起来不如 A（见下一节的对比）。除非将来要加「全校成员搜索」这类功能，否则不值得。

### 方案 C：维持现状

榜单与个人主页都是「打开时贵一次」，不是轮询。5 万日配额下，120 页/次意味着约 400 次打开就见底——**开学季不够用**，但日常够用。

- 若这一版不上量（单校 < 500 人），可以接受。
- 若预期 2000 人，建议做 A。

### 读效率 vs 写效率：A 和 B 各赢一半

| | 方案 A（评级表补 2 个字段） | 方案 B（影子集合） |
|---|---|---|
| 榜单单次读 | **约 3 个 RPC**（前 10 一页 + 名次一次计数 + 昵称批读 11 人） | 约 1~2 个 RPC |
| 个人主页单次读 | 约 4 页 + 每个项目 2 次计数（3~4 个项目 = 6~8 次） | 同左 |
| 名录单次读 | 41 页（不变） | 约 1 页 |
| **每场结算的额外写** | **0**（结算路径完全不动） | **+2~4 条**（每个参与者一条） |
| 低频变更（退会 / 转校） | 各 +4 条（4 个池） | 各 +1 条 |
| 一致性风险 | 低（2 个字段、5 处同步） | 中高（三份数据） |

**读这边，A 已经够低了**：5 万日配额 ÷ 3 ≈ **1.6 万次榜单打开**。榜单一天不可能被打开 1.6 万次；真到那个量级，先撞的是云函数并发限制，不是读配额。B 省到 1~2 个 RPC，边际收益只存在于纸面。

**写这边，A 是零成本，B 是持续成本**：B 要求每场结算都给参与者更新一条 profile——一个协会一年 800 场就是 **2400 条额外写**，而且这些写**发生在结算事务里**（结算本来就吃事务预算，见 W-0 那一轮）。

所以结论是：**单看读，B 更高；算上写与一致性，A 明显更高。** B 相当于用「贵的东西（事务内写）」去换「已经便宜的东西（读）」。

只有当将来出现「全校成员搜索」「跨协会找人」这类**必须查 profile 全字段**的功能时，B 才值得——那时它是为功能服务，不是为省读。

## 三、名录那一处（H-5 剩余）

名录的分页依赖「按昵称排序 + 关键词匹配」，排序键在 `users` 上。方案 A 不解决它。

两个选择：

| 选择 | 做法 | 代价 |
|---|---|---|
| C1（推荐） | 接受现状：41 页/次，但名录是**低频页**（翻名单），且已有游标分页（不会一次拉完） | 无 |
| C2 | 给 `schoolMembers` 补 `nickName` / `realName`（改名时同步），排序下推 `orderBy(nickName)` + 游标 | 又多一处冗余；且中文昵称的码点序与云端排序规则需实测一致，否则翻页会重/漏 |

我倾向 **C1**：名录打开频次远低于榜单与个人主页，41 页换一次数据模型变更不划算。等有人真的抱怨「名录慢」再做。

## 四、如果做方案 A：实施顺序

1. **加字段与回填**（不改读路径）：`buildRatingDoc` 写入 `gender` / `memberStatus`；写回填脚本；跑完对账测试。
2. **加仓储原语与索引**：`listTop` / `countAbove` / `listByUser`，两端同口径 + 契约测试 + 索引文档。
3. **切榜单**（先切它，因为它的读量最大且不依赖个人主页）：`getSchoolRanking` 改用新原语，删掉 `loadScopeView` 调用。
4. **切个人主页的项目排名**：`projects` 的 rank/percentile 改用 count；`nameOf` 改为按对手 id 批读。
5. **验证**：全量回归 + 用 2000 人 / 8000 条评级的夹具测「榜单 ≤ 10 页」。

每一步都可以单独回滚（第 1 步只加字段不读；第 3、4 步各自独立）。

## 五、需要拍板的两件事

1. **是否做方案 A**（榜单 120 → 5 页，个人主页 123 → 15 页，代价是 2 个冗余字段 + 5 处同步 + 一次回填）。
2. **名录是否维持现状**（41 页/次，低频页）。

若同意，我按第四节顺序做，第一步（加字段 + 回填脚本）不改任何读路径，风险最低，可以先跑通再切。

## 六、第 1 步已落地（2026-10-23）

**结论：写入侧与回填工具完成，读路径一行未动。** 榜单与个人主页的读量暂时没有变化，这是有意的——回填没跑完就切读，缺字段的老文档会被过滤掉，榜单会直接空。

落点与评估时的假设有两处出入，都以代码为准：

### 6.1 同步点只有 2 处，不是 5 处

评估时按「入会通过、退会、转校、恢复、性别变更」列了 5 处，核对代码后发现**退会 / 恢复 / 性别变更这三条路径当前并不存在**：`SCHOOL_MEMBER_STATUS.LEFT` 与 `DISABLED` 在 `miniprogram/services/` 下没有任何写入点，也没有改 `gender` 的接口。剩下真实存在的是：

| 路径 | 位置 | 同步动作 | 事务增量 |
|---|---|---|---|
| 入会审核通过 | `reviewSchoolMembership` | 该校全部协会 → `active` | 24 读（多数为 missing） |
| 转校通过 | `reviewSchoolTransfer` | **原校**全部协会 → `transferred` | 24 读 + 最多 24 写 |

转校的目标学校那一侧**刻意不扫**：转进来的人在新校还没有评级文档（惰性建档），而转校事务本身已约 31 个操作，再加 24 读 + 24 写就到 79；两边都扫会撞 100 的预算。代价是「转出后又转回」的残留文档要靠回填脚本纠正。

同理，`memberStatus` **不在结算路径写**：结算含补录旧比赛，结算那一刻不代表此人当下在册，用它写状态会把已转出的人改回 active。性别则相反——结算本来就点读了 `users`，顺手刷新 `gender` 是零成本。

### 6.2 回填是离线脚本，不是小程序接口

`tools/backfill-rating-profile.js` + `tools/rating-backfill-core.js`：

```bash
node tools/backfill-rating-profile.js --school=muc            # dry-run，只报要改多少
node tools/backfill-rating-profile.js --school=muc --apply    # 落库
node tools/backfill-rating-profile.js --adapter=memory        # 无凭据时演练脚本本身
```

- 按 `_id` 游标分页，默认 100 条/批，`--cursor` 续跑；
- 回填期间**只改动不一致的文档**，因此可重复执行；
- **验收判据：同一学校连跑两遍，第二遍 `updated` 必须是 0。** 不为 0 说明还有人在写缺字段的评级文档，先查清再切读；
- 输出会单独统计两个孤儿：`无账号`（评级在、users 没了）与 `无名册`（评级在、school_members 没了）。后者会让榜单漏人，要先查名册再决定清理还是补档案；
- 云端凭据走 `@cloudbase/node-sdk`（需自行安装）。

| 文件 | 条数 | 钉住什么 |
|---|---|---|
| `tests/rating-profile-sync.test.js` | 10 | 建档即带性别与 active；第二次结算刷新性别；结算**不改**在册状态；同步只写变化的文档；转校后原校各协会标 transferred；入会通过把重入校的旧文档恢复 active；驳回入会不动评级 |
| `tests/rating-backfill.test.js` | 8 | 缺字段补齐；连跑两遍第二遍 0 变更；dry-run 不落库；只写待改的那条；两类孤儿不猜；游标分页不重不漏；只回填指定学校 |

### 6.4 第 2~4 步也已完成（同日）

| 步骤 | 落地内容 |
|---|---|
| 第 2 步 · 原语与索引 | `memberRatings.listTop` / `countRanked` / `listByUser`（云端 + 内存 + 测试桩，契约测试同步）；索引 `schoolId + association + pool + gender + memberStatus + elo ↓` 写进索引清单 |
| 第 3 步 · 榜单 | `getSchoolRanking` 改为「一次取前 50 + 两次计数 + 一次批读」：**120 页 → 约 5 个 RPC** |
| 第 4 步 · 个人主页 | `getSchoolMemberProfile` 的排名改两次计数，整条取数链不再物化全班名册：**123 页 → 约 15 页** |

**三处需要说明的取舍**

1. **`allRows` 收窄到前 50 + 我。** 页面搜索原本在「全榜」上过滤，现在只能搜到前 50 与我。这是有意的：前 50 覆盖「找自己 / 找同学」，而全量下发 2000 行本身也是负担。
2. **回填未完成时整体回落。** 判据是 `memberStatus` 字段的**存在性计数**（`_.exists(false)`），不是"新路径取到几条"。后者在部分回填时更危险——已回填的人照常上榜、没回填的人被静默滤掉，榜单看起来正常却少了人。
3. **名次仍由本地重算。** 数据库只按 `elo + 胜场` 取「哪一批人」，名次用 `buildRows` 的完整比较器（`elo → 胜率 → 胜场 → 时间 → 编号`）算，与旧路径逐位一致。胜率是派生字段，不进索引。唯一的分叉可能是「第 50 与第 51 名 elo 完全相同」。

**验收**：`tests/rank-read-budget.test.js` 6 条钉住「不整表读评级 / 名次正确 / 性别下推 / 榜外名次 / 转出的人不上榜 / 回填未完成回落」；全量 171 文件 / 2966 用例通过。

### 6.5 上线顺序（不能颠倒）

1. **先部署代码**（写入侧 + 回填工具 + 新读路径）。此时读路径会因为「检测到残留」自动回落旧路径——慢但正确。
2. **跑回填**：`node tools/backfill-rating-profile.js --school=<id>`（先 dry-run 看数字）→ 加 `--apply` 落库。
3. **验收**：同一学校再跑一遍，`updated` 必须是 **0**。
4. 之后读路径自动切到新路径（无需再发版），日志里不再出现 `[rank] ... 回填未完成` 告警。

> 第 1 步仍可单独回滚：字段加了但读路径有保护，删掉写入点即可恢复原状。
