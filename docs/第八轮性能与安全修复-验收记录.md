## 三、关键口径

- **「读失败」与「没有这条数据」必须分开**。旧判据（`errCode === -1` 或文案含 `not exist`）把前者折成后者，而 `school-repository.write()` 把 `null` 当作「可以写入的新记录」，于是归属校验被跳过、`checked()` 把调用方 scope 写进别人的文档。这是继 `byIds` 之后第二条能跨校写的路径，本批堵在适配器一层。
- **日预算取 4000，不是把每秒阈值降到 1~2**。首页同秒会并发 6 个协会的读请求，压秒级阈值是直接打断首屏；配额问题只能按天解。4000 × 约 8 次读 ≈ 3.2 万次读，占每日 5 万配额约 64%。
- **轮询豁免、且不计数**。看一场一小时的比赛是 1800 次请求，每次只 1 次读；计进来只会误封正常观众。
- **顶层 `list()` 用静态测试守，不改运行时行为**。契约测试把顶层 `list` 当作合法形态钉着，模拟端也这么实现，运行时禁掉会造成两端分叉（本地绿、云端红）。防线改为「业务层不许这么写」。
- **缓存失效只对纯比赛类写放宽**。判据是「不写学籍 / 角色 / 会籍」；拿不准一律全清——多清几次只多付几次读，漏清是一段撤权不生效的窗口。

## 四、踩坑与纠正

- **「让 `readDoc` 一律用 count 探测」被否**。普通会员每次请求有 2 次「本来就不存在」的读（`schoolRoles` / `memberships`），全走探测等于给每次请求加 2 次 RPC——修安全问题顺手制造读放大。改成「明确文案走快路径 → 文案不明才探测」，正常路径零额外成本。
- **「顶层 `list()` 在运行时抛错」被否**。见第三段：契约测试 `cloud-repo-contract` 明确断言 `cloud.matches.list()` 返回 53 条，内存端也这么实现。真要做运行时护栏，得同时改两端 + 改契约，收益（防未来误用）不抵分叉风险。
- **「收紧 `isMissingDoc` 会让真机上的『文档不存在』变成异常」是真实风险**，不是空想：云开发文档不存在的文案在不同 SDK 版本有过变化。所以保留了探测兜底（`docAbsent`），而不是纯文案匹配。
- **`readDoc` 的三种结局在内存仓储里测不出来**（内存端不存在就是 `undefined`，不抛）。这类修复必须自造会抛错的桩，否则测试全绿也证明不了任何事。
- **本批没有新增集合与索引**：日预算是进程内 Map，与既有秒级桶同一取舍，不引入计数器集合（那会给每个请求加一次读写，把限流变成放大器）。

## 七、未完成及原因

| 项 | 原因 | 触发条件与改法 |
|---|---|---|
| 公告 / 赛事 / 学院赛列表的**查询下推** | 排序键是「置顶 → 状态 → 时间倒序」的复合口径，需要复合索引 + 游标编码 + 两端同口径重写，属独立一批；与团队战绩（单点、收益最大）不同，这批改动面横跨 4 个服务 | 单校公告 > 500 条、或赛事列表单页耗时进入秒级时启动。做法：新增 `listPage(where, order, cursor)` 原语，索引按 `(schoolId, pinned, publishTime, _id)` 建，排序口径由现有 `sortAnnouncements` 原样搬进 `order` |
| `readMatchPage` 的 `pendingCount` 按需计算 | 首屏角标与列表页都要这个数字，加开关收益为 0 | 出现「翻页请求量 > 首屏请求量 10 倍」时再拆 `withPending` 选项 |
| `idempotency.js` 的时间解析兜底 | 上游 `buildMatchRecord` 已校验时间，非法值到不了自然键；直接包一层只会把错误文案挪个位置 | 出现 `RangeError: Invalid time value` 的线上日志时再加 |
| `sweep()` 的全表遍历 | 只在桶数 ≥ 20000 时触发，触发时本就是异常流量场景 | 匿名桶分 IP 后桶数上升，若日志出现「服务繁忙」频发，改分批惰性清理 |
| 日预算的**持久化**版本 | 进程内计数是既有取舍（零额外读写）；持久化计数器要给每个请求加一次读写 | 出现「同一账号在多实例同时刷」的实际案例时，按 `openId + 日期` 建计数集合 |

## 八、回归与反向验证

- **读失败三态**：桩里让 `doc().get()` 真的抛错，逐条断言「明确不存在 → null（且不发探测）」「有权限错但文档在 → 抛」「文案不明且计数为 0 → null」「探测也失败 → 抛原错」「集合缺失 → 中文错」「事务内无法探测 → 抛」。仅断言「不返回 null」不够，所以每条都钉了探测次数与文案。
- **缓存失效分流**：不测「读了几次」（随实现变），只测「哪个动作走哪条失效」——审批进白名单就红。
- **战绩页收窄**：spy 包住 `forScope` 返回面的 `teamEvents / teamEventEntries / teamMatches / teamMembers / teams` 五个 `list()`，断言调用次数为 0；同时断言名次、近期战绩、队长名、队员数仍正确，防止「测试转绿但页面空了」。
- **日预算边界**：单独钉了「轮询不计数」「秒级被拒不计数」两条，它们是会误伤正常用户的边界，比上限值本身更容易写错。
