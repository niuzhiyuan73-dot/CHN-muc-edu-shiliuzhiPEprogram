# 石榴籽杯：需求确认与实施方案（v2）

日期：2026-10-19
状态：**需求已确认，方案待最后一句确认后开工**
修订说明：v1 把「石榴籽杯」误当成「一届跨三个项目的容器」，据此设计了届次与项目两张表。按你的说明，这个前提不成立，v2 全部改掉。

---

## 0. 本轮修正（先对齐理解）

v1 的错误：把石榴籽杯理解成「一个活动 → 三个项目 → 多场学院赛」的三层结构，并为「届次」建了集合。

修正后的结构：

```
石榴籽杯（栏目，不是数据实体）
├── 匹克球项目 ── 历次学院赛（按发起时间倒序）
├── 乒乓球项目 ── 历次学院赛（按发起时间倒序）
└── 羽毛球项目 ── 历次学院赛（按发起时间倒序）
```

- **每个项目各自就是一个「石榴籽杯」**，不是三个项目共用一个杯赛。
- **一次发起只能落在一个项目上**；发起时选定项目，之后不可改。
- **不设届次**。同一项目一年可以发起多次，每次都是一场独立的学院赛；历史按**发起时间**排序与筛选。
- 因此，「石榴籽杯」不需要一张表来承载：项目就是协会，学院赛本来就带 `association`。

## 3. 仍需你确认的一句话

Q1 选 B 时，选项里写的是「负责人可结束本场；只有校管能结束整个石榴籽杯」。但在「不设届次、每个项目就是杯赛」的模型下，**不存在「整个石榴籽杯」这个可结束的对象**——每个项目没有独立的生命周期，学院赛之间彼此独立。

因此按 B 落地后，实际只剩一个结束动作：**结束本场**，校管与该项目负责人都可以。

需要你确认：

- **甲（推荐）**：就这样。没有「关闭项目杯赛」的概念，项目永远开放，随时可发起新赛事。
- **乙**：需要一个「关闭该项目杯赛」的开关（仅校管），关闭后不能在该项目发起新赛事，历史仍可看。这需要给项目加一条状态记录。

选甲则零新增集合；选乙则加一张极轻的 `sportsCupProjects`（每个项目一条，只有 `status`）。

## 4. 实施方案

### 4.1 为什么可以不建新集合

这是 v2 与 v1 最大的差别，理由有三条，都可以在代码里核对：

1. **项目就是协会**。三个球类与 `ASSOCIATIONS` 一一对应（`pkb` / `tt` / `bd`），学院赛主记录本来就带 `association`。按项目看比赛，等价于按 `association` 查 `collegeEvents`。
2. **权限已经按项目隔离**。`buildSchoolContext` 只加载**当前协会**的 `membership`；一个乒乓球负责人进入匹克球范围时，`membership` 为空，`legacyRoleOf` 返回普通会员。因此「其他项目负责人不能管」是现有结构自带的，不需要额外的项目授权表。
3. **没有历史包袱**。当前无历史数据，旧入口立即下线，不存在「旧记录没有项目字段」的问题，也就不需要迁移与兼容分支。

结论：**不新增集合、不新增字段**。只新增一个页面、收紧一处权限、收敛三处入口。

### 4.2 数据模型

| 数据 | 处理 |
| --- | --- |
| 项目清单 | 直接读 `utils/associations.js` 的 active 项，不落库 |
| 学院赛归属 | 复用 `collegeEvents.association`，不新增 `cupId` / `projectId` |
| 历史排序 | 复用 `publishTime`（发起时间）倒序；`startTime` 仅用于年份筛选与展示 |
| 协会负责人 | 复用 `memberships`（`role = 'leader'`，可多条，即多人） |

唯一可选的增量（按第 3 节选乙时才需要）：`sportsCupProjects` 一条记录，字段 `schoolId`、`projectId`、`status`、`updatedBy`、`updatedAt`。

### 4.3 权限

**矩阵**

| 动作 | 校级管理员 | 本项目协会负责人（可多人） | 其他项目负责人 | 学院负责人 | 普通成员 |
| --- | --- | --- | --- | --- | --- |
| 发起学院赛 | ✓ | ✗ | ✗ | ✗ | ✗ |
| 结束本场 / 提交名次 | ✓ | ✓ | ✗ | ✗ | ✗ |
| 审核名单、抽签、开赛、指派裁判、置顶 | ✓ | ✓ | ✗ | ✗ | ✗ |
| 代任一学院提交名单 | ✓ | ✓ | ✗ | ✗ | ✗ |
| 本学院名单 / 排阵 / 小场录分 | ✓ | ✓ | ✗ | ✓（本学院） | ✗ |
| 查看 | ✓ | ✓ | ✓ | ✓ | ✓ |

**服务端改动只有一处**

现有 `canManageCollegeEvent(actor)` 对「校级管理员」与「当前协会负责人」都返回真（`legacyRoleOf` 把两者都映射为 `ROLE.ADMIN`）。新需求只把**发起**上收：

- `publishCollegeEvent`：判权从 `canManageCollegeEvent` 改为「本校校级管理员或平台管理员」。
- `finishCollegeEvent`：保持现状（校管或本项目 leader），已符合 Q1-B。
- 其余赛中动作：保持现状。
- 读端新增下发 `canPublish`（仅校管），与 `canManage`（校管或本项目 leader）分开，页面据此决定是否显示「发起学院赛」。

这样不需要改 `freshActorGate`，也不需要身份投影——现有上下文已经按协会加载 `membership`。

### 4.4 页面

**新增 `pages/cup-home/cup-home`**

```
┌ 石榴籽杯 ────────────────────────────┐
│ [匹克球 ●] [乒乓球] [羽毛球]           │  ← 顶部项目切换，写全局当前协会
├──────────────────────────────────────┤
│ 本项目进行中 1 场 · 已结束 6 场        │
│ [＋ 发起学院赛]        （仅校管可见）  │
│ 年份：[全部 ▾]  状态：[全部 ▾]         │
├──────────────────────────────────────┤
│ 报名中  · 石榴籽杯匹克球学院赛          │
│ 进行中  · ……                          │
│ 已结束  · ……（按发起时间倒序）         │
└──────────────────────────────────────┘
```

- 切换项目：`associationScope.setAssociation(projectId)`（与协会页同一套），随后重载列表；页面不缓存跨项目数据。
- 列表：调现有 `listCollegeEvents`（按当前协会），复用 `buildCollegeEventRow` 的行形状与状态文案。
- 发起：进入现有 `college-event-edit`，路由带 `projectId`；页面内项目单选、默认当前项，提交时按所选项目构造范围。
- 点行：进入现有 `college-event-detail`；后续六页全部复用，**不需要改**，因为它们都读全局当前协会。

**改造 `college-event-edit`**

- 顶部增加「项目」单选（三项），默认取当前协会，切换即更新全局协会与提交范围。
- 进入页的权限判断从 `canManage` 改为 `canPublish`；无校管权限直接提示，不给表单。

**入口调整**

- `association` 页「校级活动」档：运动会旁新增「石榴籽杯」卡片。
- `events-panel`：删除学院赛整块（标题、＋按钮、列表、置顶、查看全部）。
- `event-list?type=college`：分支删除；若旧链接进入，直接 `redirectTo` 杯赛首页。

### 4.7 测试

- 发起：协会负责人被拒；学院负责人被拒；校管通过。
- 结束：本项目负责人通过；其他项目负责人被拒；学院负责人被拒。
- 多人负责人：同一协会两名 leader 均可管理同一场。
- 换人：撤销 leader 后立即被拒；新 leader 立即生效。
- 项目隔离：乒乓球负责人调匹克球接口被拒；列表不串项目。
- 列表：按发起时间倒序；年份筛选；状态筛选。
- 回归：`events-panel` 删除学院赛区后，原有工作台测试更新；全量 2452 条不红。

### 4.8 风险

| 风险 | 对策 |
| --- | --- |
| 全局当前协会被杯赛页改写，用户回工作台看到别的协会 | 这是预期行为（项目即协会）；在杯赛页顶部持续显示当前项目，避免迷失 |
