# 篮球协会云端专项审计

日期：2026-10-20。范围：篮球团队、赛事、实时计分、统计审核，以及协议 2 路由、云端仓储和数据写入边界。

初次审计只记录问题。随后已按用户授权完成修复（见文末）；未访问真实云数据库、未部署。新增复现工具 `tools/audit-basketball-cloud.cjs` 只在进程内模拟数据库，执行云函数真实路由与真实云端仓储适配器；模拟集合查询限制、事务提交/回滚、JSON 序列化、RPC 中断和总操作数约束。工具现已改为正确行为验证，并由 `tests/basketball-cloud-fixes.test.js` 纳入回归。以下位置与复现结果记录的是修复前的审计快照。

## 已复现的问题

### A1 · P1 · 实时比赛能被重抽覆盖，计分丢失

位置：`miniprogram/services/team-event-service.js:846`、`:894`；部署镜像同源。

`drawTeamEvent` 只检查正式 `scoreA`，而实时比赛正式分一直是 null，实际比分在 `liveScore`。因此 LIVE 状态也能重抽，新赛程按相同主键整份 set，抹掉原 liveScore、统计关联和出场状态。旧计分台再写会提示“请先开启实时计分台”。

复现：4 队抽签 → 开台 → A 队记 3 分 → 管理者重抽，接口返回成功；原比赛由 live 变成 scheduled，liveScore 消失。这不是单纯的部署问题，本地正常流程测试同样遗漏了该入口组合；云端多个操作入口并行时更容易出现。

建议：任何 LIVE、已录分、已审核或已有实时流水的比赛均禁止重抽；判断与赛程写入必须处在同一受赛事版本控制的提交过程，防止检查后另一请求刚好开台。

### A2 · P1 · 结算中断后无法通过重试补齐球队名次

位置：`miniprogram/services/team-event-service.js:1771`、`:1782`。

先将赛事写成 finished，再逐队写 placement；各 set 是不同事务。云端在名次写入前中断，赛事已经“已结算”，但报名记录没有名次。再次结算直接被“赛事已结算”拒绝。

复现：2 队比赛录分并发布；在第一条报名 placement 写入时注入 RPC 失败。赛事为 finished，0 条报名有 placement，重试返回失败。

建议：小规模一次事务提交赛事与全部球队名次；超限规模使用可恢复的结算阶段和批次进度，全部成功后才置 finished。

### A3 · P1 · 已停用的队长仍能调用旧录分接口写成绩

位置：`miniprogram/services/team-event-service.js:955`、`:1076`、`:1991`；读取端亦有同类缺口，例如 `:246`。

`buildSchoolContext` 会返回停用账号的 actorId，本身不负责拒绝。`canRecordTeamMatch` 的记录员、队长分支只比编号，不要求账号有效和本校有效身份。旧 `recordTeamMatch`、`saveTeamMatchStats` 直接使用该判定；实时计分入口额外检查了 canReadAssociationSpace，故两个入口行为不同。

复现：将参赛队长平台账号改成 disabled，使用其 OpenID 走协议 2。getTeamEvent 仍返回成功；startTeamLiveScore 正确拒绝，但 recordTeamMatch 成功写入 99:1。前端停用提示/隐藏按钮不能阻止直接发请求。

建议：统一团队读写入口的有效身份前置；事务内按最新身份判断，再判断队长/记录员等业务角色。记录员、转校/离校成员也要覆盖，不能只补一个页面。

### A4 · P1 · 抽签跨多个事务写入，失败后留下部分赛程

位置：`miniprogram/services/team-event-service.js:888` 至 `:906`。`advanceTeamRound` 的 `:1690` 至 `:1713` 也使用多次独立提交，应一起检查。

每场比赛写完就单独提交，最后才写赛事 draw 与 scheduled 状态。RPC/函数超时会保留已提交的场次，但赛事没有对应签表；回执丢失后重新抽签又可能使用不同种子或覆盖已有场次。

复现：4 队循环赛应生成 6 场，在第 2 场写入注入异常；数据库留下 1 场比赛，赛事仍是 locked，没有 draw。这里只确认了抽签的失败复现，下一轮路径为同类代码风险。

建议：引入生成批次和赛事版本控制；规模可控时统一事务发布，较大赛程先生成带批次的不可见草稿，完整后再切换正式批次。避免直接给大循环赛套一个会超限的巨型事务。

### A5 · P2 · 锁定名单失败再重试，会永久写错 lockedCount

位置：`miniprogram/services/team-event-service.js:594` 至 `:606`。

逐条将 approved 改成 locked，再改赛事状态。中断后重试只查 approved，因此已锁定的球队被漏算；并发重报/审核也缺少统一赛事状态复核。

复现：4 支已通过的球队，在第 2 条名单写入失败；重试成功返回 locked=3，最终实际 4 支锁定，但赛事 lockedCount=3。

建议：锁定流程原子提交，或支持包含本批已锁定项的幂等恢复；统计从完整目标集计算，并冻结报名修改入口，避免重试或并发让快照不一致。

### A6 · P2 · 事务护栏只数写入，漏掉总操作数上限

位置：`cloudfunctions/data/src/adapters/cloud-repo.js:37`、`:426` 至 `:446`；触发路径 `miniprogram/services/team-event-service.js:1616`。

现有默认预算是 200 次写，仅写操作会触发检查。当前官方文档列出的限制是单事务最多 100 个操作、30 秒，包含对事务范围的整体约束，而不是“200 次写”。受范围 set 还会重复点读归属，额外增加读操作。

按该文档约束模拟：32 场同一轮顺延，身份点读 6 次 + 比赛点读 32 次 + 各场 set 的归属点读与写入 64 次，共需 102 次；第 101 次触发失败，现有护栏没有提前识别。整个事务回滚，顺延不会落一半，但界面只会收到基础设施错误。32 场对应 64 队首轮，不要求异常数据才会触发。

建议：护栏统计全部操作，事务前估算预算；大轮次采用可恢复批次方案或限制单次可处理规模，并返回明确原因。不能只把 TX_WRITE_BUDGET 调大。

依据：[CloudBase 事务操作](https://docs.cloudbase.net/database/transaction)、[事务失败错误说明](https://docs.cloudbase.net/error-code/basic/DATABASE_TRANSACTION_FAIL)。本项是按当前官方限制做的契约复现，不宣称已在当前部署的 wx-server-sdk 上跑出同一错误码。

## 真实环境仍待核对

- 未读取真实环境的集合、索引、安全规则、SDK 实装版本、函数配置或日志；源码声明 wx-server-sdk ~2.6.3、函数 timeout 20 秒，不代表已部署环境一定一致。
- 当前按 schoolId + association 全量分页读取赛事/报名/比赛/统计；scope 与 _id 排序组合索引、数据增长后的延迟和读配额应在控制台核对。不能将本地内存用例的毫秒耗时等同于云端 RPC 性能。
- 云端受范围 set 在首个写入后仍会点读其他文档的归属，本次实时统计追踪到 2 次写后读。源码多处注释声称 SDK 有读写顺序限制，但本次查到的官方文档未明确这一条，因此没有将它算作确定缺陷；需用项目实际 SDK 做兼容验证，或将归属校验预读并复用事务内结果。

## 修复与验证

- A1/A4：重抽禁止已开台或存在实时态的比赛；抽签及下一轮生成改为一个事务提交比赛和赛事，事务内复查赛事、名单及比赛快照。检查后另一请求刚开台时，也会拒绝覆盖。
- A2：结算把赛事与各队名次一起原子写入；重复结算幂等。对旧版本 finished 但报名 placement 缺失的数据，按已结算 placements 快照补齐，不重新计算名次。
- A3：团队读写统一校验有效本校身份；计分、出场名单、球队管理在事务内重读身份和业务角色，阻止停用、离校或请求期间撤权的账号绕过入口。
- A5：报名提交与审核在事务内检查最新赛事状态并增加赛事 revision；锁定同时复核完整名单，含旧版本部分 locked 的记录。RPC 失败整笔回滚，重试计数与实际名单一致。
- A6：云端仓储按读写总数限制至 100 次，环境变量只能收紧；重复点读复用事务快照且返回副本，set 后更新缓存。32 场顺延现为 71 次操作；实时统计为 15 次，无写后点读。
- 批量变更在写前按 96 次安全预算预检，超限返回 TEAM_BATCH_LIMIT。当前不实现超大赛程的后台分批发布：例如 20 队循环赛会在写入前明确拒绝，不留下半套赛程；需要更大规模时应另加可恢复批次方案。整轮顺延可按 stage 缩小范围。
- 新增 8 条云端故障/并发回归，覆盖六项原缺陷、开台与重抽交错、审核与锁定交错、晋级中断、旧数据补齐、容量预检及请求期间停用账号。云端契约测试另覆盖纯读取超预算与缓存副本隔离。
- 工作区全量 `npm test`：144 文件、2737 用例通过（包含当时已落盘的足球并行测试）；最后身份权限/快照比较调整继续做专项复核。真实云端与真机验收仍未执行。
