# 高危缺陷修复记录（第一批）

对全量代码做过一遍通读后，挑出五处「会静默算错数据 / 让数据自相矛盾」的高危缺陷，逐条修掉。这份文档记录每条缺陷的**现象、根因、修法、以及守着它的测试**，供后续复核。

- **修复日期**：2026 年 9 月 17 日
- **测试状态**：1852 通过 / 0 失败（168 个套件 / 62 个测试文件）
- **云函数镜像**：已 `npm run sync:cloud`，`lib/` 与源同步

## 总览

| # | 缺陷 | 影响面 | 修法 |
|---|---|---|---|
| 1 | `startTie` 写小场不 `bumpSeason` | 学院赛开台后录不了分 | 补 `bumpSeason` |
| 2 | `assignMatchReferee` 写裁判不 `bumpSeason` | 指派了看不见，权限收窄不生效 | 补 `bumpSeason` |

## 一、写 `matches` 却不 `bumpSeason`（三条同源）

### 现象

学院赛大场点「开始」之后，紧接着录分报**「找不到这场比赛」**；管理员指派了裁判，比赛明细里**看不到裁判**，被指派的裁判也**录不了分**（权限收窄没生效）。诡异之处在于：随便做一次别的写入，这些又会「自己好了」。

### 根因

等级分不落库，靠**按时间回放全部比赛**推导（见 `derive.js`）。回放出来的数据集按赛季的 `version` 字段缓存（内存 WeakMap + 数据库快照）。因此凡是写了 `matches` / `events` 的动作，都必须调 `bumpSeason` 让版本号 +1，否则下一次读仍命中旧缓存。

三处处理器漏了这一步：

- `college-handlers.startTie` —— 生成小场是往 `matches` 里 insert，却没 +1；
- `match-handlers.assignMatchReferee` —— `referee` 字段只从 dataset 读得到，写了却没 +1；
- `college-handlers.assignTieReferee` —— 同上，且它连带写了大场。

判据不是「这条业务线属不属于等级分」，而是**「这次写的是哪个集合」**。原始注释把两者混为一谈，这一批顺手改成了后者。

### 修法

三处在事务内补上：

```js
await bumpSeason(tx, { anchorTime: null, now: ctx.now });
```

`anchorTime: null` 表示「不是首次写入，锚点不动」——锚点只在第一次写入时钉死（见 `season.js`）。

### 守着它的测试

`tests/cloud-derive.test.js` 三条，都是「写入 → 版本号 +1 → **读到的数据真的变了**」：

- 指派个人赛裁判让版本号 +1 —— 不 +1 就是「指派了看不见」
- 开始大场让版本号 +1 —— 不 +1，刚生成的小场就查不到
- 指派大场裁判让版本号 +1，且下发到名下小场

三条都做过「临时注释掉 `bumpSeason` → 测试转红 → 恢复」的验证，确认不是空跑。

## 二、撤销撤得回分数，撤不回签表

### 现象

管理员撤销一场半决赛。分数、名次、榜单都正确退回了——但点开赛事详情，**决赛那场还在**，上面挂着一位刚刚被作废的晋级者。谁要是随手给它录个比分确认掉，就凭空多出一场不该存在的成绩。

### 根因

撤销靠**重放**把「算出来的东西」退回去，这对等级分是准的。但签表不是算出来的，是**排出来的**：

- 确认一场比赛 → `advanceAfterConfirm`（mock 侧 `advanceEvent`）把下一轮落成真实的比赛记录；
- 这条推进是**「只补不覆盖」**：目标 `_id` 已存在就跳过；
- 而写入侧**只有 `set`（upsert）与 `update`（patch），没有删除**（`repository.js` 顶部有说明：微信云开发事务里条件查询与删除受限）。

三者叠加，撤掉第 1 轮之后，第 2 轮那几场既不会被删、也不会被重排覆盖。

### 修法：撤销前拦一道

**没有选择**「级联撤销 + 复活」，原因：那要在两套实现里改核心排程逻辑（`format-plan.js` / `draw.js` / 两份 `advance`），还得再造一个「复活」机制，而真实云数据库无法在测试里联调，风险远大于收益。

**也没有选择**「删掉下游场次」，原因：`repository.js` 没有删除原语，这条路根本不存在。

改为在 `format-plan.js` 里加一个**纯谓词** `findDependentMatches({ match, matches })`，返回「已经排在这场比赛之后」的场次。撤销时非空即拒绝，提示管理员**从最后一轮往前依次撤销**。这样签表始终自洽，且完全不碰排程逻辑。

### 判定规则里两处容易搞错的地方

**阶段次序**（`STAGE_ORDER`）：小组赛 `0`，主签表 / 季军赛 / 排位赛同为 `1`，败者组 `2`，总决赛 `3`。

- 主签表、季军赛、排位赛**共用同一套轮次编号**（季军赛挂在第 r 轮负者上、被排成第 r+1 轮），所以必须同 rank 再比轮次，才问得出正确的依赖：半决赛(r) vs 季军赛(r+1) → 挡；决赛(r+1) vs 季军赛(r+1) → 同轮，不挡。若把季军赛另判为更晚的阶段，会得出「决赛也靠季军赛」，整张签表谁也撤不动。
- 小组循环的「轮次」只是把一张循环表切成几段，第 2 轮不依赖第 1 轮的结果，所以组内**不比轮次**；淘汰阶段才比。
- 双败的败者组与胜者组交错推进，光看轮次比不出先后，只能整组排在胜者组之后——宁可多拦一次。

**签表归属**（`bracketScope`）：取 `match.eventId || match.collegeEventId`。学院赛小场刻意把 `eventId` 留空、改记 `collegeEventId`（见 `college-tie.buildLegDrafts`），只认 `eventId` 会漏掉整条学院赛线。日常约球两者都没有，`isBracketMatch` 判否，永远撤得动。

### 守着它的测试

- `tests/format-plan.test.js` —— `findDependentMatches` 纯函数 8 条：后轮挡、同轮不挡、季军赛挡半决赛不挡决赛、小组各轮互不挡、小组→淘汰挡、已作废的不挡、别的不挡、学院赛小场按 `collegeEventId` 挡、日常约球永远可撤。
- `tests/datasource.test.js` —— 端到端：撤半决赛被拒（`/已经排进了后面的/`）且状态不变；从后往前撤干净后，半决赛才撤得动。

## 三、赛季软重置 `null` 参数静默压分

### 现象

一次赛季重置之后，**榜单上所有人分数完全一样**——全被压成了锚定分。没有任何报错。

### 根因

```js
const { anchorRating = DEFAULT, retentionFactor = 0.75 } = options;
if (retentionFactor < 0 || retentionFactor > 1) throw ...;
```

`null` 过得去范围比较：`null < 0` 与 `null > 1` **都是假**。于是 `1900 × null = 0`，公式退化成「返回锚定分」。`NaN` 同理（任何比较都为假）。

这两个参数来自落库的赛季文档（`season.js` 的 `resetPolicy`），手工改库或老数据都可能给到 `null`。目前的界面走 `DEFAULT_RESET_POLICY`，所以这条是**潜在缺口**而非已复现故障——但代价是一整张榜，值得提前堵上。

> 顺带确认：`undefined` 走解构默认值，等价于「没传」，**必须继续合法**，不能一并判错。

### 修法

在范围检查**之前**先判「是不是有限数字」，`retentionFactor` 与 `anchorRating` 各一条：

```js
if (typeof retentionFactor !== 'number' || !Number.isFinite(retentionFactor)) {
  throw new Error('retentionFactor 必须是有效数字');
}
```

宁可在这里炸出来，也别静默算错分。

### 守着它的测试

`tests/season.test.js`：`retentionFactor` / `anchorRating` 各一组「非数字必抛」，覆盖 `null` / `NaN` / 字符串 / 对象 / 数组；同一组里另断言 `undefined` 与 `{}` 仍走默认值、结果不变。

## 四、实时比分定稿后显示「已结束 0 : 0」

### 现象

逐球判到 2:0 赢下整场，查看端立刻显示**「已结束 · 第 4 局 · 0 : 0」**——终局比分归零、局数凭空多一局。

### 根因

`replayRallies` 每打完一局就无条件「清零 + 进下一局」。中间某一局这样处理是对的；**最后一局没有「下一局」可进**，那一局就是终局。清零点数后，`liveScoreOf` 吐出来的 `pointsA/pointsB` 是 0，`gameIndex` 还多加了 1，查看端照着显示，真正的终局比分被抹掉。

### 修法

整场打满（`gamesA >= need || gamesB >= need`）时**停在末局**：分数不清零、`gameIndex` 不再 +1，并 `break` 掉后续所有球——脏数据 / 连点不再可能往流水里塞进「赢完还在加分」的球。流水本身照记（它是审计与撤销依据），只是不再计分。

同时删掉了循环顶部那句已经走不到的 `if (finished) break;`。

### 守着它的测试

`tests/live-score.test.js`：

- 纯状态机：终局停在末局（`pointsA === 11`、`gameIndex === 1`）；赢完之后再判球不计分但留在流水里；终局撤销退回末局第 10 分。
- 端到端：过了定稿那一刻，`describeLive` 出来的是 `scoreText === '11 : 0'`、`gamesText === '2 : 0'`、`statusLabel === '已结束'`。
