## 二、主键设计约定（改键前必读）

- **全部确定性主键，禁止自增/随机**：云开发事务内不能 `where` 查询，「有没有占名额」「判过重没有」只能靠点读回答，随机键会让并发判重失效。
- **段分隔符是冒号**：外部传入段（eventKey/sessionKey/entryKey）本身含冒号，用 `rawPart` 嵌入；其余段走 `part`（空值与冒号一律拒绝），避免相邻段同形撞键。
- **`meetId` 自带下划线分隔**（`mt_muc_xxx`）：因为它要被拼进以冒号分隔的键。
- **一场比赛就是一条场次记录**：预赛（`heat`）、淘汰赛各轮（`r1`–`r9`）、小组赛（`g1`…）、循环赛（`rr`）、决赛（`final`）全部落在 `sportsMeetSessions`，复用赛程/裁判/录分能力，不新增集合。
- **道次是普通对象不是 Map**（`session.lanes`）：要落库，Map 过不了 JSON 序列化。

## 三、索引建议（控制台建，按读取路径倒推）

当前读取路径只有两类：**主键点读**与**少量等值查询**。建议组合索引：

| 集合 | 建议索引 | 服务的读取 |
| --- | --- | --- |
| `sports_meets` | `(schoolId, status)` | 届列表（按校 + 状态筛选/排序在内存做） |
| `sports_meet_events` | `(schoolId, meetId)` | 届内项目清单 |
| `sports_meet_sessions` | `(schoolId, meetId)` | 赛程页、录分场次切换 |
| `sports_meet_scores` | `(schoolId, meetId)` | 汇总预览（按届取后在内存分组） |
| `sports_meet_entries` | `(schoolId, meetId)` | 报名名单、抽签分组 |
| `sports_meet_judge_assignments` | `(schoolId, meetId)` | 「我的任务」按裁判过滤在内存做 |
| `sports_meet_result_rows` | `(schoolId, meetId)` | 已发布结果 |
| `sports_meet_standings` / `sports_meet_honors` | `(schoolId, meetId)` | 总榜、我的荣誉（一届约 800 条荣誉，深翻页告警属既有约定） |
| `sports_meet_college_leads` | `(schoolId)` | 按校列举学院部长 |

不假定其它组合索引可用；真机上若慢，优先按 §6 验证后再加。

## 四、读写权限

- **所有读写都走 `data` 云函数**（服务端 admin 能力），客户端无任何直连数据库入口。集合安全规则按既有架构配「仅服务端可访问」——这与协会维度一致，不要给运动会集合单独放宽。
- 写入范围校验在仓储层：运动会集合只进 `forMeet`（`{schoolId, meetId}`），**绝不进** `forScope` 的协会受范围清单（否则每次写入被强塞 association，等于把运动会挂到协会上）。`tests/meet-repo-contract.test.js` 与 `for-scope-contract.test.js` 双向守护。
- 权限判定在服务层：`meet-permission.js` 只认平台管理员/本校校管理员/本院学院部长，**不读 memberships**——协会负责人结构上不能行使运动会权限。

## 五、云函数同步与部署步骤

1. `node tools/sync-cloud-lib.js`（源在 `miniprogram/`，`cloudfunctions/data/lib/` 是逐字节镜像）。
2. `npm run check:cloud-sync` 确认一致（当前 **71 个文件**）。
3. 按既有流程上传部署 `data` 云函数（运动会动作已并入 `school-request.js` 的 meet 分支，无需新函数）。
4. 控制台建齐 §1 的 15 个集合（`sports_meets` 等 14 个 + `sports_meet_college_leads`），配 §4 权限。
5. 冒烟（mock 已通，云端待环境）：以校管理员发起一届 → 配项目 → 发布报名 → 部长提交 → 审核 → 定赛制抽签 → 排期派裁判 → 录分发布 → 看总榜与「我的荣誉」。

## 六、真实云端待验项（D101，环境未定故未验）

| 待验项 | 本地状态 | 真机要确认什么 |
| --- | --- | --- |
| 事务并发 | 内存仓储串行队列模拟 | 两个并发提交抢同一名额/同一学院部长授权，点读+重写是否真的不超卖 |
| 写预算 | `TX_WRITE_BUDGET` 默认 200，超限早失败 + 告警 | 最大事务（整院提交/签表/发布累加）的真实写数与上限；按实测收紧或调环境变量 |
| 批量指派拆批 | 每批 `floor(150/(人数+1))` 场次 | 云端多事务顺序执行中途失败时，已成功的批次如何处理（当前无补偿，需确认可接受） |
| 查询耗时与索引 | 无真实数据量 | 120 项目组别、40 学院下的列表/录分页耗时；索引是否命中 |

## 七、已知取舍（不阻塞发布，记录在案）

- **删除入口仍只允许草稿**：已发布需走「撤销发布」（未实现）。读取端已校验 `deleted`，软删后总榜/荣誉/列表立即不可见，无级联清理。
- **更正只做无痕**（D87）：旧版本不可追，只有版本号与原因；`rows` 摘要仅用于重发时减分，不对外展示。
- **无报名成绩字段**：预赛分组统一按「强手分散」，按成绩录取时的「强手集中」无从做起（C9，需先加报名最好成绩）。
- **出场顺序号不做**（Q13 裁决）：裁判逐人打分已满足现场需要。
- **事务内写入未过 `forMeet` 第二层校验**：运动会写路径用服务端派生的确定性键 + 每动作复查届次归属（meetId 与 schoolId 比对），`forMeet` 的写入校验主要服务于协会维度（payload 参与构键的场景）。真机验收时可顺带确认无需收紧。
